## 共同原则

现代化、简洁、清晰、干净与克制具有同等首要地位，共同约束设计文档、代码、测试和工程流程。评估今天可以采用的平台能力和工具，选择能完整交付目标、便于理解和长期维护的方案。已有规范与检查也按其实际作用复核。

编码风格是设计、实现和交付质量的一部分。名称、组织、注释与逻辑分段必须在编写时落实，并在审阅中逐项确认；类型、lint 和格式检查各自通过后，仍要核对完整阅读路径。

<a id="global-design"></a>

### 全局设计与一致性

从完整用户目标、数据与资源归属推导问题的粒度。纵向追踪输入、事实、操作、呈现和释放，横向比较同类对象在各入口、运行端和交付物中的处理。同一含义采用一致的身份、边界、名称、行为与表达。差异由真实的对象语义、使用目的或平台条件决定。

讨论方案时说明共同规则、适用范围，以及代表场景中可观察的结果。设计在共同拥有层定义合同，调用方负责自己的接入。改动沿依赖关系同步实现、调用、文档与验收，清理被替代的路径。共用的是实际共同的职责，独立的状态、操作与资源寿命各归所属边界。

审阅同时检查规则的覆盖和抽象的边界。对照实际存在的同类入口及其合同与实现，追踪局部差异的依据，再沿正常、失败、取消和清理路径核对终态。全项目检查按职责分组核对设计、源码、工具、测试与交付材料，区分已验证结果、待实施范围和需要决定的分歧。

<a id="judgment"></a>

### 判断与取舍

设计、实现、重构、规范、文档与验证，统一以已确认目标、正确性和整体质量为取舍依据。工作量、实施耗时与重做成本，不作为降低质量、缩减已确认范围或保留已知问题与不一致的理由。现有结构与目标冲突时，按终态重做受影响部分。运行性能、资源占用和长期维护复杂度属于成果质量，按实际影响评估。

整体判断优先于机械执行。任务要求、现行规范和既定方案都接受目标与事实的检验。发现与全局原则冲突，或存在正确性、整体质量、过度防御、过度设计、做法陈旧、偏离现代化最佳实践等问题时，先退一步审视目标和全部相关设计，说明依据、影响、可选方案与建议，由用户决定调整方向，再统一修改规范、设计、实现与验收。已有条文或做法本身不构成继续采用的理由。

现代化要求主动寻找更好的做法。比较方案时，从目标版本的官方资料与维护者说明核实能力，用代表场景判断它能否改善用户体验、运行效率或长期维护。已有项目的经验能揭示兼容问题与失败后果。新工具和预览版可以进入试验，采用时按实际发布状态、支持环境和关键路径验证结果说明适用范围。关键选择在所属文档保留必要理由与来源。

必须成立的行为、类型、资源与依赖约束由实现和验证保证；明确选定的命名、导出、注释语言和格式约定统一执行；使用“通常”“优先”的规则按实际语义判断。例外应有职责、语言或运行环境依据。影响公开合同、主要行为或支持范围的取舍按本节的整体判断处理。

<a id="readability"></a>

### 清晰与可读性

清晰以完整阅读和使用路径判断：读者能否从名称、结构与就近说明找到入口和职责拥有者，理解前提、输入输出、主流程与状态变化，追踪失败、取消和清理，并确定修改影响。必要的差异、适用范围和例子直接表达，已确认的目标合同、当前实现与验证结果各有明确归属。缩短文字、压平目录或减少文件数量，都不能以增加隐含约定和读者猜测为代价。

文件与目录组织、文件内分段共同构成可读性和可维护性。相同概念采用一致词汇，同层职责粒度协调，相关内容按使用与维护关系放置；审阅从目录和文件入口追踪到具体实现，核对查找与修改是否需要无谓跳转。文件数量、函数长度和注释数量不作为质量指标，也不据此设定机械拆分要求。

函数围绕连贯职责组织，调用层保持相近的语义粒度。完整操作可以在一个文件内顺读；职责、复用、变化点或资源寿命需要独立表达时，提取有明确输入和结果的步骤。只改名转发且不提供合同或边界的包装没有独立价值。

<a id="logical-sections"></a>

### 编码风格与逻辑分段

一个逻辑段完成一个能说清楚的职责或步骤。空行表达职责边界，紧邻的语句表达同一步骤的连续关系；先判断内容，再决定分段。此要求适用于源码、测试、工具、配置和设计文档中的代码示例。

| 位置 | 分段要求 |
| --- | --- |
| 文件入口 | 文件概述注释结束后空一行，再开始导入、声明或实现。连续的模块文档注释视为一个概述块。导入区与后续正文之间空一行。 |
| 顶层声明 | 独立类型、函数、类，以及职责不同的常量或状态声明之间空一行。连续导入、同一函数的重载签名，以及共同表达同一规则的短声明保持成组。 |
| 类型、对象与类 | 字段按实际关系组织，例如身份、输入、结果、运行状态与资源寿命；不同职责之间空一行。方法之间保留清楚边界，同一组内的简单字段连续排列。 |
| 函数与回调 | 输入读取与直接校验相邻。资源准备、执行、结果采用、交付与清理在职责转变处空一行；同一步中的计算、分支或短循环保持紧凑。 |
| 失败、取消与清理 | 让读者能从正常流程追踪到对应退出与释放。前置失败判断结束后再进入主流程；同一个 if／else、try／catch／finally 结构保持完整。 |
| 测试 | 以条件准备、实际动作和结果断言组织段落；多个独立场景分别组织，不将所有步骤挤成一段，也不在每个断言之间机械空行。 |
| CSS 与配置 | 按组件部件、变体、交互状态、环境条件和配置职责分组；一组共同表达相同规则的属性或条目保持紧凑。 |

说明注释紧贴它解释的声明或步骤，声明的文档注释与该声明之间不插入空行。段落之间使用一个空行，更大的职责边界通过明确的函数、类型、模块或文档标题表达。单纯按行数、分号、声明关键字或每个控制结构插入空行，不能替代上述判断。

设计文档的一个段落围绕同一判断、合同或步骤展开，章节按读者任务组织，表格用于真正并列的内容。代码示例采用与正式实现一致的命名、声明分隔和流程分段。审阅同时检查文字与代码中的职责关系，避免相同主题散落、独立要求挤在一个长段落中，或为无实际区别的内容建立层级。

逐文件审阅从概述与导入开始，沿声明、状态、正常操作、失败、取消和清理路径顺读。确认每个空行对应可解释的边界、每个紧凑段落完成一个连贯步骤；已有格式化结果仍接受这一检查。

<a id="proportionality"></a>

### 简洁、克制与原生

简洁同时衡量概念、操作、状态、间接层及长期维护成本。采用满足已确认目标的最简单完整方案，保留必要的数据、权限、公开合同和资源边界。少写行数、拆成更多文件或统一外观本身不能证明更简单；少量重复可以比错误的抽象更易维护。新增或保留机制须服务于真实职责、已确认需求或实际技术约束，收益与维护成本相称。

按终态的模型和流程判断哪些防御仍有必要。类型已经排除了无效状态，或平台、存储及操作入口已经给出保证时，内部直接依赖这些保证，移除重复检查。校验与恢复措施须对应受支持场景中的具体失败及其后果，由负责该输入、权限、数据或副作用的边界处理。根因消除后清理失效的补救路径，不为假想异常另设分支。限制须有产品语义、技术条件或资源风险的依据，内部调优参数不自动成为长期产品限制。

优先采用语言、框架、运行时和工具的公开能力与惯例，遵守其类型、异步、响应式和生命周期语义。原生优先不限定当前技术栈，选型仍从目标出发；封装承担实际产品语义、资源责任或必要兼容。界面保留系统交互与语义控件的能力。

<a id="global-coherence"></a>

### 职责完整与整体一致

设计先确定每个交付单元最终承担的职责。实现可以按依赖分步推进，交付时模型、接口、行为、状态、资源、失败处理与说明应彼此吻合。正式入口履行承诺的合同，进度文档如实记录仍缺少的能力。通用说明描述现行行为，验证记录给出支持交付判断的证据。

每项调整从完整问题和相关场景确定影响范围。同类问题在共同拥有层解决，并同步接口、调用方、测试、配置和文档。现有结构与目标冲突时，重做受影响的设计与实现。共同语义决定统一范围，平台能力、权限、数据含义和资源寿命决定合理差异。

<a id="design-completion"></a>

## 设计与实现边界

### 设计充分性

设计明确对象身份、字段含义与默认值、完整操作、公开输入输出与错误、并发与原子边界、取消与资源寿命、主要交互及支持范围。影响这些含义的主要分支提供确定的规则和例子；已知缺口继续完成设计，不交由实施者临时补定。

容易产生歧义的规则使用精确类型、行为表或例子，确有技术风险时用小型探针验证。全量声明、导出目录、常规 CRUD 签名和组件参数随实现形成。设计定稿先核对机制与限制是否必要、复杂度是否相称，再核对依据、一致性、实施充分度及[内容组织](documentation.md#writing)。

各项目拥有自己的公共合同与实现机制，消费者定义接入。不同来源或后端的差异由实际拥有者说明，共同结构引用所属方案。未确定的业务规则保留为设计缺口。

### 实现自由与交付范围

整体方案、共同原则和影响范围明确后，函数与文件组织、索引、数据结构、具体 API 调用、同语义算法优化，以及已确定预算内的批量与并发调优，由实施者判断。规格给出约束与验收依据，不预写全部实现细节。

架构与实现从产品目标、公开合同、数据与资源归属及运行约束独立推导。需要延续的用户行为以已确认要求为准，源码结构以职责和维护关系为依据，交付范围由所属项目定义。

改变模型、公开合同、主要行为、架构边界或交付范围时，按[整体判断](#judgment)说明依据、选项与代价，讨论确定后同步相关设计与验收。既定合同内的实现、接入和验证问题由实施者完成。

验证在能够直接证明承诺的边界取得证据，各接入层验证新增风险并复用仍适用的结果。交付可以按完整职责单元接续，设计充分性、正式实现、运行验收和发布分别判断，实际进度由所属项目维护。

<a id="source-language"></a>

## 源码与工具能力

JavaScript 环境中的自维护源码使用 TypeScript，普通模块、脚本、配置、测试和示例使用 `.ts`，JSX 使用 `.tsx`。Rust、SQL、CSS、HTML 和声明式配置使用各自语言。生成代码、绑定声明与第三方发行内容由来源维护，不手工修改输出；类型、lint 和源码检查覆盖工具、测试与模板。

<a id="deprecated-apis"></a>

采用锁定版本支持的公开 API 与配置。TypeScript 的共用 lint 检查依赖声明中的弃用标记；发现自维护用法的弃用提示时，核对当前类型声明与官方迁移说明，适用的成熟替代经对应验证后采用。需要保留的兼容用法说明原因和适用条件。类型断言、关闭检查、修改第三方源码或强制覆盖传递依赖不能代替正确接入。

<a id="naming"></a>

## 组织与命名

TypeScript 工程的目录和普通文件使用 kebab-case，组件、类和类型使用 PascalCase，函数与变量使用 camelCase。Rust 的模块、函数与变量使用 snake_case，类型采用 UpperCamelCase，静态项与常量使用 SCREAMING_SNAKE_CASE，模块文件与模块名对应。工具规定的名称、外部字段与生成绑定由各自拥有者定义。

名称表达对象、动作或业务判断；跨边界数量注明必要单位和口径，如 `timeoutMs`、`sizeBytes`。缩写沿用明确的领域惯例，局部短名称由紧邻上下文解释，不用编号或泛化名称掩盖职责。同一个变量在其寿命内保持同一业务含义。

<a id="naming-scope"></a>

### 范围与限定词

先确定名称所指的对象及其责任，再选择读者在实际使用位置需要的限定词。对外名称应能在参数、返回值和跨模块调用中辨明所属对象；局部类型、变量和辅助函数可以利用所在模块及紧邻流程的明确上下文。是否导出、调用者数量或结构相似，本身不决定名称是否应当通用。

限定词表达模型自身的范围。ExtensionManifest 描述扩展包，保留 Extension；同时覆盖本体与扩展页面的 PageRef 保留共同名称。领域能力和通用机制按自身职责命名，不能仅因扩展使用它们就增加 Extension。扩展专有的贡献定义则明确其归属，尤其是其文件路径、身份或生命周期依赖当前扩展上下文时。

场景拥有的投影可以保留场景名称，例如仅用于搜索结果的 SearchIcon。共同类型在已确认的共同语义及消费合同成立时提取；结构相似或未来可能复用，不构成提前上移的依据。已有具体对象词能够说明范围时，采用该对象词，避免重复叠加限定。

同一职责中的同类名称保持一致的词序与缩写。自有 TypeScript 标识符中的一般缩写按词拼接，例如 ExtensionUiIcon、RpcConnection、extensionId；标准对象名、外部 API、协议字段和原始材料沿所属定义保留。名称不以编程语法类别代替对象含义。

<a id="type-roles"></a>

### 类型与对象角色

类型和类优先使用准确的业务名或职责名；需要区分同一对象的不同角色时，再使用相应角色词。常用角色按下表理解，同一层次中含义相同的值采用一致名称。

| 角色词 | 含义 |
| --- | --- |
| Create、Update | 普通对象的新建资料或字段变更；由对象名称限定，如 ScanConfigCreate、ScanConfigUpdate |
| Input | 完整业务操作或值采用所需的输入，如 OnboardingApplyInput、FileInput |
| Options | 在明确目标之外控制读取、执行或呈现方式的选项；由实际用途决定，不以字段是否可选判断 |
| Definition | 配置、能力或贡献的声明，描述由拥有者采用的内容与行为，如 MetadataProfileDefinition |
| Descriptor | 对能力或已登记对象的可读描述，提供身份、元数据或能力信息，如 MetadataProviderDescriptor |
| Ref | 指向正式对象或运行期对象的身份与必要归属，如 EntryRef、ReadResourceRef；读取内容和生命周期操作由对应能力提供 |
| Handle | 可直接操作的运行期句柄，说明其更新、关闭或释放责任，如 ToastHandle |
| Registration | 已建立的登记及其撤销、替换等能力，如 ExtensionThemeRegistration |
| Snapshot | 某次取得的固定值，范围与取得时点由所属操作明确，如 ScanConfigSnapshot |
| State | 对象在本次观察中的状态及其合法组合，如 ExtensionState |
| Summary | 面向明确消费范围的摘要投影，保留该范围所需信息，如 ErrorSummary、InstalledExtensionSummary |
| Result | 一次操作按合同交付的结果，包括该操作允许的部分成果，如 OnboardingApplyResult |
| Context | 有明确作用域的一组环境、身份或能力，如 ExecutionContext、ExtensionContext |

已有完整业务名称的对象直接使用该名称。角色词用于说明实际区别，不为每个参数对象增加 Input、每个返回对象增加 Result，也不为同一份值建立只换名称的类型。需要专门的创建、更新或调用输入时，连同允许字段、默认值与基线定义其角色，避免用同一个模糊类型承担不同合同。

类、工厂与模块都按实际承担的对象和责任命名。接口说明调用方可以依赖的承诺，实现名称说明它提供的具体能力；状态、资源与寿命的边界见[运行架构](../architecture.md#module-interfaces)。

<a id="operation-names"></a>

### 操作与回调

函数和方法用实际完成的动作或计算结果命名，判断函数表达可回答的业务条件。对象与作用域已经由所属 API 或参数明确时，名称保留区分操作所需的信息；同一领域中相同动作使用相同词序。get、list、read、resolve 等名称按所属合同的对象与结果含义选择。

事件、回调、处理函数和订阅入口按各自职责命名。框架规定的 onClick 等入口遵循框架惯例；自有回调说明发生的事实或请求，处理函数说明负责的动作。异步性通过返回类型与完成合同表达，Async 等限定只用于确实需要区分的对应能力。

这些选择参照 [Google TypeScript 的描述性命名与缩写惯例](https://google.github.io/styleguide/tsguide.html#naming)和 [Rust API 的命名与词序规则](https://rust-lang.github.io/api-guidelines/naming.html)，具体对象范围、角色和语言差异仍由本项目合同确定。

<a id="directory-readability"></a>
<a id="source-layout"></a>

### 文件与目录

目录按能力、工作对象、运行环境或工程边界组织，同级采用清楚的划分依据。专用实现随拥有者放置，共享代码归相同语义的最小合理范围；测试复用本身不构成上移理由。入口、内部实现、配置、样本和工具的角色可辨，目录层级不重复表达同一含义。工程维护代码与测试专用代码分别遵守[工具归属](layout.md#tools)和[测试归属](layout.md#test-placement)。

目录名表达共同主题，文件名说明其中的具体对象或职责。项目自行命名的 TypeScript 源文件，去掉 `.ts` 或 `.tsx` 后的文件名须与直接父目录名不同。

文件拆分以能独立说明的职责、消费方式或依赖边界为依据。同一对象的类型、校验与操作按实际维护关系组织，不仅因声明种类不同而拆成平行文件；需要分离时，名称与目录应表达各部分的关系。局部类型与辅助随使用者放置，`values`、`types`、`utils` 等名称须有清楚且有限的上下文。

同一主题按清楚的模块边界组织，入口、实现和公开范围保持明确的归属关系。内容内聚时放在一个文件中；需要多个协作模块时按语言的模块规则集中维护，不以同级前缀文件模拟内部层级。独立能力使用各自准确的名称分别维护，不能仅凭名称相近强行合并。

普通 TypeScript 多文件主题的源码与自身入口集中在同一目录，不在目录外另设同名入口。接口组合、运行装配等实际职责在主题内按职责命名；公开入口遵守[导入与公开入口规则](#module-imports)。`api.ts` 可以定义主题整体的调用合同或组合能力，相关输入、结果与校验随其维护；具体对象的合同归各自主题，不按声明种类集中，也不把 `api.ts` 作为每个目录的固定模板。

入口位置遵循语言和工具的原生规则。Rust 的 `foo.rs` 与 `foo/` 分别承载模块及其子模块，采用[语言的惯用组织](https://doc.rust-lang.org/book/ch07-05-separating-modules-into-different-files.html#alternate-file-paths)。工具约定的入口、生成文件与配置遵守其自身规则；原始样本、上游快照和与记录摘要绑定的验证输入保持可复现的来源身份。

单文件可以承载完整职责，多文件协作或独立工程边界可以形成目录；不预建空目录，不为文件数量建立转发层。模块按对象、操作、状态和资源寿命命名：manager 管理对象及其寿命，coordinator 协调参与者，registry 负责登记与查找。小型纯辅助可以放入 utils，业务策略和运行副作用使用具体名称。

工程身份与分发边界依据实际职责和已确认范围保留，不能因当前文件少而删除。程序保留自身入口和寿命，可以共用相同的协议、视图与机制。源码移动同时维护导入、发现规则、项目配置、测试和文档，实际布局由所属项目定义。

<a id="configuration-layout"></a>

### 配置归属

配置属于实际使用它的工程。默认发现入口和项目声明保留原生位置，如 `tsconfig.json`、`package.json`、`tsdown.config.ts` 和 `Cargo.toml`；环境配置与测试变体放在所属工程的 `config/<工具名>/`。跨工程共享基线由共同拥有者提供稳定入口，`.github/workflows`、`.cargo` 等工具专用目录保持其约定。

只有默认入口的工程不额外建立 config 层级；有实际内部配置时按同一归属规则组织，不增加纯转发配置。配置调整核对相对路径、有效选项、源码覆盖、编辑器项目归属和任务输入。运行期设置与用户数据继续归业务模块。

<a id="module-imports"></a>

### 导入与公开入口

跨包通过已声明的包名和 exports 消费，公共包提供构建结果。公开入口按稳定职责和运行环境划分，可独立消费的能力优先使用子路径，单一内聚机制可以使用根入口；公开路径与内部文件按各自用途组织。

TypeScript 单文件能力可以直接作为构建入口。多文件主题需要公开入口时，由目录内的 `index.ts` 从定义文件转导出选定的接口。完整复用另一模块已确定的公开面时，可以整体转导出。包的构建配置与 exports 将入口映射到稳定的公开路径。分类目录不增加统一导出，内部主题不因形成目录就增加入口。

目录提供一个静态组合值时，`index.ts` 可以直接组装并导出它，例如由各领域词表组成的完整消息树。需要独立维护的算法、运行状态和资源寿命管理逻辑放在主题内按职责命名的文件中。

包内有稳定命名需求的模块入口由自身 package.json 的 imports 定义，以 `#` 开头；模块内部使用相对导入。内部协作直接引用所需文件，不经过公共导出入口绕行。

代码、测试、类型检查、构建和依赖检查使用同一份标准包映射，不分别维护等价的 paths 或构建别名。imports 按发起导入文件所属的包生效，不随 tsconfig 继承或命令工作目录变化。相对目标位于所属包内，跨包目标使用已声明依赖；别名不扩大访问权限。

工具可以消费本工程明确供工程流程使用的纯合同与纯函数，不启动应用运行模块。共用支撑不反向依赖具体工作流、CLI 或测试夹具。打包后的内部导入指向实际交付内容；公共库通过仓库外消费者核对制品边界，具体依赖权限由所属项目定义。

package.json 的依赖块按包名排序，脚本按开发、构建、验证和维护组织，条件 exports 保持实际匹配顺序。任务名称表达调用范围与动作，具体约定由所属工程定义。

<a id="validation"></a>

## 类型与边界

类型表达合法组合，区分缺省、空值、未知与失败。互斥状态使用可区分的状态模型，独立条件可以保留布尔值；不以布尔值数量决定是否建立状态机。领域值和正式合同复用唯一定义，局部运行类型留在拥有者内部。

输入已经确定的对象种类、资源归属和请求键，在读取结果、保存结果与资源句柄中保持关联。动态集合与可选输入保留结果项可能缺席的语义。同一对象的身份、字段和配置按合法分支共同定义；读取的可编辑值可以直接用于所属写入合同，展示投影和临时输入仍按各自职责转换。

公共接口与重要操作明确输入和输出，显然的局部值使用类型推断。只读合同在类型中表达，必要的局部构造与更新可以直接修改。类型导入使用 `import type`；`any`、连续断言和同形别名不能掩盖未确定的边界。

文件、网络、IPC、扩展输入和持久化数据在对应边界按合同解析，未知值先按 `unknown` 处理。纯校验规则归值定义的拥有者，传输适配负责调用与结果交付。结构已经成立的内部调用不逐层重复校验；受控工程输入可沿来源保证的合同标注类型，类型标注与断言不代表完成了运行时校验。

结构合法与业务操作可执行分别判断。操作拥有者保障当前状态、并发、原子性、取消和资源条件，数据库约束与事务承担各自职责。缺省、重试、去重、补偿和回退需要实际输入、失败后果及所属合同的依据，结果未知的写入不自动重放。

解析外来值使用 `parse`、`validate`、`require`、`assertValid` 等准确名称，判断可信业务状态使用 `is`、`has`、`can`、`should`。持久化的读取、写入与格式迁移遵循所属数据合同，普通读写不隐含迁移。

TypeScript 使用严格类型检查，不同宿主的全局类型分别配置。公共声明通过最终制品的独立消费完整检查；项目配置和检查分工由实际拥有者定义，不用宽松配置或忽略错误取得通过结果。

<a id="coding-style"></a>

## 代码、控制流与资源

具名操作通常使用函数声明，回调使用箭头函数；短小的纯计算可以直接返回表达式。默认使用 `const`，需要重新赋值时使用 `let`。

前置失败与无效输入尽早处理，正常路径按执行次序展开。控制流使用代码块，`else`、`catch`、`finally` 保持完整结构。简单二选一取值可以用三元表达式，复杂分支使用 `if`、`switch` 或具名判断。

纯数据转换使用 `map`、`filter` 等适合的表达，顺序副作用通常使用循环。并发操作可以通过明确等待的 Promise 集合表达；等待方式符合失败和清理合同。`Promise.all` 的提前拒绝不表示其他操作已结束，需要等待全部操作收尾时使用 `Promise.allSettled` 或所属机制。属性读取与条件表达式不隐藏写入、登记或资源获取。

异步操作明确完成条件、哪些工作可并行，以及失败、取消和关闭由谁负责。每项 Promise 都有等待或结果处理的拥有者；`void` 只表达不等待，不处理拒绝。允许调用已由拥有者处理失败与寿命的异步入口，不为通过 lint 追加无意义的 `catch` 或忽略标记。

资源获取与释放通过 `try/finally`、语言资源管理或框架生命周期对应，创建失败和退出同样收尾。取消等待只结束等待，已发生的副作用按所属合同处理，清理前等待仍可能使用资源的工作结束。锁、订阅、重试和预算只处理实际支持的场景。

遵守所属框架的响应式和生命周期语义，保留活跃值、快照、派生值与副作用的区别。各语言沿用自身的类型、所有权和资源管理惯例；共同要求统一行为与责任，不统一不同语言的语法。

格式由 Prettier、rustfmt 等工具处理。工具负责缩进、换行与语法排版，作者和审阅者负责语义分段、命名、职责和完整阅读路径。

<a id="comments"></a>

## 注释与说明

代码注释使用简洁英文。文件概述说明定位，声明文档说明对象职责与调用合同，实现注释解释算法、次序和约束的依据。读者可以在对应位置取得所需信息，各层通过引用连接。

<a id="file-module-comments"></a>

每份自维护源码都有简短文件概述，包括业务与库实现、工具脚本、测试、自有声明和模板中的源码，覆盖简单文件和纯导出入口。概述说明主要职责与所属范围，简短文件通常一句即可；文件同时承担模块入口时合写。

TypeScript 在顶部使用 JSDoc `@fileoverview`，Rust 使用 `//!` 模块文档，其他源码采用原生注释语法。概述放在实现或导入之前，保留 shebang、编码声明、许可证、doctype 和工具要求的位置；概述结束后按[文件入口分段](#logical-sections)空一行。正文说明当前职责，不设置空栏目或记录实施经过。

配置文件按实际需要说明关键取值的原因、环境约束和非直观逻辑，使用就近注释、原生说明字段或所属文档。TypeScript 配置与 JSON、YAML、TOML 等配置采用同一原则，不统一要求文件概述；工具入口、字段和继承关系已经清楚表达的信息不再重复。配置中的具名声明同样遵守下方要求。生成文件的说明由生成器维护，第三方原文和历史验证材料保留来源内容。

<a id="comment-coverage"></a>

### 声明覆盖与说明归属

所有自维护的模块级具名声明，在定义处统一提供文档注释，包括函数、类、组件、接口、类型、枚举、变量和常量。函数、方法、访问器、类、组件、接口、类型和枚举在嵌套作用域中同样覆盖；独立定义的可调用值按函数处理；先声明后实现的函数在具名绑定处说明职责。是否导出、是否为私有成员及实现长短不影响最低覆盖要求。简短声明可以只有一句概述。

覆盖按所定义对象判断，不依赖初始化表达式的语法。直接声明、字面量、工厂调用和组合器产生的列构造函数、codec、校验 schema、数据库表、关系映射、规则表、配置及资源实例，都遵守相同的模块级声明要求。解构声明中共同表达一项职责的绑定共享该声明的文档。

直接作为调用参数交给接收方、没有独立名称的内联回调，由接收接口与所在流程说明其作用。绑定到变量、具名属性或定义为对象方法的函数，在定义处提供文档；方法语法与函数属性写法遵守同一要求。转交或暂存已有回调时沿用其定义与接收接口的合同，只补充新增的时机、所有权或释放责任。普通局部变量与临时值通过名称和类型表达含义。字段、参数及策略值补充类型没有表达的单位、默认值、空值、范围、关联和所有权规则。非直观的实现理由仍在相关语句旁说明。

纯重导出沿用原定义的文档，入口文件说明自身组合职责。同一个函数的重载签名共用合同，公开消费时能够取得相应说明。接口、Props 或基类拥有共同的字段与方法合同；实现的概述说明具体职责，并就近补充新增条件，通过链接引用共同定义。

<a id="comment-objects"></a>

### 代码对象的调用合同

公开消费入口包括包导出、SDK，以及模块承诺给其他模块的稳定能力。声明的概述建立对象含义，以下内容按实际合同补充：

| 对象                                                 | 需要说明的内容                                                                                                   |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 函数、方法与完整业务操作                             | 输入条件、结果含义、完成时点、失败、重复调用、副作用与取消。                                                     |
| 组件与类                                             | 使用范围、状态与所有权、回调时序、焦点、无障碍和释放责任。                                                       |
| 状态工厂、响应式工具和持续资源实例                   | 创建环境、活跃值与快照、资源转交、订阅、关闭及失败清理。                                                         |
| 类型、领域值、状态模型、稳定接口和传递结构           | 对象角色、身份、粒度、合法组合、调用方与实现方责任。类型别名说明采用该名称的语义。                               |
| 列构造、codec、schema、表、关系映射与规则表           | 定义或约束的事实、读写与缺省策略、关联和寿命边界，以及消费者需要知道的适用条件；不逐项复述结构。                 |
| 字段、参数与策略值                                   | 类型未表达的单位、时区、坐标系、默认值、空值、范围、精度、所有权、关联约束及策略依据。显然的局部变量不逐个注释。 |
| 事件、回调、登记和订阅                               | 触发条件、载荷、顺序、完成、错误、取消与撤销。                                                                   |
| 非直观算法、并发、平台差异与安全边界                 | 实现原因和必须成立的条件；Rust unsafe 块用 `SAFETY:` 说明前提及保证来源。                                        |
| 测试与样本                                           | 用例名称表达行为与预期，特殊安排说明故障注入、替身范围和回归条件；样本保留来源、许可、合成范围与预期。           |

说明围绕调用者可观察的行为。Promise 说明何时完成，取消说明已经接纳的工作与已发生副作用如何处理，资源说明由谁持有和释放。条件与后果相邻，事实可以沿设计、实现和验证核对。尚未确定的行为归设计讨论，不在注释中补定。

<a id="comment-writing"></a>

### 表达与审阅

TypeScript 声明使用 JSDoc，Rust 使用 Rustdoc；文档注释紧邻声明。首句说明对象是什么或操作完成什么，函数与方法采用第三人称现在时，如 Parses、Creates、Releases。需要进一步说明时，另起段落组织条件、结果和生命周期；具体实现技巧的理由放在实现旁。

Rust 的局部闭包绑定使用紧邻的普通注释，保留相同的职责说明；[Rustdoc 不处理这类语句位置的文档注释](https://doc.rust-lang.org/rustc/lints/listing/warn-by-default.html#unused-doc-comments)。语言工具的语法差异不改变声明覆盖要求。

简短概述允许少量必要的信息重复，以保持稳定的阅读入口。内容按实际对象编写，避免只把标识符拆成单词、重复类型、使用泛化的正确性承诺，或将多个职责挤在一个长句中。详细程度由合同决定，不统一字数，也不要求每份声明填写固定栏目。

`@param`、`@returns`、`@throws` 等标签只补充适用信息。Rust API 按实际行为说明 `Errors`、`Panics` 与 `Safety`。说明结构参照 [TypeScript 文档注释与实现注释的分工](https://google.github.io/styleguide/tsguide.html#jsdoc-versus-comments)及 [TSDoc 的概述与详细说明](https://tsdoc.org/pages/tags/remarks/)；独立具名声明的统一覆盖是本项目的明确约定。

审阅分别核对覆盖与内容：具名声明和对应文档逐项对应，再沿调用、正常操作、失败、取消及清理核对说明。公开入口还要核对构建后声明能够提供相应文档。已有准确内容保留，缺失内容补齐，含糊或失效内容改写，重复的详细说明归并到拥有者。注释、实现、类型、测试和公共文档同步维护；设计缺口与实施待办按[文档归属](documentation.md#owners)处理。

## 错误与日志

自行抛出的错误使用安全英文消息，需要补充上下文时通过 `cause` 保留原始原因。错误分类依靠类型或原因字段，不解析 `error.message`。只在负责恢复、补充上下文、转换边界消息或交付失败的位置捕获错误；正常业务结果与异常按所属合同区分。

运行日志由项目日志入口提供，使用稳定的责任领域，动态 ID 和路径作为参数。负责失败的模块记录一次必要上下文，界面或后台负责人按所属场景反馈。记录生命周期、失败、恢复和连接变化，避免逐帧或逐回调日志；凭据、用户正文、完整记录和无界数据不进入日志。

## 工具、验证与交付

### 工程工具

CLI 解析参数、调用工作流、呈现结果和设置退出状态；工作流通过明确参数与返回值复用，拥有操作次序、外部调用及清理。工具模块导入不启动任务，可复用函数不调用 `process.exit`，CLI 在清理后交付退出状态。生产运行代码与工程工具不依赖测试辅助。

构建、监听和检查采用现成工具的公开能力，每份输出由一个任务拥有。普通编译与装配目录是可重建工作区，成功后才供下游采用；构建和缓存恢复先准备同一份干净输出。实际读取者持有的运行目录在释放后清理，已经核验的发行文件另行固定留存。清理只作用于声明输出，开发资料、用户文件和全局配置分别管理。

### 验证

类型检查验证值与接口，ESLint 检查已选的静态规则，格式工具处理排版，测试验证可观察行为。检查规则须有明确收益，沿所属工程的实际类型项目和运行环境执行，不建立另一套宽松项目来取得通过结果。机械检查不能判断命名、职责、注释内容或整体设计，不能代替人工审查。

审查覆盖本次改动的完整影响，沿实际存在的正常、失败、取消和关闭路径核对，不为形式覆盖引入额外机制。全项目审查逐项核对当前维护范围，同构文件可以成组审查，并核对身份与配置差异；不要求每个文件都修改或新增测试。样本、生成物和验证材料按实际来源与用途处理。

<a id="test-retention"></a>

长期用例按消费者需要持续依赖的行为组织。判断一项用例的价值，看它能检出哪种实际错误、其余检查能否发现，以及是否值得长期维护。已有保证足够时直接复用。同一保证在所属层验证，接入只核对新增风险。删去重复断言、照抄实现或冻结无关目录与配置的用例，连同只服务于它们的夹具一起清理。用例数量和覆盖数字不作为质量目标。

检查范围和运行环境按变更影响选择，复用仍适用的证据。文档、注释或等价组织调整不自动扩大到全部运行、制品与性能验收。具体环境和完成条件由所属项目的验收要求确定。

### 完整交付

交付单元完整履行自身合同，实现、制品、适用验证和使用说明齐备，已知缺项和无用途内容得到处理后登记完成。消费者负责自己的业务接入。纯合同、工程入口和运行能力各按自身职责验收，正常、失败、取消与清理共同成立。测试替身与演示载体保留在测试范围。

一次变更不需要同时实现所有后续能力，也不能把未完成能力报告为已交付。结果区分实现、验证、制品与公开发布，项目进度如实记录；仓库、包发布和部署操作按实际授权执行。
