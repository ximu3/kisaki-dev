# 全面测试必要性复核

2026-10-26—27，继续复核过度测试。范围从个别故障注入扩大到测试目的、重复覆盖、断言质量、运行层级、fixture 成本、任务与 CI，以及正式文档中的验证义务。本轮为审查与修改建议，尚未删改测试、CI 或正式验收合同。

## 范围与判断方法

检查了全部 23 份现行测试文件及其辅助、消费者样板、运行配置、项目脚本、Turbo 任务和三份 GitHub 工作流。按当前参数展开，共 68 项用例；其中启动性能用例内部运行 20 次。数量只用于核对清单，不作为删减目标。

当前 218 份非历史 Markdown 纳入文档清单，包括 144 篇正式设计、15 篇验收与覆盖文档、3 篇实施文档和 56 份工程指南／README。逐主题复核其中的测试、验收、平台与性能要求，并回读相关合同；同构扩展说明按共同内容及各项身份核对。relay 的两份配置 JSON 没有另立测试矩阵。历史证据按当前引用与适用范围复用，不重写旧结果，也没有重新认证外部 API 或运行旧探针。

判断以每项测试能发现的独立错误为起点，同时核对：

- 所保护的是消费者行为、正式合同，还是某次实现的字段排列、目录名称或固定写法。
- 共同机制是否已在拥有层验证，另一入口是否新增了序列化、权限、平台或生命周期风险。
- 是否必须启动真实宿主，能否在更小的实际接入边界取得同样证据。
- fixture、运行时间、失败定位、环境依赖和长期维护成本是否与收益相称。
- 首次交付、相关变更回归、完整性能测量和普通修改是否被混成同一执行义务。

参考 [Google 的测试审查要求](https://google.github.io/eng-practices/review/reviewer/looking-for.html#tests)与[集成测试分层讨论](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)。采用其行为、诊断和维护成本依据，不套用固定的单测／集成／端到端数量比例。

## 执行范围与测试层级

### CI 把不同风险的任务绑在一起

[Verification 工作流](../../../../../.github/workflows/verification.yml)只有一个 `desktop` 受影响结果。选中后，六个目标都执行浏览器组件、完整开发回归、性能、打包与制品检查。当前 20 次采样因此成为每轮选中桌面任务的 120 次新进程启动。仓库任务还无条件运行八包消费者，未区分公共制品／消费者输入是否变化。

这与[按变更影响选择验证](../../../../verification/acceptance.md#verification-scope)及[构建验证边界](../../../../design/engineering/build.md#pipeline)没有完全衔接。20 次本身是已确认的 W00 测量口径；应先调整执行条件，不随意削减样本后继续声称测得同一 P95。

建议采用以下分工，保留首次交付与正式发行的完整门槛：

| 任务                 | 日常触发依据                                         | 必须保留的覆盖                                                                                          |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 类型、lint、常规行为 | 实际任务输入与依赖变化；沿现有缓存和任务图           | 变更项目、实际消费者与必要根检查；无法判断影响时执行完整范围                                            |
| 仓库外包消费         | 公共包、声明、成品样式、打包、消费者或工具链输入变化 | Node、无框架与 Solid 的实际 tarball 消费；publint、ATTW 继续负责各自检查                                |
| 浏览器组件           | 对应 UI、样式、交互与工具链变化                      | 当前通用 Chromium 场景可在一个参考环境执行；有平台输入差异时增加对应环境，不仅因 CPU 架构而复制相同用例 |
| 开发会话             | 构建、监听、依赖快照、启动器与退出接入变化           | 实际受影响平台的启动、重载、保留旧实例及收尾；保留真实回归条件                                          |
| 完整性能测量         | 启动／加载／资源路径相关变化，或明确的完整验收       | 同一基线、输入、设备口径与充分样本；保留各目标已有证据的适用范围                                        |
| 原生与最终制品       | 对应运行时、平台实现、资源、打包、签名或发行变化     | 受影响系统与架构的真实验证；首次交付及发行的六目标要求不变                                              |

当前锁定的 Turbo 2.11.10 已提供 `query affected --tasks/--packages`，本轮只读取了其帮助；[官方 CI 文档](https://turborepo.dev/docs/crafting-your-repository/constructing-ci#running-only-affected-tasks)也说明了按任务输入选择。落实时使用现有任务和输入声明，不新建一套变更推断框架。Required checks 仍须确认全部已选择任务成功，无法选择或执行失败不能冒充“不受影响”。具体 CI 分流属于需要确认的执行策略。

### 依赖边界测试重复建立同一工程

[boundaries.test.ts](../../../../../tests/tools/structure/boundaries.test.ts)的 11 个案例各自复制相同基础配置、创建相同假包和链接，并启动一次 dependency-cruiser。案例有不同价值，准备和工具启动则明显重复。[上一轮日志](check.log)中这 11 例耗时约 15.4 秒；这只是该次本机结果，不是优化后的性能承诺。

建议将兼容的案例放进同一合成工程，一次读取真实依赖图，按来源、目标和规则分别断言。需要独立配置或相互干扰的案例再隔离。保留直接依赖边、测试目标、`contest.ts`、未声明依赖、私有入口与允许工程导入等全部有效反例，不通过删除这些已捕获真实问题的案例提速。

### 开发综合用例承担过多职责

[session.test.ts](../../../../../clients/desktop/app/tests/tools/dev/session.test.ts)在一个最长 240 秒的用例中串联退出取消、宿主存活、CSS HMR、Vite 配置、imports、公共包配置、编译失败、改名恢复、UI 快照采用、窗口关闭、profile 保留和 clean。前段失败会使后面的独立行为都未执行；[已有日志](../../tooling-review/2026-10-26/implementation/development-final.log)中该用例约 79.8 秒，启动取消与重试另约 40.5 秒。

建议按实际边界重新分工：保留少量真实 Electron 的整体启动／重载／退出链路；解析与快照交接沿已有较小集成用例；监听范围由监听接入验证；输出清理验证自己的文件副作用。复用现有准备与控制器，避免拆分后为每个小案例再安装、构建整套工作区。

这些步骤不能一律删除：公共包构建失败与 Node 程序编译失败走不同准备路径，Vite 重启后监听丢失也已实际发生；窗口拒绝关闭后宿主继续存活属于真实回归。收敛的是承担层级、重复准备和失败耦合。

## 收尾与后续修改边界

本轮未启动测试、浏览器、Electron、故障探针、打包或远端 CI。时间数据引用已有日志；没有生成新的全仓哈希清单或验证框架。上一轮偶发 Windows `EPERM` 的根因仍未确认，它不作为删除测试的理由。

建议先落实明确的等价删减和文档分工，再调整边界测试准备及综合开发用例；CI 触发与完整验收频率按上面的方案确认后实施。修改后的验证只覆盖改变的断言、运行分工或调度，不机械重复全部 68 项和六目标。正式产品范围、平台支持与 RPC 方案保持已确认合同。
