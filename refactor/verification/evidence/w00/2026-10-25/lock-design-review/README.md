# W00 工程锁设计审视

本轮审视工程工具的输出所有权、互斥范围和交接寿命。结论为：**部分共享输出需要协调，但当前锁的位置和覆盖范围不完整；直接全部删除或全部替换成系统文件锁，都不能完整解决问题。** 优先减少共享中间输出，再为保留的共享输出确定完整操作边界。

本轮没有修改应用、公共包、工具实现或依赖。用户已确认 buildId 保留现有机制，本轮不重新设计其生成方式。此前的输入补漏和浏览器入口修正继续保留，见[局部修正记录](../corrections/README.md)。工程锁仍待修正，W00 不登记为通过。

## 依据与实际范围

[构建规则](../../../../../design/engineering/build.md#outputs)要求每份输出有唯一写入者、不同目标和开发输出分开；[开发规则](../../../../../design/engineering/workspace.md#tooling)要求成功后完整交接，失败不覆盖当前结果。规则没有指定文件锁库，也没有要求建立通用锁管理服务。

| 输出或状态 | 实际参与者 | 当前保护与问题 |
| --- | --- | --- |
| 公共包 dist | 包构建、Turbo 缓存恢复、下游编译、开发快照、pnpm pack | 八包的 build.lock 只包围自身构建函数；缓存恢复及读取不参与 |
| 应用 out/resources 与 out/native | 开发会话、有限构建、显式准备命令 | 写入阶段由 replaceOutput 互斥，返回共享路径后调用者才开始复制 |
| 应用 out/&lt;target&gt; | 有限构建、package、实际运行与测试 | 构建期间互斥；package 在构建返回后校验、复制，未持有对应占用 |
| 应用 dist/&lt;target&gt; | 打包、制品验证、clean | 打包期间互斥，其他消费者不参与；验证阶段已有禁止同时重建／清理的使用约束 |
| session 与 generation 目录 | 创建它们的开发会话 | mkdtemp 和会话内代际已经隔离目录；目标级 .session-lock 同时限制会话数量并充当 clean 占用标记 |
| Cargo 缓存与原生交付拷贝 | Cargo、napi CLI、应用 native 工作流 | 上游有自己的协调范围；改变交付输出的位置后，仍需核对编译完成到绑定拷贝的完整寿命 |
| clean | 应用与八包清理入口 | 扫描锁或 stat 通过后才删除，检查与删除之间没有阻止新任务进入 |

独立工作流在同一个固定输出上互相覆盖不是抽象风险；当前资源／原生准备和公共包输出就是实际共享点。反过来，私有候选目录的独占性不应再依靠一个目标级会话锁来建立。

## 确认的缺口

### 1. 锁目录存在不代表仍有持有者

[replaceOutput](../../../../../../clients/desktop/app/tools/lib/output.ts) 第 21–22 行、八包 build.lock 和开发 .session-lock 都依靠 mkdir 获得互斥，正常 finally 才删除。进程结束后遗留目录阻止重试的事实沿用[终审 F2](../final-review/README.md)，本轮没有重复终止进程。开发 CLI 在异步初始化结束后才安装信号处理，也是现有取消路径需要修正的部分。

### 2. 写入互斥没有覆盖读取交接

[公共包快照](../../../../../../clients/desktop/app/tools/dev/dependencies.ts)逐文件读取 dist，没有在读取期间阻止目录替换。本轮使用真实 captureDependencies 和 replaceOutput，在读取 a.js 后安排完整的输出替换，再继续读取 b.js；结果快照被正常接受，但 a.js 来自旧构建、b.js 来自新构建。

这是受控安排的合法读写交错，不是概率压力测试；仅替换探针进程中的读取时序，没有改写两个生产函数。结果见 [results.json](results.json) 的 snapshot 字段。

同类静态缺口还存在于[打包交接](../../../../../../clients/desktop/app/tools/package/packager.ts)第 39–49 行，以及资源、原生输出的返回后复制。先核对摘要再复制不能阻止后续替换。本轮没有将这两条静态推导登记为已经运行的完整打包／原生并发复现。

### 3. Turbo 缓存恢复绕过包构建函数的锁

探针在独立工作区使用当前锁定的 Turbo 2.11.10，以及字节一致的 RPC 包构建源码。先完成一次真实构建以填充缓存，再移走 dist 并建立 build.lock：

- Turbo 命中缓存，退出码为 0，恢复 dist，锁目录仍存在。
- 直接执行同一包的 build 命令，退出码为 1，因 mkdir 返回 EEXIST 而拒绝。

缓存恢复本来就是 [Turbo 的公开行为](https://turborepo.dev/docs/crafting-your-repository/caching)。这里不是 Turbo 违反了项目锁合同，而是项目只保护了其中一条写入路径。[缓存命中日志](cache-locked.log)中的编译文字是重放的旧日志，不能当作本轮又执行了 build.ts。

因此，即便 build.ts 改用系统文件锁，也不能单独保证公共包输出的互斥。证据为[首次构建](cache-first.log)、[带锁缓存恢复](cache-locked.log)、[直接构建对照](direct-locked.log)及 [results.json](results.json)。

### 4. clean 的检查与删除不是同一个互斥操作

[应用清理](../../../../../../clients/desktop/app/tools/clean.ts)第 26–29 行和各包清理先检查、后删除。新任务可以在检查通过后进入，旧锁也可以让无活动的工程无法清理。本项为代码审查结论，没有额外安排并发删除实验。

## 建议的设计方向

1. **私有中间输出由调用工作流直接拥有。** 资源准备和原生交付支持明确的目标目录；开发候选与打包候选直接取得自己的完整输入。package 不必先改写公共的有限构建目录，再从那里复制。显式 CLI 仍可拥有约定的固定输出。
2. **固定共享输出保留必要的互斥。** 相同目的地的实际写入者必须采用同一规则；完整结果被复制或交接给消费者前，不能释放所依赖的占用。普通并行编译仍由 Turbo／构建器调度，不增加自己的任务调度系统。
3. **公共包在任务与消费交接层处理。** 互斥范围必须覆盖缓存恢复、实际构建和必要的快照取得；只修改八个 build.ts 不充分。具体接入需保持包 exports、Turbo 缓存和跨项目公开入口，不通过关闭缓存或扩大应用私有工具的访问范围掩盖缺口。这一接入尚未形成可直接实施的完整方案。
4. **会话目录隔离与活动占用分别表达。** 在共享上游和 clean 的活动范围闭合后，可移除仅为私有 session 目录设置的目标级锁。应用资料根的单实例保护继续由其拥有者负责；不能顺带移除。
5. **clean 与被清理输出采用同一接纳边界。** 维持活动任务结束后再清理的行为；如承诺自动拒绝冲突，检查和删除期间必须持续持有对应占用，不能靠扫描 .lock 目录模拟。

采用系统文件锁仍是剩余互斥的一种合理实现，其优势是持有寿命与系统资源关联；它不替代以上输出归属和交接设计，也不自动负责子进程结束或候选清理。本轮不引入 fs-native-extensions，不以依赖选型先行决定全部工具结构。

```powershell
pnpm exec tsx refactor/verification/evidence/w00/2026-10-25/lock-design-review/probe.ts 'C:/Users/ximu/AppData/Local/pnpm/.tools/pnpm/11.11.0/node_modules/pnpm/bin/pnpm.mjs'
```

环境为 Windows 10 x64、Node 24.11.1。探针复用已安装的依赖，没有下载、安装或发布包。临时工作区均为本轮创建，实际进程和文件资源结束后已清理；生产工程的锁、输出和用户资料未被删除。保存的结果说明缺口已经被观察到，不代表缺口已修复。

完整检查和六目标运行不属于本轮纯审视范围，未重复执行。来源文件与版本摘要见[审查输入](inputs.json)。
