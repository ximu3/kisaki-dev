# 项目文档与协作入口

项目文档分别面向使用者、维护者和具体任务的执行者。每份文档负责说明一类问题；同一规则只保留一份完整定义，其他文档通过链接引用。

<a id="owners"></a>

## 各类文档的职责

| 文档                                | 主要内容                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------- |
| README 及其语言版本                 | 产品定位、可用功能、下载与运行方式、简短的开发概览，以及协作指南、Issues 和 TG 反馈入口 |
| CONTRIBUTING.md                     | 维护者和受邀协作者共同遵守的环境准备、开发验证、PR、版本准备与发布流程                  |
| CONVENTIONS.md                      | 所属项目完整、长期维护的编码规范，归属见[编码规范](conventions.md#ownership)      |
| ARCHITECTURE.md                     | 模块职责、状态归属、运行边界和包之间的依赖关系                                          |
| AGENTS.md                           | 每次任务都需要了解的产品范围、架构边界、数据与错误规则，以及具体规范的入口              |
| `.agents/skills/<project>/SKILL.md` | 适用任务、资料选择与可复用的工作指引                                                    |
| 模块或包的 README                   | 该模块或包的使用方式、协议、资源要求和限制                                              |
| 公共 JSDoc                          | 调用者可观察的行为，包括单位、空值、生命周期、取消、失败和副作用                        |
| 代码注释                            | 文件与模块概述、对象调用合同，以及实现意图、约束和不变量                              |
| refactor/design                     | 产品、架构、领域、界面、扩展和工程的实现规格                                            |
| refactor/implementation             | 工作包、实施依赖和实际进度                                                              |
| refactor/verification               | 验收标准、要求覆盖情况和验证证据                                                        |

规范描述正式职责、行为、接口和约束，必要时说明这些约束的理由。[简洁、原生与适度复杂度](conventions.md#simplicity-native)在协作入口、根规范和设计入口中优先呈现，具体规则仍由所属主题维护。文档自身减少重复概念和间接导航，不另造一套术语解释工具已有的能力。使用文档描述已经交付的能力；设计要求、实现状态和验证结果分别记录，不能相互代替。

通用文档，包括 README、CONTRIBUTING、CONVENTIONS、ARCHITECTURE、AGENTS、skill 指引与设计正文，只描述当前有效的规则、能力、使用方法和必要依据。不得加入具体实施轮次、修改先后、工作进展、阶段回顾或任务对话记录。方案演进、实施经过和验证进度分别归入实施状态与验证证据；必要的取舍理由在所属规则处直接说明。

每份自维护代码文件和每个模块都在源码中提供简短概述，覆盖要求与格式由[注释规范](conventions.md#file-module-comments)定义。架构说明与项目文档维护跨模块关系、完整生命周期和使用指南；具体函数、组件、类与类型的调用合同及局部实现约束就近写在代码中，各层不重复复制详细内容。

界面文字遵守[文案规范](../ui/components.md#copy)，代码对象的注释范围、位置、内容和维护要求遵守[注释规范](conventions.md#comments)。发行变化记录在提交、PR 和发行说明中。

<a id="writing"></a>

## 写作要求

内容选择、组织与表述共同构成设计质量，也是定稿条件。正文先说明用途、职责和正常流程，再解释影响结果的条件、差异与失败。每段围绕一个重点展开，写清主体、动作和结果，句子之间保留必要的承接。

限制写在它所属的边界，并说明理由或后果。删除重复的防御式展开、口号化强调和术语堆叠；“完整、真实、明确”等词须有可核对的所指。篇幅与内容相称，简洁表达仍保留必要细节和有依据的领域差异。

句子保留清楚的主语、动词和逻辑关系。并列事项使用标点或列表，“和”“或”“分别”等关系明确写出；斜线用于路径及有确定含义的技术记法，缩写在读者能够理解时使用。

同一概念在各篇文档中使用同一名称。普通说明使用自然语言，类型、字段、函数和文件名称保留准确拼写。表格适合比较职责、列举字段和对应规则；需要解释条件、顺序或因果的内容使用完整段落。

<a id="pull-request-descriptions"></a>

### PR 描述

PR 描述简洁说明最终改动，面向未参与实现的审阅者，只补充影响审阅判断的信息。简单改动可以用一两句话；复杂改动按内容关系使用短段落或列表，不强制固定栏目、模板或篇幅。

问题与动机、方案取舍、验证结果、限制、风险和迁移信息按需要说明，不作为必填项。CI 已清楚展示的状态无需复述，需要详细证据时链接所属记录。描述不记录工作过程、讨论经过或中间提交清单，措辞直接、具体，避免口号和笼统保证。

<a id="specification"></a>

## 设计规格的维护

`refactor/` 按读者任务与内容职责组织。设计定义当前规则，工作包定义实施依赖与门槛，验收定义场景与预期结果，证据保存来源、比较和实际结果。status 维护工作包汇总和当前未闭合事项；delivery-checklist 拥有已经拆分的子交付状态，两者按[状态归属](../../implementation/delivery-checklist.md)引用，不重复维护同一项事实。

独立项目各自拥有公共合同和实现机制，Kisaki 文档只定义自身接入。一个主题需要多个文件时，以实际职责和查阅需要拆分；紧密相连的规则保持在同一主题中，不按讨论轮次扩张文件。总览给出入口与边界，不复制完整规则。

查询语义由 library-queries 定义，library-query-contracts 固定可传递的字段和形状；完整写入行为由 library-operations 及领域主题定义，library-write-contracts 限定比较单位与错误目录。communication 定义调用完成与事件语义，engineering/protocols 定义通信帧和接入。它们分别负责语义、值形状和传输机制，不各自重新定义同一个事实。

验收文档引用规则，并给出能区分不同行为的输入、预期结果和证据要求；架构检查使用带来源的索引。相同原子性、取消、排序或资源规则在拥有层验证，来源和接入只增加自身差异。证据记录版本、环境、输入、实际结果与限制，历史进度使用当时日期；后续结论另存并相互引用。当前进度由 status 维护，已经完成的事项从待办中移出。

修改规则时先修改所属设计，再同步必要验收和引用。移动或合并文档须核对本地路径、锚点与 R／W／A 关系，原始试件和结果不随文字整理改写。

## 按任务组织 skill 参考文档

项目 skill 按实际任务组织工作指引，引用所属项目的正式规范和当前实施资料。以下为 Kisaki 的主题组织示例，参考文件在有实际内容时建立；独立项目按自身的进程与窗口、阅读、媒体绑定或服务部署等职责组织。

```text
.agents/skills/kisaki/
├── SKILL.md
└── references/
    ├── data/
    │   ├── operations.md
    │   ├── ingest.md
    │   ├── holdings.md
    │   └── schema.md
    ├── ui/
    │   ├── composition.md
    │   └── state.md
    ├── extensions/
    │   ├── contracts.md
    │   └── lifecycle.md
    └── engineering/
        ├── packages.md
        ├── resources.md
        ├── testing.md
        └── releases.md
```

SKILL.md 统一提供任务到参考文档的导航，references 直接按实际任务主题收纳有内容的参考文档。目录按查阅与维护需要划分，导航集中在 SKILL.md。

执行具体任务时，只读取相关参考文档。例如，修改标签替换操作时，阅读 data/operations.md 及对应测试；调整统计页的详情弹窗时，阅读 ui/composition.md 和 ui/state.md；处理扩展更新时，阅读 extensions/lifecycle.md 和 engineering/packages.md；修改新库初始化时，阅读 data/schema.md 和 engineering/testing.md。

参考文档通过链接引用 README、CONTRIBUTING、CONVENTIONS、ARCHITECTURE、公共类型和既有工程入口，不重复维护其中已有的规则。CONTRIBUTING 说明开发与交付流程，CONVENTIONS 拥有完整编码规范；skill 补充资料选择、任务步骤和验证方法。工程工作流归 tools，测试专用辅助归 tests/support，skill 不维护平行脚本。

<a id="lifecycle"></a>

## 项目文档交付与维护

项目文档依据已实现并验证的工程集中交付。Kisaki monorepo 的根文档、模块与包说明、官方扩展使用说明、模板配套说明及协作入口由 [W12](../../implementation/work-packages.md#w12) 完成。四个独立项目各自完成文档交付，在公开交付前具备完整、可用的开发、使用和验证说明；其安排不与 Kisaki 锁步。文档职责遵守[归属定义](#owners)。

实施期间直接遵守 refactor 中已确认的规范。接口声明、schema、代码注释、界面与 CLI 文案、测试和验证记录随所属实现维护，工程命令由实际脚本、配置和工具入口表达。

文档交付核对内容完整性、规则归属、实际命令、可运行示例、skill 路由及引用。正文描述当前能力与行为，待实现的命令和计划留在实施记录中。协作入口、CLAUDE.md 和 skill 别名引用同一份规范。

交付后的项目文档随相关实现同步维护。发行说明、许可及对应源码材料分别按[发行](releases.md)与[许可](licensing.md)规则准备。
