# 浮动辅助断页与排版上下文

2026-10-20，继续验证[已确认的原生排版与 Kana 分页职责](../../../design/projects/kana/layout.md)。本轮用 [float.cjs](float.cjs)检查一个局部补齐方法，完整结果见 [float-contract.json](float-contract.json)。该方法尚未作为通用分页实现采用。

## 方法与完整保留的源结构

辅助盒放在合法容器的 ShadowRoot 中，原有源节点通过手动 slot 分配参与布局。源节点保留原父子关系、兄弟次序与对象身份，没有将辅助盒插进原有兄弟序列。

一个目标断点的试件先用浮动盒与 shape-outside 留出前文的正常排字区域，再用 clear 让后文越过该浮动范围。目标前应保留的 20px 间距由下一片段起始处的辅助浮动盒承担。浮动盒仅服务布局，不承载源文字。

多个直接子块的试件则将 slot 与辅助盒按源顺序交替安排：先取得前一块的实际结束位置，再填满该片段的剩余块向空间，保留下一片段起始间距，然后处理后一个断点。这是根据实际几何逐个推进的受控样例，不是一般 CSS 断点发现与规划器。

浮动、clear 与独立块排版上下文有各自作用范围，参照 [CSS 浮动规则](https://www.w3.org/TR/CSS22/visuren.html#floats)、[clear 的作用](https://www.w3.org/TR/CSS22/visuren.html#flow-control)和 [shape-outside](https://www.w3.org/TR/css-shapes-1/#shape-outside-property)。表格行不因具有一个 DOM 节点就成为可以套用同一 clear 操作的普通块。

## 实际结果

三个测试引擎分别运行横排、vertical-rl、vertical-lr；每种方向包含十种上下文，共 90 组场景。每组在同一个 Document 中经历两套布局：280×400px、20px 字号，以及 360×500px、26px 字号。内容块使用 3em 块向尺寸，随字号从 60px 变为 78px，辅助尺寸重新按实际布局取得。

| 场景                                           | 观察                                                                             |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| 两个普通块、普通嵌套块                         | 前文留在原片段，后文进入下一片段并保留 20px 间距                                 |
| 常规有序列表中的一个断点                       | 可以在外层合法宿主建立辅助盒，原列表和两个列表项不需改父子关系；本次位置符合预期 |
| 独立块排版容器内部的断点，辅助盒放在该容器内部 | 本次位置符合预期                                                                 |
| 同一独立容器，辅助盒放在外层                   | 原有容器及前文受到挤压，未得到预期的分片结果                                     |
| 自身建立独立排版上下文的列表，辅助盒放在外层   | 同样未得到预期结果，不能因普通列表成功就推广                                     |
| 整张表格之前断页                               | 本次整体移动与起始间距符合预期                                                   |
| 表格第二行之前断页                             | 整张表格被推走，两行仍在同一片段，没有实现行间断页                               |
| 三个直接子块，两个断点按内容顺序交替处理       | 两个后续块分别进入下一片段，间距及源顺序保持                                     |
| 一个列表中两个断点，所有辅助盒集中放在列表之前 | 中间内容被过度推进，后两个列表项仍挤在同一片段；不是有效的连续断页方案           |

六类场景在两次布局中均匹配预期，四类保留为反例。共 180 个候选布局中，108 个匹配，72 个未匹配。脚本同时校验正向结果与这些反例，没有将“记录生成成功”写成“所有内容都正确分页”。

三种方向下，匹配场景的首块保持原位置，后续块位于下一原生片段；初始横排的第二块是 x=300、y=20，重排后是 x=380、y=20。竖排分别按其块推进方向保留 20px 间距，没有统一当作 vertical-rl 解释。

所有场景在两套布局中均保留源节点对象、源子树序列化结果、AB／ABC 正文及 Range 提取的文字；受查兄弟选择器、红色和粗体结果保持。同一 Document 没有重建。这些观察不证明全部 CSS 上下文都保持，也不代替列表计数器、真实格式源地址、复制、键盘焦点和辅助技术的验收。

## 对实现方向的约束

本轮支持继续研究普通块流中的局部补齐，并给出三个需要明确处理的问题：

- 辅助操作必须归属于目标的实际排版上下文。仅按最近祖先或标签选择插入位置不够。
- 多个断点需要沿内容顺序协调。把所有辅助盒提前放在章首或列表前，不能代替逐个断点的布局执行。
- 整体表格与表格内部行／行组具有不同要求。前者成功不能作为后者已经支持的证据；平行流也需按其实际片段化关系解释，见 [CSS Fragmentation](https://www.w3.org/TR/css-break-3/#parallel-flows)。

目前没有一般上下文识别、有效作者声明解析、嵌套与平行流的完整算法；受控场景中的宿主和断点由夹具明确给定。跨片段浮动、负边距、复杂表格、超大内容及实际出版物尚未验证。重复列表与表格内部断点说明该候选仍不完整。后续已确认[保留原生能力边界](../../../design/projects/kana/layout.md)，不再将此候选扩展为正式通用补齐；这些记录不构成缩减正文内容或其他阅读要求的依据。

## 复现与环境

```powershell
node refactor/verification/evidence/kana-breaks/float.cjs
```

运行复用[浏览器机制环境](../kana-browser-scope/source-input.json)，并在启动前核对可执行文件摘要：Chromium 149.0.7827.55、Firefox 153.0、Windows WebKit 26.5。没有运行真实 Safari、WebKitGTK、辅助技术或完整 Kana Reader；这些版本不替代已经确认的维护窗口。

所有输入均为自建片段，页面请求被阻止，实际外部请求为零；没有写入系统剪贴板。独立浏览器配置位于忽略缓存，45 秒期限与 finally 负责结束本次上下文。没有修改工作区依赖。
