# 验收环境、场景与完成标准

验收检查真实产品行为、完整调用、持久化、界面、性能和最终制品。纯逻辑、技术原型、真实应用和发行文件各自提供对应范围的证据，不能互相替代。本篇规定设计验证与实现验收的要求。设计验证证据随对应设计记录，实施验收结果记录在实施状态中。

<a id="verification-scope"></a>

## 验证范围与投入

遵守[简洁、原生与适度复杂度](../design/engineering/conventions.md#simplicity-native)，核对直接的用户流程、既有平台能力及定制部分的依据，再按本次修改影响的行为、合同或宿主条件选择检查。本篇场景规定完整交付的覆盖要求，各次修改按影响取得或复用证据，不机械重跑全部场景。

文档、注释和等价组织调整通常核对内容、链接、解析与适用的静态检查；运行输入或宿主行为改变时再执行相关运行验证。构建身份或文件摘要变化本身不是全量回归的充分理由。已有结果可沿仍成立的实现、依赖和环境边界复用，并说明适用范围；旧运行记录不改写成新输入的实测。

新增测试应能指出它会发现的实际错误或守护的必要合同。已覆盖的共同规则不在每个入口重复验证，测试辅助不为假想场景建立复杂框架。检查通过且当前疑问已经解决后停止扩大验证；新的失败、实现变化或未解决风险才构成继续检查的依据。

<a id="design-validation"></a>

## 设计定稿前的验证

桌面本体、公共包、官方扩展和独立项目都应达到可以直接实施的程度。设计明确模型与字段映射、公开输入输出、主要操作流程、依赖、资源归属、支持范围和关键技术方案；实施者负责在这些合同内完成代码，不接手尚未确定的来源语义、接口能力或平台路线。

验证围绕会影响上述决定的具体疑问进行，优先采用官方规范、固定版本源码和真实格式样本。需要运行证据才能判断时，在隔离环境编写最小原型或探测程序，并据结果修订设计，再将其作为实施依据。验证须覆盖结论依赖的平台或后端差异，不能用单个环境的结果概括其他目标。原型只用于验证所需链路，不算完整功能交付。

设计阶段核实本地设备与 CI 环境的实际可用性，确定构建、桌面与图形用例的执行安排，结果记录在[实施状态](../implementation/status.md#environments)。

<a id="platform-evidence"></a>

macOS／Linux 的平台方案以官方接口、固定版本源码、成熟实现和实际协议为依据，明确调用、资源归属、能力条件及失败边界。设计定稿以这些依据及已解决的技术选择为条件，本地实机验证按后续验收范围安排。仍未确定的接口和技术选择继续完成资料核对，不能据此假定所有候选都可行。

设计依据与运行结果分别记录，未执行的 macOS／Linux 场景标为未执行。正式实现与发行使用[实施状态](../implementation/status.md#environments)中登记的环境，按目标矩阵执行检查，交付按[运行覆盖规则](#runtime-coverage)判定。历史试件保留原始执行范围。

具体环境及责任遵守[目标环境安排](../design/engineering/build.md#platform-testing)。普通构建、真实桌面会话、GPU 共享和系统下限各按自身条件取得证据。独立项目验证原生能力，本体与扩展验证真实消费，W13 汇总同一发行的实际结果、兼容性依据及未实测范围；跳过结果不记为通过。

本次需要核实的关键范围包括来源实际端点、授权、分页、字段与对象映射，导入格式版本及转换规则，数据库运行时与迁移组合，原生桌面观察、控制与采集后端，libmpv 与 Electron 的帧交接和释放，Kana 各格式的解析与源位置恢复，以及正式制品保留加固配置后的验证入口。

每项结论关联采用的版本、样本或环境、验证方式、实际结果及适用范围。已有可靠证据可以复用；尚未确定的设计事项明确保留为未完成，不能把技术选择留给实施时临时决定。macOS／Linux 的设计按上述依据核对，运行结果由实施验收记录。验证规模以解决当前设计疑问为准，普通失败仍遵守[不过度防御](../design/engineering/conventions.md#validation)的规则。

设计验证通过后，W00–W13 完成正式工程、业务集成、回归、性能和制品验收。设计阶段的可行性证据与正式实现的正确性证据分别成立；前者不能代替后者，后者也不用于推迟已知的设计验证。

<a id="runtime-coverage"></a>

## 运行覆盖与交付

按六目标矩阵完成构建和适用的运行测试，分别记录系统版本、架构、桌面与图形条件。尚未接入的环境、尚未实现的用例和可以执行但尚未运行的检查，均属于待完成工作。

| 结果     | 含义                                                   |
| -------- | ------------------------------------------------------ |
| 实测通过 | 在记录的系统、架构、权限和设备条件下执行，相应断言成立 |
| 未实测   | 尚未取得该场景的运行结果，记录具体范围与原因           |
| 失败     | 已执行但断言不成立，或兼容性核对发现尚未解决的支持冲突 |

<a id="minimum-runtime"></a>

### 必须取得的最低运行证据

六个桌面目标都须有对应架构的正式候选制品和基础运行结果。基础运行至少完成应用启动、真实数据库创建与读写重开、适用原生模块加载、主窗口呈现及正常退出；运行使用该目标的原生架构，交叉构建和仿真不代替它。安装形态、更新和签名仍按各自场景检查。

每条主要后端还须在至少一个符合支持条件的真实环境中贯通自己的正常链路。一次用例可以同时覆盖独立库与宿主接入，证据分别标明使用的制品、接口和断言；不能把同一套原型拆成多项正式通过。

| 范围 | 不可由整条“未实测”代替的最低链路 |
| --- | --- |
| Vantage Windows | 原实例发现、观察接续、明确控制、WGC 单窗采集及释放，并由 Kisaki 完成一次受管理使用与采集 |
| Vantage macOS | 签名宿主的实际授权身份、AX 与 ScreenCaptureKit 窗口对应、观察／控制／采集及释放 |
| Vantage Linux X11 | XRes 归属、窗口观察／控制、XComposite 图像及本体消费 |
| Vantage GNOME Wayland | 实际组件加载、窗口对应、Mutter／PipeWire 采集、断连与本体收尾；旧式与 ESM 入口各取得适用运行结果 |
| Vantage KWin Wayland | 实际 KWin 5／6 接入、控制与单窗采集，覆盖需要桌面登记和已取消该登记检查的实现分支 |
| libmpv-node 与 Electron | Windows D3D11、macOS CGL／IOSurface、Linux EGL／dma-buf 分别完成带音频与字幕的播放、定位／切换、画面消费、截图及最终回收；Linux 消费同时覆盖 X11 与原生 Wayland |
| Kana | 在声明维护的浏览器与实际端口中，从打包资源打开代表性的重排、原始页与混合内容，完成定位、选择／复制及关闭；Safari、WebKitGTK 和 Electron 三条维护线使用各自实际运行时 |
| oauth-relay | 两种目标架构镜像分别完成启动、HTTP 请求、健康检查和正常停止；实际部署与客户端完成各来源已承诺的授权／刷新链路，远端账号操作不因架构数量重复执行 |

这些是首次交付的运行下限，具体正确性仍由所属 A 场景判断。组件加载、授权、系统接口或资源交接存在实质不同的实现分支时，分别取得至少一份运行证据；同一分支的全部系统小版本、GPU 型号与设置不要求组成笛卡尔积矩阵。普通纯规则在拥有层验证，共同机制不因调用入口多就重跑整套测试。

已经取得的正式证据可以在其输入、依赖、实现与宿主路径仍适用时复用，并说明范围。修改原生实现、运行时、平台组件、权限接入、共享图像或释放路径时，重新执行受影响链路；普通文案修改不触发全平台手工回归。历史设计探针不能替代正式制品的首次链路。

缺少最低链路所需环境时，该交付仍未完成，先落实执行环境；不能仅保留支持声明，再把整条后端列为未实测后发布。已完成最低链路的其他明确组合，才可以适用下述例外。

### 其余组合的未实测记录

个别场景确因具体系统版本、设备或图形条件无法执行时，保留支持目标，满足以下条件后可随交付列为未实测：

- 所属主要后端及实质不同的实现分支已满足上述最低运行证据；功能与目标制品完整，适用的构建、声明、包消费及其他可执行检查已经通过。
- 核对实际调用的 API 可用版本、SDK 与部署目标、二进制架构、系统符号和 ABI，以及 Electron、Node-API、SQLite、媒体库等实际依赖的下限。采用固定版本源码、官方合同及适用的上游证据，列明仍不能据此确定的运行行为。
- 交付报告和发行支持说明分开列出支持目标、已实测组合、未实测场景与兼容性依据。源码或 ABI 核对不标为运行通过，未实测项目不从矩阵中删除。

这项条件适用于本体、公共包、官方扩展及四个独立项目。交付仍须满足完整功能、六目标制品、签名、许可、资料完整性和资源寿命要求。已知失败、正常输入缺陷和实际依赖不兼容须修复；改变系统下限或功能范围仍需另行讨论。

## 测试运行环境

测试源码、样本、工具用例与辅助代码遵守[统一目录与归属](../design/engineering/layout.md#tests)。各套件按下表选择运行环境，不能只因文件位于 tests 中就使用同一 Node 进程执行全部测试。

| 层次                  | 工具与环境                                     | 验证内容                                                  |
| --------------------- | ---------------------------------------------- | --------------------------------------------------------- |
| 纯合同与纯逻辑        | Vitest，普通 Node                              | 值规则、计划、映射、排序和确定性政策                      |
| 原生业务与数据库集成  | Vitest forks，由开发 Electron 的 Node 模式启动 | 实际 better-sqlite3 ABI、事务、约束、查询、文件与初始化   |
| Solid 组件            | Vitest Browser Mode + Playwright Chromium      | 真实 DOM、事件、焦点、响应式草稿、组件/弹窗接口           |
| Electron 集成与端到端 | Playwright 的 Electron 能力及真实开发应用      | preload、窗口、进程、协议、生命周期和完整工作流           |
| 正式制品              | 实际打包应用，普通产品操作与合适的外部验证方式 | 打包路径、原生依赖、fuses、资源、初始化、更新、安装和启动 |

开发 Electron 的 Node 模式只用于不依赖 app 或 BrowserWindow 的原生测试。测试脚本在运行器启动前设置宿主运行条件，按 [Electron Node 模式](https://www.electronjs.org/docs/latest/api/environment-variables#electron_run_as_node)启动匹配版本；fixture 或测试中的环境变量配置不能切换进程 ABI。真正的 Electron API 在实际应用中验证，实例准备与关闭使用现成运行器的 fixture 及所属 tests/support。正式包保留安全 fuses；开发调试入口与正式限制分别处理，不能关闭 fuses 后把测试包当作原样制品。W00 验证所选运行组合并建立可执行的外部或现场验证路径，W11 对最终文件执行并保存结果。

公共包与三种作者接入的消费检查见[工程场景](scenarios/engineering.md#public-consumers)；原生库、Kana 和 relay 的专项断言见[独立项目联合交付](scenarios/projects.md)。

共同映射与确定性规则在其拥有层验证，各导入器和接入层只补充自身格式、调用与生命周期风险。已有用例能够覆盖同一不变量时复用其依据，新增失败场景须对应实际机制、已知缺陷或重要边界。

<a id="isolation"></a>

## 数据隔离、替身与诊断

集成用例使用独立临时 profile、磁盘数据库和用户文件样本，不使用真实开发库、媒体或个人凭据，也不共用一个全局临时目录。SQLite 约束、事务和文件恢复使用真实驱动。初始化、WAL、关闭重开和崩溃场景不能全部包在测试外层的回滚事务中，否则会掩盖真实持久行为。

外部来源、时钟、网络、对话框和必要子进程边界可以使用明确的测试替身。生产代码通过正常依赖注入接入，不散布 if(TEST)。资源关闭后再清理，并行用例不共享资料库。失败时可以保留有界 trace、截图和报告，但用户内容或认证材料不能进入制品。

<a id="performance"></a>

## 固定场景与性能预算

代表规模、资源不足的结果和比较方法按[数据规模与性能边界](../design/engineering/performance.md)执行。W00 建立测量入口并将预算写入测试配置。场景的工作量、预算和允许波动在新实现测量前固定，测量至少覆盖：

- 主界面显示、资料可用和扩展贡献可用三个时点。
- 详情、编辑器、统计和阅读首次打开及再次打开的响应。
- 大库筛选排序、连续滚动和远处直达的请求次数、响应量、视图内存及主进程耗时。
- 代表查询和短事务的耗时分布与长阻塞，以及扫描、导入、图片处理或索引期间的基础 UI 响应。
- 反复打开和关闭文档、窗口、Dialog 与扩展后，进程、监听和内存是否回落。

图片处理、扫描正则、区间批量、预取和并发等数值属于所属模块的内部实现参数。对可能持续增长或阻塞的工作按实际机制设置预算，并选择相关的边界、超限、取消或释放验证，不机械要求每项参数覆盖所有场景。调优不改变产品范围、结果含义、失败处理或已经固定的验收预算。这些参数不成为用户必填配置，也不允许来源或扩展任意覆盖。

发现问题时，先检查索引、无界工作、重复 IPC、静态依赖和加载边界，不用全局查询缓存补救。bundle 或 chunk 数据可以帮助解释结果，但不能独立证明体验更快。

## 目标工程命令

| 命令                                                 | 责任                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------- |
| pnpm desktop:dev                                     | 启动隔离资料目录中的桌面会话，完成依赖首轮构建和实际就绪协调              |
| pnpm desktop:build                                   | 编译桌面各程序与依赖，不签名、发布或生成安装包                            |
| pnpm desktop:package --target windows-x64            | 为明确目标准备完整资源并打包，CI 另提供适用的签名环境                     |
| pnpm desktop:test:artifacts                          | 对明确提供的最终桌面制品执行结构与实际运行测试                            |
| pnpm desktop:test:e2e                                | 在真实开发应用中运行桌面完整工作流测试                                    |
| pnpm typecheck / pnpm lint / pnpm test               | 调度根工程及实际 workspace 的对应检查；test 为明确配置的常规测试          |
| pnpm format:check                                    | 全仓格式检查，不先构建依赖                                                |
| pnpm format / pnpm lint:fix                          | 显式修改，开发者审阅后自行暂存                                            |
| pnpm check                                           | 类型、lint、格式及常规测试的统一入口                                      |
| pnpm build                                           | 通过 Turbo 按实际依赖编译工作区，不隐含正式发行                           |
| pnpm desktop:packages:test:consumers                                  | 调度各包及根跨包消费者任务，核对实际 tarball 的结构、声明、样式与作者接入 |
| `pnpm release:check --base <commit> --head <commit>` | 只读检查本次明确版本变化、依赖、所属说明语言要求并输出发行矩阵                    |
| pnpm release:notes:build                             | 从源说明生成可检查的发布正文和静态元数据，不上传                          |
| pnpm install:hooks / pnpm uninstall:hooks            | 当前仓库 hooks 的明确生命周期                                             |
| pnpm run clean                                       | 仅清理项目声明的构建输出                                                  |

根命令区分全仓任务与 clients/desktop/app 目标。desktop:* 不隐式构建或发布全部 .kisx，build 和 check 根据真实 workspace 依赖图执行，桌面开发入口固定为 desktop:dev。根 tools 处理机械交付工作，clients/desktop/app/tools 处理桌面会话与制品。项目级操作使用 pnpm filter，扩展作者使用 kisx。

工程操作命令落到[app/tools 对应工作流](../design/engineering/layout.md#desktop-tools)，测试命令按[任务分工](../design/engineering/layout.md#test-tasks)直接启动所属运行器和配置。test:e2e 选择应用 tests/e2e，test:artifacts 选择 tests/artifacts；原生与数据库任务在启动前选定匹配宿主。公共包的 check:package 检查自身 tarball 的结构与声明，根 desktop:packages:test:consumers 同时调度这些检查和 tests/desktop/consumers 的真实跨包消费。正式 .kisx 的安装与宿主接入由应用 tests/e2e 验证，不能用 tarball 消费替代。

消费者和最终制品任务明确接收待验证文件、版本和构建身份，并核对适用目标，缺失或不匹配时失败。CI 先完成对应构建、打包与适用签名，再执行消费和制品任务，并保存检查与用例的实际结果；测试不重建或替换待发行制品。普通 test 的默认范围与这些任务分别配置，必需但未执行的检查不能计为通过。

按[工作区合同](../design/engineering/workspace.md#workspace)核对唯一根 pnpm workspace、锁文件与实际项目身份。每项依赖由使用它的项目声明，根工具依赖不替代应用声明，catalog 不抹平真实环境差异。各项目配置隔离运行与测试 globals；共享配置或锁文件变化时按真实影响扩大检查，不能仅以顶层目录未变为由跳过必要消费者。按目标启动和构建不强制运行无依赖关系的其他工程，各发行单位仍保持自己的版本与说明。

构建与打包入口的 --target 由所属工程工具解析，不要求底层工具使用同名选项。测试任务采用运行器支持的项目、配置和参数，制品位置与目标由测试配置接收明确输入，不向运行器转发其不支持的自定义选项。版本 PR 直接编辑明确的版本和说明，不增加自动推版常驻命令。release.yml 调用只读 release:check 和项目任务后，再显式执行 npm、Release 或 Pages 发布；metadata.yml 只更正已发布说明。build、pack、check 和 prepare 都不暗中对外发布。

纯 typecheck 或库 build 不反复下载媒体，完整运行与包装前才准备当前目标资源。cache 清理和开发数据重置不混入 clean。当前可用状态见[实施状态](../implementation/status.md)。

## 最终完成条件

完整交付同时满足下列条件。目标平台的运行覆盖与实际结果按[运行覆盖与交付](#runtime-coverage)统一判定和记录。

- R01–R32 和 A01–A33 都有适用实现与真实证据，必需工作没有遗留。四个独立项目完成自身工程，并且新制品已经由调用方真实消费。
