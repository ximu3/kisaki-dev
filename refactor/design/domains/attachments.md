# 附件、图片与字节存储

附件是由应用保存、登记后不再改写的字节内容。业务字段和正文通过附件身份引用这些内容。保存前的准备、编辑与读取占用、正式引用和回收分别有明确的生命周期。用户自己持有的媒体文件属于 holdings，不属于附件。

<a id="storage"></a>

## 附件身份与存储

attachments 保存以下字段：

| 字段       | 含义与约束                                                  |
| ---------- | ----------------------------------------------------------- |
| id         | 稳定附件 ID，主键；不复用已删除 ID                          |
| media_type | 根据实际内容验证的媒体类型，不仅采用文件名或下载响应声明    |
| byte_size  | 正式字节的大小，非负整数                                    |
| sha256     | 正式字节的完整性校验值；不作为附件 ID，也不设置全局唯一约束 |
| width      | 图片的实际像素宽度，正整数；非图片为空                      |
| height     | 图片的实际像素高度，正整数；非图片为空                      |
| created_at | 该附件实际登记的时间                                        |

一行附件表示已经验证并登记的正式字节，不表示某个封面位置或用户媒体文件。图片必须实际解码，以核对格式和尺寸；游戏存档归档的条目与路径由备份能力检验。用途、来源、备注、锁定状态和保留政策都由使用附件的业务保存。

附件字节按 id 对应的固定规则存放在应用目录中，业务值通过该身份引用，因此移动资料目录无需重写引用。已登记内容保持不可变；裁剪或替换生成新 id。同一次采用可以让多个用途共用一份附件，独立导入则分别取得自己的身份。

本地路径、URL 和输入字节都只是来源。应用必须完成复制、下载或生成并验证内容后，才能登记附件，不能把外部地址当成应用已经持有的正式内容。

<a id="references"></a>

## 业务字段与正文引用

主图、背景、标题标志和卷封面等单一用途，通过可空外键直接引用 attachments.id。附件表不保存 owner_type、owner_id 或另一份用途记录。清空一处图片字段只解除这一处引用。正文中的多张图片由实际拥有者的关系表保存，例如：

| 表                            | 主键与引用                                                                |
| ----------------------------- | ------------------------------------------------------------------------- |
| entry_description_attachments | (entry_id, attachment_id) 联合主键；分别引用 entries.id 与 attachments.id |

同一图片在一篇正文中多次出现，只保留一个关系对，具体位置、顺序和说明由 Markdown 表达。笔记、合集、分部和标注各自使用指向真实表的外键，不设置通用 owner 引用。删除拥有者时级联解除正文关联；正文附件端及所有单图引用都限制附件删除，并提供反查索引。删除附件不能级联删除使用者，模型也不维护 ref_count 或一份通用引用副本。

正文以 `attachment:<id>` 保存稳定的逻辑引用。保存时，本体按共同的 Markdown 解析规则提取实际图片节点，验证它们引用的是正式附件或本次可采用的准备结果，再在同一短事务中提交正文和完整引用集合。代码块和普通文字不能被简单字符串搜索误认成图片。正文是图片引用的唯一事实来源，调用方不另行维护内文路径数组。复制正文可以复用附件 id；合并正文则按最终内容调整引用，不因条目 id 改变而移动或复制字节。

<a id="preparation"></a>

## 准备、采用与编辑占用

选择、粘贴、下载和裁剪图片时，主进程先准备内容及预览。准备成功后预分配 attachmentId，正式采用时沿用这个 id，草稿可以直接写入 `attachment:<id>`。此时字节已经验证，但尚未建立正式附件行，预览通过准备结果的 ReadResourceRef 读取。用户无需先创建空条目或空笔记，保存时也不必将另一种临时引用批量改写。

保存端必须验证每个 id 确实对应有效附件，或者属于当前可采用的准备结果，不能只检查字符串形式。操作只采用最终字段和正文真正使用的结果。字节先放入最终位置，再通过短同步事务登记附件、业务字段及引用。目标消失、基线冲突或事务失败时，原正式资料保持不变。

编辑器仍然存在时，保存失败保留它的准备结果，供用户修改和重试。内部操作失败后，如果没有编辑器或其他调用方继续使用结果，则由该操作清理。保存成功后，正式引用接管内容的保留；释放准备句柄不会删除已经采用的内容。已经接纳的保存独立占用输入，关闭窗口只释放窗口自己的占用。取消保存需要明确请求，释放占用不会回滚已提交结果。

草稿中仍可通过撤销恢复的图片，应保留到编辑结束。已有附件、准备结果和读取过程分别取得运行期占用，各窗口独立持有，不按固定超时回收活动编辑。正常取消释放本编辑的占用；异常退出后的残留在下次启动核对清理。[编辑状态](../ui/state.md)不另设持久草稿，因此运行期保护并不承诺恢复未保存的文字或图片。

<a id="collection"></a>

## 回收、修复与保留责任

只有最后一处正式引用已解除，且不存在准备、编辑或读取占用时，附件才可回收。主进程协调新增引用与回收，在短事务中重新检查真实引用，并依靠外键限制删除附件行。事务提交后，再删除字节和派生缓存。资料保存不必等待旧字节物理删除；删除失败可以留下孤立内容，后续重试。附件 id 永不复用，附件行删除后也不能重新引用旧 id。

已经放到最终位置、但尚未提交的字节仍受活动准备占用保护。启动或用户明确清理时，系统在数据库可用后结合实际行和运行期占用核对内容，只删除能够证明属于应用管理布局的孤立文件。如果附件行及引用仍在、字节却不可读，应保留引用并报告不可用，不能删行将问题伪装成空值。找回与记录校验值一致的字节时，可以修复原 id；其他内容必须作为新附件明确采用。

游戏备份通过 game_save_backups.archive_attachment_id 引用归档。附件提供归档大小和 sha256，备份记录则保存来源、展开摘要、备注、锁定状态及恢复政策。附件清理不能先删除备份记录，再把归档视为无引用文件。正在恢复以及尚未解决的恢复过程所需材料，都受业务引用和运行期占用保护。

attachments 设施负责准备、存储、读取占用和受托清理，业务拥有者负责资料及保留政策。设施不能接受任意表名并修改业务列。用户媒体、游戏内容目录和实际存档由 holdings 管理。解除绑定、删除资料、构建 clean 和缓存清理都不会隐式删除用户文件。物理删除必须是单独的明确操作，说明目标路径与效果，并核对解析后的实际归属范围。

## 图片输入与处理

不同图片输入按以下规则处理：

| 情况                                | 处理约定                                       |
| ----------------------------------- | ---------------------------------------------- |
| 未编辑的 JPEG、PNG、WebP、AVIF、GIF | 验证后保留实际输入字节                         |
| 静态图片的裁剪、旋转、翻转          | 生成新的 PNG 结果，保留透明度                  |
| SVG 输入                            | 在准备阶段明确转换为 PNG，以转换后的预览为准   |
| ICO 输入                            | 选择最大有效尺寸层并转换为保留透明度的 PNG     |
| 系统图标提取                        | 提取结果作为普通 PNG 输入                      |
| 动图原样采用                        | 保留动画；列表缩略图使用静态帧，完整查看时播放 |
| 动图编辑                            | 明确选择一帧生成静态图片，不静默丢弃动画       |

PreparedImage 在 PreparedAttachment 的只读字段上增加 width、height、format 和 frameCount。宽高为纠正原方向后的实际像素尺寸，format 只取 jpeg、png、webp、avif、gif，frameCount 表示实际可读帧数，静态图片为 1。SVG、ICO 转换后以 PNG 作为正式准备结果。

ICO 按实际可读内容选择最大有效尺寸层，同尺寸优先更高位深，以转换后的预览为准。容器内多个尺寸层不作为动画帧；来源声明的 0 宽高不代替实际解码结果。没有有效层、转换失败或超限时拒绝准备，不改写旧图片。

images.transform 接收 ReadResourceRef 及 { frameIndex?, flipHorizontal?, flipVertical?, rotationDegrees?, crop? }，返回新的 PreparedImage。动图必须明确指定非负、从零开始的 frameIndex；静态图片只允许 0 或省略。两个翻转参数默认 false。rotationDegrees 按顺时针计算，默认 0，必须是 [0,360) 内的有限数。crop 使用 { left, top, width, height }，坐标为整数，宽高为正数，范围不能越界。

处理顺序固定为纠正方向、翻转、旋转、裁剪。裁剪坐标依据前三步完成后的实际像素，界面显示缩放不进入处理参数。前端负责交互，sharp 负责实际处理，不向调用方开放任意编码器或透传参数。SVG 按受限输入处理，不作为活动文档加载，也不读取未经授权的外部依赖。

images 集中维护压缩输入字节数、累计解码像素数和并发量的有限预算，动画计入实际解码帧，不能只按首帧估算。单项超限时拒绝准备或处理，并说明实际限制；不自动缩小原图、删帧或改用缩略图。并发占满时使用可取消的有界等待，不能无限累积完整图片。阈值由具名的内部实现参数定义。验证按实际机制选择：正常输入完成处理，输入字节与解码像素预算核对拒绝边界，等待队列核对取消，已取得的资源核对释放；不为每个数值参数机械配置同一组用例。调优不能改变上述结果语义或放宽[性能验收](../../verification/acceptance.md#performance)。

图片候选通过共同的 FileInput 提供原图及可选缩略图。候选声明的尺寸只用于展示，技术信息以实际验证为准。用户确定候选后准备原图，后续编辑和提交复用这份字节，不再次下载可能已变化的内容。拖动裁剪框只修改草稿，处理失败或提交冲突时保留旧引用。单独采用图片，不会同时采用来源的其他资料或身份。

候选缩略只接受受支持的图片，不接入 WebM 或其他视频缩略。不可用的可选缩略不使有效原图失效；没有可用图片缩略时，可在当前可见范围内按需读取原图生成静态预览，沿用字节、解码、并发、缓存与取消约束。预览读取不建立正式附件，不预取全图库，也不把缩略图替代为最终采用的原图。

显示缩放和卡片裁切属于缓存，只有用户明确保存的处理结果才成为新附件。例如，主图和背景共用附件 A，裁剪主图得到 B 后，背景仍然引用 A。编辑结束后按真实引用回收内容，不建立长期图片历史或额外的原图保留关系。如果只采用新结果，系统不承诺恢复旧原图，但不会修改用户本地来源文件。

<a id="cache"></a>

## 派生缓存与验收

缩略图、转码预览和显示裁切的缓存键包含附件 id、完整规范化参数和算法版本。用户持有文件的预览还须依据文件身份及适用的源变化失效，不能永久按路径复用。显示尺寸收敛到少量规格，相同规格的并发请求共用生成过程，生成完成后才发布结果。缓存设置总容量上限，按最近使用情况淘汰；损坏项可重建，失败请求可重试，活动占用仍受保护。

缓存不进入正式引用或业务表，也不承担长期资料查询缓存。正式定位中不复制缓存修订号、文件基线或哈希。缓存清理只删除可重新生成的内容，不解除业务引用，也不删除正式附件。

生命周期验收覆盖保存前插图、取消、多窗口共用、正文重复图片、主图与正文共用、条目合并，以及准备失败、提交冲突和中断。还须验证物理删除失败、占用与清理竞态、正式字节缺失、锁定备份和恢复材料保护。图片交互、实际处理和六个平台制品都遵守相同的处理顺序与资源合同。
