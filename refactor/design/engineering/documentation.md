# 项目文档与协作入口

项目文档分别面向使用者、维护者和具体任务的执行者。每份文档负责说明一类问题；同一规则只保留一份完整定义，其他文档通过链接引用。

文档遵守[共同原则](conventions.md#quality)，读者能够按任务找到规则、理解适用条件，并沿引用继续到所需细节。相关主题采用同一规则和词汇，结构调整按完整阅读与维护路径判断。

<a id="owners"></a>

## 各类文档的职责

| 文档                                | 主要内容                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| README 及其语言版本                 | 产品定位、可用功能、下载与运行方式、简短的开发概览，以及协作指南、Issues 和 TG 反馈入口                |
| CONTRIBUTING.md                     | 维护者和受邀协作者共同遵守的环境准备、开发验证、PR、版本准备与发布流程                                 |
| 共用工程与编写规范                  | 当前实施共用的质量原则、设计判断与编写要求，见[规范归属](conventions.md#ownership)                     |
| CONVENTIONS.md                      | 正式项目的仓库级工程与编写规范，结合共用要求、语言生态和实际职责形成                                   |
| ARCHITECTURE.md                     | 模块职责、状态归属、运行边界和包之间的依赖关系                                                         |
| AGENTS.md                           | 每次任务都需要了解的产品范围、架构边界、数据与错误规则，以及具体规范的入口                             |
| GitHub Issue Forms 与配置           | Bug report、Feature request 的反馈字段、语言、提示、标签及联系入口，见[反馈规则](repository.md#issues) |
| `.agents/skills/<project>/SKILL.md` | 适用任务、资料选择与可复用的工作指引                                                                   |
| 模块或包的 README                   | 该模块或包的使用方式、协议、资源要求和限制                                                             |
| 公共 JSDoc                          | 调用者可观察的行为，包括单位、空值、生命周期、取消、失败和副作用                                       |
| 代码注释                            | 文件与模块概述、对象调用合同，以及实现意图、约束和不变量                                               |
| refactor/design                     | 产品、架构、领域、界面、扩展和工程的实现规格                                                           |
| refactor/implementation             | 工作包、实施依赖和实际进度                                                                             |
| refactor/verification               | 验收标准、要求覆盖情况和验证证据                                                                       |

规范描述正式职责、行为、接口和约束，必要时说明这些约束的理由。[简洁、清晰、干净与克制](conventions.md#quality)在协作入口、共用规范和设计入口中优先呈现，具体规则仍由所属主题维护。文档自身减少重复概念和间接导航，保留读者理解职责、前提和结果所需的说明。使用文档描述已经交付的能力；设计要求、实现状态和验证结果分别记录，不能相互代替。

通用文档，包括 README、CONTRIBUTING、CONVENTIONS、ARCHITECTURE、AGENTS、共用规范、skill 指引与设计正文，只描述当前有效的规则、能力、使用方法和必要依据。实施状态集中说明当前完成度、未闭合事项及证据入口；验证证据保存支持现行判断的来源、比较和结果。普通修改经过由 Git 历史与 PR 承载，必要的取舍理由在所属规则处直接说明。

源码概述、代码对象合同和配置说明的覆盖与格式由[注释规范](conventions.md#comments)定义。架构与项目文档维护跨模块关系、完整生命周期和使用指南，具体调用条件与局部实现约束就近写在代码中，各层不重复复制详细内容。

界面文字遵守[文案规范](../ui/components.md#copy)，代码对象的注释范围、位置、内容和维护要求遵守[注释规范](conventions.md#comments)。发行变化记录在提交、PR 和发行说明中。

<a id="writing"></a>

## 写作要求

先确定读者要理解什么、据此做什么，再选择内容。正文直接说明当前采用的职责、行为和结果。删去上下文已经表达的说明、重复强调，以及为排除假想误解而罗列的备选做法。

前提、差异或失败会改变含义、选择或操作结果时，在读者需要知道的位置说清条件和后果。读者需要理解某项取舍时保留理由，需要区分实际选择时保留对照。例如，[译本](../ui/localization.md#validation)缺键时回退英语，空字符串则作为译文原样显示。这个区别直接决定作者如何填写目录。

每段围绕一个重点展开，写清主体、动作和结果，句子之间保留必要的承接。主题或步骤转换时明确分段，简短而内聚的说明保持紧凑。文档及其代码示例遵守[编码风格与逻辑分段](conventions.md#logical-sections)，审阅同时核对章节、段落与示例中的职责关系。

文档的文件、目录与章节共同表达主题边界，拆分与合并同样按[主题组织规则](conventions.md#source-layout)判断。单篇文档使用明确标题；多篇共同维护的主题集中在目录内，README 承载该主题的实际入口内容，不在目录外另留同名总览或用同级前缀文件代替主题层级。文档与章节的标题说明它回答的问题或负责的对象，层级反映内容关系。同一任务所需的规则保持相邻，跨主题内容引用其拥有者。较长文档按实际查阅任务提供简短导航，使读者能先找到入口，再进入字段、操作和边界；导航深度随内容决定。

表格用于比较平行项和表达对应关系，列表用于并列要点或有顺序的操作。需要解释前提、步骤、完成与失败的完整操作使用小节和连贯段落，避免把整段流程挤进单元格。拆分依据主题转换，代码示例围绕明确任务，并就近交代理解示例所需的条件。

句子使用具体的对象和动作，避免口号和术语堆叠。保留清楚的主语、动词和逻辑关系。并列事项使用标点或列表，“和”“或”“分别”等关系明确写出；斜线用于路径及有确定含义的技术记法，缩写在读者能够理解时使用。

同一概念在各篇文档中使用同一名称。普通说明使用自然语言，类型、字段、函数和文件名称保留准确拼写。

<a id="pull-request-descriptions"></a>

### PR 描述

PR 描述简洁说明最终改动，面向未参与实现的审阅者，只补充影响审阅判断的信息。简单改动可以用一两句话；复杂改动按内容关系使用短段落或列表，不强制固定栏目、模板或篇幅。

问题与动机、方案取舍、验证结果、限制、风险和迁移信息按需要说明，不作为必填项。CI 已清楚展示的状态无需复述，需要详细证据时链接所属记录。描述不记录工作过程、讨论经过或中间提交清单，措辞直接、具体，避免口号和笼统保证。

<a id="specification"></a>

## 设计规格的维护

`refactor/` 按读者任务与内容职责组织。设计定义当前规则，工作包定义实施依赖与门槛，验收定义场景与预期结果，证据保存来源、比较和实际结果。status 维护工作包进度和当前未闭合事项；delivery-checklist 拥有逐项扩展和独立项目的交付结果，两者按[状态归属](../../implementation/delivery-checklist.md)引用，不重复维护同一项事实。

独立项目各自拥有公共合同和实现机制，Kisaki 文档只定义自身接入。一个主题需要多个文件时，以实际职责和查阅需要拆分；紧密相连的规则保持在同一主题中，不按讨论轮次扩张文件。总览给出入口与边界，不复制完整规则。

资料查询主题由 library/query 的 README 定义语义，contracts 固定可传递的字段和形状；资料写入主题由 library/write 的 README 及领域文档定义行为，contracts 限定比较单位与错误目录，graph 定义完整图输入。communication 定义调用完成与事件语义，engineering/protocols 定义通信帧和接入。它们分别负责语义、值形状和传输机制，不各自重新定义同一个事实。

验收文档引用规则，并给出能区分不同行为的输入、预期结果和证据要求；架构检查使用带来源的索引。相同原子性、取消、排序或资源规则在拥有层验证，来源和接入只增加自身差异。证据注明版本、环境、输入、实际结果与限制；结论和依据按现行合同维护，修改经过由 Git 与 PR 承载。当前进度由 status 维护，已经完成的事项从待办中移出。

修改规则时先修改所属设计，再同步必要验收和引用。移动或合并文档须核对本地路径、锚点与 R／W／A 关系，保留的试件和结果准确表达实际执行范围。

<a id="evidence"></a>

### 验证材料的取舍

保留仍用于设计选择、验收结论、复现当前问题或后续接入的材料，按主题维护简短结论与必要输入。日志、快照、候选试验和重复报告在失去这些用途后清理，历史提交与 PR 可以继续查阅。验证投入与材料保留都以当前问题为依据，日常修改无需另建逐轮记录或全仓清单。

工作包按现行合同和适用验证结果判断完成。历史偶发异常只有在仍影响当前行为、已知缺陷或验收结论时列为缺项；有价值的观察说明实际范围，不因尚未解释每次历史失败而推迟已满足条件的交付。

<a id="skill"></a>

## 按任务组织 skill 参考文档

项目 skill 按实际任务组织工作指引，引用所属项目的正式规范和当前实施资料。以下为 Kisaki 的主题组织示例，参考文件在有实际内容时建立；独立项目按自身的进程与窗口、阅读、媒体绑定或服务部署等职责组织。

```text
.agents/skills/kisaki/
├── SKILL.md
└── references/
    ├── data/
    │   ├── operations.md
    │   ├── ingest.md
    │   ├── holdings.md
    │   └── schema.md
    ├── ui/
    │   ├── composition.md
    │   └── state.md
    ├── extensions/
    │   ├── contracts.md
    │   └── lifecycle.md
    └── engineering/
        ├── packages.md
        ├── resources.md
        ├── testing.md
        └── releases.md
```

SKILL.md 统一提供任务到参考文档的导航，references 直接按实际任务主题收纳有内容的参考文档。目录按查阅与维护需要划分，导航集中在 SKILL.md。

执行具体任务时，只读取相关参考文档。例如，修改标签替换操作时，阅读 data/operations.md 及对应测试；调整统计页的详情弹窗时，阅读 ui/composition.md 和 ui/state.md；处理扩展更新时，阅读 extensions/lifecycle.md 和 engineering/packages.md；修改新库初始化时，阅读 data/schema.md 和 engineering/testing.md。

参考文档通过链接引用项目说明、适用规范、公共类型和既有工程入口。实施期间读取 refactor 的共用要求；项目文档交付后，CONTRIBUTING 说明开发与交付流程，CONVENTIONS 维护该项目的完整工程与编写规范。skill 补充资料选择、任务步骤和验证方法，工程工作流归 tools，测试专用辅助归 tests/support。

<a id="lifecycle"></a>

## 项目文档交付与维护

实施期间以 AGENTS.md 为任务入口，refactor 承载设计、共用规范、实施说明与验证依据。环境准备、当前源码职责和可运行命令见[当前工程与开发](../../implementation/development.md)。接口声明、schema、JSDoc、Rustdoc、代码注释、界面与 CLI 文案、测试及验证记录随所属实现维护。

[W23 项目文档与协作入口](../../implementation/work-packages.md#w23)集中形成 README 及其语言版本、CONTRIBUTING、CONVENTIONS、ARCHITECTURE、模块与包说明、官方扩展说明、模板使用指南、项目 skill 和 GitHub Issue Forms。范围包括 Kisaki monorepo 与四个独立项目，按各对象的实现与验收进度分批完成，在 W24 整体验收前就绪。文档落在所属项目，职责遵守[归属定义](#owners)。

各仓库的 CONVENTIONS.md 在这一环节结合共用要求、实际语言、运行环境和公开职责形成完整规范。正式文档依据已验证的实现组织阅读入口、公开合同、使用方法、可运行示例和维护命令；成篇说明采用后，refactor 中的对应实施说明完成归并，产品与技术规格继续由设计正文维护。

文档交付核对内容完整性、规则归属、实际命令、可运行示例、语言版本、skill 路由及引用，并同步 AGENTS 的入口。Issue Forms 及 config.yml 核对字段、语法、标签与反馈链接；CLAUDE.md 和 skill 别名引用同一份规范。[W24 整体验收](../../implementation/work-packages.md#w24)核对候选版本的文档、实现与制品，W25 核对正式仓库和公开渠道中的实际取得与使用。

实现与适用验收、项目文档、对外发布分别记录；本轮按[发布前与最终完成条件](../../verification/acceptance.md#pre-release-completion)接续整体验收和首次发行。交付后的项目文档随相关实现同步维护。发行说明、许可及对应源码材料随所属版本和制品准备，分别遵守[发行](releases.md)与[许可](licensing.md)规则。
