# 数据库约束、事务与迁移

数据库由主进程管理，使用 SQLite、Drizzle 1.x 和 better-sqlite3。schema 定义存储结构，纯值编码处理持久表示，数据库约束和业务事务保障资料完整性。文件字节的准备与清理由对应资源模块负责。

<a id="integrity"></a>

## 数据约束与查询

每张表明确声明主键、外键、可空字段的含义、唯一性和值域约束，以及删除和合并时的处理规则。业务读写连接启用外键检查，迁移须保留既有引用完整性。正式本地库使用 WAL，写入连接设置 synchronous=FULL；macOS 同时设置 fullfsync=ON，使 SQLite 在支持的系统上请求 F_FULLFSYNC。fullfsync 开启后覆盖 checkpoint 的同步，无需另外维护一份 checkpoint 开关。连接初始化回读实际配置，性能验证使用相同设置，不以降低耐久性取得通过结果。依据见[SQLite 同步选项](https://www.sqlite.org/pragma.html#pragma_fullfsync)。

资料根必须位于能够提供 SQLite 文件锁、WAL 共享内存和同步写入语义的本地文件系统。SMB、NFS 等网络文件系统及映射到这些位置的驱动器不属于资料根支持范围；这不限制媒体文件按自己的读取合同位于其他位置。[WAL 的文件系统条件](https://www.sqlite.org/wal.html)由 app/paths 在打开资料库前核对，不能因某次连接能打开就推定支持，也不自动切换日志模式或另建空库。

索引应支持类型筛选、名称自然排序、关系反查、外部身份查找、Part 排列、文件绑定、活动时间和任务状态查询。关键查询通过 EXPLAIN 和具有代表性的数据量验证。界面按完整查询取得所需结果，不为每一行分别发送 IPC 请求。

FTS 和其他辅助索引由数据库设施维护，并且可以从正式资料重建。搜索需要覆盖已声明支持的内容、别名和组织入口；辅助索引不成为第二份资料来源。

主进程以同步数据库调用执行短事务，事务中的工作限于本次查询、约束核对和写入。网络、文件准备与扩展调用在事务外完成。公共入口按完整业务操作组织，Drizzle 承担查询和存储映射。

SQLite 事务只保证数据库修改的原子性。涉及文件字节时，先准备资源，再在事务中提交引用，最后清理无用资源；失败恢复遵守 [附件规则](../domains/attachments.md) 和 [完整操作规则](../domains/library-operations.md)，不能承诺跨数据库和文件系统的整体回滚。

<a id="new-system"></a>

## 存储格式

本体数据库只接纳自身正式迁移链支持的结构。初始化和打开时先确认存储格式，完成必要迁移后再按当前结构使用。迁移范围包括这条链中的结构与数据演进，不包含其他存储格式的条目身份、资源布局、设置或扩展数据转换，也不提供跨格式双写和兼容视图。

存储实现必须支持正常事务、关闭后重开，以及运行中断、文件失联和附件处理失败后的恢复。游戏存档备份属于独立业务，按其备份与恢复合同执行。

<a id="initialization"></a>

## 初始化与版本迁移

schema 是数据库结构的定义来源。空库与已有本体数据库共用一条 SQL 迁移链：空库执行全部迁移，已有库只执行尚未应用的部分，不另生成一份仅供新库使用的最新建表 SQL。

database/initialize.ts 在本体业务装配前调用所选 better-sqlite3 适配器的原生 migrate()，遵循 [Drizzle 运行时迁移流程](https://orm.drizzle.team/docs/migrations)。迁移文件由 app/paths 定位，已执行记录与待执行判定由 Drizzle 管理。

onboarding_state 的固定初始行写入初始迁移，由 migrate() 执行插入，初值遵守[引导状态](../domains/onboarding.md#state)。preferences 在全部迁移完成后、首行不存在时执行一次普通插入，按当前版本的[偏好默认值](../domains/preferences.md#storage)保存完整配置。先迁移再插入，是为了让当前版本的写入代码使用当前数据库结构；初值来自当前默认定义，已有偏好不重新覆盖。

偏好默认值与 getDefaults 共用一份定义。静态配置组可以由 schema 引用该定义声明 SQL DEFAULT，随迁移更新，插入时交给数据库填充；需要平台或初始语言建议等应用上下文的值由应用提供。首行创建只准备数据库记录。仓库添加、扩展安装、资料方案、扫描配置和展示柜创建由相应业务及引导中的明确操作完成。

迁移在适配器支持的数据库事务中执行，失败时回滚并报告错误。初始化、迁移及必要结构检查全部完成后开放依赖业务；重开时读取迁移记录，只执行尚未应用的部分，既有资料继续保留。

开发和测试使用明确的新目录。已有资料保持原样，应用仅接纳本体迁移链支持的格式和结构；其他输入报告具体错误，由用户选择后续处理。

<a id="migration-files"></a>

## 迁移生成与交付

开发时使用 Drizzle Kit [generate](https://orm.drizzle.team/docs/drizzle-kit-generate) 根据 schema 变化生成 SQL 迁移和所需元数据，审阅后随源码提交。已经发布的 SQL 迁移保持不变，后续结构或数据调整追加迁移；应用运行时不生成迁移，也不使用 push 直接改写用户库。

结构差异由工具生成，业务数据变换由对应变更明确编写。需要修改 JSON 内部结构或补齐偏好字段时，使用 Drizzle 支持的自定义 SQL 迁移。新增字段采用该次迁移明确的初始值，保留已有用户选择，不把当前默认配置整组覆盖到旧记录，也不为偏好另设版本流程。

受版本控制的迁移目录是构建输入。迁移资源采用所选 Kit 的真实输出布局，包括每次迁移的 migration.sql、snapshot.json 及原生迁移器需要的元数据；资源打包保留实际相对结构并验证完整性。构建不重新生成或改写迁移。迁移产物、Drizzle 类型声明、Kit、better-sqlite3 和 Electron 使用经过验证的固定版本组合。

<a id="verification"></a>

## 持久性验证

从空库建立七类条目、关系、个人记录、文件绑定与失联状态、Note、备份和扩展设置等测试资料。验证外键、CHECK、唯一约束、codec、短事务和关键查询，并覆盖初始化失败、正常关闭重开和异常中断后的读取。通过隔离的迁移夹具验证同一迁移链的前向升级、已有数据与用户选择保留、迁移失败回滚，以及重开后不重复执行；正式新增迁移时使用相应历史结构的样本验证。

正式制品还要验证包内迁移资源与实际驱动可用，空库和已有本体数据库均能走同一原生迁移流程。开发和测试资料必须隔离；验收范围遵循本篇支持的存储格式与迁移链。

<a id="query-evidence"></a>

## 代表查询的设计验证

代表查询与事务的依据见[查询验证证据](../../verification/evidence/storage-contracts/2026-10-22/README.md)。动态条件在 SQL 内按候选 ID 集合组织并复用索引，list、total、locate 共用相同谓词。未分类与 JSON 日期查询按性能预算测量主线程成本，候选集合只服务本次查询。

ORM、Kit、驱动与 Electron 的组合依据见[版本组合验证](../../verification/evidence/public-contracts/2026-10-22/README.md)。正式验收使用完整 schema、codec 和发布资源，覆盖生成、迁移、重开、回滚、自定义列、关系与身份，并将动态规则、文件及活动统计和实际交互纳入性能矩阵。证据的版本与范围不扩张为其他组合的通过结论。
