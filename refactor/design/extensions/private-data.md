# 扩展私有存储与来源认证

来源扩展负责账号连接、授权和令牌刷新。本体提供与真实扩展身份绑定的私有存储、系统凭据保护、网络及外部打开能力。正式资料、普通设置、连接结果和正在进行的授权各有自己的归属，不能混为一份状态。

<a id="storage"></a>

## 私有值、凭据与原子提交

设置文档、同步游标及[导入批次](importers.md#repeat)的索引与分项进度等小型状态统一使用 storage.values，不按用途另建 KV。令牌、API key 和 Cookie 使用 storage.secrets。大型文件保存在扩展 data 目录，可重建索引和临时文件保存在 cache 目录。正式条目、关系、记录和附件仍通过本体 API 管理，扩展不能在私有存储中另建权威资料库。

| 表                | 主键               | 值与变更标记                                  |
| ----------------- | ------------------ | --------------------------------------------- |
| extension_storage | extension_id + key | value，合法 JSON；revision，变更标记          |
| extension_secrets | extension_id + key | encrypted_value，密文字节；revision，变更标记 |

extension_id 来自真实 ExtensionContext，调用者不能自行指定。私有命名空间不会因安装记录删除而级联消失。停用保留私有值和凭据；卸载默认只移除安装，只有明确选择删除私有资料时才一并清除。已写入本体的数据不随卸载删除，代码更新失败也不承诺回滚私有数据。

读取时，value 与 revision 来自同一次快照。写入不带 expectedRevision 时直接提交，最后一次提交生效；带有该条件时，只有当前键的变更标记相符才允许写入。缺少条件不会自动获得并发保护。修改会更新标记，删除后重建也不能复用旧标记。revision 表达完整键值的变更，不是格式版本、历史记录或全扩展锁。多键提交只核对相关条件，任一条件失败则整组不写入，不自动合并或重试。

storage.commit 在本扩展内一次提交普通值与凭据。扩展 Node 完成业务校验，宿主在事务外准备密文，再通过短事务核对条件并写入。调用方传递键值和比较条件，宿主持有 SQL 与事务执行。草稿冲突时保留用户输入；revision 按扩展私有键的合同管理。

Webview 默认只获得配置状态和变更标记。未提交新值表示保持原值，明确的新值表示替换，明确的移除操作表示删除。实际秘密只能通过 Node 的专用路径读取，不能根据键名是否包含 password 或 token 来猜测加解密方式。凭据“已配置”也不代表远端认证仍有效。

<a id="protection"></a>

## 系统保护与不可读状态

普通安装和便携运行统一使用 Electron safeStorage，通过当前系统环境保护凭据。加解密能力位于主进程，密文和 revision 由实际业务拥有者保存；extension_secrets 与代理凭据分别使用各自的存储列。safeStorage 的保护范围是交给它处理的秘密值，不管理数据行，也不加密整份数据库或附件。应用不保存主密钥或随行 key 文件。

[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) 使用 Windows DPAPI、macOS Keychain 和 Linux 实际可用的秘密后端。[DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) 通常与登录用户及计算机关联，但存在漫游例外，因此不能承诺同一登录用户下的其他程序无法读取。macOS 需要保持一致签名，Linux 需要核实真实后端。实现必须遵循冻结运行时公开的可用性、保护强度和必要重加密合同，不启用 setUsePlainTextEncryption、basic 或自建弱保护回退，也不能仅凭某个字符串判断缺席就推定底层已经降级。

移动数据目录不会改变保护策略，应用不会拆出并导出操作系统密钥。一致迁移必须包含数据库、所需持久文件，以及运行时要求的应用侧状态，不能只复制数据库。辅助系统保护状态也不是能脱离系统使用的随行密钥。在相同且有效的保护环境中，应用不主动清除凭据；跨机器、用户或保护条件后，凭据可能无法读取，但资料仍可使用。备份恢复不承诺恢复登录。

接口区分凭据不存在、系统保护暂不可用、密文不可读和远端授权失效。系统保护与密文读取失败使用[凭据错误分类](../domains/library-write-contracts.md#errors)，远端授权状态由来源解释。保护失败时保留密文，不将其报告为未配置或资料库损坏。暂不可用可以在条件恢复后重试，无须一律要求重新登录。仅存入内存不能报告持久保存成功，认证代理失败也不能暗中改为直连。只有用户明确重新授权或录入成功后，才替换原凭据。

令牌、Cookie、代理密码、密文、code、state、verifier 和私有值都不能进入普通 DTO 或日志。需要显式持久保存的来源 Cookie 写入 secrets；外部系统浏览器的会话不属于本体资料。加密不放入数据库 customType。必要重加密通过真实 API 和条件写入完成，不扩展为新的密码管理平台。

<a id="authorization"></a>

## 来源扩展负责授权流程

浏览器授权由扩展 Node 使用 loopback 和普通协议依赖完成，扩展拥有来源协议及本次授权会话。本体负责平台能力、实例释放和 secrets；ui.openExternal 受控打开 HTTP(S) 地址，授权结果由扩展的 loopback 入口接收。

扩展必须先成功监听本机回环地址，再打开浏览器。优先使用动态端口；来源要求精确登记时使用固定地址。监听失败应在打开浏览器前报告，不使用宿主全局端口池或 custom scheme 兜底。固定路径和端口无法区分前后两次操作，因此仍须核对发起者、state、有效期和当前实例。重复或迟到的回调不能完成或取消新的操作。

扩展负责 PKCE、来源响应解析、令牌交换、账号核验、凭据提交及后续刷新。直连与 relay 的差异体现在 URL 和交换流程中。S256 及明确的兼容例外按来源实现确定，不能在失败后自动降级。使用 API key、个人令牌或 client_credentials 的来源遵循实际凭据流程，不强制增加浏览器授权。

未完成的授权只保存在实例内存中，不跨应用重启恢复；已保存的值正常保留。私有存储只读取本扩展声明的数据格式，旧项目的凭据及私有数据不在接入范围内。来源协议和 relay 的权威文档分别属于各自项目，Kisaki 文档只定义自身消费边界。

| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| TMDB                     | 资料读取使用应用访问令牌；本人收藏、评分与列表操作使用独立的用户授权会话，经浏览器确认后取得并保护相应凭据                                                                                        |
| IGDB                     | 使用用户自己的 Twitch Client ID 与 Client Secret 取得应用令牌；不内嵌维护者的保密客户端 secret，不增加私人账号登录，见[接入设计](sources/igdb.md#settings)                                        |

| MangaDex                 | 使用用户自己的已获批个人客户端；client secret 与令牌保护保存，密码只用于主动登录的当次请求，后续刷新令牌；不共享客户端，不使用尚未开放的公共浏览器授权，见[专门方案](sources/mangadex.md#account) |

| itch.io                  | 使用已登记公共客户端的授权码流程、S256 和 loopback；读取权限、账号核验及共用令牌的断开含义见[账号合同](sources/itchio.md#account) |

MAL 的 plain PKCE 和 MangaDex 的个人客户端模式是明确的兼容范围。它们不构成运行失败后的降级路径，也不允许在后台保存密码并反复登录，不能宣称满足全部现代协议目标。匿名可读资料不强制要求连接账号。各来源实际支持的账号与记录能力见[平台目录](catalog.md)。

### TMDB：应用认证与本人授权

TMDB 的应用认证与本人账号授权分别处理。应用访问令牌不作为本扩展取得用户许可或完成本人连接的依据，其可读范围另按[凭据范围核验](../../verification/evidence/tmdb/account-api.md)处理。本人连接按 [v4 用户授权流程](https://developer.themoviedb.org/v4/docs/authentication-user)创建请求令牌、打开授权页面，再用已批准令牌取得用户 access token。随后通过[官方转换接口](https://developer.themoviedb.org/reference/authentication-create-session-from-v4-token)建立所需 v3 session，用户只登录一次。回调继续遵守本篇的 loopback、实例归属和取消规则；用户 access token 与 session_id 作为秘密保存。个人接入只采用[适用动画影片](sources/tmdb.md#account)，不因 v4 列表包含 TV 成员就扩大作品范围。

### Google Books：桌面客户端与账号身份

Google Books 的官方桌面 client 由项目登记，客户端类型、权限和回调采用官方 Desktop 应用合同，用户无须自行创建开发者应用。独立 relay 为其他消费者提供的 Google 能力遵守其自身合同。

Google Books 的 Desktop 客户端交换及刷新使用其桌面 client_secret 配置，同时启用 S256。桌面应用配置不能被当作能够保密的 Web 客户端秘密，用户令牌与自定义凭据仍独立保护。本人连接请求 books、openid、email 范围并验证 Google ID token，以 sub 识别账号、邮箱用于显示；不请求 profile，也不将 sub 当作 Books user ID。客户端配置和身份依据见[来源方案](sources/googlebooks.md#account)。

## 连接、换账号、刷新与断开

连接操作拥有独立的输入和提交。更换账号先完成验证与授权，再原子保存新连接配置和凭据；失败或取消保留原有连接。成功后停止旧连接的后续工作，清除其同步确认值，关闭自动导入和自动同步，由用户在新账号下重新启用。旧任务保持原账号归属，同账号的正常凭据刷新则保留原有选择。

整页设置草稿与连接操作分别保存。连接成功不采用其他导入或同步选项，取消设置页也不撤销已完成的连接。手填 API key 的保存与联网验证分开，格式合法的配置可以在网络不可用时保存。

授权由 Node 拥有，页面通过私有方法启动、观察或明确取消。关闭页面默认不终止授权，授权完成后也不重新打开页面；浏览器等待不能绑在页面 RPC 的生命周期上。默认等待时间为 10 分钟。重复点击显示现有操作，不再次打开浏览器。明确取消、超时、实例失效或应用退出会结束操作，此后的迟到回调不能提交凭据。

同一连接的并发刷新合并执行。提交前复核所用配置、凭据及操作是否仍有效；连接已删除或凭据已替换时，旧结果失去提交资格。

网络失败、限流与认证失效分别判断。需要重新授权时，由用户发起浏览器流程。来源校验和凭据提交均成功后才报告已连接，页面只取得所需账号摘要。

来源接入的[令牌采用细化](#adoption)进一步区分新授权与使用旧 refresh_token 的续期：正常刷新缺少新的 refresh_token 时仅保留本次快照中的原值，不跨账号拼接凭据；新授权按当前操作和配置条件提交，迟到刷新仍受原凭据 revision 约束。候选结果不能先成为页面上的“已连接”，也不能用再次发送上游请求补偿保存失败。

断开连接会取消相关授权、停止该连接的后续导入和同步，并清除本地用户凭据；普通设置和本体资料保留，旧请求不能再次提交结果。上游撤销是另一项明确操作，且只适用于来源真正支持的能力。本地断开不能报告为服务端授权已撤销。

<a id="relay-boundary"></a>

## 独立中转服务的接入

[oauth-relay.ximu.dev](https://oauth-relay.ximu.dev) 的服务规则、部署及配置由[独立项目](../projects/oauth-relay/README.md)拥有。Kisaki 不将扩展、Entry、Task、账号或 SDK 模型带入服务，最后一跳只使用 loopback。

各来源按 application/provider 登记自己的应用、回调和权限；客户端不保存上游保密应用的 client_secret。接入验证覆盖实际登记、域名、代理、授权、刷新及错误处理，秘密不进入核对材料。端点与令牌封装以公共协议为准，不读取旧服务格式。

<a id="relay-protocol"></a>

## 中转协议的消费

服务端点、一次性交换、两段 PKCE、错误及启动配置由 [oauth-relay 公共协议](../projects/oauth-relay/protocol.md)和[上游适配](../projects/oauth-relay/providers.md)完整定义。Kisaki 作为普通客户端消费这些合同，不复制服务的会话实现。

Bangumi／AniList 使用各自登记的 relay 接入；扩展先建立动态 loopback，再发起授权。客户端与 relay 之间强制 S256，上游遵循各自明确的绑定能力。账号识别、凭据保存、刷新与断开继续由本页的来源扩展合同负责。

<a id="consumer"></a>

## 普通客户端只消费公开协议

独立项目交付普通 Node 客户端示例与消费者测试；示例只调用公开 HTTP 端点，不导入 sessions、providers 等私有模块，不读取服务环境或上游秘密。服务测试可以装配受控 provider，客户端仍按相同协议生成 state／verifier、接收回调和提交 token。

客户端先成功建立指定回环地址上的监听，再打开浏览器；保存本次完整 redirect_uri、state、verifier 和操作身份。它只接纳当前操作、指定路径、有效期限内且 state 匹配的一次回调。错误或迟到的关联不能消费新的操作，重复有效回调也不触发第二次兑换。

回调接收器取得结果后立即给浏览器静态说明并结束监听，不让浏览器连接等待令牌交换或数据库提交。说明只表示回调已接收，不能提前显示“已连接”；页面不包含 code、state、令牌或外部资源。后续 token 兑换、本人校验及保存继续由客户端拥有者执行。

对于 Kisaki，该拥有者仍是来源扩展 Node，网络请求使用应用网络策略下的 HTTP 能力，宿主只提供外部打开、实例释放和私有存储等设施。关闭 Webview 不撤销操作；明确取消、超时或实例结束则使操作失效并关闭监听。relay 没有远程取消端点，其短期状态独立按合同回收。

<a id="adoption"></a>

## 采用令牌同时核对操作身份和持久值

Kisaki 的来源扩展在自己内部协调连接、同一连接的合并刷新和短时提交，不新增宿主账号服务。网络请求不占用数据库事务或提交锁；事务只对已经准备好的候选与相关 revision 作最终核对。

| 操作               | 结果可以采用的前提                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 新连接或换账号     | 当前授权操作仍有效，所用接入配置未被替换，新的来源身份已经核实；将本次完整候选与所需连接信息一并提交 |
| 同一连接刷新       | 使用原配置与凭据快照，只合并同一个未完成刷新；提交须匹配该快照对应的 revision 和当前操作身份         |
| 明确断开           | 先使相关操作失效，等待已提交给存储的短时操作收尾，再清除当前连接凭据；迟到网络结果不得提交           |
| 保存失败或条件冲突 | 不报告已连接或已续期；保留已有持久内容，不用重放上游请求补偿本地失败                                 |

两种检查各自有用：内存中的操作身份阻止已取消的工作继续采用，存储 revision 阻止已经换过的值被旧结果覆盖。连接请求所用配置与令牌组分别拥有自己的私有键；正常刷新不重写未改变的接入配置。普通导入／同步草稿不作为刷新输入，不能因为无关选项改变就把已经取得的刷新结果判成连接冲突。

新授权没有使用旧 refresh_token，不应把授权发起时的整份旧秘密快照作为所有后续步骤的业务前提。本人校验通过且操作仍有效后，在短时提交前读取需要替换的当前 revision；与实际用于本次请求的配置条件一并核对。这样同账号的正常刷新不会无理由使正在完成的新授权失败，另一项换账号、断开或配置替换仍会使旧操作失效。迟到刷新则继续以其最初使用的凭据 revision 提交，不能覆盖新授权。

正常刷新未返回 refresh_token 时，客户端可保留**本次刷新所用同一快照**中的 refresh_token；返回新值则和新 access_token 一起采用。relay 不补写这个字段。不同账号或不同接入的新授权不能继承旧连接的刷新令牌；新 access_token 缺少有效期也不能沿用上一个 access_token 的到期时间。[RFC 6749 的刷新规则](https://www.rfc-editor.org/rfc/rfc6749.html#section-6)

刷新响应成功但持久保存失败时，上游仍可能已经使旧刷新令牌失效。本地原密文予以保留，不承诺它仍有效，也不建立持久的交换结果领取库。需要重新授权时明确交给用户发起，后台不自行打开浏览器。

Kisaki 的换账号副作用、普通设置保留、同步选项和本地断开含义继续以[连接合同](#connection)为准。Google 撤销、本人资料查询及来源写入不会成为保存凭据的隐式副作用。
