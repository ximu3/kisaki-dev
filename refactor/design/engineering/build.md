# 构建、桌面制品与便携模式

桌面应用交付 Windows、macOS 和 Linux 的 x64、arm64 制品。各目标从固定输入完成资源准备、编译与打包，并按[运行覆盖规则](../../verification/acceptance.md#runtime-coverage)验证。发行使用通过适用检查的同一份文件。安装形式、资料位置、应用身份和更新方式按本页规则执行。

<a id="outputs"></a>

## 输入、输出与清理范围

| 类别         | 归属与示例                                                                    | 生命周期                                 |
| ------------ | ----------------------------------------------------------------------------- | ---------------------------------------- |
| 可审查输入   | 源码、公开入口、资源源稿、schema、构建配置、依赖锁文件、各项目 release-notes  | 进入版本控制；生成过不构成删除理由       |
| 程序构建输出 | 各包 dist、桌面 `out/<target>`、扩展自己的构建目录                            | 由对应任务拥有，按声明输出清理           |
| 最终交付文件 | 桌面 `dist/<target>`、npm tarball、.kisx、`artifacts/<commit>` 中的已核验文件 | 构建后记录来源与摘要，发布使用这些文件   |
| 工具缓存     | .turbo、下载归档、字体处理等 .cache 数据                                      | 可单独清理；已验证的发行文件另存独立副本 |
| 开发状态     | .local 中隔离的资料库、偏好、账号与开发会话                                   | 跨会话保留，重置是单独明确动作           |
| 测试状态     | 测试拥有的临时 profile、数据库和目录                                          | 资源关闭后由测试清理，不复用真实资料     |

不同目标的输出分别存放，开发输出另设位置。每个输出目录由对应任务拥有，单次任务内并行步骤使用不同输出。独立任务遵守[顺序执行约束](workspace.md#output-access)。各目标的运行布局如下：

开发会话的程序与公共包快照位于会话独占的开发目录，由会话关闭后清理。开发资料位于 .local，不属于构建输出。

```text
clients/desktop/app/out/<target>/
├── main/
├── extension-host/
├── preload/
├── renderer/
│   ├── main/
│   ├── reader/
│   ├── player/
│   └── game-panel/
└── resources/
    ├── icons/
    ├── fonts/
    ├── kana/
    ├── native/
    └── database/
```

图标由唯一源稿生成，数据库资源来自受版本控制的 Drizzle 迁移目录，SQL 与运行时所需元数据按[迁移交付规则](database.md#migration-files)保留结构并打包，构建不临时生成迁移。字体来自锁定依赖和处理配置，媒体运行库及其依赖来自已核验的 libmpv-node 制品。app/paths 统一提供实际路径。需要作为程序执行的资源必须外置或解包，不能假定它们可以直接在 asar 中执行。桌面 resources 不包含扩展安装包。

kana 按[发行资产清单](../projects/kana/distribution.md#integration-assets)保留版本身份及完整相对目录，复制真实包中的 worker、Wasm、样式、字体和数据，并核对摘要。app/paths 与窗口所属 session 的受控协议共同提供同源 assetsBaseUrl；JS／Wasm 的缺失请求不能回退成 HTML。正式包与应用使用同一份已验收资产，不从另一份全局缓存补齐文件。

build 生成程序，package 生成交付制品，publish 才写入外部平台。打包使用明确的 allowlist，确保 fixture、工具源码、开发地址、.local 和秘密不会进入制品。必需资源缺失时构建失败，不能补用旧输出。

clean 清理任务声明的输出；缓存清理、开发资料重置和发行制品留存各有独立入口。用户内容、全局 Git 配置和个人工具保持原样。发行文件另行保存稳定副本，签名与时间戳等处理按实际机制记录可复现范围。

clean 在相关构建、测试和开发任务停止后执行，删除所属项目声明的输出。

<a id="media-tools"></a>

## 媒体与原生资源

播放和媒体文件信息读取都通过 @ximu3/libmpv-node 的公开接口接入。读取流程由本体 infrastructure/media 组织，库保持命令、属性、hook 与原生资源寿命的职责；本体不交付独立 ffprobe，也不调用 ffmpeg 可执行程序。

libmpv、FFmpeg 及其匹配运行依赖由 libmpv-node 按固定版本、目标、来源、摘要和许可统一交付，Kisaki 消费已核验的包及其资源。文件信息读取的原生路线已作[隔离验证](../../verification/evidence/media-information/2026-10-24/results.json)；正式包、宿主接入和六目标运行仍按所属工作包验收。

本体资源准备校验实际消费的固定输入，按目标装配原生文件。准备成功后替换对应输出；失败保留此前完成的结果。字体、图标、私有原生模块和独立项目资源分别由其拥有者提供来源及许可材料。

<a id="native"></a>

## 本体私有原生制品

本体自维护能力按[私有原生规范](native.md)组织，native 工程拥有 Rust 实现、Node 入口、类型和加载规则。桌面构建调用 app/tools/native 的统一流程，生成当前目标的绑定与配套资源，再装配到 resources/native；实际输入、输出、声明核对和消费验证见[原生构建与交付](native.md#delivery)。

原生制品与本体构建身份对应，开发与不同目标输出互不覆盖。app/paths 解析部署路径，装配层通过原生工程的 Node 入口取得所需能力；正式制品按加载要求外置或解包，启动不现场编译。文件恢复消费其中的[不覆盖移动](native.md#files)，系统原语与错误语义由该能力合同定义。

<a id="pipeline"></a>

## 构建流程与发行条件

构建依次使用固定源码和锁文件，准备目标依赖与资源，编译程序，装配并检查完整性，完成打包与签名，再验证最终文件并留存供发行。本地与 CI 调用同一组任务，CI 只负责选择 runner、目标和权限。普通 build 不产生发布副作用。

工程任务保留自身必要的输入与输出校验；产品和制品行为由[测试任务](layout.md#test-tasks)验证。消费者任务接收已经打包的公共包，最终制品任务接收完成适用签名的实际交付文件。测试通过后留存并发布同一份文件，不以测试时重新构建的替代品作为交付证据。

依赖 Electron 或 V8 ABI 的模块必须匹配对应 Electron。Node-API 模块按所需等级和平台选择，并在真实 Electron 中加载；Node-API 兼容不能代替外部原生库兼容检查。开发、普通 Node 测试和 Electron 测试不互相覆盖不同 ABI 的二进制。

下表列出各范围涉及的验证边界。日常修改按[实际影响](../../verification/acceptance.md#verification-scope)选择检查并复用仍有效的证据；首次交付和正式发行取得各自要求的完整覆盖。

| 改动或发行范围                   | 对应的验证边界                                             |
| -------------------------------- | ---------------------------------------------------------- |
| 纯值或单个公开包                 | 对应测试、实际依赖者检查、exports/类型/样式及 tarball 消费 |
| UI、renderer 和跨进程合同        | 受影响包、真浏览器组件和相应 Electron 工作流               |
| 原生、资源、系统集成、打包或更新 | 全部受影响系统与架构的构建及真实目标验证                   |
| 单个官方扩展                     | 相关 SDK/合同消费、kisx 构建、.kisx 安装和兼容范围         |
| 应用正式发行                     | Windows、macOS、Linux × x64、arm64 的完整制品与更新资料    |

正式目标为 windows-x64、windows-arm64、macos-x64、macos-arm64、linux-x64 和 linux-arm64。每个目标都需要原生依赖、媒体纹理、系统集成、安装、更新和卸载的验证证据。交叉构建不能代替目标运行验证；runner 无法覆盖 GPU 或桌面交互时，使用对应真实环境验证。

任一必需 SQL、字体、原生模块、媒体资源或更新资料缺失，整个桌面发行都不能发布。公共包和扩展只等待自身实际依赖及支持范围完成验证。

最终 tarball、.kisx、签名后的安装包和更新元数据记录源码提交、目标、工具输入和文件摘要。发布使用留存的同一份文件，正式制品保留安全 fuses。相关跨平台检查在合并前完成，发行再验证最终 main 提交；签名和实时外部状态检查不使用任务缓存。

## 安装形式与更新

| 系统与形态     | 交付物                                                                                               | 资料模式             | 更新责任                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------- | -------------------- | ------------------------------------------------------------ |
| Windows 安装   | x64/arm64 各自的 NSIS 安装包，默认按当前用户安装                                                     | 普通                 | 应用检查、下载，沿共同退出流程交接 NSIS 更新                 |
| Windows 免安装 | x64/arm64 各自的文件夹式 ZIP                                                                         | 默认普通，可启用便携 | 应用检查、展示说明和下载入口；用户手动换版                   |
| macOS          | Intel/Apple Silicon 各自的 DMG 与供更新器使用的 ZIP，包含同架构同版本的完整 .app；签名按平台策略执行 | 默认普通，可启用便携 | 应用检查、下载并沿共同退出流程替换 .app                      |
| Linux DEB      | x64/arm64 各自的 DEB                                                                                 | 普通                 | 应用内下载、校验，经系统授权调用包管理器安装；须完成目标验证 |
| Linux RPM      | x64/arm64 各自的 RPM                                                                                 | 普通                 | 应用内下载、校验，经系统授权调用包管理器安装；须完成目标验证 |
| Linux 免安装   | x64/arm64 各自的 AppImage                                                                            | 默认普通，可启用便携 | 应用检查、下载并沿共同退出流程替换 AppImage 文件             |

基线使用 Electron 45.0.0、electron-builder 26.15.3 和 electron-updater 6.8.9，锁定组合按六目标验收。应用负责版本选择、四语说明、准备安装状态与完整退出；底层工具通过公开接口及其标准更新元数据完成下载、校验和安装。

各架构分别提供表中制品。Windows 每个架构交付单一 NSIS 安装包和文件夹式 ZIP；macOS 交付 DMG 与更新 ZIP；Linux 交付 DEB、RPM 和 AppImage。交付集合不包含 Universal、MSI、MSIX、web installer、portable.exe、TAR.GZ、Snap 或 Flatpak。

通过 GitHub Releases 直接分发的 DEB 和 RPM 支持应用内更新，经系统授权调用包管理器。日常应用进程保持普通用户权限，更新验证覆盖提权参数、依赖修复、包锁、用户取消、失败后的包状态和新版启动。发行版仓库或应用商店管理的安装由对应渠道更新，应用不运行竞争的安装流程。

macOS 的 DMG 用于首次取得 .app。更新 ZIP 包含同版本、同架构且已签名的完整 .app，由更新器下载、解压和采用。结构按 [Apple bundle](https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle) 与[更新器规则](https://www.electron.build/v26/docs/features/auto-update/)验证。

AppImage 是可移动的单文件，支持应用内更新。交付必须验证系统库、FUSE、runtime、权限和沙箱条件，并按 [AppImage 系统要求](https://docs.appimage.org/introduction/concepts.html)、[FUSE 说明](https://docs.appimage.org/user-guide/troubleshooting/fuse.html)与[启动兼容政策](#appimage-compatibility)处理。

官方 HTTPS 与摘要用于下载内容一致性检查，发布者身份另按对应签名机制判断。准备、校验和安装绑定同一版本、目标与摘要，底层工具原有校验保持。应用下载、macOS 代码身份及扩展 registry 签名各自承担明确职责，所用密钥独立。

<a id="appimage-compatibility"></a>

## AppImage 启动兼容性

AppImage 沿用锁定 electron-builder 所提供 AppRun 的条件兼容行为：系统允许创建用户命名空间时保留 Chromium 进程沙箱；上游检测到限制时允许通过 --no-sandbox 启动。此选择接受受限系统上的进程隔离下降，不承诺 AppImage 始终具有操作系统级 Chromium 沙箱。

appImage.executableArgs 设为空数组，生成的 .desktop 入口为 AppRun %U，不无条件附加 --no-sandbox。直接启动与桌面入口都由同一 AppRun 判断，不另写启动器、命名空间探测或应用内降级逻辑，也不要求用户先登记路径权限或修改全局系统策略。

承载窗口仍配置 sandbox、contextIsolation 和 webSecurity，关闭 Node 集成，并保留受控来源、CSP、最小 preload 桥接及现行 fuses；这些配置不能证明降级运行时仍有进程沙箱。该政策仅适用于 AppImage，不扩展到其他载体或源码运行。验收检查最终启动文件、允许与受限条件下的真实渲染进程状态，范围与依据见[采用验证](../../verification/evidence/appimage-policy/2026-10-26/adoption/README.md)。

<a id="portable-marker"></a>

## 普通模式与便携模式

应用默认使用普通模式。Windows ZIP、macOS .app 和 Linux AppImage 可以通过标记启用便携模式；NSIS、DEB 和 RPM 只使用系统用户资料目录，不在程序安装根目录保存资料。产品不提供第三种自定义目录模式、命令行路径覆盖或便携专用业务版本。

kisaki-portable.txt 是可为空的普通文件，仅以文件存在性标记下次启动模式。它位于 Windows 的 Kisaki.exe 同级、macOS 的 .app 外部同级，或原 AppImage 文件所在目录。启动只依据这个标记选择模式，文件内容保持不解析。

首次手动启用便携时，同时准备标记和固定名称的空目录或完整资料目录。界面中的明确操作可以帮助创建空目录，但启动不能把资料目录丢失解释为需要新建空库。

| 标记与资料情况                         | 启动行为                                 |
| -------------------------------------- | ---------------------------------------- |
| 无标记，无便携资料目录                 | 普通模式                                 |
| 无标记，便携资料目录仍在               | 普通模式，保留并不采用该便携资料         |
| 有有效标记，有完整便携资料             | 便携模式，读取该资料                     |
| 有有效标记，有明确准备的空目录         | 便携模式，进入新资料初始化               |
| 有有效标记，资料目录不存在             | 报告便携资料位置缺失，不补建、不回退     |
| 标记位置是无效对象，或模式依据无法核对 | 报告启动约定不可用，不把失败当作无标记   |
| 所选资料只读、无法读取或已知损坏       | 报告实际问题，不切到另一位置、不清空重建 |

手动修改标记前须完全退出应用。移除或改名标记会停用便携，但保留资料；恢复标记后可以再次读取。界面操作修改同一标记，本次运行的 dataRoot 不随之变化。

标记读取失败、权限不足或路径对象非法时报告错误；模式选定后，资料不可用也在该位置报告。标记缺席时进入普通模式，包括用户误删或漏带标记的情况。当前标记是模式选择的依据，移动或更新便携应用时一并保留程序、资料和标记。

<a id="paths"></a>

## 资料根与切换操作

普通模式使用系统标准的 Kisaki 用户资料目录。Windows ZIP 的便携资料放在可执行文件同级 data 目录，macOS .app 和 Linux AppImage 的便携资料放在程序旁的 kisaki-portable-data。名称固定，不含版本或架构。

Windows ZIP 使用平铺布局；macOS 资料位于 .app 之外，Linux 资料使用规定的持久路径，避开临时挂载目录。开发和测试使用隔离 profile，用户模式仍为普通与便携。

数据库、设置、附件、已安装扩展、扩展私有值与密文，以及必要的持久运行状态共同放在 dataRoot。日志、缓存和临时文件可以分别清理，唯一状态不能只保存在缓存中。

普通与便携资料根都遵守[本地文件系统条件](database.md#integrity)。app/paths 根据最终解析位置和实际卷／挂载信息核对，不能只检查路径字符串或盘符；确认是网络文件系统时停止在该根打开数据库，说明不支持并保留数据。位置或能力无法核实时明确报告，不通过初始化写入、切换日志模式或采用另一资料根试探。媒体目录与存档目标继续按各自操作的访问和文件系统条件检查，不因资料根限制而一并改写。

app/paths 在数据库、日志、浏览器 Session、扩展和监听启动前，根据可信发行形态及标记确定路径并检查占用。sessionData 必须在 ready 前通过 setPath 设置，见 [Electron 路径接口](https://www.electronjs.org/docs/latest/api/app#appsetpathname-path)。应用不修改全局 APPDATA 或 HOME，也不通过系统链接模拟模式；同一资料根不能被两个实例同时写入。

系统集成中的模式开关是立即执行并保存的原生操作，不属于 preferences 表单草稿。界面显示当前模式、当前路径和下次启动选择，是否待重启由两者差异推导，不另存 pending 字段。

切换前展示两个资料位置，由用户选择采用目标已有资料或新建空资料。空目标先准备目录，再写入模式标记；异常目录报告问题并保持原样。目录准备成功后才提交选择，标记写入失败时重读实际结果。模式由有效标记确定，全部操作使用当前系统权限；当前资料库由用户按下述流程另行转移。

标记修改成功后，本次运行仍使用原 dataRoot，关闭 Dialog 不撤销已经保存的选择。重启遵守 [完整退出流程](../ui/navigation.md#shutdown)；用户取消退出时保留选择和待重启状态，不显示为已经切换。改回当前模式会消除差异。下次启动读取所选位置，两处资料彼此独立，不自动同步。

延续同一资料库时，用户先完全退出相关实例及后台，再按说明转移完整资料根，包括数据库、附件、私有数据和必要状态。目标非空时保留两份并明确选择；损坏或未复制完整的资料按错误处理。应用的模式切换负责选择资料位置，资料搬移与合并由用户单独处理。

从安装版改用便携版时，用户另行取得可移动制品并手动处理。应用不复制自身程序、不卸载原安装，也不暗改系统登记；普通卸载同样不隐式销毁用户资料。

<a id="updates-and-portability"></a>

## 更新与便携资料保留

Windows ZIP 由用户手动换版，无论当前采用哪种资料模式。完全退出后，将新版解压到干净目录，再带入资料和有效标记，以保持程序文件与版本一致。发行 ZIP 仅包含程序，便携标记与 data 由用户选择产生。NSIS、DEB 和 RPM 按自身安装范围更新。

macOS 更新替换 .app，AppImage 更新替换原文件，外部资料和标记继续保留。electron-updater 6.8.9 的 AppImage 更新可能改变文件名，并且先删除旧文件再移动新文件，不能将其描述为原子替换或完整回滚。AppImage 替换失败后的恢复方式是重新取得并校验本次更新对应版本、同架构的正式制品，放回原程序目录，恢复执行权限后启动；原资料和标记继续使用，不能通过新建空库掩盖程序更新失败。使用文档提供该恢复步骤，验收分别覆盖资料保留与按步骤恢复启动。

各目标的 asset 名称包含系统、架构和格式，latest.yml 等汇总文件不得冲突。区分方式使用工具的官方 provider 和格式，不手写第二份清单。

macOS 不修改签名后的包内容，并验证首次路径随机化、只读位置、权限、移动与更新，依据 [Apple 代码签名说明](https://developer.apple.com/library/archive/technotes/tn2206/) 执行。正式便携使用不依赖删除 quarantine、关闭 Gatekeeper 或私有定位方法。AppImage 的普通与便携模式采用同一[启动兼容政策](#appimage-compatibility)。

免安装制品默认不主动登记自启动、协议或文件关联。用户明确启用时，界面说明登记属于当前机器；系统自然产生的记录与应用主动写入分别判断。便携模式不承诺零痕迹，也不承诺完整 PortableApps 格式。

凭据通过 safeStorage 使用系统保护，跨环境移动后可能需要重新登录。外部作品、扫描目录和启动配置中的绝对路径随盘符或挂载变化重新定位，附件继续使用逻辑引用。原生组件与当前系统、架构匹配；本地解密和远端有效性按[凭据保护](../extensions/private-data.md#protection)分别判断。

所有适用的正式载体都要验证手动和界面操作使用同一标记、目录缺失与写入失败、当前模式与下次选择、取消重启、两处资料独立、空目录与损坏资料的区别、更新保留资料及标记、完整手动转移，以及同环境和跨环境凭据行为。六目标均列入验证矩阵，实际执行范围按[运行覆盖与交付](../../verification/acceptance.md#runtime-coverage)记录。

Windows x64 和 arm64 的系统下限为 Windows 10 2004（build 19041）。WGC、独立线程帧池及系统光标开关的版本依据见[平台路线](../projects/vantage/backends.md#windows)。

两个原生架构按 2004 下限、常规 22H2 与 Windows 11 列出验证范围，分别记录实际执行结果。API、依赖和 ABI 的最低兼容性同步核对，交付按[运行覆盖规则](../../verification/acceptance.md#runtime-coverage)判定。实际冲突须修复，支持下限或架构的变更另行讨论。

操作系统是否仍被厂商维护与应用兼容性分别判断，应用不增加 ESU 或账号检查。Windows 11 x64 仿真和 Windows 10 ARM 的正式 x86 仿真能力差异影响外部游戏或工具，不代替 Kisaki 及其原生依赖的验证，见 [微软仿真说明](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)。

最低 ABI 根据 Electron、libmpv、Vantage、SQLite 及全部随包依赖的实际系统符号和 CPU 要求确定，发行版运行验证另行记录。macOS 部署目标、原生依赖以及 Windows 实际 API 分别核对，每个预编译依赖也须满足目标环境条件。

本次交付采用已规定的运行时与系统下限。依赖维护可以升级 Electron，但升级必须保持支持目标，并完成可用环境测试与对应兼容性核对；已知不兼容的组合不能纳入发行。结构化兼容信息用于发行、安装和更新筛选，不能向用户推送已知无法运行的版本；未实测范围在发行支持说明中明确列出。

| 目标          | 构建 runner 基线 |
| ------------- | ---------------- |
| windows-x64   | windows-2025     |
| windows-arm64 | windows-11-arm   |
| macos-x64     | macos-15-intel   |
| macos-arm64   | macos-15         |
| linux-x64     | ubuntu-22.04     |
| linux-arm64   | ubuntu-22.04-arm |

构建使用 [GitHub runner](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) 的明确标签，并记录实际镜像与工具版本。ARM 制品在原生 ARM 环境验证，macOS Intel 制品在原生 x64 环境验证；用户系统下限、普通权限和桌面交互另在对应环境检查。

Linux 分别验证 X11 和原生 Wayland，运行方式依据 [Electron 行为](https://www.electronjs.org/docs/latest/breaking-changes#removed-electron_ozone_platform_hint-environment-variable)。除应用启动外，还需核对前台识别、聚焦、快捷键、截图与纹理交接。

[独立原生库](../projects/vantage/api.md#surface)按 GNOME、KDE 和实际会话交付进程、窗口、控制与采集能力，所需桌面组件随该项目实现和验证。未知观察状态保持未知，计时沿既定规则处理。应用自身窗口和快捷键由宿主分别验证，不以全局切换 XWayland 代替原生 Wayland 支持。

权限、portal 后端或可靠观察能力不足时，所属操作报告不可用状态，并保留配置与已成立的会话事实。计时规则保持原义。支持环境中的必需能力按合同实现和验证，接入缺陷记录为未完成项；范围调整按产品决定处理。

日常 PR 按影响选择检查。原生依赖、运行时、系统集成、资源和打包变化需要扩大矩阵；首次接入和相关变化在适用目标环境完成验证，可以引用仍有效的已有证据。普通文案修改不要求重新手测所有平台。

CI 配置、制品接入与各阶段验收按[工作包](../../implementation/work-packages.md)安排。

每份结果记录项目提交、制品摘要、系统与架构、桌面及图形后端、权限前提、执行命令和断言范围。环境不具备所需条件时登记未实测及兼容性依据；用例失败时登记失败。两者均不计为运行通过，但前者可在满足统一交付边界后交付，后者须解决。日常修改只重跑实际受影响范围，不重复已成立且仍适用的整套证据。

<a id="signing"></a>

## 平台签名

| 平台                       | 发行策略                                                                                            | 验证要求                                                                                              |
| -------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Windows NSIS / ZIP         | 不配置代码签名凭据，不增加项目 Authenticode 自签名                                                  | 不虚构 publisherName；保留更新器默认检查和下载摘要，如实展示未签名状态；NSIS 应用内更新、ZIP 手动换版 |
| macOS .app / DMG / ZIP     | 使用项目长期持有的代码签名证书，由受限 CI 自动签署；mac.forceCodeSigning: true、mac.notarize: false | 签名身份缺失或失败即停止；保持 Squirrel 的连续代码身份检查，不回退为 ad-hoc 或未签名产物              |
| Linux DEB / RPM / AppImage | 不另建项目 GPG 包或软件源签名，使用直接分发与摘要校验                                               | 核对所采用安装器参数、授权、依赖变更和失败恢复；不把摘要描述为发布者认证                              |

Windows 构建不配置签名凭据或 publisherName。NSIS 保留更新器默认检查、下载摘要验证，以及图标和版本资源写入，不统一关闭 verifyUpdateCodeSignature。各平台签名要求由构建配置明确声明，必需签名失败时停止发行，接入依据 [代码签名接口](https://www.electron.build/v26/docs/features/code-signing/)。

Linux 采用直接分发，摘要和元数据提供内容一致性验证；该方式不提供发布者签名认证。macOS 使用稳定项目身份签名，不执行公证；签名配置缺失或执行失败时停止构建。

无凭据测试可以生成明确标识的测试制品，但不能作为正式发行。正式文件摘要与更新元数据在全部签名和字节处理完成后生成并核对。签名材料不进入源码、日志、制品或 fixture。macOS 的强制签名要求不改变 Windows 允许未签名发行的政策。

<a id="macos-signing"></a>

## macOS 签署身份与更新验证

macOS 使用项目长期持有的代码签名证书，由受限 CI 自动签署，不依赖个人 Apple Developer ID 或逐次手工签名。证书用于版本之间的代码身份校验，制品不进行 Apple 公证。配置使用 mac.forceCodeSigning: true 和 mac.notarize: false，签名失败即停止发行。

Squirrel.Mac 按原有 designated requirement 检查新版及嵌套代码，不能只比较签名显示名称或 bundle ID，依据 [Squirrel 校验实现](https://github.com/Squirrel/Squirrel.Mac/blob/8d808803bc89ec0e2aa1450474856dfee3b00c6b/Squirrel/SQRLCodeSignature.m) 和 [Apple 代码身份说明](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html) 验证。更新必须保持连续签署身份，ad-hoc 签名不能替代。

项目自签名保留 Gatekeeper 的未认证提示，公开分发的限制见 [Apple 指南](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html)。首开验收使用[系统允许的用户操作](https://support.apple.com/en-us/102445)，不要求导入根证书、改变全局信任、关闭 Gatekeeper 或删除 quarantine。签名损坏仍按失败处理，受管理 Mac 的可用性取决于其实际策略。

证书使用项目名称和真实证书类别。跨版本维护密钥、证书链与 requirement，配套备份、到期轮换和丢失恢复流程；身份连续性按实际签名验证。密钥丢失按恢复流程处理，验签保持启用。扩展 registry 使用独立密钥。

同架构 DMG 和更新 ZIP 使用同一份完成签名的 .app，普通与便携模式共用制品，资料和标记位于包外。签名覆盖 helper、原生模块、媒体动态库和最终内容。Hardened Runtime 与 entitlements 根据实际装载逐项确定；必要的库验证例外需要说明并测试，不能默认关闭全部加固。

发行前在未导入项目证书、未修改信任的独立 Mac 上，通过真实浏览器下载并完成首开，覆盖两种架构、系统下限和当前稳定系统。使用两个不同版本验证检查、下载、验签、退出、替换和重启，并确认篡改、其他身份或签名不完整的更新被拒绝。

同一验证还要覆盖普通与便携资料、标记、密文、原生依赖、权限、路径随机化和只读失败恢复。证书到期、轮换、密钥缺失时的明确失败，以及 CI 输出和发布字节一致性，也属于发行条件。仅在构建机器上成功不能放行。

## Linux 桌面身份与快捷键

X11 直接注册和 Wayland portal 分别验证，Electron 身份须对应实际 .desktop 文件。DEB 与 RPM 正常完成桌面集成；AppImage 需要登记时，由系统集成 Dialog 提供明确的可选操作并读取真实结果，便携模式不自动写入。

接入使用锁定 Electron 与桌面版本的公开能力，核对 portal 后端、权限、桌面登记和实例释放。快捷键注册结果只描述快捷键，游戏退出与前台变化按各自观察来源判断。安装前提与运行结果共同决定能力是否可用，依据 [Electron globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut) 和 [GNOME portal](https://github.com/GNOME/xdg-desktop-portal-gnome)验证。

<a id="library-backup"></a>

## 资料库冷备份与恢复

本地备份与恢复通过完整退出后的资料目录复制完成，游戏存档备份由独立业务提供。本节是覆盖安装与便携两种资料位置的完整使用流程。

1. 从系统集成界面确认本次实际 dataRoot，完全退出应用及其后台实例，等待正常收尾。仅关闭主窗口或暂停任务不满足复制条件。
2. 用文件工具复制整个 dataRoot 到独立目标，保留数据库及仍存在的配套文件、附件、字体、已安装扩展、扩展私有数据、批次进度和必要应用状态。复制目标位于原 dataRoot 之外；不只复制主 SQLite 文件，也不手动删去仍存在的 WAL 等文件。
3. 记录应用版本及复制时间，并通过复制工具核对完整性。备份本身不包含 holdings 指向的用户媒体和游戏安装；这些外部文件按用户自己的存储方式另行保留。
4. 恢复前同样完全退出。先保留当前 dataRoot 的完整副本，再把所选备份复制到当前载体规定的资料位置，不把新旧目录直接混合覆盖。便携标记按原规则单独保留；应用仍只读取已确定的数据根。
5. 使用能够读取该备份结构的应用版本打开恢复副本。新基线的正常前向迁移沿唯一迁移链执行；不支持的结构明确失败，原备份保持不变，不以初始化空库恢复启动。
6. 核对条目、完成记录、笔记与正文图片、标注、用户字体、扩展私有配置及未完成导入批次；外部目录变化后用明确重定位处理。必要内容不能读取时保留备份与原目录，停止覆盖并报告实际问题。

凭据继续受系统 safeStorage 保护。相同有效保护环境中可以保留，跨机器、用户或保护条件时可能需要重新连接；复制资料根不包含可脱离系统使用的密钥，也不承诺恢复账号登录。运行中断的 TaskRun 按既有规则处理，导入批次仍按自己的步骤状态判断，恢复不自动重放写入。

存档恢复工作区可能位于媒体或存档所在卷，整个 dataRoot 的复制不包含这些外部材料。冷备份前查看恢复索引：先完成待处理恢复，或把仍需保留的工作区另行完整复制并记录原路径。恢复资料根后材料不可用时如实显示，不自动重放或清除索引。

本流程不承诺合并两份资料库、恢复旧实现格式或逐项导出，也不生成新的备份文件格式。验收使用隔离的完整资料根，从已退出的源复制到干净目标，实际验证重开、附件与私有数据保留、外部路径失联、不支持版本拒绝，以及保留原副本后的恢复失败处理。
