# oauth-relay 验收

A22 和 A33 验证公开 HTTP、来源适配、客户端凭据交接和正式部署。共同交付条件见[独立项目联合交付](projects.md)，依据见[HTTP 与配置合同](../../design/projects/oauth-relay/protocol.md)、[来源适配](../../design/projects/oauth-relay/providers.md)及[部署](../../design/projects/oauth-relay/deployment.md)。

## 授权与来源能力

覆盖应用／来源隔离、登记、可信回调、state、S256、scope、重复参数及并发兑换。错误 verifier 不消耗有效会话；并发兑换只允许一次领取，已领取会话在成功、失败或结果未知后均不重新开放。

逐一执行三个 provider 实际支持的授权、刷新、revoke／token-status 及拒绝分支。保留各自编码、字段和绑定能力，无旧会话时刷新仍符合合同；不支持的能力明确拒绝，不发出猜测请求。客户端到 relay 的 S256 与上游绑定能力分别检查，Bangumi／AniList 的[来源证据](../evidence/oauth-relay-provider/providers.md)只证明其实际范围。

## HTTP 结果与客户端保存

限流、超时、断连、响应损坏、取消和服务停止均返回稳定错误分类，并结束实际 HTTP 资源。本机取消与上游撤销分别表达，未知结果不触发重放，也不因此清除客户端旧凭据。

普通消费者只使用公开 HTTP。新授权、同一连接的合并刷新、换账号、明确断开及迟到提交核对各自操作身份、配置和 revision。账号核实与原子保存完成后才报告连接，保存失败不重发上游请求，换账号不继承旧刷新令牌。

以受控上游验证 Node Fetch 和宿主网络接入：认证端点返回重定向时，目标端点没有收到凭据；解码后正文超限时停止读取；正文阶段取消实际结束该调用。未知结果与保存失败均不引起应用重新调用令牌操作。共用传输验证一个代表来源，各 provider 只补自己的编码和结果差异。

421 的协议接续记录在[运行时对照](../evidence/oauth-relay-integration/integration.md)，不以“底层只发送一次”作为验收门槛。正式 provider、凭据保存和客户端联合流程分别验证。

## 配置、镜像与停止

监听前校验配置和秘密环境引用；秘密不进入镜像或记录，不使用用户授权持久卷。正式双架构镜像、Compose 和健康检查核对容器内实际环境值、配置权限与真实客户端消费。

停止时验证 Node 接收信号、停止接纳、在途响应、活动响应结束后的空闲连接回收，以及进程期限与容器宽限的配合。已有[Compose 解析与 Node 收尾证据](../evidence/oauth-relay-delivery/delivery.md)保留环境范围，正式镜像中的 Linux 容器运行另行取得结果。

切换部署前用实际接入应用完成域名、上游回调、代理、完整授权和刷新验证。包、镜像发布及服务切换分别登记。
