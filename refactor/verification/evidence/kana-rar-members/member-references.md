# RAR 成员引用与内容身份验证

本轮接续[基础 Wasm 验证](../kana-rar/rar-wasm.md)，验证符号链接、硬链接与复制引用如何成为归档内可读取的资源。9 份归档中的 27 次成员请求，以及 27 项独立命名空间用例，已在真实 Chromium Worker 中通过；详细结果见 [browser-contract.json](browser-contract.json)。这仍是设计试件，未形成正式 Kana reader 或完整归档名称校验器。

## 引用与身份

引用成员保留自己的 memberPath，目标只决定从哪里取得字节。例如两个图片成员引用同一份内容，它们仍是两个源成员；其页序与持久位置不自动合并。已校验目标可以共享同一份缓存，不为每个别名复制解码结果。

符号链接相对自身所在目录解析，硬链接和文件复制引用从归档根解析。目录引用可以参与资源路径解析，不据此虚构额外的归档成员或递归扩充图片页序。引用链逐项处理；先处理目录引用再处理后续 `..`，不能先对整条字符串做简化而改变实际含义。

源名称保持大小写和 Unicode 组合形式。Unix 名称中的字面反斜杠与 Windows 引用的路径分隔符分别处理；百分号编码是名称自身的字符，不作为 URL 解码。绝对路径、逃出根目录、缺失或歧义目标、循环、类型矛盾和超过解析预算都有明确失败原因。所有查找只发生在本次归档索引内，不读取外部文件或请求引用中的 URL。

[members.mjs](members.mjs) 用索引持有这些规则；27 个独立用例包含根相对硬链接、复制引用、目录前缀、链接之后的父目录、Unicode／大小写差异、规范路径碰撞和链式越界。这些原因是试件内部分类，正式接入仍使用已确认的 ReadingFailure，不扩展公共错误合同。

## 原生桥接与真实样本

[RAR5 格式说明](https://www.rarlab.com/technote.htm)定义了五种重定向记录、目标名称和目录标记。RAR3／4 的 Unix 符号链接则把目标放在数据区，普通 `RAR_TEST` 不交付该内容；这一差异已与固定 UnRAR 7.23 源码核对。

[member-bridge.cpp](member-bridge.cpp) 把固定上游 DLL 实现编译到同一翻译单元，使用其真实 DataSet 类型，不复制私有结构布局。旧式链接的当前头部按数据读取，继续由原生路径执行解密与校验，结果只作为内部目标字符串，不创建任何操作系统链接。目标字节有 64 KiB 上限，并按 UTF-8 严格解码。新试件复用已核对的基础对象文件，单独输出 Wasm 与许可；没有改写上游文件或上一轮证据，见 [build-contract.json](build-contract.json)。

完整读取旧版 Unicode 样本时，发现默认 C locale 会错误转换其中一个不带独立 Unicode 名称字段的 UTF-8 文件名。Wasm 实例内固定 `C.UTF-8` 后，六个成员的对应名称与上游预期一致；日文链接目标也正确解析。此设置不改变宿主系统 locale，也不等于已经解决所有旧式非 UTF-8 档名。

| 样本                     | 已执行结果                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| RAR3／RAR5 Unix 符号链接 | 别名和实际成员均读出已知的 `data` 加换行；越界目标被拒绝                                                          |
| Windows 符号链接         | 相对文件链接、目录链接正常解析；越界链接和指向外部绝对路径的 junction 被拒绝                                      |
| 硬链接                   | 三个成员路径共享一个 2 KiB 目标，只解码一次，各自取得相同内容                                                     |
| 文件复制引用             | 同一目标的两个复制成员与原成员读取一致，只解码一次；样本由硬链接样本只修改重定向类型与头部 CRC 得到，压缩数据不变 |
| 链式越界归档             | 即使归档确实含有 `up/pwned.txt`，仍先解释指向 `..` 的 `up`，拒绝访问，不绕过父目录引用直接命中子项                |
| RAR3 日文成员            | 符号链接读出已知 `kanji`；重新打开后可读取此前受 locale 影响的完整文件名                                          |
| RAR5 补充平面字符        | emoji、圈字硬链接和数学字体符号链接保持各自身份，读出同一目标内容                                                 |

新增上游样本固定在 rarfile 提交 `60c8513276ea462c39822db487c10111b9039442`，保留 ISC 许可、原始期望文件及指纹；另复用三份已有 libarchive 样本。派生文件复制样本的修改步骤完整记录在 [prepare-fixtures.py](prepare-fixtures.py) 和 [fixture-input.json](fixture-input.json)，没有执行商业压缩器。

本轮缓存只服务这些小样本，明确限制总量为 64 KiB；最大实际占用为 2 KiB。原生解码完成前不加入缓存；别名读取不重新解码已验证目标，结束后清空缓存并关闭文件和 worker。该结果补充上一轮背压与 OPFS 证据，没有证明完整 reader 的缓存淘汰或大目标重读策略。

## 尚未通过的边界

[原始名称实验](../kana-formats/format-sources.md)另行验证名称修整前的字节、旧 Unicode 编码完整性及显式旧档名编码。本页的 27 次成员读取与 27 项命名空间检查只覆盖所列试件。

UnRAR 的部分名称处理面向文件系统提取，会修整某些非法名称。正式资源索引必须在这种修整之前核对源名称，拒绝非法或歧义身份，不能把修整结果当成原始 memberPath。本轮 `fullArchiveNameValidation` 保持 false；旧式非 UTF-8 名称的确定解释也还需继续验证。

其他未覆盖项包括大规模引用图、加密旧式链接样本、极长名称、引用与完整缓存预算的结合，以及完整归档浏览器矩阵和正式包消费。上述已验证规则属于现有归档授权范围和成员身份合同的具体落实，不缩减格式，也不改写已保存位置。

复现时先准备上一轮固定 SDK 与对象文件，再从仓库根目录运行：

```powershell
python -B refactor/verification/evidence/kana-rar-members/prepare-fixtures.py
python -B refactor/verification/evidence/kana-rar-members/build-probe.py
python -B refactor/verification/evidence/kana-rar-members/run-browser.py
```
