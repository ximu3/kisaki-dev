# 设计充分性与实施判断

设计以简洁、干净与克制为首要原则，明确完整职责与公开含义，实施据此形成可维护的代码。共同原则及编码、注释和审查规则，由根目录的 [CONVENTIONS.md](../../../CONVENTIONS.md#quality) 完整定义。

现行要求与方案同样接受[整体判断](../../../CONVENTIONS.md#judgment)：发现原则、正确性、质量或技术实践问题时，重新审视相关设计，说明取舍并由用户决定调整方向。

<a id="design-completion"></a>

## 设计充分性

设计明确对象身份、字段含义与默认值、完整操作、公开输入输出与错误、并发与原子边界、取消与资源寿命、主要交互及支持范围。影响这些含义的主要分支提供确定的规则和例子；已知缺口继续完成设计，不交由实施者临时补定。

容易产生歧义的规则使用精确类型、行为表或例子，确有技术风险时用小型探针验证。全量声明、导出目录、常规 CRUD 签名和组件参数随实现形成。设计定稿先核对机制与限制是否必要、复杂度是否相称，再核对依据、一致性、实施充分度及[内容组织](documentation.md#writing)。

独立项目各自拥有公共合同与实现机制，Kisaki 规格定义自身接入。官方扩展按来源确定页面、账号、导入对象、触发、同步方向及字段，说明请求、解析、映射与界面的职责；共同结构引用所属方案，来源差异单独说明。未确定的业务规则记录在[设计状态](../../implementation/status.md#design)。

## 实现自由与交付范围

整体方案、共同原则和影响范围明确后，函数与文件组织、索引、数据结构、具体 API 调用、同语义算法优化，以及已确定预算内的批量与并发调优，由实施者判断。规格给出约束与验收依据，不预写全部实现细节。

架构与实现从产品目标、公开合同、数据与资源归属及运行约束推导。旧项目的实现、规范和协作文件不作为默认模板；需要延续的用户行为以已确认要求为准，保留结构须有目标依据。重写范围见[项目范围](../../README.md#rewrite)。

改变模型、公开合同、主要行为、架构边界或交付范围时，按[实施讨论规则](../../implementation/work-packages.md#unexpected-issues)说明依据、选项与代价，讨论确定后同步相关设计与验收。既定合同内的实现、接入和验证问题由实施者完成。

验证在能够直接证明承诺的边界取得证据，各接入层验证新增风险并复用仍适用的结果。交付可以按完整职责单元接续，设计充分性、正式实现、运行验收和发布分别判断；工作包及当前完成度由[实施计划](../../implementation/work-packages.md)和[状态页](../../implementation/status.md)维护。
