# 数据库约束、事务与迁移

主进程管理资料根下的本体数据库 `kisaki.sqlite`，唯一运行驱动为 better-sqlite3。Drizzle 1.x 维护 schema、类型化查询、值映射与迁移。纯值编码负责持久表示，数据库约束与业务事务保障资料完整性。同一个写连接也可以执行参数化的原生 SQL。文件字节的准备与清理由对应资源模块负责。

<a id="integrity"></a>

## 数据约束与查询

每张表明确声明主键、外键、可空字段的含义、唯一性和值域约束，以及删除和合并时的处理规则。业务读写连接启用外键检查，迁移须保留既有引用完整性。

同作品的文件和分部绑定、漫画卷话收录及备份恢复引用使用包含作品身份的复合外键。会话活动、标注和备份用记录自身的作品 ID 与可空的对象 ID 组成复合外键，保证引用的对象属于该作品。对象 ID 另有单列外键，删除对象时仅将该列置空，记录仍保留所属作品和已保存的内容。业务写入仍负责校验本次操作的目的、内容和实际归属。

正式本地库使用 WAL，写入连接设置 synchronous=FULL；macOS 同时设置 fullfsync=ON，使 SQLite 在支持的系统上请求 F_FULLFSYNC。fullfsync 开启后覆盖 checkpoint 的同步，无需另外维护一份 checkpoint 开关。连接初始化回读实际配置，性能验证使用相同设置，不以降低耐久性取得通过结果。依据见[SQLite 同步选项](https://www.sqlite.org/pragma.html#pragma_fullfsync)。

Linux 通过实际挂载类型识别已知本地和共享文件系统，无法确认的类型保留为 unknown。资料根必须位于能够提供 SQLite 文件锁、WAL 共享内存和同步写入语义的本地文件系统。SMB、NFS 等网络文件系统及映射到这些位置的驱动器不属于资料根支持范围；这不限制媒体文件按自己的读取合同位于其他位置。[WAL 的文件系统条件](https://www.sqlite.org/wal.html)由 app/paths 在打开资料库前核对，不能因某次连接能打开就推定支持，也不自动切换日志模式或另建空库。

索引应支持类型筛选、资料库语言排序、关系反查、外部身份查找、Part 排列、文件绑定、活动时间和任务状态查询。关键查询通过 EXPLAIN 和具有代表性的数据量验证。界面按完整查询取得所需结果，不为每一行分别发送 IPC 请求。

名称索引使用私有原生模块登记的 SQLite collation，由 ICU4X 按软件实际生效的 locale 比较。打开既有库时先恢复建立索引所用的语言，以便完成迁移并读取偏好。i18n 确认生效语言后，主进程等待数据库执行线程采用该语言并提交索引，再开放对应的名称查询。索引的语言或实现修订变化时执行 `REINDEX kisaki_name`。索引可从名称原文重建；身份判等与[名称排序](../domains/library/query/README.md#name-order)各有其规则。正式表结构由迁移链建立，在迁移与制品验收中核对。

FTS 和其他辅助索引由数据库设施维护，并且可以从正式资料重建。搜索需要覆盖已声明支持的内容、别名和组织入口；辅助索引不成为第二份资料来源。

主进程创建专用数据库 worker。执行线程独占 SQLite 写连接，按请求顺序执行完整业务操作中的同步查询与短事务。短事务调用 better-sqlite3，在同一连接上使用 Drizzle 查询与值映射，只执行本次必要的读取、约束核对与写入。事务回调同步返回，提交后 worker 才交付结果。列表与计数共用读快照时采用短读事务，读后写需要先取得写资格时采用 `immediate`。网络、文件准备与扩展调用在事务外完成。

同一批内反复执行的固定语句只预编译一次，每项单独绑定参数。分页返回稳定的业务结果，活跃迭代器在所属操作内关闭。运行中的同步 SQL 不能响应该 worker 排队的取消消息。领域操作以约定的提交边界核对取消与保留结果。 [驱动接口](https://github.com/WiseLibs/better-sqlite3/blob/v13.2.0/docs/api.md)

SQLite 事务只保证数据库修改的原子性。涉及文件字节时，先准备资源，再在事务中提交引用，最后清理无用资源；失败恢复遵守 [附件规则](../domains/attachments.md) 和 [完整操作规则](../domains/library/write/README.md)，不能承诺跨数据库和文件系统的整体回滚。

<a id="new-system"></a>

## 存储格式

本体数据库只接纳自身正式迁移链支持的结构。初始化和打开时先确认存储格式，完成必要迁移后再按当前结构使用。迁移范围包括这条链中的结构与数据演进，不包含其他存储格式的条目身份、资源布局、设置或扩展数据转换，也不提供跨格式双写和兼容视图。

存储实现必须支持正常事务、关闭后重开，以及运行中断、文件失联和附件处理失败后的恢复。游戏存档备份属于独立业务，按其备份与恢复合同执行。

<a id="initialization"></a>

## 初始化与版本迁移

首次发行前以当前 schema 维护一份初始迁移及其快照，开发数据库用专用目录重新创建。首个正式格式发行后保留其迁移字节，后续受支持的变更追加到同一条链。详见[首次发行前的兼容范围](conventions.md#before-first-release)。

schema 是数据库结构的定义来源。空库与已有本体数据库共用一条 SQL 迁移链：空库执行全部迁移，已有库只执行尚未应用的部分，不另生成一份仅供新库使用的最新建表 SQL。

认领新库时，在同一个 SQLite 事务中确认库内没有用户定义的表、索引、视图或触发器，且 `application_id` 与 `user_version` 均为零，再写入 Kisaki 的 `application_id`。Drizzle 随后建立迁移记录表。

首个迁移中断后，带有本体标识的空库或仅有空迁移记录表的本体库可以重试。已迁移的本体库按名称和摘要核对历史。其他格式保留原文件并报告错误，包括只有通用空迁移记录表、没有本体标识的文件。

database/initialize.ts 在本体业务装配前调用所选 better-sqlite3 适配器的原生 migrate()，遵循 [Drizzle 运行时迁移流程](https://orm.drizzle.team/docs/migrations)。迁移文件由 app/paths 定位，已执行记录与待执行判定由 Drizzle 管理。

onboarding_state 的固定初始行写入初始迁移，由 migrate() 执行插入，初值遵守[引导状态](../domains/onboarding.md#state)。preferences 在全部迁移完成后、首行不存在时执行一次普通插入，按当前版本的[偏好默认值](../domains/preferences.md#storage)保存完整配置。先迁移再插入，是为了让当前版本的写入代码使用当前数据库结构；初值来自当前默认定义，已有偏好不重新覆盖。

偏好默认值与 getDefaults 共用一份定义。静态配置组可以由 schema 引用该定义声明 SQL DEFAULT，随迁移更新，插入时交给数据库填充；需要平台或初始语言建议等应用上下文的值由应用提供。首行创建只准备数据库记录。仓库添加、扩展安装、资料方案、扫描配置和展示柜创建由相应业务及引导中的明确操作完成。

迁移在适配器支持的数据库事务中执行，失败时回滚并报告错误。格式与迁移链确认、原生迁移和名称索引采用完成后开放依赖业务；重开时读取迁移记录，只执行尚未应用的部分，既有资料继续保留。

开发和测试使用明确的新目录。已有资料保持原样，应用仅接纳本体迁移链支持的格式和结构；其他输入报告具体错误，由用户选择后续处理。

<a id="migration-files"></a>

## 迁移生成与交付

开发时使用 Drizzle Kit [generate](https://orm.drizzle.team/docs/drizzle-kit-generate) 根据 schema 变化生成 SQL 迁移和所需元数据，审阅后随源码提交。已经发布的 SQL 迁移保持不变，后续结构或数据调整追加迁移；应用运行时不生成迁移，也不使用 push 直接改写用户库。

结构差异由工具生成，业务数据变换由对应变更明确编写。需要修改 JSON 内部结构或补齐偏好字段时，使用 Drizzle 支持的自定义 SQL 迁移。新增字段采用该次迁移明确的初始值，保留已有用户选择，不把当前默认配置整组覆盖到旧记录，也不为偏好另设版本流程。

受版本控制的迁移目录是构建输入。迁移资源采用所选 Kit 的真实输出布局，包括每次迁移的 migration.sql、snapshot.json 及原生迁移器需要的元数据；资源打包保留实际相对结构并验证完整性。构建不重新生成或改写迁移。迁移产物、Drizzle 类型声明、Kit、better-sqlite3 和 Electron 使用经过验证的固定版本组合。

<a id="verification"></a>

## 持久性验证

从空库建立七类条目、关系、个人记录、文件绑定与失联状态、Note、备份和扩展设置等测试资料。验证外键、CHECK、唯一约束、codec、短事务和关键查询，并覆盖初始化失败、正常关闭重开和异常中断后的读取。通过隔离的迁移夹具验证同一迁移链的前向升级、已有数据与用户选择保留、迁移失败回滚，以及重开后不重复执行；正式新增迁移时使用相应历史结构的样本验证。

正式制品还要验证包内迁移资源与实际驱动可用，空库和已有本体数据库均能走同一原生迁移流程。开发和测试资料必须隔离；验收范围遵循本篇支持的存储格式与迁移链。

<a id="query-evidence"></a>

## 代表查询的设计验证

代表查询与事务的依据见[查询验证证据](../../verification/evidence/storage-contracts/2026-10-22/README.md)。动态条件在 SQL 内按候选 ID 集合组织并复用索引，list、total、locate 共用相同谓词。未分类与 JSON 日期查询按性能预算测量主线程成本，候选集合只服务本次查询。

ORM、Kit、驱动与 Electron 的组合依据见[版本组合验证](../../verification/evidence/public-contracts/2026-10-22/README.md)。正式验收使用完整 schema、codec 和发布资源，覆盖生成、迁移、重开、回滚、自定义列、关系与身份，并将动态规则、文件及活动统计和实际交互纳入性能矩阵。证据的版本与范围不扩张为其他组合的通过结论。
