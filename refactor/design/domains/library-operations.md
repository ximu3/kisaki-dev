# 资料库完整操作与并发提交

library 将明确的用户意图落实为完整业务操作，负责确认目标、校验约束、准备资源、提交事务和发布实际变化。公开 API 按业务用途划分，内部复用写入规则。调用者不必拼接表操作，也不直接组织事务。

<a id="ownership"></a>

## 管理范围与模块组织

library 管理资料、关系参与、本地持有、个人记录、活动、Note、Annotation 和展示柜。资料获取策略、扫描配置、任务历史、应用偏好及扩展管理分别归各自领域。数据存放在同一个数据库中，不代表它们都由 library 管理。

| 命名空间    | library 内的实现归属   | 职责                                                                     |
| ----------- | ---------------------- | ------------------------------------------------------------------------ |
| entries     | entries                | 七类条目的资料与外部身份，以及适用的评价、收藏、作品当前状态和补记当前值 |
| parts       | parts                  | 五类真实分部及其内容组织、当前完成标记                                   |
| completions | records/completions    | 四类作品的逐次完成事实、日期和备注，以及记录本次完成的完整操作           |
| relations   | relations              | 条目资料图中的关系及人员、组织参与事实                                   |
| collections | organizers/collections | 合集定义、分组与成员管理                                                 |
| tags        | organizers/tags        | 标签定义及标签应用                                                       |
| notes       | records/notes          | 独立笔记及其条目关联                                                     |
| annotations | records/annotations    | 内容标注及其目标、正文和采用资源的完整管理                               |
| activities  | records/activities     | 已发生的使用活动及其独立历史管理                                         |
| holdings    | holdings               | 本地内容范围、文件对应、使用配置及游戏备份的完整管理                     |
| showcase    | showcase               | 展示区块配置、排列、固定预设目录及保存查询的引用维护                     |

公共 API 按可调用的业务能力组织，不设置 library.records 或 library.organizers。entries 和 parts 提供当前个人值，completions 管理作品完成历史，holdings.files 管理文件位置，activities 管理实际使用历史，sessions 管理运行。接口归属不会改变相应表或数据寿命。relations 只管理资料图中的四类事实；标签、合集、笔记和文件关联由各自的完整操作维护。

Note 具有独立身份、正文、附件和零到多个条目关联，由 library.notes 管理。条目删除或合并时，library 完整协调笔记关联。Entry 创建的最低完整性是同 ID 的基础行与类型行；文件、评分、关系和分部按实际需要另行保存。文件失联后保留身份，解绑后保留活动与游戏备份。

内部根层按 entries、parts、relations、organizers、records、holdings 和 showcase 这些职责区域组织，各区域内再划分具体能力，保持同级相近的职责粒度。organizers 包含 collections 与 tags，holdings 包含游戏配置和备份。分类目录可以包含规则与生命周期不同的子模块，公共 API 则按完整调用能力组织。

每项公开能力有唯一的实现拥有者，按上表及[公开操作目录](#api)建立直接对应。records 和 organizers 承担内部分类，媒介分支与 query、validation、write 按实现职责拆分。API 装配直接连接相应能力，公开路径按业务含义确定；内部分类调整与公开边界变更分别判断。

资料图提交、合并、删除和领域检索分别由 write-graph.ts、merge.ts、delete.ts、search.ts 组织。它们承担跨区域的完整操作或读取，复用区域内部规则；子模块不反向调用这些协调操作来补齐不变量。目录分组不改变事务、资源与提交后通知的责任。

查询可以连接相关表，由结果所属模块提供，不按私有目录拆成大量调用。领域内跨对象检索可以是 library 根部方法，无须扩张 Entry 定义或增加空的 search.execute 层。应用级 [search](search.md) 另行协调全应用入口。EntryDetails 只是有界详情投影，不装入全部历史，也不能作为可变对象原样写回。

<a id="completion"></a>

## 完成条件、结果与失败

每个接口必须声明自己的完成条件、正常分支、失败方式、合法部分结果及责任归属。返回值直接使用适合该操作的资料、引用、报告、标量、void 或资源句柄，类型名表达具体含义。耗时长短、所在进程和内部调用次数都不改变这些语义。

组合业务按自己的范围交付结果。例如，ingest 返回资料采用结果，scanner 返回发现及候选处理报告。IPC、SDK 和 tasks.run 直接传递被调用业务的结果。会话或视图打开时，要等实例可用才算完成；普通完整操作等待业务结果，任务管理入口则按自身合同返回执行身份。

已存在、未变化、正常未命中、规则跳过，以及合同允许的逐项问题，都由业务正常分支表达。无法满足本次承诺时使用 [ExecutionFailure](../communication.md)。失败常见或可预期，并不自动使其变成正常结果；任意异常也不能塞进 issues 后宣告完成。

partialResult 必须是该操作自身结果类型中的合法已知事实，不能使用 `Partial<Result>`，也不能拿下层结果冒充整份报告。没有合法部分结果时就省略。调用返回、实时观察、历史和事实事件使用同一批真实事实，但可以各取所需内容，不必共享相同外壳。例如，tasks.wait 正常返回一条 failed 记录，并不表示等待调用失败。

操作结果不成为新的持久实体，历史表也无须照存整份调用返回。UI Toast 不进入领域结果。资料提交、运行采用和通知分别由各自能力负责：偏好 update 表示保存完成，主题或网络等能力另报采用结果；会话 close 则包含必要记录提交和资源收尾。必须与本次业务共同成功的数据，不能依靠变更订阅事后补写。

<a id="inputs"></a>

## 创建、编辑与关联写入

创建、更新和独立动作分别使用 create、update 及对应动作名，不让 save 根据是否有 id 猜测行为。创建输入直接包含条目 type 和字段，不再包裹 entry.fields。evaluation 表示适用评价，record 表示该主体对应的当前个人值，completionRecords 表示明确的初始作品完成记录，tags 和 collections 表示初始关联。非 Work 不能带作品状态或完成记录，缺少个人值时不创建空行。

```ts
await library.entries.create({
  type: 'game',
  name: '星屿',
  evaluation: { rating: 85, favorite: true },
  record: { status: 'planned' },
  tags: [{ tagId }],
  collections: [{ collectionId }]
})

await library.entries.update(gameRef, {
  changes: {
    name: '星屿 完整版',
    evaluation: { favorite: true },
    record: { status: 'active' },
    tags: {
      type: 'modify',
      add: [{ tagId, note: null, isSpoiler: false }],
      remove: [oldTagId]
    }
  },
  expected: {
    name: '星屿',
    evaluation: { favorite: false },
    record: { status: 'planned' }
  }
})
```

changes 只包含实际修改。普通字段、关系 binding、完整集合与排列的[允许基线和输入](library-write-contracts.md#expected)按实际操作限定。字段缺席表示保持原值，null 只用于清除允许为空的值。expected 表示本次决定依赖的业务基线，与取消等执行上下文分别传递。

各写入输入独立定义，不能从 EntryDetails 或 `Partial<EntryDetails>` 推导，也不能接收派生值。技术 ID、维护时间、运行状态、汇总和读取地址由所属模块生成。Entry 类型、Part 类型，以及分部和文件的所属作品不属于普通字段 patch。动画内容的[种类更正](anime.md#kind-correction)使用 changeKind；分部归属仅随作品合并迁移。

值集合与关系集合各自表达意图。例如 aliases: [] 会清空别名；标签关系则明确使用 add、remove 或 replace。增加和移除可以组合，replace 不能与它们混用。替换必须覆盖完整的指定范围，不能拿当前筛选片段代替全集，并须保留未修改的关联属性和另一侧顺序。

note_entry_links 的 order_in_note 与 order_in_entry，以及其他 order_in_*，分别属于实际列表。修改一侧顺序不能覆盖另一侧。当前状态设置、记录本次完成、历史补录和分部标记使用[各自完整操作](records.md#operations)，普通 patch 不接受完成次数或派生完成状态，也不追加历史。

文件位置和活动只接受真实上下文。外部累计使用时长通过附加时长的绝对值采用。图片与本地文件遵守[附件](attachments.md)和[持有](holdings.md)合同；URL、临时读取引用及解析对象都不能存为正式外键。

## 活动补录、修正与删除

library.activities 管理四类作品的活动明细，允许用户补录已知的使用时间段、修正已有记录或删除错误记录。手动记录、自动计时和真实明细导入使用各媒介已有的活动表，不另建补录历史或运行会话。

手动新增填写所属 WorkRef、startedAt、endedAt 和 durationMs。起止时间使用 UTC 毫秒，结束晚于开始，且不晚于提交时的当前时间；有效时长使用非负毫秒值，不能大于该时间段的长度。编辑器默认采用起止差值，用户可以按实际使用修正时长。只有累计量而没有明确时间段时，不据此生成活动；四类作品使用 additional_duration_ms 保存附加时长。

自动记录的 UTC 起止由 sessions 按[单调时钟映射](sessions.md#clock)形成。系统校时可以使已经保存的区间暂时处于当前系统时间之后，读取和后续统计保留原事实；本条手动提交限制不用于回溯修补既有活动。

补录不要求本地文件或启动配置，也不创建占位记录。明确提供的分部、文件或配置引用须符合该媒介已有的归属合同，未知时留空；不能根据当前首选、文件名或打开入口补造发生时上下文。

手动 update 只修改起止时间与有效时长，使用相同值约束，并保留原活动 ID、所属作品及既有上下文。changes 与 expected 遵守相关字段基线；删除只移除明确选中的活动。当前仍由会话计时更新的活动，须等该区间结束后再编辑或删除；其他已结束活动正常可改，不因此锁定整部作品的历史。

新增、修改和删除后，活动列表与统计读取保存后的事实；累计时长和最近使用随之更新，不另设可独立编辑的统计总数。跨日分配、重叠时长与记录数遵守[活动统计口径](library-queries.md#activity-statistics)。附加时长与活动分别保存，修改活动不自动反算补记；没有日期的补记不进入按日、周、月统计或热力图。这些操作不改变作品状态、完成标记、完成次数、文件位置或当前会话的累计值，也不触发自动已看或一次虚假的使用开始。

作品详情的活动区提供补录、编辑和删除入口，复用同一活动编辑器与本体操作。补录以当前作品为目标；已有记录保留上下文展示，只编辑时间与有效时长。保存与失败反馈沿用普通表单规则。原生界面与 SDK 使用同一合同，实际变更提交后通过既有 activityCreated、activityUpdated、activityDeleted 事件刷新相关查询。

## 资料图的原子提交

library.writeGraph 接收完成本地对应后的创建、更新和关系意图。metadata 取得并整合来源，ingest 决定创建、复用及更新范围，library 保证本地提交完整。Graph 组织本次请求，其寿命随调用结束。

完整区域、动作、临时引用与结果见[图写入值](library-graph-contracts.md)。下例演示合同组合，Part 的业务资料放在 data 中，与外层对象种类分开。

```ts
const result = await library.writeGraph({
  entries: {
    create: [{ key: 'work', type: 'anime', name: '星屿' }],
    update: [
      {
        ref: personRef,
        changes: { name: '新名称' },
        expected: { name: '旧名称' }
      }
    ]
  },
  parts: {
    create: [
      {
        key: 'episode1',
        type: 'animeEpisode',
        work: { key: 'work' },
        data: { numberLabel: '1', name: '第一集' }
      }
    ]
  },
  relations: {
    personWorks: {
      add: [
        {
          work: { key: 'work' },
          person: personRef,
          character: null,
          role: staffRole
        }
      ]
    }
  }
})

const workRef = result.entries.work
const episodeRef = result.parts.episode1
```

已有对象使用真实引用。仅引用对象不会修改其普通资料，只有显式 update/changes 才授予对应更新范围。新对象使用请求内唯一 key，其他节点通过 { key } 连接待创建对象；成功后返回 key 到正式引用的映射。key 不持久化，调用者不能据此伪造 ID，也不需要泛化的 LibraryObject。

图请求复用具体 create、update、expected 和关系合同，只在寻址上增加请求内引用。外部身份可以保存并校验冲突，但 writeGraph 不重新执行模糊匹配或自动合并，也不把创建静默改为复用。输入不包含 provider、profile、matching 或采用策略。changed 只表示实际变化，不扩大任何更新资格。

图请求可以明确创建或更新七类 Entry、五类 Part 和本次必要标签，并处理资料关系、内容组织关系、标签应用，以及创建时的个人值、完成记录和初始关联。已有作品的完成历史使用 completions 的完整操作，不通过图更新替换数组。扫描新增所必需且已经确定的本地目录、文件或配置登记，随作品原子提交，不能先建作品，再由 scanner 补登记。目录使用具体媒介的创建合同；游戏仅有目录输入时创建 GameDirectory，不为保存路径补造配置。发现、匹配和后续刷新仍由 holdings 承担。

实体删除、合并、Part 种类更正、启动和备份恢复不属于图请求。删除关系不删除端点，来源缺少 Part 也不授予删除权限。公共合同不接收任意 method/args 脚本、通用 batch 或事务回调。

执行先校验引用、种类、字段和关系，在事务外准备图片等资源，再通过短同步事务重查目标、相关基线与约束，一次提交全部选定事实。提交后发布通知并返回引用。失败不能留下部分图。

ingest 可以在提交前排除无法采用的分支及其依赖，并说明问题。剩余图一旦确定，就整体提交，library 不能逐节点跳过失败。普通编辑、短批量和图写入复用内部规则，长扫描或导入则仍按完整作品逐项提交。

<a id="transactions"></a>

## 内部写入与批量边界

公开完整操作负责接纳请求、确认前提、控制事务、返回结果和发布提交后通知。事务内函数在传入的同一事务中执行对象规则和写入，不自行提交、通知或启动后台工作。

创建条目时，基础行、类型行、标签与合集关联及初始个人值共同成功或失败。独立创建、导入和合并都复用这些内部规则，不靠串行调用公开 CRUD 模拟原子性。跨模块的本体组合由一个明确业务入口拥有事务，依赖方仅取得拥有者显式提供的有限同步写入能力；不取得任意 SQL 回调，不导入私有写入文件。准备、写入与提交后通知使用原领域规则，适用范围按[引导原子采用](onboarding.md#composition)列明。

加标签、收藏、设置状态、分部标记和批量记录完成等短纯数据库操作，一次整体提交。必要目标失效时整批失败，不能静默部分成功。包含远端获取、文件探测或备份的长流程，以可以独立成立的完整业务项提交；失败或取消时保留已完成项，不能把网络和文件 I/O 包进长事务。遇错政策由操作合同规定，不由 UI 临时选择。

准备与提交遵守[接纳与执行边界](../communication.md#admission)。准备过程绑定本次目标及判断真正依赖的依据。最终事务按操作规则读取当前字段、关系和从属资料，核对身份、引用与使用占用；无关封面变化不阻止记录编辑。修改既有目标时，目标在准备后被删除须按合同失败，不能根据输入快照重新创建它或改为修改其他目标。合并采用固定取值规则，删除处理目标当前拥有的完整范围，不为这些内部核对增加预览或逐项确认。条件检查与写入之间不能 await，资产准备后还须重查必要事实。

<a id="concurrency"></a>

## 相关基线与条件提交

expected 携带本次决定依赖的原值，用于相关基线比较。表单基于已读内容编辑时提交相应基线；即时设置、成员增减和相对移动按当前事实表达意图。异步准备的拥有者捕获并复核可能失效的依据。纯读取、运行控制和登记按各自身份与状态校验。expected 只承担比较语义，权限、并发处理和执行结果分别遵守所属合同。

操作输入限定本次写入范围，expected 限定本次提交依赖且合同允许比较的事实，二者不要求字段一一对应。普通编辑核对所修改字段或紧密关联的完整值组；操作明确依赖的相关上下文也可以成为基线。例如，完成记录新增允许比较该作品的只读 completionCount，不因此开放计数写入。每个接口按[闭合目录](library-write-contracts.md#expected)定义允许的基线，范围必须与其目标和职责相符，不接受任意库对象字段、查询表达式或从详情投影复制的整份条件。

目标存在性、种类、归属、引用、唯一性和使用占用等业务约束始终由操作拥有者核对，不要求调用方将它们逐项列为 expected。提供基线不授予额外修改范围，省略基线也不跳过这些约束。

修改单位可以是独立字段、紧密关联的字段组、完整正文、完整 definition 或明确的关系范围。扩展私有 KV 按键的完整值及 expectedRevision 提交，本体字段按实际业务值比较。updated_at 不充当版本标记。接口不提供字符级合并或任意 JSON 路径合并。

| 操作                                        | 条件来源与范围                                                                                                                   |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 资料、关系、Note、Annotation 及普通设置表单 | 使用开始编辑的真实值，按实际编辑单位和必要上下文核对；保存成功以实际提交结果建立新基线，并保留提交后继续输入的内容               |
| metadata.profiles、scanner.configs 编辑     | 名称等独立字段各自核对，definition 整体核对；已有执行保留其采用快照，不因配置保存而重写本次运行                                  |
| 扩展私有配置及凭据                          | 条件写入使用同次读取取得的键值 revision；字段级整理归扩展自己的业务，宿主只保证该键或已声明多键提交的条件与原子性                |
| 表单中的完整成员集合或顺序替换              | 使用完整编辑范围的基线，不能拿部分加载或筛选结果当全集；参与比较的成员、属性和顺序按具体操作声明                                 |
| 依赖空历史的完成记录新增                    | 仅使用[新增记录合同](records.md#creation-baseline)允许的目标作品数量基线；比较发生在本次记录写入前，不成为所有新增操作的默认条件 |
| 即时设置、增加或移除成员、立即相对移动      | 在当前事实上执行明确意图，核对目标和范围，不机械附加整份旧对象或旧列表；表单内同类改动仍随其实际保存单位提交                     |
| 合并与删除                                  | 固定明确目标，在事务中按当前事实应用完整规则并核对使用占用；目标失效或约束不满足时正常失败，不由旧请求复活或转投其他身份         |
| 资料获取、文件探测或其他异步准备后提交      | 由操作拥有者捕获必要依据，并在最终提交时核对；可按当前事实重新求值的规则在提交时求值，不因存在异步过程就比较整份旧快照           |
| 登记更新、预览、会话报告与任务控制          | 核对真实拥有者、实例和运行顺序，不以数据库字段基线替代运行控制                                                                   |

条件读取、约束检查和写入必须处于同一短同步事务。网络、文件、扩展调用及用户等待都在事务外。expected 缺项表示不设置该条件，null 表示要求当前值为空。对象比较不受 JSON 键顺序影响，有序数组比较内容与顺序，关系按身份及相关属性比较。基线来自真实值，不能根据显示文案或宽松名称匹配反推。

值相等只证明当前值符合条件，不能证明期间从未变化。需要检测中间变化时，应使用对应版本或运行条件。条件失败按[错误目录](library-write-contracts.md#errors)中的 Conflict、TargetChanged、NotFound 等类型处理，不根据 error.message 分支。

发生冲突后保留草稿，重新读取并展示受影响内容，由用户决定保留哪些值，再提交相应基线。不能自动刷新 expected 后重放，也不提供绕过全部检查的强制保存。技术事务重试仍须核对原条件。同次提交中一项失败，整次不写入；长批次则保留先前已经完成的项。后台操作报告冲突，不转为等待人工决定，也不盲目重放。

已保存值和草稿分别维护。后台变化可以更新没有冲突的展示，不能覆盖用户输入。保存成功后以实际提交结果建立新基线，同时保留提交后继续输入的内容。只有确有未保存内容即将被丢弃时，才提供保存、放弃和继续编辑的选择；内容已还原或切换时仍保留草稿，就不反复确认。即时设置失败时恢复到已提交状态。

“保存主题并选用”需要两个基线：主题内容使用开始编辑时的值，主题选择使用发起组合操作时的正式选择。主题保存成功而条件选用失败时，保留主题并报告“已保存，但未选用”，不能覆盖准备期间发生的新选择。普通立即选用仍是直接设置，这种值条件也不承诺检测 A → B → A 的中间变化。

<a id="selection"></a>

## 固定目标集合

手动选择、Shift 范围选择和全选，都得到选择当时的固定身份集合。未加载区间由本体解析真实范围，全选取得完整匹配 ID，不能只使用已加载记录，也无须下载全部详情。

Entry 操作按 Entry 去重，关系或成员操作按真实关系 ID 或完整联合键去重。分组中的重复显示实例不会重复执行。选择之后新加入的匹配对象不会自动进入集合，系统不把选择保存为持续扩张的查询加排除条件。ID 集合只在当前浏览或操作中存活，其规模成本需要验证。

排序、分组，以及网格与表格切换保留选择。用户改变检索文字、条件、类别或入口范围时清空选择，不提供跨查询选择篮子。刷新不能加入新目标。已选对象发生真实删除或合并时，应在提交前明确处理，不能静默缩小集合或转向其他 ID。

批量完成可能使对象退出原筛选，但本次仍处理开始时确定的全部目标，不边执行边重算条件。目标准备和最终提交继续遵守完整操作规则。

<a id="identity-operations"></a>

## 合并与删除的完整影响

将同类条目 A 并入用户选择保留的 B 时，library 在一次完整操作中应用下表规则。标题、文件名或卷号相同不能代替真实身份判断。操作不生成差异编辑稿，也不让用户逐字段选择。

| 内容                           | 默认行为                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 名称、简介等普通资料           | 保留 B 已填写的值，只用 A 补充 B 未填写的资料                                                          |
| 别名、外部身份、标签、合集成员 | 按真实身份整合；已有目标关系保留身份与顺序，新关系追加；关系属性按对应关系合同合并                     |
| 评分、收藏、当前状态、附加时长 | 保留 B 的值，包括 null、false 和 0；不取较高分、较新状态或两侧时长之和                                 |
| 作品完成记录                   | 全部保留 ID、日期和备注并迁入 B；次数与日期摘要从合并后的记录计算                                      |
| 独立笔记、实际活动             | 笔记保留独立身份并整合条目关联，活动保留身份并迁移归属；不因文字或时间相似自动删除                     |
| 分部                           | 保留各分部稳定 ID 并迁入 B；同名同号不自动归并，需要时再由用户明确合并同一内容                         |
| 文件、位置与首选               | 按真实文件身份迁移；保留各自位置，保留 B 已设置的首选；B 没有首选时采用 A 的明确首选，不按文件顺序猜测 |

同一天或相同备注的完成记录仍可能是不同事实，合并时完整保留。需要更正资料或删除完成记录时，先使用各自的普通编辑入口。同位置的重复文件按[文件合并](file-maintenance.md#file-merges)保留身份与历史；其余无法合法并存的身份、位置或约束冲突使本次合并失败，结果说明具体对象与原因。用户处理冲突后可以重新发起合并。

保存查询中的结构化引用同样属于影响范围。合并时重新映射引用，删除时保留明确失效状态，不能删除条件而扩大查询。MetadataProfile 不承担本地整理策略。

删除按具体对象的完整含义执行。删除关联不删除端点，移除成员、删除条目和删除文件记录分别是不同操作，不能用任意 cascade 开关拼装语义。必要确认只说明对象、数量和影响范围，不逐层展示从属记录。独立 Note 和用户媒体继续遵守各自留存合同。删除作品同时删除其完成记录并退出来源同步范围，不删除平台上的收藏或用户记录。

正在打开或使用的真实身份由 sessions 登记占用。合并或删除前必须结束对应会话，普通查看和元数据编辑不受此限制。sessions 在异步打开前登记占用，打开失败后释放。最终占用核对与身份提交之间不能留异步间隙。系统不推广通用租约，也不静默注销会话或强退游戏来绕过占用。目标失效或相关事实冲突时应明确失败，旧请求不能转投新身份。 已结束会话仍有[未保存记录](sessions.md#pending-recordings)引用目标时，删除或合并返回 PendingRecording，先处理该快照；普通编辑和新的使用仍按各自规则执行。

正式文件的分部关联、访问路径和记录移除同时遵守[使用期间的文件修改](file-maintenance.md#file-use)：实际修改前结束受影响文件会话，只读测试和预览仍可进行。后台空关联匹配在占用解除后按最新事实及[关联方式](holdings.md#association-mode)重新核对；手动关联采用不在后台延期提交。关联采用与重定位的选定有效修改分别在同一短事务完成，不用逐条公开 CRUD 形成半份结果。

<a id="part-merges"></a>

## 明确合并重复分部

library.parts.merge({ source, target }) 接收两个 PartRef，返回保留的 target。两者必须属于同一作品且种类相同，source 与 target 相同为 InvalidInput；跨作品归属先通过完整作品合并处理，Episode／Extra 的种类更正继续使用 changeKind。此操作由用户明确判断两条记录描述同一内容，不按同名、同号或相似资料自动触发。

| 内容               | 合并结果                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------- |
| 身份与资料         | 保留 target 的 id、创建时间和顺序；编号等普通资料保留已填写值，只用 source 补空；删除 source 行 |
| 外部身份           | 迁入 target，核对所有真实绑定；不生成来源别名或按名称搬移其他对象身份                           |
| 完成标记           | 任一侧为 true 则保留 true                                                                       |
| 文件关联           | 按实际文件身份整合；重复关联保留 target 关系属性，新的关联保留其文件身份、位置和关联方式        |
| 分部首选           | 保留 target 已有首选；target 没有时采用 source 的明确首选，不改变作品级首选                     |
| 漫画卷的话收录     | 合并两卷的真实成员；重复话保留 target 侧编号与顺序，新成员按 source 原顺序追加                  |
| 漫画话的卷收录     | 各卷重定向到 target；同卷重复关系保留已有 target 关系的编号与顺序                               |
| 活动与其他正式引用 | 将 source 分部引用迁到 target，保持活动 ID、时长及发生时的显示快照；不改文件位置或作品完成历史  |
| 正文及图片         | 按最终保留的资料维护真实附件引用，已有字节复用，解除的引用按正常回收处理                        |

两端存在性、种类、归属、引用、首选与所有受影响文件的使用占用，在同一短同步事务内核对并提交。普通字段按提交时的当前事实应用固定取值规则。目标缺失为 NotFound，种类／归属不符为 InvalidReference，使用占用为 InUse，无法同时满足的约束为 Conflict；失败不留下部分迁移。

界面只选择两项及保留目标，并简要说明身份、资料、文件与标记的处理，不另设字段差异编辑器。需要更正资料时使用普通编辑。提交后发布 partMerged，携带 source 的身份快照、target 和 work，并使分部、持有、活动及相关条目汇总失效；不将合并表示为用户单独删除 source。来源刷新继续通过已迁入的真实身份找到 target。

<a id="merge-action"></a>

## 合并入口

用户选择要合并的同类条目与保留目标后执行合并。入口简要说明固定取值与历史保留规则，不生成整份结果预览、字段差异展开、记录取舍勾选或另一个资料编辑器。

提交时重新核对真实目标、引用与使用占用，并按当前事实执行完整合并。取消未提交操作不修改数据，失败保留原条目，成功返回实际保留的条目。普通编辑、记录管理和关联编辑继续通过各自入口完成，不在合并中增加补救向导。

<a id="catalog-regions"></a>

## 条目、分部与关系的内部组织

entries 以七类条目已经成立的共用身份、资料和操作为基础组织实现，不为每种类型预先复制一套查询、创建和更新模块。

| 内部位置        | 负责内容                                                   |
| --------------- | ---------------------------------------------------------- |
| query           | 列表、详情、定位、分组与选择范围，以及相应条件、排序和投影 |
| create.ts       | 条目身份、类型资料及明确初值的完整创建                     |
| update.ts       | 资料修改、相关基线核对与完整提交                           |
| personal.ts     | 评价、收藏、作品当前状态与作品附加时长的个人操作           |
| external-ids.ts | 外部身份的实际绑定、解除与冲突处理                         |
| write.ts        | 对 library 内部完整操作提供的同步事务内写入规则            |

专属字段和约束在对应查询与写入中明确处理。某类出现实质性的专属流程后，再提取相应模块；共用机制不扩展成同时控制数据库、业务流程和 UI 的万能 EntrySpec。query 内按实际查询职责拆分，公开合同直接从所属合同包引用。

create、update 和个人操作各自负责完整入口的资源准备、事务及提交后通知。write.ts 接收所属操作的同一事务连接，不自行提交、发布通知或执行文件 I/O。library 内部的资料图提交、合并等完整操作按明确依赖复用这项能力。UI 和 SDK 只调用完整业务接口；确有同库原子要求的本体组合，通过拥有者明确提供的有界同步写入能力协作，具体范围见[引导采用](onboarding.md#composition)。外部身份的纯格式与比较规则留在公共值定义中，不因实际绑定由 entries 管理而移入私有实现。

parts 按实际内容体系划分为 anime、comic 和 novel。anime 同时管理 AnimeEpisode 与 AnimeExtra，包括保留身份及关联的种类更正；comic 同时管理 ComicVolume、ComicChapter 与卷话收录，话直接属于漫画，卷对话的收录具有自己的规则；novel 管理 NovelVolume 的资料与排列。紧密协作的操作留在对应内容体系中，不按五种 Part 类型机械复制完整模块。

真正同义的字段处理、排列和基础读写可以复用；五种 Part 各自拥有正式表、约束和 PartRef 分支，按各媒介的业务流程实现。

relations 按 work-characters.ts、person-works.ts、organization-works.ts 和 work-relations.ts 划分四个职责模块。各模块拥有其端点、职责、业务唯一性和排列规则，从不同界面编辑同一事实仍使用同一身份和规则。人员工作指定角色时，须核对真实作品角色关联；作品联系正确处理方向与反向展示；删除作品角色关联时，完整处理依赖它的具体角色工作。

四类关系分别保存自己的事实，相同的端点检查、顺序处理和存储机制可以复用。一个文件足以承担时保持单文件，需要多份逻辑协作后再拆成同名目录。模块私有类型表达内部协作，公开合同从所属模块直接引用。

<a id="personal-regions"></a>

## 整理与个人记录的内部归属

organizers 按 collections 和 tags 划分完整能力，管理用户组织条目集合与标记关系的规则。二者可以复用相同的基础机制，各自拥有身份、成员或应用、排列及合并约束。

records 按具有独立身份和管理操作的个人事实与内容划分，包含以下模块：

| 内部位置            | 负责内容                               |
| ------------------- | -------------------------------------- |
| records/completions | 每次明确登记的作品完成事实、日期和备注 |
| records/activities  | 实际使用活动及其时间、时长和上下文     |
| records/notes       | 独立私人文字、附件引用及条目关联       |
| records/annotations | 内容位置、摘录、画面和批注的正式保存   |

Note 的条目关联服务于文章的整理和访问，其主要对象仍是用户保存的独立内容。Annotation 保留对作品实际内容的定位与摘录，源文件不可用不使已保存内容失效。它们分别位于 records/notes 与 records/annotations，不因存在条目关联而归入 organizers 或 relations。

当前属性跟随所属对象管理：评价、收藏、作品当前状态和作品附加时长位于 entries，分部完成标记位于 parts，唯一的文件续读或续播位置位于 holdings 的文件能力。数据库表名不直接决定代码目录。作品使用的运行上下文由 sessions 管理，内部技术资源沿各执行者的合同取得和释放；活动即使由运行会话持续更新，其持久事实仍由 records/activities 管理。

showcase 管理保存的查询、展示配置和排列，不修改条目的真实合集成员或标签关系，保持独立职责区域。界面绘制与临时草稿属于 renderer。

跨区域的原子关系由完整操作保证。例如，records/completions 的 recordCurrent 在同一事务中新增完成记录并清除 entries 管理的作品当前状态，复用相应内部写入规则。两个区域各自拥有相应数据，通过该事务共同完成修改。公共接口使用 library.completions、library.activities、library.notes 和 library.annotations。
