# 任务执行、结果与自动行为

tasks 管理明确纳入任务中心的实际执行。每次执行由 TaskRun 保存通用状态、进度、控制能力和历史。业务模块负责执行步骤、结果含义，以及可以安全暂停或取消的位置；任务中心统一呈现这些信息。

<a id="boundary"></a>

## 任务粒度与业务调用

一次任务执行对应一个 TaskRun，保存于 task_runs。对外引用使用 TaskRunRef，身份字段命名为 taskRunId，存储引用命名为 task_run_id。模型不另设任务定义、持久任务树或通用子项执行实体，也不把所有异步调用和使用会话都纳入任务中心。

不同操作的任务边界如下：

| 操作                               | 任务边界                                   |
| ---------------------------------- | ------------------------------------------ |
| 独立执行资料新增或更新             | 一次完整操作一个任务                       |
| 批量新增或更新                     | 整个批次一个任务，逐项事实包含在业务结果中 |
| 扫描                               | 一次扫描一个任务                           |
| 创建或恢复备份、扩展安装更新       | 各自完整操作一个任务                       |
| 搜索、候选读取、预览、普通字段编辑 | 按调用寿命执行，不默认建立任务             |
| 游戏、播放与阅读                   | 继续由 sessions 管理实际使用               |

任务管理遵守[接纳与执行边界](../communication.md#admission)。待核对的自动变化属于尚未接纳的触发收集，不为这些范围预建 TaskRun。已接纳工作中的异步准备、资源等待和收尾都属于实际执行，由业务拥有者承担；其中明确纳入任务系统的执行，才使用对应 TaskRun 管理进度与控制。不能以尚未开始业务步骤为由，将已接纳工作排除在等待和取消范围之外。

业务实现与任务包装分开，业务规则只实现一次。独立添加资料时包装一个任务；批量添加和扫描则各自包装一次，内部复用逐项业务能力，不再生成嵌套任务。入口明确决定任务范围，不根据调用来源、耗时、prepared 输入或父任务标识猜测是否合并。一次资料更新任务完整执行获取、对应、处理和提交，不在获取完成后等待另一轮采用确认。

普通业务调用等待自己的完整结果，并通过 ExecutionFailure 表达失败；明确管理执行的入口交付实际任务引用。SDK 按公开能力选择入口，内部协作函数保留自身边界。主进程已经接纳的独立工作不会因页面关闭而终止；需要扩展实例参与的执行，则受该实例生命周期约束。

## 运行器与执行上下文

SDK 为扩展工作提供相同的任务托管能力：扩展实例持有执行函数，宿主管理 TaskRun、调用关联与控制。执行依赖该扩展实例的寿命，任务历史由主进程持久保存。渲染界面通过正式业务接口发起工作。

运行器先登记唯一的 TaskRun，再将只读引用和控制能力交给业务回调。业务回调返回原本的业务结果，tasks.run 等到执行及托管收尾全部完成后，才把结果交付给调用方。例如：

```ts
return tasks.run(
  {
    type: 'scanner.scan',
    title: '扫描作品',
    input: scanInputSnapshot
  },
  async (context) => {
    currentScan.taskRef = context.ref
    return executeScan(input, context)
  }
)
```

执行上下文提供以下能力：

| 执行能力            | 职责                                                    |
| ------------------- | ------------------------------------------------------- |
| ref                 | 当前已登记 TaskRun 的只读引用，供业务拥有者关联本次执行 |
| signal              | 向可取消的实际操作传递取消                              |
| checkpoint()        | 在业务安全位置检查取消，并响应暂停                      |
| reportProgress(...) | 报告实际进度或当前阶段                                  |
| reportResult(...)   | 交付已经成立的阶段性业务结果，供结果检查点保存          |

任务历史的 input 只保存必要业务快照，type 用于分类和解释结果。执行函数在所属运行端持有本次真实请求，并通过明确调用组织业务；IPC 传递相应合同值。凭据、完整来源响应与执行上下文禁止写入历史。

scanner 等业务拥有者通过 context.ref 保存本次运行关联，不能查询最近一条任务来猜测身份。该关联保留到 tasks.run 完整结束，再按本次身份清理，不能在业务回调刚返回时就宣布收尾完成。任务中心直接使用任务身份；扫描页也通过同一引用调用 tasks 的控制能力，不另外保存暂停标志，或由页面自行写入另一份扫描历史。

checkpoint 应放在候选处理完成等真实安全位置，不能在同步数据库事务中暂停。signal 传给可以取消的实际操作，下层只接收需要的资源，无需层层携带整个上下文。取消仍须完成必要收尾，已经提交的事实继续保留。阶段结果必须符合业务结果合同，并在批次或关键边界保存，不能每次报告进度都重写整份结果。

## 持久记录与业务结果

任务记录及状态定义如下：

```ts
interface TaskRun {
  id: string
  type: string
  title: string
  description: string | null
  status: TaskRunStatus

  input: JsonValue | null
  result: JsonValue | null
  error: ErrorSummary | null

  createdAt: number
  startedAt: number | null
  finishedAt: number | null
}

type TaskRunStatus =
  | 'queued'
  | 'running'
  | 'pausing'
  | 'paused'
  | 'cancelling'
  | 'completed'
  | 'failed'
  | 'cancelled'
  | 'interrupted'
```

input、result 和 error 使用 JSON 保存，时间采用 UTC 毫秒，存储列使用 snake_case。尚未开始或无法确认结束时，相应时间为 null。ErrorSummary 直接使用 desktop-contracts/errors 的定义，不增加同形别名。业务根据 type 解释输入和结果。title 与 description 保存当时的展示说明，不作为解析协议，配置改名也不重写旧任务文字。

准备完成后固定本次输入；无法形成有效参数时，input 可以为 null，没有参数的操作则使用空对象。result 保存已经产生的事实，尚无结果时可以为 null。error 只包含任务级稳定分类和安全说明，不保存堆栈或日志。失败任务可以同时具有合法的部分结果，逐候选问题则保留在业务报告中。

TaskRun 自己保存足以展示的结果快照。单项和批量执行共用这一模型，不要求所有业务都具有 items 字段，也不能只保存必须回查另一份历史的引用。结果没有独立 id、表或生命周期，模型不设 TaskItem、TaskItemResult、task_run_items 或 isBatch。运行进度与结果分别表达不同事实，产生部分结果不代表任务已经结束。

任务中心提供共同列表与详情框架，业务补充具体报告和补救操作。每份 ScanResult 保存本次扫描的问题，重新扫描或修复产生新的结果，原报告保留当时事实。用户反馈由[界面入口](../ui/components.md)负责，运行器只交付执行状态和结果。

再次执行会创建新的 TaskRun，不重开旧记录，也不保存 retryOfTaskRunId。通用任务记录不设置 source、trigger、ref、rule、scanner_id、is_batch、last_observed_at 或仅为观察而增加的 updated_at；本次操作由实际输入和说明表达。

## 状态观察与控制完成条件

任务管理提供以下方法：

| 方法                    | 职责                                                            |
| ----------------------- | --------------------------------------------------------------- |
| list                    | 分段读取任务摘要及相同查询范围下的总量                          |
| get                     | 读取任务详情，包括输入、已生成结果与错误；记录不存在时返回 null |
| observe                 | 观察指定任务的轻量运行状态                                      |
| onInvalidated           | 通知任务列表或详情需要重新读取                                  |
| wait                    | 等待指定任务终结，取得包含 status / result / error 的终态记录   |
| pause / resume / cancel | 处理控制请求，返回处理后的实际状态                              |
| clearHistory            | 清理符合条件的已结束记录                                        |

queued、running、pausing、paused 和 cancelling 表示尚未结束；completed、failed、cancelled 和 interrupted 表示终态。只有具有真实安全检查点的工作才支持暂停。如果业务允许部分成功，completed 的界面仍须分别展示成功、失败、跳过和警告，不能将“执行完成”写成“全部成功”。

observe 先交付当前轻量快照，再按顺序交付变化，保证初始读取与订阅之间不丢失状态。快照包括实际状态、进度或阶段提示，以及 canPause、canResume、canCancel。终态交付后观察结束；目标已经终结时，立即交付终态再结束。释放观察只停止订阅，不取消任务。无法可靠计算比例时，只报告阶段；进度达到 100% 也不直接决定任务终态。

get 按需读取完整结果。创建、结果检查点、终态和历史清理通过 onInvalidated 通知调用方合并重读。高频进度通过运行观察单独推送，完整报告按需加载。

await pause、resume 或 cancel 表示控制请求已经处理，返回值是当时实际状态，不保证任务已立即暂停或结束。暂停在下一个安全点生效；resume 可以恢复已暂停任务，也可以撤回尚未生效的暂停请求。cancel 停止后续工作并完成收尾，无法撤回的提交段允许完成，已提交结果不回滚。迟到取消不能把 completed 改成 cancelled。对终态重复发送控制请求，幂等返回实际结果，不重新执行业务。

需要确认任务真正结束时使用 wait，它返回含 status、result 和 error 的终态记录。任务自身失败通过记录表达；引用不存在、读取失败或等待连接中断才属于 wait 调用失败。取消等待或关闭页面都不取消任务。clearHistory 只删除符合条件的已结束记录，不停止工作，也不删除业务产物；已经交付的运行观察与结果不会因清理历史而失效。

## 历史、检查点与中断处理

### 独立历史与提交次序

tasks 保存通用执行历史。scanner 等业务如果有独立查询、处理和保留报告的需要，可以另外保存业务快照；没有实际需要时，不机械地增加历史表。两处复用同一次生成的结果及展示逻辑，不分别计算成功数量或结论。TaskCenter 查询 task_runs，scanner 查询 scan_runs，各自记录的基本含义不依赖另一份历史仍然存在，也不依赖一条历史引用链。

两份快照分别保存当时的参数、名称和所需完整报告。必要事实可以重复，但不能扩展成来源全文、日志或附件字节的重复存储。配置改名、后续修复和另一份历史被清理，都不重写这些快照。正式对象或产物 id 可以作为事实引用，但不能代替当前记录本身应保存的内容。

可能产生副作用的业务必须在所需起始记录保存后才开始。执行期间按检查点保存结果，每份记录的最终状态和结果一起提交。通用历史与业务历史由各自拥有者保存，不因同库或具有同一完成边界而要求共同提交。需要共同定义一项业务完整性的事实仍按所属业务要求原子提交；独立历史不建立跨模块联合提交协议。高频运行状态留在内存中。

业务回调负责自身操作、报告及必要收尾，tasks 在回调结束后完成 TaskRun 和托管收尾，再交付完整调用结果。以扫描为例，scanner 保存 ScanRun 并交付同次生成的 ScanResult，tasks 再用该结果完成 TaskRun。ScanRun 的终态表达扫描业务及自身报告的结果，TaskRun 的终态表达整个任务托管的结果；两处在执行中、保存失败或进程中断时可以停留在不同阶段，不能要求同时可见或始终具有相同状态。

### 保存失败与读取投影

历史写入失败时，停止本次执行的后续业务，完成必要收尾并报告失败。业务报告保存失败须向运行器传播；TaskRun 的保存失败则由 tasks 报告，不能反向撤销已经保存的业务报告。已经形成的合法结果按共同失败合同交付，已提交的业务变更保留；本次执行结束后不补存历史，也不自动重做业务。

持久记录证明最后成功保存的阶段，实际运行状态由当前上下文确定。终态保存失败时，observe 交付实际 failed 终态；已进入的 wait 取得包含历史保存错误和合法结果的终态记录。随后释放运行上下文，轻量观察不传输整份报告。

list、get，以及运行上下文释放后新发起的 observe／wait，按持久记录读取。记录仍为非终态且没有对应运行上下文时，将读取状态投影为 interrupted，表示历史无法确认完整结束；保留最后保存的输入与结果，finishedAt 为 null。该投影不回写数据库，也不从 ScanRun 补出任务结果。例如，扫描报告已保存而 TaskRun 最后保存失败时，当前等待者取得失败结果，之后的任务详情显示最后检查点与完成未确认，扫描详情仍保留自己的完整报告。

列表筛选、计数和历史清理使用同一状态判断。当前仍有运行上下文的记录受运行保护；实际执行已结束的未确认历史可以明确清理，不因数据库保留旧状态而永久无法删除。

### 启动中断与历史清理

启动时将前一个主进程遗留的非终态记录标记为 interrupted，展示已知结果和仍无法确认的范围，finished_at 保持未知。旧工作可能已经产生副作用，因此重新执行前由所属业务读取当前事实。只有具备明确证据与专用恢复合同的流程才可继续；游戏启动、外部写入、增量记录和资料修改均须重新发起，不能自动重放。

通用历史和业务历史默认都保留，各自支持按时间或全部清理已结束记录，不设置自动过期。运行和暂停中的记录不可清理。两份历史互不级联，清理也不删除正式资料、个人活动、文件、备份或尚需处理的恢复材料。界面必须区分“没有报告”和“报告确认没有问题”。

## 各功能的自动行为

自动行为由实际业务拥有，具体分工如下：

| 自动行为                 | 拥有者与配置                                      | 执行与反馈                                                                                                                                      |
| ------------------------ | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 新作品发现与增量核对     | scanner 与 ScanConfig 的监听设置                  | 启动时核对当前范围，之后处理真实文件变化；产生 ScanResult，由同一 TaskRun 提供进度与控制                                                        |
| 本地内容发现与文件核对   | library.holdings 与本地内容自动刷新偏好           | 按[持有刷新](file-maintenance.md#refresh)执行启动、恢复、监听与监听失败时的定期刷新；发现过滤与已有文件维护独立，只匹配已有分部，不请求来源资料 |
| 游戏确认退出后的存档备份 | library.holdings.backups 与同一启动配置的当前选择 | 接纳前核对当前开关，使用会话保存的真实来源快照检查并备份；备份失败不改写游戏已退出的事实                                                        |
| 应用更新检查             | updates 与应用更新偏好                            | 按 [更新偏好](preferences.md#fields) 的启动及 24 小时规则检查；下载、安装和重启各有明确入口                                                     |
| 来源记录自动同步         | 具体来源扩展与其账号、范围、字段及自动开关        | 按[平台记录同步](../extensions/synchronization.md#automatic)在启用、启动和相关本地变化时以本地值更新平台；不定时轮询远端，不自动导入新作品      |
| 授权有效性与令牌续期     | 具体来源扩展                                      | 在来源调用与凭据生命周期内处理；需要重新授权时显示问题，由用户发起授权                                                                          |

每个功能自行定义触发条件、配置、范围、并发规则和结果，手动与自动执行复用同一业务操作。界面分别表达用户是否启用、监听或定时器是否可用，以及当前是否正在执行。关闭自动开关停止后续触发，已经接纳的工作仍按自身取消合同处理。配置修改在下一次执行时采用。

scanner 合并同一范围内等待核对的变化。来源同步按连接和对象控制并发，执行与重试读取最新本地目标，并核对平台实际值；不以旧指纹代替当前核对。队列必须有界，但不能因繁忙而丢弃全部变化。tasks 只负责已经接纳的执行，不决定下一次扫描或同步的时机。

启动或恢复时，功能先读取当前配置和已保存状态，再建立监听和定时器，不补放离线事件，也不重放结果未知的写入。依赖文件变化的发现流程先接入监听，再核对当前范围，并合并处理核对期间的新变化，不能在首次遍历与监听之间留下遗漏窗口。应用范围的固定跨模块订阅按[集中装配](../architecture.md#app-composition)建立和释放；功能内部及实例范围的订阅、时钟、取消和在途调用归实际模块或扩展实例所有。停用时停止新触发并在有界时间内收尾，异常结束则如实记录中断。

共享机制提供实际复用的时钟、取消、释放和任务能力，自动触发规则与业务动作由各自拥有者实现。自动调用需要交互时，按[共同调用合同](../communication.md)明确失败，不能等待合同之外的人工补救。
