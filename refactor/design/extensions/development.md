# 扩展作者工具与开发流程

extension-cli 通过 kisx 命令和程序化入口提供同一套工作流。源码工作区负责组织项目，扩展构建负责生成完整安装包，分发仓库负责维护可发现和可安装的制品。第三方作者使用公开包和真实 Kisaki 应用完成开发，无须克隆或编译主应用。

<a id="tools"></a>

## 命令与公共依赖

| 命令组    | 工作对象                 | 责任与边界                                       |
| --------- | ------------------------ | ------------------------------------------------ |
| workspace | 源码工作区               | 初始化多项目共享的包管理、工程配置及批量脚本     |
| extension | 扩展源码项目或已构建制品 | 创建、开发、静态合同校验、构建及打包             |
| registry  | 扩展分发仓库             | 消费已完成安装包，维护索引与发布资料，校验并签名 |

workspace 组织源码工程，registry 是发现、安装和更新所用的协议目录，Git 仓库则提供版本边界。三者可以放在同一个仓库，也可以分别维护。作者可以只交付安装包，仓库维护者可以收录其他作者的包，同一个包也可以进入多个仓库；签名由仓库负责。统一安装工具可以共享依赖，但延迟加载只能减少初始化开销，不能减少安装体积。

创建入口分别为 `kisx workspace create <directory>`、`kisx extension create <directory>` 和 `kisx registry init <directory>`。单扩展不必建立多包工作区。向现有工作区添加扩展时，复用同一生成流程并将项目加入普通 pnpm 成员，无须预先存在分发索引、README 生成块、专用标记或未修改的旧模板。

程序化入口为 extension-cli/workspace、extension-cli/extension、extension-cli/registry 和 extension-cli/config，直接复用 CLI 背后的工作流实现。调用显式传入目录，不修改整个进程的 cwd。只有 CLI 负责交互提问、终端输出和退出码。一次操作完成后返回结构化产物，dev 则返回可停止的会话。config 只提供轻量类型和 defineConfig，不另建配置包。

extension-distribution 定义 manifest、registry、静态展示、兼容规则和纯校验，并通过 Node 子入口提供签名能力，不依赖本体 API。extension-api 定义运行合同，SDK 实现接入。应用只消费制品格式，不依赖 CLI 或编译器。独立创建器并入 CLI，官方扩展同样使用公开工作流，不通过调用 CLI 再解析终端文字完成自动化。

<a id="build"></a>

## 源码声明与完整构建

| 位置    | 内容                                          |
| ------- | --------------------------------------------- |
| src/    | 扩展源码                                      |
| out/    | 完整运行布局：生成的 manifest、编译代码和资源 |
| dist/   | 可交付的 .kisx                                |
| .local/ | 持续保留的开发资料                            |

package.json.version 是唯一版本来源，package.json.kisaki 保存扩展元信息。kisx.config.ts 只配置 Node 入口、Webview 构建输入、资源、输出和构建选项。工具生成的 manifest 描述完整包内运行布局。Webview 如何构建文档，与运行时如何使用 document 是两个职责；构建器不能执行 activate 来猜测所有页面。

extension 命令组提供 create、dev、validate、build 和 pack。build 依次检查声明、编译代码、装配运行依赖与资源，再验证完整布局。pack 默认完成必要构建，也允许明确指定已有的完整目录。validate 可以检查源码、构建目录和 .kisx，并给出可定位诊断。build 与 pack 自动执行必要检查，不要求作者先手动运行 validate。静态检查不执行贡献，也不能冒充运行验收；类型、lint、格式和测试仍使用普通项目脚本。

编译和插件能力由构建器负责，kisx 负责扩展入口映射、装配和制品。配置如果与输出、manifest 或运行边界冲突，必须在开始前拒绝。开发服务器地址只属于开发会话，不写入正式 manifest。普通清理与重置 .local 是不同操作，需要明确表达。开发运行成功也不能替代真实安装验证。

<a id="registry"></a>

## 制品维护、签名与部署

registry 命令组提供初始化、添加或移除版本、维护展示资料与说明、校验、签名和生成密钥。添加版本从真实 .kisx 提取身份、版本、目标、兼容和展示信息，计算哈希，并接收获取 URL 与发行说明；所需输入仅为制品及发布资料。同一版本、同一目标的字节保持不可变。移除只删除发布记录，用户安装与远端字节继续由各自拥有者管理。

registry.json 保存待签名正文，dist/index.json 保存采用同一业务结构的签名结果。作者可以先准备、校验正文，再由持有私钥的维护者或 CI 签名。内容改变后须重新签名才可发布。相对 URL 统一以最终响应 URL 为基准解析。

部署必须明确执行，先发布包和展示资源，再更新完整的签名索引。旧索引引用的资源仍须可用。build、pack 和本地准备不会暗中上传，也不能把仅生成本地产物的操作称为远端 publish。CI 的触发、权限和并发见[发行规则](../engineering/releases.md)，稳定地址和身份见[仓库规则](../engineering/repository.md)。

## 开发实例与首次就绪

`kisx extension dev <project...> --app <application>` 接受一个或多个显式项目。作者使用本机应用，无须编译主应用；本机应用路径和 .local 路径也不必写入需要提交的通用配置。工具先检查重复扩展 ID，建立编译监听和必要 Web 服务器，等所有项目的第一份完整构建都成功后，才启动专用应用。首轮源码错误留在终端等待修复，不循环启动失败的应用。不可恢复的配置或启动错误必须完整收尾。

启动前确定独立的开发 profile 和身份，为数据库、浏览器会话、锁及 .local 持久数据划定开发范围。正常重开保留测试资料、设置与凭据。显式开发项目在相同 ID 下优先加载，安装记录保持原样；同仓项目也须经过显式选择。应用核对 manifest、API 与运行条件后逐项激活，并分别报告进程、连接和激活状态。

默认由 CLI 启动器拥有它启动的应用实例。同仓 desktop:dev 则由源码应用启动器拥有应用进程，并组合相同的程序化 dev 会话。一个进程只能有一个启动、重启和退出拥有者。工具不能另起第二个 Electron，也不能扫描普通实例后自动附加。

<a id="reload"></a>

## 构建交接与热更新

| 改动或情况                           | 重载行为                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------- |
| Webview 样式与可接受热更新的界面模块 | 使用开发服务器和框架的 HMR；需要时刷新该页面，Node 实例继续运行                    |
| 扩展 Node 代码构建成功               | 调用宿主的重建流程，替换共享扩展进程并重新激活全部应启用实例；桌面应用本身继续运行 |
| 新构建失败                           | 保留上一份成功构建及当前有效运行状态，报告构建错误                                 |
| 新代码构建成功但激活失败             | 展示该实例真实的激活错误，不把编译成功报告成运行成功，也不伪称已恢复旧运行状态     |
| 停止开发会话                         | 收尾编译监听、服务器、开发实例及会话资源，保留 .local 中已持久保存的资料           |

Node 代码、manifest 和依赖资源形成完整结果后，工具才交付明确的构建引用。不能根据输出文件存在、日志文字或固定延时猜测 ready。当前运行目录与候选输出分开，每个输出只有一个写入者。失败构建不能覆盖现用内容，已经交付的构建必须保留到所有读取者释放。短期构建身份不修改 package.version，也不进入安装历史。

共享宿主一次只执行一个重建。相邻完成的构建可以短暂合并，每个扩展只保留最新待采用结果。重建开始时固定本轮完整集合，期间到达的新结果进入下一轮，迟到的旧结果不能使版本倒退。防抖不能代替编译就绪。工具负责报告构建，应用负责报告采用和激活，各层失败分别显示。旧目录只有在宿主及其他读取者都释放后才能清理。

Node 构建成功后，默认自动重建共享宿主：撤销旧贡献和调用，完成有界清理，再建立新 context。重建不重放业务，也不重发 app.ready；原生已接管的任务按剩余依赖处理。开发重建允许丢失尚未保存的内存草稿，不逐次执行普通 close 确认，不设置 dirty 门槛，也不序列化全部状态。该规则不能用于正式更新。主动开发重建不消耗异常恢复次数。

重建后，应用按 extensionId、pageId 和所属窗口重新创建原有注册页面，执行新 setup 并取得业务快照。页面未重新登记或实例激活失败时显示不可用。旧句柄失效，临时闭包 Dialog 不自动重开。前端 HMR 能保留多少状态由框架决定，不承诺保全草稿。

纯文档刷新只重建前端连接，并清除旧文档请求与监听。Node 实例和宿主视图仍在时，不重复执行 setup。只有真正替换 Node 实例时才创建新视图，迟到的旧消息不能进入新连接。

共用包必须通过 exports 和构建结果消费。UI 样式、SDK 或合同变化，需要真实触发下游构建或 HMR，并正确处理缓存。Turbo 选中了任务，不代表整条变化链已经有效；不能直接导入其他包的 src 来绕过公开入口。

## 变化范围与开发连接

| 变化                                           | 处理规则                                                                   |
| ---------------------------------------------- | -------------------------------------------------------------------------- |
| Webview 样式与界面模块                         | 使用 Vite/框架的 HMR，必要时重新创建页面文档；Node 实例保持                |
| Node 源码及其被编译的依赖                      | 形成完整新构建，再按共享宿主流程采用                                       |
| 扩展的展示声明、兼容声明或资源                 | 重新校验并生成构建，按实际需要更新页面或重建宿主；不依据文件扩展名猜测影响 |
| kisx 构建配置或入口布局                        | 重新建立相关编译监听/开发服务器，完成新一轮就绪检查后交接                  |
| 扩展身份、应用路径、目标平台或运行依赖安装状态 | 明确要求重新启动开发会话；工具不自动安装依赖或在会话中改投另一应用         |

工具与应用使用 node:net 的本地 IPC：Windows 使用命名管道，macOS 与 Linux 使用 Unix socket，见 [Node IPC](https://nodejs.org/api/net.html#ipc-support)。启动参数携带明确的会话身份和端点，只连接预期开发应用。协议只传输有限的握手、完整构建、采用结果和停止消息，不提供任意方法或对象执行，也不建立常驻服务。握手、长度帧、有限消息、构建引用、逐项采用与目录释放使用[开发字节流合同](../engineering/protocols.md#development)；连接失败或应用退出时返回诊断，不猜测端口或无限重启。

desktop-contracts/development 拥有类型、帧边界、协议版本和启动传参，CLI 与应用直接消费并严格解析。SDK 不因此获得宿主重启或安装管理能力。Vite HTTP 和 HMR 只使用本会话登记的本机来源与文档映射；按[开发视图规则](webview.md#development)保留每视图来源，施加精确资源 CSP 和有限开发例外。正式包仍使用包内入口，不放宽 iframe 资源或实例桥接边界。每一层连接按自己的生命周期清理，文档刷新不代表重新执行业务。

<a id="stop"></a>

## 退出、诊断与验证

应用退出后，工具停止编译监听、服务器和连接。工具主动停止时，由唯一启动器请求应用走共同退出流程，仍被使用的资源不能提前删除。退出被取消时明确报告，并保留尚在使用的资源。强制结束只适用于明确由该开发会话拥有的进程，不能靠清空 .local 恢复状态。

终端展示构建、连接、重载和逐项激活的结果，应用展示真实运行状态。普通保存不重复发送业务 Toast，也不能通过解析日志恢复运行状态。开发工具提供 source map、显式 Node inspector 和 Webview 调试入口，调试参数只作用于实际进程，不写入正式包。

验证必须覆盖首次启动、编译错误修复、连续保存与多扩展、激活失败后修复、页面重建与 Dialog 结束、配置变化、连接失败和完整退出。编译监听、IPC 与资源生命周期应在真实 Electron 的各支持平台核对。

## 脚手架与仓库外使用

模板提供基本 Node、Node 加框架无关 Webview，以及 Node 加官方 Solid/ui 三种结构。provider、译本和主题示例复用这些结构。生成内容包括源码、声明、必要依赖、构建配置、脚本，以及开发、发布和兼容说明，可以与 workspace 及按需选用的 hooks、版本工具组合。

模板提供运行与构建起点：Node-only 模板使用 src/entry.ts，Node 加 Webview 的两种模板分别组织 src/node 与 src/webview，共用纯合同放在 src/shared。官方扩展使用哪种结构、提供哪些页面与业务模块，必须在其[逐项设计](../../implementation/status.md#design)中明确；模板不能代替这些决定，也不生成账号、导入或同步的空模块。

项目只声明实际导入的包和框架。运行类型从 SDK 的公共作者入口取得，UI、视觉和工具能力分别从其正式入口取得。模板不预装全部八个包，不要求作者直接依赖 desktop-contracts 或 rpc，也不生成私有路径或跨包 src alias。官方 UI 基于 Solid，第三方扩展可以使用 Vue 等其他框架。

必须使用真实 tarball 在仓库外验证安装，并覆盖独立项目、工作区成员、类型检查、开发、build、pack 和真实 .kisx 安装。仓库维护流程还要验证在没有源码的情况下维护 registry。重点检查作者类型入口、Node、Webview、CSS、Solid peer 和 CLI 模板，确保 API 能被 SDK 完整消费，且 SDK 不直接依赖 desktop-contracts。dist 目录存在本身不能证明公开包可用。
