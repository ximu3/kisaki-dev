# 本地持有与文件身份

library.holdings 管理四类 Work 与用户本地内容的联系。作品内容目录保存用户登记的本地位置，动画、漫画和小说还从中持续发现文件；文件或启动配置表示实际使用目标。目录、文件和配置分别直接属于作品，各有稳定身份，文件系统位置使用绝对路径。登记持有或删除资料，都不会隐式改动用户文件的字节。

本文说明目录、文件和启动配置的登记，以及关联与使用目标的选择。[文件识别](file-recognition.md)定义命名规则和分部匹配，[文件维护](file-maintenance.md)定义刷新、重定位与重复登记修复。

<a id="directories"></a>

## 作品内容目录

四类作品分别保存自己的目录记录，每行标识该作品的一处内容位置。作品可以拥有零个或多个同等地位的目录，也可以只登记目录外的文件或启动目标。目录直接属于作品，生命周期由持有管理，与扫描配置独立。

| 对象           | 表                | 所属作品外键                  | 专属用途                         |
| -------------- | ----------------- | ----------------------------- | -------------------------------- |
| GameDirectory  | game_directories  | game_id 引用 games.entry_id   | 游戏内容位置与明确的启动入口选择 |
| AnimeDirectory | anime_directories | anime_id 引用 animes.entry_id | 视频发现与已有分集、Extra 对应   |
| ComicDirectory | comic_directories | comic_id 引用 comics.entry_id | 阅读文件发现与已有卷、话对应     |
| NovelDirectory | novel_directories | novel_id 引用 novels.entry_id | 阅读文件发现与已有卷对应         |

四张表共同保存 id（TEXT 稳定主键）、所属作品外键（TEXT）、path（TEXT [规范绝对路径](file-maintenance.md#operations)），以及 created_at、updated_at（INTEGER，UTC 毫秒）。同一作品不能重复登记按[文件系统规则](file-maintenance.md#operations)等价的位置，但不设置跨作品的全局路径唯一约束。

AnimeDirectory、ComicDirectory 和 NovelDirectory 另有 definition，只保存经过语义校验的 JSON 目录发现范围、包含与排除条件；命名解释使用下方[文件识别方案](file-recognition.md#recognition-profiles)。三个目录表分别保存可空的 recognition_profile_id，引用同类方案，默认 NULL 表示仅使用内置识别规则。目录不内联方案副本，也不在方案之上叠加目录覆盖规则。GameDirectory 不保存这些文件发现设置或方案引用。共同的路径、枚举和规则执行机制可以复用，设置改变不删除已经登记的文件。

目录共同参与本地内容管理，不设置首选目录或持久的当前目录。按目录筛选文件只是视图选择，不切换实际内容，也不改变首选文件。动画、漫画和小说在同一作品下登记的内容目录互不包含，按规范路径检查；多个不同磁盘位置或互不包含的目录可以并列存在。该约束独立于深度和过滤，不能通过排除子树同时登记父、子目录，也不用于限制 scanner 的不同扫描配置。

新增目录、修改路径，以及合并作品等会改变目录归属或范围的写入，在同一提交中核对路径约束。冲突时明确指出已有目录，不擅自删除登记、修改过滤或选择一份方案。一个目录内部的多种命名结构，由其识别方案中的多条规则处理，不建立多目录结果合并或目录优先级。

普通子文件夹不自动成为目录记录，也不要求逐卷登记目录。一个图片目录已经构成实际阅读目标时，可以直接作为文件加入作品并关联已有卷；登记内容目录只表达从该位置持续发现文件的意图，不声称包含完整作品，也不创建卷或新的 Work。

多张磁盘，或分别存放 TV 与 BD 的目录，不会建立作品版本或另一套私人记录。混合多个作品的目录可以作为 scanner 的总范围，但不能仅因包含某作品文件，就把整个目录绑定给该作品。

在作品边界发现的独立文件可以作为新增输入；在已经明确归属的作品目录内发现内容，则沿用该作品。混合目录中的新文件不能自动追加给某个已有作品。

<a id="directory-discovery"></a>

## 目录范围与过滤

动画、漫画和小说的目录 definition 使用同一结构，只决定本目录遍历哪些路径、自动发现和登记哪些新文件，不保存识别规则或文件关联。内容目录的路径与方案引用分别确定已有文件的识别上下文，不由发现过滤选择或切换。

```ts
interface DirectoryDiscoveryDefinition {
  maxDepth: number | null
  include: readonly PathFilter[]
  exclude: readonly PathFilter[]
}
```

PathFilter 使用[相对路径过滤](scanner.md#path-filters)合同，不在 holdings 再定义另一份。新目录默认 `{ maxDepth: null, include: [], exclude: [] }`，表示不限层数递归发现。maxDepth 为 null 或大于等于 1 的安全整数；1 包含直接子项，2 再包含下一层，区别于 scanner 只接纳固定一层候选的 entryDepth。明确根本身符合图片阅读目标时深度为 0，不因 maxDepth 为 1 而被排除。

目录遍历只接纳符合深度、包含和排除条件，并且没有越过已确定读取边界的路径。被过滤的路径不进入本次发现流程，不据此登记新文件或运行新文件匹配。排除目录覆盖其子树；未遍历的路径不构成完整覆盖，不能因为本次没有看到它就把已有文件标为失联。

发现新文件与维护已登记文件是两个独立范围。过滤和深度调整不修改已有文件、关联、首选或位置，不停止其原有维护，也不更换识别方案。仅修改发现设置不触发已有文件重新关联。正常的文件核对、资料补齐或方案修改仍按[刷新规则](file-maintenance.md#refresh)维护已登记文件；空关联资格与非空关联保护均不由过滤决定。

即使路径被过滤，只要已登记文件仍位于这个内容目录内，命名解释就继续使用同一目录上下文，不能将它改作零散文件或回退到另一种识别。明确手动添加文件也不受自动发现过滤阻止。需要停止管理某份文件时，移除文件记录；同时排除实际路径可以防止后续自动重新发现，不建立隐藏黑名单或文件级禁止匹配状态。

目录本身形成的图片阅读目标与普通文件使用相同过滤合同；其页面和压缩包成员不作为新的发现候选。包含与排除不能用于绕过父子读取范围冲突，也不能将部分枚举当作已确认不存在其他子读物。

保存时严格校验完整 definition。损坏存储读取为带问题的不可用发现设置，不替换成不限层数的默认值，该目录停止新发现。已登记文件的维护不依赖这些发现设置；目录路径、方案引用与方案定义仍有效时，继续使用其原有识别上下文，不能将发现设置损坏解释成没有目录或没有方案。

由[恢复索引](backups.md#recovery)明确拥有的工作区不参加目录和文件发现；排除按真实注册路径判断，不按目录名称猜测。

<a id="registration"></a>

## 为已有作品登记本地内容

library.holdings.registerLocalContent 承接已经明确作品的一份目录或文件输入。它核对真实位置、作品归属和当前登记，复用各媒介的完整写入规则；不创建作品、不获取元数据，也不修改作品个人值。scanner 在 registerExistingContent 开启且取得准确身份对应后使用此入口，普通明确目标的调用使用同一规则。

```ts
type LocalContentInput = { type: 'directory' | 'file'; path: string }

interface LocalContentRegistrationResult {
  work: WorkRef
  registrations: readonly {
    type: 'directory' | 'file' | 'launchConfig'
    id: string
    outcome: 'registered' | 'alreadyRegistered'
  }[]
  issues: readonly (
    | { code: 'initialRefreshFailed'; error: ErrorSummary }
    | { code: 'launchConfigIncomplete'; launchConfigId: string }
  )[]
}
```

registerLocalContent(work, input, options?, execution?) 返回 Promise<LocalContentRegistrationResult>。work 为明确 WorkRef；input.path 是规范绝对路径；options 只含可选的 expectedIdentities: readonly ExternalIdentity[]，提供时必须非空。execution 使用共同的取消与调用归属合同。scanner 必须传入 AddResult.matchedIdentities；在最终登记事务中核对它们仍全部绑定到同一 work，变化或冲突时失败，不转投另一作品。

| 输入与作品              | 完整登记行为                                                                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 任一 Work 的 directory  | 复用同位置的本作品目录，或新增对应目录；动画、漫画、小说使用默认发现设置与内置识别，游戏只登记 GameDirectory                                                                       |
| 动画、漫画或小说的 file | 核对真实受支持文件或图片阅读目标，复用已有位置或新增文件；新文件以 automatic 开始，按当前规则匹配已有分部                                                                          |
| 游戏的 file             | 只接纳明确可作为系统文件启动目标的文件；已有同目标文件启动配置时返回这些配置，不改名称、监测、首选或存档设置；没有时创建一份文件启动配置，名称取实际文件名，监测仍须按游戏合同补齐 |

registrations 非空，返回本次实际登记或复用的身份。游戏同目标存在多套配置时全部返回 alreadyRegistered，不挑选一项作为首选。目录包含冲突、文件身份冲突或类型不符时不写入。已有目录、文件与配置的关联方式、关联、首选、位置、规则和私人设置保持原值。

新登记目录或文件在提交后完成适用的首次本地核对，失败时保留已提交登记，并以 initialRefreshFailed 说明；已有登记直接返回，不因扫描重复发现而重做首次刷新。游戏配置尚缺监测条件时返回 launchConfigIncomplete，界面可打开实际配置，不报告已经可以启动。登记从不启动游戏、播放或阅读内容。

目标缺失为 NotFound，类型或归属不符为 InvalidReference，输入结构错误为 InvalidInput，已确认身份改变为 Conflict，位置不可访问为 FileUnavailable，位置关系无法确认为 PathUnresolved，登记或目录范围冲突为 PathConflict。取消或失败发生在提交前时不留下新登记；提交后发生时，通过 ExecutionFailure.partialResult 保留实际登记结果。文件准备在事务外，提交前再次检查必要位置依据、身份和使用占用。

同一作品、同一输入的重复登记只复用已存在记录；不同作品不因路径相同而合并。并发登记复用相同唯一约束和短事务，scanner 不维护自己的登记副本。新作品的初始登记仍随 library.writeGraph 与作品共同提交，不先新增作品再调用本接口补齐。

## 使用目标与分部对应

发现流程先识别实际可读目标，再确定它对应的逻辑分部。漫画与小说使用共同的阅读格式支持范围，不按作品类别排除固定页面或可重排内容。普通文件分别登记；图片目录整体形成一个 ComicFile 或 NovelFile，不逐页登记。具体文件类型只表达所属作品与记录归属。

自动识别图片目录时，要求该目录直接包含图片，且没有下级独立阅读目标。如果根目录图片与子读物混合，不能同时登记父子范围；明确的子目标正常处理，剩余范围交由用户选择。手动登记的图片目录形成读取边界，后续刷新不再拆分其内部。

文件直接属于作品，可以没有直接分部关联，也可以关联多个分部。已经指定本地 Part 时先核对归属；具有规范 ExternalIdentity 时查询实际绑定；其他情况再按[有序规则](file-recognition.md#recognition-rules)、[编号比较](file-recognition.md#number-label-matching)和[完整关联](file-recognition.md#recognition-ranges)，使用目录明确引用的识别方案及内置依据。只有对应唯一且无冲突时才能自动关联。

显式规则失效时保留问题，不能换另一种解释凑出结果。裸编号不能根据文件格式猜成卷或话，解释卷内话号前必须确定卷范围。

没有分部资料也可以登记和使用文件。发现流程不补造占位分部，不调用 provider 解释不明编号，也不请求资料新增。具体文件关系见 [小说](novels.md)、[漫画](comics.md) 和 [动画](anime.md)。

<a id="manual-files"></a>

## 手动添加与关联编辑

手动添加先明确所属作品，再核对本媒介支持的实际文件或图片文档。从作品文件列表添加时，登记文件并按当前规则匹配已有分部；合法文件没有分部对应，仍可保存和使用。从某一分集、卷或话的详情添加时，本次已经明确真实分部，校验它属于同一作品后直接建立所选关联，不用文件名否决这项明确选择。

同一作品中，同一规范绝对路径复用已有文件身份，不再次创建记录。普通添加保留已有文件的关联方式及关联；从分部详情明确添加时，增加本次选择的关联，并在同次提交中采用 manual，保留其他关联、文件位置及首选。已经存在的同一关联不重复创建，也不改变其属性；仅关联方式发生变化时，仍按实际修改发布失效通知。另一实际文件即使对应同一分部，仍拥有独立身份与位置。

关联编辑器读取文件的完整直接关联，使用真实分部引用保存明确的增加、移除或替换范围。漫画的卷关联与话关联分别呈现；卷内收录及直接文件话关联按各自事实读取。保存所用的集合覆盖完整编辑范围，目标通过稳定引用对应，筛选和显示顺序只影响呈现。

手动纠正关联不改变文件的所属作品，不创造分部、播放位置或完成记录。保存明确的关联增减、替换或清空时，同次采用 manual；清空后的空集合保持到用户再次明确修改，普通刷新不恢复已移除关联。只有明确添加内容目录，才改变后续目录发现范围；单个文件添加不附带登记父目录。

<a id="association-mode"></a>

## 自动匹配与手动关联

anime_files、comic_files 和 novel_files 各自保存 association_mode，使用非空 TEXT、默认 automatic，并以 CHECK 限定 automatic 或 manual。公共字段为 associationMode，值类型 FileAssociationMode 定义在 desktop-contracts/library/holdings。它表达后续自动采用是否获准，不记录关联来源或编辑历史；游戏没有这项字段。

| 值        | 普通刷新可以做什么                               | 已保存关联                           |
| --------- | ------------------------------------------------ | ------------------------------------ |
| automatic | 直接关联集合为空时，按当前有效规则完整匹配       | 非空集合继续保留，不因刷新重算或追加 |
| manual    | 继续核对文件可用性和技术事实，不自动采用分部关联 | 完整保留用户选择，包括明确空集合     |

新发现或仅按路径添加的文件使用 automatic。创建时明确给出分部关联，或通过关联编辑保存增减、替换、清空时，使用 manual；明确的空关联与未提供关联输入分别处理。重复添加已有路径不重置模式。导入明确采用的源关联同样属于显式选择，不因入口是扩展而恢复自动。

本篇“空关联核对”只处理 automatic 模式下的空集合。manual 文件仍参加可用性与技术事实维护，普通手动刷新也遵守这一采用资格。

用户可以暂停自动匹配，或恢复 automatic。切换只修改模式，不清空已有关系、位置或首选。恢复后，非空关联仍保持；空关联在自动刷新已开启时安排一次当前核对，关闭时由用户手动刷新。设置模式的完成条件是选择已提交，后续匹配通过正常刷新流程报告结果。

library.holdings.files.setAssociationMode 的公开参数如下：

```ts
type FileAssociationMode = 'automatic' | 'manual'

declare function setAssociationMode(
  work: EntryRef<'anime' | 'comic' | 'novel'>,
  fileId: string,
  input: {
    mode: FileAssociationMode
    expected?: { associationMode: FileAssociationMode }
  }
): Promise<void>
```

该操作核对文件的真实作品归属，在同一短事务比较提供的基线并保存。目标不存在为 NotFound，归属不符为 InvalidReference，模式非法为 InvalidInput，基线不符为 Conflict；无变化时成功且不发变更。UI 和 Node SDK 共用此入口。关联编辑同时比较原关联与模式，保存成功后一起形成新基线。单独切换模式不改变当前文件内容，可在使用期间执行；实际关联写入仍遵守文件使用占用。

“重新识别”采用本次合法计算结果，并保留原 associationMode。规则测试、预览、改路径、修改分部资料和应用重启同样保持该模式；恢复持续自动匹配通过对应的显式动作执行。分部删除或合并按完整操作维护引用并保留文件模式。模式无法解释时，停止自动采用，报告该字段不可用，其他可读内容继续呈现。

<a id="games"></a>

## 游戏目录与启动配置

GameDirectory 与 GameLaunchConfig 分别直接属于 Game，不在配置上保存 directory_id。游戏可以有目录而没有配置，也可以只有平台启动配置而没有目录。内容目录保存与打开游戏内容位置，配置保存如何启动和观察游戏；内部 DLL、纹理和音频不逐个成为持有对象，不创建 Game Part 或通用文件行。

目录候选新增成功时，随 Game 原子登记 GameDirectory，不会仅为保存目录生成空配置或未完成配置。输入已经明确指定启动文件，或可靠启动描述明确给出入口时，可以初始化对应配置。只有目录时，其中的可执行文件都是候选，即使只有一个也不默认采用；用户明确选择后再创建配置。没有依据的命令内容与存档路径保持未设置，普通刷新不创建或修改配置。

从内容目录创建启动配置时，自动将该目录填入目录监测目标；创建命令启动配置时，还可填入工作目录。之后各位置分别维护。其他新建情形由用户指定监测目标。文件与链接启动只使用各自的目标，命令工作目录留空时遵守[游戏启动](games.md#launch)的默认行为。

内容目录、启动目标、命令工作目录和存档路径分别服务发现、启动、执行环境与备份，可以相同，也可以位于彼此之外。多个配置可以共用位置，并保留不同的使用选择。目录登记和平台配置描述本地绑定；是否能够启动由实际启动结果确定，运行与进程监测由 sessions 负责。

<a id="selection"></a>

## 默认目标与目录入口

首选表示用户明确保存的默认配置或默认文件，本次显式选择不自动修改首选。正在使用的目标由会话表达，最近使用来自真实活动，不另存持久的当前配置、当前文件或当前目录。实际打开、继续与会话复用遵守 [sessions](sessions.md#open)，界面入口遵守[使用与位置操作](../ui/components.md#local-actions)。

作品级首选文件只指定直接文件入口的默认目标，不表示首选分集、卷、话或整套文件来源。分部入口按各自关联选择文件，继续入口固定真实使用过的具体文件。换用另一文件恢复其自身位置，不复制原文件位置。目录位置与文件首选分别维护，打开目录不触发播放、阅读或首选修改。

文件列表可以按目录筛选并多选已经关联分部的文件，然后执行“设为默认”。操作使用本次明确文件及其直接分部关联，不生成配对预览或独立向导。每个分部只能对应一份选中文件；同一分部选中多份文件、缺少合法直接关联或目标失效时，本次修改不提交，并指出具体冲突，不按路径或顺序代选。

合法配对在同一事务中核对并设置，取消相应分部的旧首选。未选范围保持原值，后续新增的文件或关联不继承这次选择，不建立目录级播放来源或版本模型。作品级单个默认文件仍按自己的入口设置，不与分部批量操作混用。

## 持有的内部组织

holdings 内部按 game、anime、comic 和 novel 划分四类作品的持有实现，使用与 parts 相同的媒介名称。各分支拥有相应正式数据、约束和完整操作，公共 API 按调用能力组织。游戏备份通过 library.holdings.backups 开放，实现位于 game/backups。

| 分支  | 主要职责                                                                                         |
| ----- | ------------------------------------------------------------------------------------------------ |
| game  | directories.ts 管理游戏内容目录，configuration.ts 管理启动与观察配置，backups 管理存档归档与恢复 |
| anime | 视频文件、Episode 与 Extra 的直接关联、首选、续播位置、保存的播放设置，以及识别和本地维护        |
| comic | 阅读文件、卷与话的直接关联、首选、续读位置、保存的阅读设置，以及识别和本地维护                   |
| novel | 阅读文件、卷的直接关联、首选、续读位置、保存的阅读设置，以及识别和本地维护                       |

动画、漫画和小说内部按目录与文件管理、关联与首选、位置与设置、识别方案，以及刷新、重新识别、重定位和监听生命周期组织实际职责。一个文件可以完整承担时保持单文件，需要多份逻辑协作时再拆为模块目录，各分支按实际需要安排文件。游戏持有管理启动配置与备份，启动配置由明确操作建立，普通目录发现不推断配置。

各媒介的识别模块拥有自己的内置命名解释、自定义目标校验和实际分部查找；方案管理也留在相应媒介中。动画识别区分分集与无结构化编号的附加内容，漫画识别区分卷、作品话号与卷内话号，小说只匹配真实卷。识别方案按目录明确选用，同类目录可以共用，也可以采用独立副本；不强制每部作品独占方案，也不把不同媒介的目标语义压成一套共同流程。

可终止的正则求值、捕获与模板展开，以及合同已经统一的编号比较等具体机制可以复用。各媒介的识别业务拥有作品范围、分部含义与关联采用规则，并调用所需共享机制；具有领域含义的纯规则同样由领域拥有。

refresh 负责发现新文件、维护已有文件，并匹配允许自动关联的空关联文件；reidentify 负责对明确选中的文件重新计算并采用合法的完整关联，未形成结果时保留原关联。文件的[关联方式](#association-mode)保存用户是否允许自动匹配的选择。relocation 维护明确选择的访问位置及稳定身份。各媒介拥有监听的业务范围和触发寿命，目录枚举、文件系统监听、格式探测与媒体读取等技术能力由 infrastructure.files 和 infrastructure.media 提供。

保存的续播、续读位置和使用设置属于 holdings，实际运行目标、临时控制及使用中的技术资源属于 sessions。分支组织不改变这条边界，也不把刷新、识别或方案编辑变成运行控制。
