# 本地文件维护与位置修复

文件维护在保留正式身份和用户选择的前提下，核对访问位置、修复登记并持续更新可用性。本篇定义路径等价、重定位、重复登记合并、刷新和重新识别；目录与关联模型见[本地持有](holdings.md)，命名解释见[文件识别](file-recognition.md)。

<a id="operations"></a>

## 绝对位置与明确整理

文件系统位置进入持有域时必须是绝对路径。确有相对路径输入的入口，先按自身明确的基准解析，不用进程工作目录或所属作品目录推测位置。平台 URL、命令文本和文件内位置遵守各自合同，不套用文件系统路径的规范化。目录外文件可以正常保存和核对，也不会因此自动把发现范围扩大到任意父目录。

路径文本按当前平台整理分隔符与点路径，去除非根路径末尾分隔符，Windows 盘符统一为大写。可能经过链接的 .. 必须保持实际解析含义，不能只折叠字符串后改读另一位置。目录名和文件名保留原文字与大小写，表示整理本身不证明两个名称是否等价。

路径相等与包含关系由 infrastructure.files 按实际文件系统的名称规则核对，目录去重、文件复用、重定位和目录上下文使用同一结果。Windows 可以逐目录启用大小写敏感，不能统一假设所有 Windows 名称等价，也不能将所有平台字符串直接精确比较。依据见 [Microsoft 路径规则](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)与[目录大小写设置](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)。

| 当次能够确认的事实                           | 比较与写入行为                                                         |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| 词法规范后为同一绝对位置                     | 复用同作品既有登记；不会因输入分隔符或盘符写法新增记录                 |
| 所在目录不区分大小写，两个名称实际等价       | 按同一位置复用，保留原记录身份与用户数据                               |
| 所在目录区分大小写，两个名字是不同目录项     | 按不同位置处理；不能全量转小写合并                                     |
| 位置暂不可用，差异又可能只来自名称等价规则   | 返回路径关系无法确认；保留现有记录，暂不新增可能重复的登记或采用重定位 |
| 外部文件系统条件改变，使已有登记发生位置冲突 | 保留各记录及私人数据，报告冲突，交给明确的修正操作                     |

包含判断按完整路径分量和相应目录规则执行，Books2 不属于 Books。对大小写不敏感的父目录，Books 与 books 使用同一包含范围；相应目录明确区分大小写时则保留差异。无法确认潜在包含关系时，不提交违反目录范围约束风险的新登记；普通查看、非路径字段编辑和已有记录留存继续成立。

核对结果表示当次位置事实。文件系统读取在事务外完成，短事务再次核对本体记录与所用路径依据；实际打开或刷新重新检查可用性，不把曾经可读当作永远可读。稳定 ID 不由路径、文件标识或比较键生成。硬链接的不同名称、显式链接入口和内容相同的文件，不因物理对象或 hash 相同而自动合并；移动仍使用明确的重定位或重新对应操作。

| 操作         | 明确效果                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------ |
| 添加内容目录 | 登记所属作品的位置；动画、漫画、小说由 holdings 识别并登记实际文件，游戏不据此生成启动配置 |
| 移除内容目录 | 移除这处目录登记及适用的发现范围，保留已登记文件、分部关联和游戏配置                       |
| 核对文件     | 刷新可访问性和技术事实，保留正式身份与用户关联                                             |
| 重新定位目录 | 根据明确的新根更新核对通过的当前位置，保留文件、配置和分部身份                             |
| 移除文件记录 | 沿用私人记录与历史留存规则，不隐式删除磁盘文件                                             |
| 删除扫描配置 | 停止后续发现与监听，保留已接纳执行及正式持有资料                                           |

重定位直接处理本次明确范围内的位置，核对失败的项目保留原路径并报告原因，不提供路径配对预览。文件、配置和分部身份保持，不能对自由文本或历史快照进行字符串替换。

移除文件记录后，只要实际文件仍位于发现范围且符合规则，后续就仍可重新发现。需要持续忽略时使用显式排除规则。作品内容目录在该作品的本地内容区管理。

<a id="relocation"></a>

## 文件与目录的重新定位

重新定位告诉应用同一份内容现在位于哪里，只修改正式记录中的访问位置。单文件重新定位固定原文件身份和用户选择的新路径，保留其关联、首选、位置与设置，以及标注和历史引用。另一版本、译本或新制文件应独立登记，不能借重定位继承原文件的位置；实际打开时仍须在当前内容中验证已保存定位。

目录重新定位固定用户选择的旧根和新根，按相对位置为旧根下已经登记的文件生成路径映射，核对后直接提交合法修改。已登记文件不受当前发现深度、包含或排除条件限制；根自身形成的图片文档也属于映射目标。旧根之外的文件不因同属作品而迁移。不通过重新发现创建另一批文件替代旧身份，也不增加逐项路径预览或配对确认。

同作品中实际保存的游戏配置路径和手动字幕路径，只在本次输入明确包含这些字段时一并按旧根与新根转换。游戏配置并不从属于内容目录，不能仅因目录路径变化就修改全部配置。完整命令、正文中的路径文字、URL、活动与备份的发生时快照不参加前缀替换。

目标不存在、不可读取或存在登记冲突时，分别报告未验证、不可访问或冲突，不能显示为已经找到，也不按同名、大小、时间或单一 hash 另选替代。未形成可采用对应的项目保留原位置，不自动覆盖或合并另一份文件记录。结果须说明哪些位置已更新、哪些仍待处理，不能仅因目录记录已更新就声称全部文件已恢复。

采用前重新核对选定记录的原位置、归属、目标路径约束与使用占用，同一批选定的有效映射作为一次短事务提交。新的内容目录路径仍须满足该媒介的唯一性及不相互包含约束。路径相关的识别上下文可以因此变化，已有非空分部关联不重新解释；后续空关联核对按当前正式路径与方案进行。

磁盘文件的移动、复制和删除各有明确操作含义，不能由重定位记录隐式执行。原路径暂时不可读取不证明发生了移动，普通刷新保留记录和实际观察问题，不自动启动重定位。

<a id="external-path-changes"></a>

## 应用外的改名与移动

应用外的改名或移动不使普通刷新自动更新已登记目录、文件或配置的访问位置。保留原记录身份、路径、分部关联、首选、位置与历史，按原位置的实际核对结果更新可访问性。监听中的改名事件只用于安排范围核对，不授予迁移记录的权限；不根据文件名、大小、时间、内容 hash 或其他观察结果自动继承旧身份。

新位置落入已登记内容目录的发现范围时，按正常发现规则处理。同一规范位置已经登记就复用对应记录；尚未登记则建立独立文件，可以按当前规则关联同一分部，但不继承另一位置的文件身份、使用位置或首选。位于全部发现范围之外的新位置，不因旧文件失联而被自动搜索或登记，也不自动扩大目录范围。

用户确认同一份内容的新位置后，使用明确重新定位保留原记录。新位置已对应另一条文件记录时，先报告冲突并保留双方；用户可以通过[合并文件登记](#file-merges)明确选择保留身份与实际位置。普通刷新与重定位不会自动替用户执行合并，相同分部关联也不证明两份文件内容相同。

原来的规范位置重新可访问时，核对可以恢复原记录的可用状态，这不构成移动或新建记录。目录整体在应用外改名或移动时，相关文件及配置也不会随之自动改写路径；明确的目录重定位仍须逐项核对本次选择的映射。

<a id="file-merges"></a>

## 合并重复文件登记

library.holdings.files.merge(work, { sourceFileId, targetFileId, path }) 用于用户确认两条登记实际描述同一份内容的修正。work 必须为动画、漫画或小说；两份文件都属于该作品，ID 不同，否则为 InvalidInput。targetFileId 是保留身份，path 明确选择两条记录之一的当前访问位置，其他路径为 InvalidInput；仅有新路径而没有重复登记时使用普通重定位。

操作返回 { fileId, removedFileId, path }，分别为实际保留身份、移除身份和采用位置。它只整理本体登记，不移动、覆盖或删除用户媒体。相同名称、分部、大小或 hash 不自动触发此操作；不同版本和译本仍应保持各自文件。

| 内容                           | 确定结果                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| 文件身份与当前位置             | 保留 targetFileId，采用用户明确的 path，并重新核对实际类型及可访问性                    |
| 续播／续读、定位编码与使用设置 | 保留 target 的完整值，包括空值；不取最新时间或复制 source 的坐标                        |
| 直接分部关联                   | 合并真实关联并按组合键去重，重复关系保留 target 属性；这次明确采用的完整集合使用 manual |
| 作品与分部首选                 | 原来指向 source 的首选重定向到 target，其他文件的既有首选不变；重复配对共同维护唯一性   |
| 标注与活动                     | 全部保留原记录 ID、内容和发生时快照，将文件引用迁到 target；位置在实际跳转时继续校验    |
| 文件备注                       | 相同内容保留一份，不同非空备注按 target、source 顺序分段保留                            |
| 观察事实                       | 按选中位置的本次核对更新，不用旧可用性冒充新位置已经可读                                |

准备期间固定两条记录和所选原路径，事务前完成实际文件核对；最终短事务重查路径依据、作品、全部引用与两份文件的使用占用，一起迁移并移除 source。保存前出现路径变化、第三份登记冲突或必要引用冲突时整项失败，不改选另一位置。任一文件不存在为 NotFound，类型／归属不符为 InvalidReference，占用为 InUse，路径关系无法确认或冲突按 PathUnresolved／PathConflict，其他并发依据变化为 Conflict。

界面从重定位冲突或文件列表进入，明确选择保留记录和实际位置，简要说明续读与设置保留哪一份、关联与历史怎样迁移。完成后可打开保留记录，不设置自动配对或按正文相似度去重。发布 holdingsChanged 时附 fileMerged: { sourceFileId, targetFileId }，相关文件、标注、活动和分部查询重新读取。

完整作品合并中，两份登记已经确认指向同一命名位置时，也沿这组内部取值与引用规则合并到保留作品的已有文件；原作品归属和全部引用共同提交。不同位置的文件正常迁入并保持各自身份，无法确认的冲突保留为失败。公开 files.merge 仍只接受同一作品，不通过串行公开操作制造中间归属。

<a id="refresh"></a>

## 观察、自动刷新与用户选择

“自动刷新本地内容”全局默认开启。用户可以关闭后台读取，手动刷新始终可用。刷新独立于 scanner 配置：启动或恢复后核对，平时按监听增量处理，对明确无法使用监听的范围按下述规则定期刷新。手动、监听与定时触发复用同一套本地内容刷新操作。

开启、启动或恢复自动刷新时，先接入能够建立的监听，再立即核对当前范围，并合并处理核对期间发生的变化。不能先完成一次遍历，再从那一刻才开始接收变化而留下遗漏窗口。手动刷新不依赖监听建立成功。

监听机制明确报告不支持、无法建立或当前监听失效时，对实际受影响范围安排定期刷新。上一轮刷新结束后等待 5 分钟再执行下一轮，同一范围不重叠运行，也不积压周期次数；首次开启、应用启动或恢复后的核对不等待这段间隔。只有实际可读取的范围才能完成发现和维护，目录不可访问时如实报告并保留已有记录，不能将读取失败解释为空目录。监听正常的其他范围仍按变化事件处理。

长时间没有事件不表示监听失效，也不能只根据网络路径等外观推断监听不可用。底层明确报告事件丢失或需要重新枚举时，合并安排一次受影响范围的刷新；仍有效的监听继续使用，不因此永久切换为定时方式。监听恢复后先接入监听并核对一次，再结束相应定期刷新。关闭自动刷新停止后续自动触发，手动刷新继续可用。

同一作品的手动、监听和后台请求合并或串行执行。提交前重新读取绑定与首选，避免旧观察覆盖用户的新决定。

目录发现按当前深度和过滤接纳新文件，已有文件维护直接使用已登记身份与路径。发现文件可以更新正向事实；确认缺失则需要充分可信的范围覆盖或对已有目标的可靠核对。被过滤或未遍历的路径不能据此判为失联。根目录离线、枚举失败和探测失败分别表达，技术信息未知不等于文件不存在。文件失联不删除 Entry、Part、关联、笔记、完成记录或活动。

首选文件失联时仍保留用户决定，实际使用时可以选择替代，但不能永久改写偏好。文件数据分别保存稳定身份、访问位置、观察事实、用户关联、首选、备注，以及最近核对结果与原因。普通观察可以更新技术事实和可访问性，却没有因此取得修改已定关联的权限。

| 操作             | 作用                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------- |
| 刷新本地内容     | 发现新文件，匹配 automatic 模式且直接关联为空的文件，核对已有文件的技术事实与可访问性 |
| 重新识别所选文件 | 对指定文件按当前规则重新计算并更新合法关联，失败项保留原值并报告                      |

新文件和已有文件只有在 associationMode 为 automatic、直接关联集合为空时，才具备普通刷新的自动匹配资格。初次失败或分部尚不存在时保留这一资格；用户手动清空后采用 manual，后续刷新保持空集合。模式的修改与恢复遵守[关联方式](holdings.md#association-mode)。

直接关联集合非空时，普通刷新不能增加、删除或替换关联。修改这些关联须通过明确的重新识别或编辑。

空集合判断覆盖文件的全部直接关联。例如漫画文件已关联卷时，集合即为非空，自动匹配不再补话；卷的收录关系仍与文件直接关联分开。

自动提交前，再次确认模式为 automatic、直接关联仍为空且匹配依据有效。用户已保存 manual 时，旧自动结果失去采用资格。

这项限制只针对同一文件。另一个新文件仍可以关联已有文件所对应的同一分部，同时保留旧文件、首选和记录；这些文件可以处于同一内容目录或不同目录。识别中的唯一对应约束每个声明目标的分部身份，不限制同一分部的关联文件数量，也不将多个文件指向同一分部视为识别冲突。

自动刷新开启时，分部资料、目录路径或登记、方案引用及共享识别方案的定义修改成功后，合并调度实际受影响目录及作品的空关联核对，不必等待磁盘变化。仅修改深度、包含或排除条件，只按新设置安排目录发现，不因此重做已有文件关联；已登记文件原有的维护与空关联匹配规则仍正常生效。旧的未匹配结果不能阻止使用新依据。核对不获取资料，也不反向调用 ingest。关闭自动刷新时，手动刷新仍使用当前规则。

分部变化触发的是已有文件的本地维护。holdings 根据成功提交的实际变化合并核对请求，更新来源不改变这项行为：从资料源补充分部清单、手动创建分部或更正匹配依据，都在相关事实提交后生效。没有实际资料变化的更新不额外触发这一轮核对，事务失败也不能发布可供采用的新依据。

这类核对只处理受影响作品中已登记、采用 automatic 且直接关联为空的文件，不重新遍历目录或扩大文件登记范围。资料提交与文件匹配分别完成；匹配没有结果、失败或等待使用占用时，保留已提交分部及文件原值，结果由本地维护说明。自动刷新关闭时不触发后续匹配，用户之后手动刷新仍遵守关联方式，明确重新识别则执行一次选定范围的计算与采用。关联提交后不反向获取来源清单，形成单向的资料变化与本地核对关系。

外部位置变化遵守[明确重新定位](#external-path-changes)的边界，普通刷新只报告观察到的事实。相同规范路径被新内容替换时，重新判断定位器是否适用，不因此自动迁移另一份文件的记录。格式识别和枚举属于技术机制，作品与分部归属、私人记录保留则由本体决定。

<a id="reidentify"></a>

## 重新识别所选文件

文件列表提供一个“重新识别”动作，统一处理明确选择的已登记文件。未关联是列表筛选与目标选择范围，不另设识别未关联文件的业务流程。所选文件仍使用当前作品、目录上下文与已保存方案；规则求值和已有分部查找沿用普通识别合同，不临时改换作品或方案。

文件的已有分部关联只作为待比较的原值，不作为本次预先指定的匹配目标；否则旧关联会覆盖重新计算的意图。用户在关联编辑中明确选择真实分部，与这里从当前命名规则重新计算分别处理。

重新识别计算结果后直接按下表执行，不先生成预览或等待采用。报告说明实际命中规则、关联修改和未处理原因，不承担配对选择。

| 识别结果                           | 采用语义                                 |
| ---------------------------------- | ---------------------------------------- |
| 完整且唯一的关联与原值不同         | 更新为规则得到的完整关联集合             |
| 关联与原值相同                     | 返回无变化，不重复改写                   |
| 未命中、分部缺失或多个匹配无法确定 | 保留原关联，报告对应原因，不用空集合替换 |
| 配置失效或执行失败                 | 保留原关联，报告失败                     |

没有识别结果不表示清空关联。用户需要清空或自行纠正时，使用普通关联编辑。多个声明目标仍须完整成立，不因仅找到其中一部分就生成可以采用的部分关联。

本次选定文件中已得到合法结果的关联修改在同一个短事务中提交，其他文件保留原值并进入结果报告，不再要求用户选择一遍计算结果。提交时核对文件归属、原关联、原关联方式及会改变的属性、目录上下文、方案定义和目标唯一性；必要依据已经变化或存在使用占用时，这批修改不提交并正常报错。关联方式保持原值，用户仍可另行恢复自动匹配。无关的资料或位置更新不扩大为整行冲突。提交前取消不改关联，已经提交的结果不因迟到取消撤回。

保留的关联继续保留自己的首选属性。移除关联时，同时取消依赖该关联的分部首选；新增关联默认不成为首选。作品级文件首选、文件位置、分部完成标记和既有活动不因重新识别而重写。普通关联纠正不追溯修改历史归属；实际身份更正与合并仍使用其独立操作。

<a id="file-use"></a>

## 使用期间的文件修改

正在打开、播放或阅读的文件，可以测试规则、查看识别结果及编辑草稿；实际改变该文件的分部关联、访问路径，或移除其记录前，须先结束受影响的文件会话。系统不为完成这些写入而静默关闭正在使用的内容，也不在同次使用过程中更换活动归属或自动完成判断依据。无变化的采用不制造占用冲突。

后台匹配遇到文件使用占用时，保留本次尚未提交的事实，不把它记作识别失败或清空关联。会话结束且自动刷新仍开启时，重新核对文件的关联方式和资格，再使用当时最新的资料与规则计算，不补交占用期间的旧结果。手动操作不能提交时明确说明使用占用，不保留一份稍后自动采用的用户关联修改。使用占用属于运行条件，不改变持久的关联方式。

占用核对与最终修改之间不留异步间隙。普通查看、资料文字编辑和仅影响后续打开的首选设置继续使用自身合同；游戏启动配置的后续编辑也不改写当前游戏会话已经固定的配置与存档来源快照。

<a id="execution"></a>

## 刷新与持续维护的执行组织

动画、漫画和小说各自按以下职责组织持有操作，文件名表达具体能力，公开 API 沿用所属持有合同。游戏持有按启动配置与备份的职责组织。

| 内部位置      | 负责内容                                                                   |
| ------------- | -------------------------------------------------------------------------- |
| watch.ts      | 持续观察与自动维护，拥有文件监听、适用定时器和自动触发的启停               |
| refresh.ts    | 接纳刷新请求，协调同一作品的在途与待处理范围，并执行发现、核对和空关联匹配 |
| reidentify.ts | 对明确选择的文件重新计算关联，核对采用依据并完成对应提交                   |
| relocation.ts | 核对明确的新访问位置，保留正式身份并提交合法位置修改                       |

watch 根据自动刷新偏好及实际变化决定是否请求维护，调用与手动入口相同的 refresh 能力。app 集中建立相关固定跨模块订阅，通过已声明的事件或变化合同将输入交给所属媒介的完整处理入口，由媒介判断影响范围；连接句柄由 app 持有，功能内部及实例范围的订阅、文件监听和定时器由 watch 建立并释放。首次接入、恢复和监听不可用时的行为遵守[刷新合同](#refresh)，不在装配层另写一套自动维护规则。

refresh 管理本媒介按作品区分的正在执行及待处理范围。同一作品的请求按实际覆盖能力合并或串行执行，执行期间到达且未被本轮可靠覆盖的变化进入后续核对，不能因已有执行就丢弃。手动调用须等待其请求范围得到实际处理并返回相应报告。目录发现与已有文件维护分别保留范围；分部资料变化只安排相关空关联核对，不扩大为目录遍历。

请求协调与一轮执行属于同一个刷新能力，先在 refresh.ts 内保持清楚的职责和状态归属，实际协作复杂度需要时再拆分。排队与取消等明确同义的机制可以复用，各媒介仍拥有识别语义、关联资格和提交规则。重新识别与重定位使用各自明确输入和结果，不混入普通刷新请求，普通字段编辑也不经刷新队列。

关闭自动刷新停止后续自动触发，手动刷新继续可用，已经接纳的工作按自身取消合同处理。应用退出时先停止新的触发，再等待或取消在途工作并释放资源；数据库在依赖它的收尾完成后关闭。文件使用占用由 sessions 的实际登记提供检查依据，后台等待在释放占用后按[使用期间的文件修改](#file-use)重新计算，不补交旧结果。
