# 作品关系、角色与参与者

资料图保存四类结构化关系：作品之间的直接关系、作品与角色的关联、人物在作品中的工作，以及组织对作品的参与。每一项关系都有明确的作品范围。作品页、角色页、人物页和组织页只是查看、编辑这些记录的不同入口，反向展示不另存镜像记录。

<a id="model"></a>

## 关系记录与身份

四张关系表分别表达以下事实：

| 表                      | 一行表达的事实                         | 业务唯一性                                                                           |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------------------------------ |
| work_character_links    | 角色与某作品的关联及本作定位           | (work_id, character_id)                                                              |
| work_person_links       | 人物在某作品中的一项工作，可具体到角色 | 无角色：(work_id, person_id, role)；有角色：(work_id, person_id, role, character_id) |
| work_organization_links | 组织在某作品中的一项参与               | (work_id, organization_id, role)                                                     |
| work_relations          | 两部作品之间的一项直接关系             | 方向规范化后的 (from_id, to_id, type)                                                |

每张表都使用非空的 TEXT id 作为稳定主键，并另外约束业务唯一性。修改作品、参与者、职责或角色限定时，记录仍保留原 id。表单据此识别正在编辑的记录，不用名称、顺序或其他可变字段代替身份。work_person_links 分别为有角色和无角色的工作建立条件唯一索引；NULL 既不是主键的一部分，也不代表一个占位角色。

作品角色的 role 为 main、supporting、cameo、other 或 NULL，表达角色在当前作品中的定位。它不参与业务唯一性，同一角色在不同作品中可以有不同定位；修改定位保留关联身份和人物职责。

角色设计等工作可以需要作品与角色关联。这项关联只确认作品范围，是否正式出场及其定位仍须各自有依据。

人物工作按实际职责逐项记录，也可以限定到一个角色。一人兼任编剧和配音、为两个角色配音，或者参与三部作品，都会形成相应的独立工作记录。模型不另设普通参与父行、角色工作子行或脱离作品的汇总关系。同一角色允许由多个人物承担原作语种的配音；年龄阶段等补充信息写入 note，不为此创建配音版本对象。

人物条目采用当前正式名称，艺名保存在 aliases；作品实际署名保存在对应工作关系的 note 中。人员列表显示统一人物名，关系详情呈现本作署名。同一业务键有多个署名时，在说明中一并保留，仍作为同一条关系管理。

人物、角色和组织可以独立编目。不过，脱离具体作品的创作、配音或背景联系不属于这里的结构化关系，也不能通过虚构作品来保存。两个主体具有共同背景，不足以证明其中一方参与了某部作品。合集成员、标签应用和正文引用则沿用各自的组合键，不为了形式一致而增加关系 id。

<a id="schema"></a>

## 作品关联的字段与约束

三类作品关联按各自用途使用下列字段：

| 字段                  | 类型与空值            | 适用范围与含义                                           |
| --------------------- | --------------------- | -------------------------------------------------------- |
| id                    | TEXT，必填            | 关系主键                                                 |
| work_id               | TEXT，必填            | 实际作品                                                 |
| work_type             | TEXT，必填            | 本体取得的 game、anime、comic、novel 之一                |
| character_id          | TEXT                  | 作品角色表必填；人员工作表可空；组织参与表不设置         |
| person_id             | TEXT，必填            | 仅人员工作表                                             |
| organization_id       | TEXT，必填            | 仅组织参与表                                             |
| role                  | TEXT                  | 作品角色分类可空；人员与组织职责必填                     |
| note                  | TEXT，可空            | 当前关系的说明                                           |
| is_spoiler            | INTEGER，必填，默认 0 | 仅允许 0 或 1                                            |
| order_in_work         | INTEGER，必填，默认 0 | 作品侧相应列表的排列                                     |
| order_in_character    | INTEGER，按所在表约束 | 作品角色表中必填；人员工作表中有角色时必填、无角色时为空 |
| order_in_person       | INTEGER，必填，默认 0 | 人员工作表中的人物侧排列                                 |
| order_in_organization | INTEGER，必填，默认 0 | 组织参与表中的组织侧作品排列                             |

每张关系表保存自身需要的端点和排序字段。人物工作中的 character_id 与 order_in_character 必须同时为空或同时有值。未指定角色时，角色侧顺序默认为 NULL；指定角色时，由新增或编辑操作计算追加位置。作品内某个角色的人员列表直接使用该作品人员顺序中对应的部分。

三张表都以 (work_id, work_type) 引用 entries(id, type)，并通过 CHECK 将作品类型限定为 game、anime、comic、novel。人物、组织和角色端点分别引用 persons、organizations、characters 的 entry_id。指定了角色的人物工作还必须以 (work_id, character_id) 引用 work_character_links 的业务唯一键，从而保证角色确实关联当前作品；只验证作品和角色分别存在并不充分。

人工顺序使用非负安全整数。虽然数据库默认值为 0，正常新增仍应计算并追加到列表末尾，不将每一项都插到开头。顺序相同时按稳定 id 排列。保存时同时检查职责适用的作品类型和角色范围。索引覆盖业务唯一性、反向端点、作品与角色的组合，以及各侧人工顺序。

删除一个端点会移除引用它的关系。删除作品角色关联时，依赖该关联的具体角色工作也随之删除，不能通过 SET NULL 将它们改成无角色工作。用户主动清空某项工作的角色则是另一种编辑：保留工作 id，并检查清空后是否与已有记录冲突。删除关系不会删除它连接的条目；更正端点或职责时，相关引用与唯一性必须在同一次同步操作中维护。

## 两部作品之间的直接关系

合集用于组织一组内容，直接关系用于说明两部作品的具体联系。两部作品也可以组成合集，成员数量不决定应使用哪种模型。同一作品可以属于多个合集；系列、世界观、推荐清单或个人记忆都不会形成唯一的系列父层，也不会自动生成成员之间的关系。

关系 (A, B, sequel) 表示 B 是 A 的续作。在 B 的页面中，同一记录以反向类型 prequel 展示，无需再写一行。方向类型及其反向含义如下：

| 从 A 看 B 的类型 | B 与 A 的含义                       | 从 B 看 A 的反向类型 |
| ---------------- | ----------------------------------- | -------------------- |
| sequel           | B 是 A 的续作                       | prequel              |
| sideStory        | B 是 A 的外传或补充故事             | mainStory            |
| spinOff          | B 是从 A 衍生的独立作品             | spinOffOrigin        |
| summary          | B 是对 A 的总集或内容压缩           | fullStory            |
| adaptation       | B 是对 A 的改编                     | sourceMaterial       |
| remake           | B 是 A 的重制作品                   | remakeSource         |
| remaster         | B 是基于 A 修复或高清化的再发行作品 | remasterSource       |
| port             | B 是由 A 移植而来的游戏作品         | portSource           |
| expansion        | B 是针对 A 的游戏扩展作品           | baseGame             |
| compilation      | B 是收录了 A 的合编作品             | includedWork         |

前后作、外传、衍生、总集、改编和合编可用于四类作品之间有意义的组合。remake、remaster 及其反向类型要求两端作品类型相同；port、expansion 及其反向类型只用于游戏。关系的两端必须是已独立管理的作品。文件、字幕、平台入口、启动配置、购买包和用户合集不会因为需要描述联系而变成新作品。

sideStory 包含对本篇的故事补充。例如，游戏原作与其 Fandisc 使用 sideStory／mainStory，并在 note 中保留 Fandisc 的具体称谓；两个读取方向对应同一条正式关系，不因来源叫法不同而新增关系类型。

另外两种直接关系及跨作品类型的表示方式如下：

| 表达内容         | 正式表示           | 含义与范围                                                           |
| ---------------- | ------------------ | -------------------------------------------------------------------- |
| 不同演绎         | alternativeVersion | 对应故事或内容基础的另一种展开与演绎，两侧含义相同                   |
| 跨作品类型的联系 | 端点类型与实际关系 | 两端类型通过查询取得，使用实际关系或 related；不设置 crossMedia 类型 |
| 普通关联         | related            | 用户明确建立或来源明确给出的直接联系，可以附加说明                   |

alternativeVersion 要求存在明确的另一种故事展开或内容演绎，两侧含义相同。仅仅同属系列、出自同一作者、使用相同角色或改编自同一原作，都不足以推导这种关系；已知更具体的联系时，应使用具体类型。格式或清晰度不同的文件仍属于 holdings。系统通过端点类型识别跨媒体联系，不保存 crossMedia 类型。能够确认直接联系、却无法确定改编方向时，可以使用 related 并补充说明，不另设未知方向类型。

用户可以主动建立 related，note 也可以留空，不必提交来源证明。自动采用来源资料时则必须确认来源表达的是直接联系，不能将未知枚举、请求失败或算法推荐转换成 related。后来取得更具体的关系，也不会自动删除已有普通关联及其说明。

work_relations 保存以下字段：

| 字段          | 含义                                           |
| ------------- | ---------------------------------------------- |
| id            | 稳定的关系记录身份                             |
| from_id       | 规范方向的起点作品 ID                          |
| from_type     | 该作品的真实作品类型，用于数据库端点约束       |
| to_id         | 规范方向的终点作品 ID                          |
| to_type       | 相关作品的真实作品类型，用于数据库端点约束     |
| type          | 从 from 看向 to 的规范关系类型，必填           |
| note          | 本条关系的说明，可空文本                       |
| order_in_from | 在 from 作品关系列表中的排列，非负整数，默认 0 |
| order_in_to   | 在 to 作品关系列表中的排列，非负整数，默认 0   |

除 note 外，所有字段都不能为空。两个排列字段各自使用非负安全整数，默认 0。两端通过真实的 (id, type) 复合外键引用 entries，类型限于四类作品，且禁止自指。索引分别支持两端的关系列表和人工顺序，关系表不额外增加时间戳或另一层身份。

有方向的关系按上表左列类型存储。写入 prequel 等反向表达时，交换两端并转换为对应的规范类型。例如，(B, A, prequel) 与 (A, B, sequel) 形成相同的业务键。alternativeVersion 和 related 两种对称关系按本地 ID 的 UTF-8 字节序排列端点；这只决定存储形状，不决定展示顺序。schema 限定规范类型，并对对称关系约束端点顺序，再以 UNIQUE(from_id, to_id, type) 保证同一事实只保存一次。不同类型的真实联系仍可并存。

## 共同身份与双向编辑

一项作品联系只有一个 id 和一份 note。A 页显示“B 是续作”，B 页显示“A 是前作”，两边读取和编辑同一记录。新增、查重、资料采用和条目合并共用方向规范化规则，不因读取端或来源表达方向相反而建立第二份记录。重复创建按业务键冲突处理；资料采用复用已经对应的关系身份。

order_in_from 和 order_in_to 分别管理两端列表的顺序。修改一侧排列保留另一侧；规范化交换存储端点时，排列值仍跟随实际作品。更正关系类型或端点保留 id，未变端点的顺序继续保留，新增端点按正常规则追加。编辑时核对实际字段、端点和当前侧顺序的基线，不用整部作品的 updated_at 锁住所有关系操作。

资料更新的范围由实际目标和本次选择决定，不按存储中的 from 一侧划分所有权。更新 A 的作品联系时，只处理与 A 直接相连且属于所选关系范围的记录，不扩展到 B 与其他作品的联系。属性更新作用于同一份关系资料，替换明确范围会使被移除的联系同时从两端消失；新增和已有关系分别遵守追加与保留各侧顺序的规则。来源未回答、请求失败、集合不完整或端点未能对应时，仍不得据此清除关系。关系两端必须是已经确认或本次明确创建的作品，采用不递归扩展资料图。

更正端点或类型后，先按规范方向检查业务键。若与另一条既有关系重复，本次更新返回 Conflict，原关系及既有关系的身份、说明和两端顺序均保持。资料采用仍复用已经对应的关系身份。明确的条目合并重映射端点后重新规范方向，移除自指，并按[固定合并规则](#transactions)处理重复，保留说明及各侧顺序。

从任一端删除关系，都删除同一记录，两端视图随之更新。删除某种关系不影响同一对作品的其他关系，解除全部联系必须明确覆盖范围。删除不阻止来源在之后的明确资料采用中再次提供该关系。

## 人物与组织的职责

职责使用有助于浏览和筛选的常用分类。同义工作使用同一代码，界面则按作品媒介选择自然的文案。表单、本体和数据库都要验证职责与作品类型的组合，不能仅靠界面隐藏选项来保证有效性。

人物职责及其适用范围如下：

| 值                | 界面含义             | 适用作品类型     |
| ----------------- | -------------------- | ---------------- |
| creator           | 作者／创作者         | 四类作品         |
| characterCreator  | 角色创作             | 四类作品         |
| originalCreator   | 原作／原案           | 四类作品         |
| director          | 导演／监督           | 游戏、动画       |
| scenario          | 编剧／脚本           | 游戏、动画、漫画 |
| seriesComposition | 系列构成             | 动画             |
| direction         | 演出                 | 游戏、动画       |
| storyboard        | 分镜                 | 游戏、动画、漫画 |
| characterDesign   | 角色设计             | 四类作品         |
| illustration      | 插画；游戏中可称原画 | 四类作品         |
| drawing           | 作画                 | 游戏、动画、漫画 |
| animationDirector | 作画监督             | 游戏、动画       |
| art               | 美术                 | 四类作品         |
| photography       | 摄影／合成           | 游戏、动画       |
| sound             | 音响                 | 游戏、动画       |
| music             | 音乐                 | 游戏、动画       |
| programmer        | 程序开发             | 游戏             |
| producer          | 制作人               | 游戏、动画       |
| publisher         | 出版／发行           | 四类作品         |
| translator        | 翻译／本地化         | 四类作品         |
| editor            | 编辑／剪辑           | 四类作品         |
| voiceActor        | 配音                 | 游戏、动画       |
| other             | 其他参与             | 四类作品         |

creator 表示当前作品的作者或创作主体，包括以个人身份署名的游戏开发方。人物不另设 developer；programmer 只表示明确的程序编写工作，不能由开发方署名推导。同一人有两种明确署名时，可以同时记录 creator 与 programmer。

人物与组织的 publisher 都表示明确的出版或发行责任。个人创作与个人发行分别按实际署名记录，不能由 creator 推导 publisher，也不能由 publisher 推导创作或制作人职责。个人明确承担两种职责时，可以同时记录；作品类型和角色限定仍遵守本节规则。

characterCreator 表示角色创作，originalCreator 表示原作、原案等内容基础。这些署名不能互相推导，也不能证明资料库中一定存在另一部原作作品。scenario 表示实际编写脚本，原作署名本身不代表参与改编脚本。director、direction、storyboard、seriesComposition 分别表示导演、演出、分镜和动画系列构成；系列构成与合集没有关系。

drawing 用于漫画正文、动画作画等工作，illustration 用于插画、封面、立绘和 CG。动画署名中的“原画”通常属于 drawing；游戏中的“原画”则应按实际插画或设计含义映射。同一作品可以同时记录两项职责，但任何一项都不等于负责整个动画制作。角色设计和图像绘制也不能互相推导。总监督、助理、协力、作曲、编曲、演唱、责任编辑和剪辑等细项保留在 note，不为每个前后缀创建职责类型。

组织职责及其适用范围如下：

| 值              | 界面含义       | 适用作品类型 |
| --------------- | -------------- | ------------ |
| creator         | 作者／创作者   | 四类作品     |
| originalCreator | 原作／原案     | 四类作品     |
| developer       | 开发           | 游戏         |
| studio          | 动画制作       | 游戏、动画   |
| producer        | 企划／出品     | 游戏、动画   |
| music           | 音乐制作       | 游戏、动画   |
| sound           | 音响制作       | 游戏、动画   |
| publisher       | 出版／发行     | 四类作品     |
| distributor     | 经销／发行协助 | 四类作品     |
| imprint         | 出版品牌       | 漫画、小说   |
| localization    | 翻译／本地化   | 四类作品     |
| other           | 其他参与       | 四类作品     |

组织职责依据署名和参与事实确定，组织本身可以被署名为作者、原作或音乐制作方。publisher 表达出版或发行责任，distributor 表达经销或发行协助，适配器按来源语义选择。

imprint 引用出版品牌组织，localization 需要本地化参与证据。系列名称、文件发布组和组织通常从事的业务，都不足以单独确定这些职责；本地化参与也不表示版权授权。

素材品牌或服务以独立署名提供作品所用素材时，采用组织 other，并在 note 中说明音乐、图像等实际素材提供事实。素材被采用本身不能推导为本作直接创作或音乐制作，不因此建立经营者或素材作者的人物身份。

只有以下人物职责可以指定具体角色：

| 值               | 含义                             | 适用作品类型     |
| ---------------- | -------------------------------- | ---------------- |
| characterCreator | 角色创作，与整部作品作者区分     | 四类作品         |
| characterDesign  | 角色形象或设定设计               | 四类作品         |
| drawing          | 针对角色的作画工作               | 游戏、动画、漫画 |
| illustration     | 角色插画、立绘等图像绘制         | 四类作品         |
| voiceActor       | 作品中的配音工作                 | 游戏、动画       |
| other            | 已确认但未进一步分类的作品内工作 | 四类作品         |

这六项职责也允许不指定角色，并始终受各自作品类型的限制。其他职责必须保持角色为空。创作角色、设计角色和绘制角色图像是不同的工作，作品作者或美术署名不能自动关联全部角色。清空角色不会将 characterCreator 改为 creator。某人独立绘制同人图，也不能仅因角色出自作品 M 就记为参与 M。

other 用于已确认但尚未细分的作品内参与。note 可空，来源提供原始称谓时予以保留。职业介绍、推荐名单或获取失败均不构成作品参与事实。

职责映射结合媒介与署名语境解释“监督”“演出”等词。两项常用职责可以拆为两行；同一业务键下的细项合并到说明中，保留已有内容。note 供人阅读，分部引用、语言、排序、授权和执行仍使用各自正式字段或接口。

<a id="voice-scope"></a>

## 配音资料范围

voiceActor 只记录作品正式采用的原作语种角色—声优关系，不收录译配。原作语种以作品的原始创作语言为准。采用条件是作品归属与配音语种，不以首次发行的时间截断名单。

来源采用须依据实际配音语种、明确的原语种名单或该接入已确认的采用约定。未标语种的缺省必须在来源设计中写明依据与资料质量限制，不能视为所有来源共有的保证；VNDB 的具体约定见[原作语种配音](../extensions/sources/vndb.md#voice-scope)。声优母语和界面语言不用于推断配音语种，明确的译配记录不转存为 other 等职责。来源无法按既定规则判断所需范围时，按资料读取的完整性合同处理，不把未经筛选的混合语种名单称为原作语种名单。

<a id="editing"></a>

## 不同入口如何编辑同一记录

各入口对应的实际记录如下：

| 页面入口       | 实际表与范围                          | 编辑的内容                     |
| -------------- | ------------------------------------- | ------------------------------ |
| 作品的人物参与 | work_person_links，限定当前作品       | 人物、职责、可选角色及工作属性 |
| 人物的作品参与 | work_person_links，限定当前人物       | 作品、职责、可选角色及工作属性 |
| 人物的角色工作 | work_person_links，当前人物且角色非空 | 实际作品、角色、职责及工作属性 |
| 角色的相关人物 | work_person_links，限定当前角色       | 实际作品、人物、职责及工作属性 |
| 作品的角色关联 | work_character_links，限定当前作品    | 角色、作品内分类及关联属性     |
| 角色的作品关联 | work_character_links，限定当前角色    | 作品、作品内分类及关联属性     |

前四个入口编辑 work_person_links，后两个入口编辑 work_character_links。页面上下文只负责限定范围或预填目标。作品角色列表中的配音入口可以带入作品和角色打开工作编辑器，但作品角色关联不会因此成为其他资料的父容器。汇总中的一个人物或一部作品可能对应多项工作，编辑某项工作前必须展开或选定实际记录。

character_id 为空只表示这项工作没有指定角色，不表示负责全部角色、作品没有角色，或存在一个未知角色。只取得配音名单、或者需要记录旁白时，可以保存无角色工作。后来明确为原工作补选角色，应保留原 id；确认另一项角色工作则应新建。无角色和具体角色使用不同业务键，可以同时存在。

指定角色的操作必须同时确认作品角色关联已经存在，必要时补建，新增关联的分类留空。补建不能覆盖已有说明、剧透标记或排列，编辑或采用界面要呈现这项必要影响。清空角色时保留作品、职责、说明和仍适用的顺序，并检查无角色业务键是否冲突；这一编辑不删除作品角色关联。

删除工作会移除整行，不删除任何条目。移除作品角色关联会同时删除依赖它的具体角色工作，删除动作的简短说明包含这个范围，不增加逐条影响预览。其他角色、其他作品和原有无角色工作继续保留。切换职责后如果角色组合变得非法，保存失败并指出具体字段，保留草稿，不自动抹掉角色。

补选或清空角色可能使工作进入或离开某个角色筛选页，但作品和人物入口仍引用同一 id。反向展示或汇总结果本身不授权一次修改全部底层行。

<a id="transactions"></a>

## 提交、并发修改与重复处理

编辑器中的新增、修改、删除和重排先保存在当前草稿中，保存时一次提交，连同必要的关联补建和依赖移除一起生效。取消丢弃尚未提交的改动，保存失败则保留输入。同步提交前重新核对实际字段、引用、上下文和依赖集合，草稿与资产准备不能代替提交校验。

并发修改不同普通字段时可以保留双方结果。同一字段冲突，或作品、人物、角色、职责变化时，操作须重新核对；已删除记录保持删除。关系表单按[绑定基线](library-write-contracts.md#expected)核对原事实与实际修改的属性，重排按[完整顺序与子集位置](library-write-contracts.md#membership)核对成员和顺序，依赖删除核对完整影响范围。各操作以这些实际依赖确定冲突范围。

补选角色、更正职责或更换端点后，如果业务键与已有工作重合，本次保存按重复关系失败并指出已有关系，不自动合并或进入差异编辑。普通说明和关系删除仍由各自编辑操作完成。

明确的条目合并形成重复关系时，保留目标已有关系的 id 和排列；相同说明保留一份，不同说明保留为两段。任意一项涉及剧透时，合并结果继续隐藏剧透。没有重复业务键的关系追加到目标，不因同名人物或相似说明而合并。

用户选择的是要保留的实际内容，不需要理解技术 id。操作结果返回最终保留与移除记录的对应关系。用户可以通过明确编辑调整剧透标记，但自动去重不能降低原有保护程度。

<a id="ordering"></a>

## 各侧列表的人工顺序

每种关系分别保存以下顺序：

| 表                      | 排列字段                                                |
| ----------------------- | ------------------------------------------------------- |
| work_character_links    | order_in_work、order_in_character                       |
| work_person_links       | order_in_work、order_in_person、可空 order_in_character |
| work_organization_links | order_in_work、order_in_organization                    |
| work_relations          | order_in_from、order_in_to                              |

为工作补选角色时，该工作追加到角色的工作列表，作品侧和人物侧的顺序保持不变。清空角色时，同时清空角色侧顺序。更换端点只会使记录追加到新端点的列表，未变端点的顺序继续保留。作品内某个角色的人员列表使用作品人员顺序的对应子集。汇总浏览以第一条可见记录的位置确定汇总项位置，人工重排仍操作实际记录。

筛选后的重排只置换所选记录原来占据的位置。例如，原顺序为 A、B、C、D、E，选择 A、C、E 并改为 E、A、C 后，完整顺序应是 E、B、A、D、C。操作读取数据库中的完整范围，不能将已加载的一页当成全部成员。使用名称或日期排序时，用户须先切换到人工顺序才能拖动。正常新增追加到末尾，普通来源刷新保留人工顺序，同值按 id 确定先后。

<a id="adoption"></a>

## 资料采用的更新范围

来源结果按以下规则采用：

| 输入情况                         | 实际采用行为                                               |
| -------------------------------- | ---------------------------------------------------------- |
| 本地条目身份及关系业务键完全一致 | 更新同一记录，保留 id                                      |
| 已有无角色配音，本次取得具体角色 | 默认视为不同业务键；用户可在本地关系编辑中明确补全已有工作 |
| 来源缺席、失败或只取得部分名单   | 保留尚未回答和范围之外的资料                               |
| 已明确取得完整范围并选择替换     | 更新、追加和移除该范围内的实际记录                         |

NULL 不会匹配任意角色。相同人物和职责不足以证明粗略名单与某项具体角色工作是同一记录；只有用户在本地编辑中明确补全时，才将角色写入原工作。普通资料更新按[采用流程](metadata.md)直接执行，不在获取后增加预览步骤。

关系替换同时采用输入 relationScopes 与用户 scope。前者来自已完成的固定范围读取，后者限定本次修改；值形状和合成见[范围合同](metadata-contracts.md#relation-scopes)。局部参与事实可以通过 prepared 补充，完整范围需要相应来源依据。

采用先更新相同业务键并保留 ID 与人工顺序，再追加新项，最后移除授权范围内明确不保留的项。未知职责按缺少依据处理，已有明确职责保留。

作品联系在完成端点对应后，先规范方向，再比较业务键。更新任一端都使用同一关系记录；属性采用与集合替换的范围遵守[双向编辑](#maintenance)，不能把反向读取当作新增资格，也不为两端分别保存来源陈述。

<a id="visibility"></a>

## 可见范围与修改范围

展示、筛选、分组、计数、汇总和定位都使用同一组可见事实。具体角色工作同时受自身和作品角色关联的剧透标记约束，不能从另一个入口泄露隐藏工作。人物如果还有其他可见工作，仍可以出现在结果中。作品汇总按身份去重，详细编辑则保留每项职责，不为汇总补建作者或演员镜像。

目标被隐藏不等于查询条件失效。包含和排除条件继续按可见集合正常计算，既不强制返回空集，也不提示隐藏原因。没有可见结果时统一显示“当前可见范围内，没有相应记录。”用户可以主动选择包含剧透的范围；这个入口始终存在，不根据是否真的有隐藏内容决定是否提示。

动态合集保留原规则，仅在查询时按可见范围计算结果。引用真正失效、语法错误和读取失败分别报告。删除和合并按用户明确指定的完整范围执行，显示偏好不会缩小修改集合；简短确认说明这一范围，不展开剧透内容形成影响预览。查询条件详见[库查询](library-queries.md)。

<a id="parts"></a>

## 分部与作品参与的边界

小说卷、漫画卷与话、动画分集与附加内容各自拥有资料、所属关系、排列、文件、记录、链接和附件。人物、组织、角色及具体角色工作的关系统一归作品所有。模型不建立分部参与表，不给作品关系增加分部范围，也不通过 staff JSON、姓名文本或出版社文本保存另一套参与关系。

因此，产品不支持逐集履历、逐卷译者或出版组织比较，也不支持按分集角色与配音差异进行结构化查询或自动跟随。这些信息可以留在说明或来源页面中，但文字不能替代精确关联。这是分部模型的产品边界。

分部来源中的参与信息，只要在作品尺度下仍然准确，就可以采用为作品参与。例如，某人为动画 M 第 7 集的角色 C 配音，可以记录 M—人物—voiceActor—C，并在 note 中保留第 7 集的说明。这条记录不宣称该人物覆盖全部分集，不保存隐藏的分集引用，也不另建普通配音镜像。卷封面画师可按作品 illustration 采用，但不能据此推断其负责全作角色设计；卷后记作者也不能无依据地记为整部作品的 creator。

适配器按实际职责和目标决定能否形成作品关系。单集或单卷名单只证明其局部范围，不能用于替换整部作品名单。

无法准确映射的资料列入未采用说明，适用的文字或链接可以保留。文字是当时的来源说明，分部编号或顺序变化后不会自动重写。

分部页可以链接到所属作品的参与资料，但不能将它显示成该分部的独立名单。删除分部时处理分部自身资料、收录、文件、附件、来源和记录，不删除原本就属于作品的参与。公共 API 同样不提供分部参与的查询和写入。

<a id="example"></a>

## 示例：同一工作如何出现在不同页面

以下使用虚构资料说明记录归属。《星屿》和《星屿·动画》是两部独立作品，角色关联如下：

| id  | 作品      | 角色 | 本作分类 |
| --- | --------- | ---- | -------- |
| mc1 | 星屿      | 澪   | 主要角色 |
| mc2 | 星屿      | 千夏 | 配角     |
| mc3 | 星屿·动画 | 澪   | 配角     |

人物工作如下：

| id  | 作品      | 人物 | 职责     | 角色   | 说明               |
| --- | --------- | ---- | -------- | ------ | ------------------ |
| mp1 | 星屿      | 林悠 | 编剧     | 未指定 | 共通线             |
| mp2 | 星屿      | 林悠 | 配音     | 澪     | 少年时期           |
| mp3 | 星屿      | 林悠 | 配音     | 千夏   | —                  |
| mp4 | 星屿·动画 | 林悠 | 配音     | 澪     | —                  |
| mp5 | 星屿      | 白川 | 角色设计 | 澪     | 服装设计           |
| mp6 | 星屿      | 白川 | 角色创作 | 澪     | 本作角色设定       |
| mp7 | 星屿      | 夏岚 | 配音     | 未指定 | 仅取得本作配音名单 |

各入口读取同一组实际记录：

| 入口            | 显示的实际记录               | 主要编辑字段                   |
| --------------- | ---------------------------- | ------------------------------ |
| 星屿 → 人物参与 | mp1、mp2、mp3、mp5、mp6、mp7 | 人物、职责、可选角色、工作属性 |
| 林悠 → 作品参与 | mp1、mp2、mp3、mp4           | 作品、职责、可选角色、工作属性 |
| 林悠 → 角色工作 | mp2、mp3、mp4                | 实际作品、角色、职责、工作属性 |
| 澪 → 相关人物   | mp2、mp4、mp5、mp6           | 实际作品、人物、职责、工作属性 |
| 星屿 → 角色关联 | mc1、mc2                     | 角色、本作分类、关联属性       |
| 澪 → 作品关联   | mc1、mc3                     | 作品、本作分类、关联属性       |

下列操作分别以表中的初始状态为起点。修改 mp2 的说明后，作品、人物和角色入口都会显示新内容。为 mp7 补选凛时，工作仍使用 mp7，并在同次操作中补建分类为空的《星屿》—凛关联。清空 mp2 的角色时，它只离开澪的视图，仍是一项作品配音工作；提交前需要检查是否与已有无角色工作冲突。

删除 mp2 不影响 mc1 或其他工作。移除 mc1 则同时移除依赖它的 mp2、mp5、mp6，其他角色、动画作品和无角色工作继续保留。修改 mc1 的角色分类不会改变任何人物职责。林悠参与作品的汇总仍包含《星屿·动画》，即使他在那里只有具体角色工作；白川的角色设计和角色创作也不会让他自动成为整部作品的作者。
