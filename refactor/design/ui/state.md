# 视图状态、编辑草稿与加载

renderer 保存当前视图需要的查询快照和交互状态。正式数据、未提交草稿、主进程运行状态和技术资源各有拥有者，不能只根据组件是否挂载来决定它们的生命周期。

<a id="layers"></a>

## 界面代码分层

| 层                  | 例子                                                    | 依赖方向                                                    |
| ------------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| app                 | 路由、窗口根、宿主、全局装配                            | 组合场景、业务 UI 和设施                                    |
| features            | 统计页、库管理、导入向导、扩展管理场景                  | 使用 domain-ui 和设施，不导入另一个场景的内部组件与状态     |
| domain-ui           | EntryPicker、EntryDetails、EntryEditor、ActivitySummary | 理解产品对象，调用类型化 API；不依赖场景或 app              |
| 公共 desktop-ui     | 控件、图表、Markdown 与拖拽接入                         | 拥有通用呈现、交互及自身资源寿命，边界见[UI 包](package.md) |
| 应用 infrastructure | 窗口客户端、查询生命周期、通用弹窗宿主                  | 接入本窗口的能力与资源，不拥有领域保存规则或场景政策        |

domain-ui 是桌面应用私有的业务界面层。多个窗口共用的能力放在 renderer/domain-ui，单窗口能力留在对应窗口中，文件按业务职责组织。组件通过显式参数和窗口提供的狭窄接口接入，每个挂载实例独立拥有草稿、查询和资源。组件不能导入另一窗口的路由、客户端或当前选择。

<a id="editing-units"></a>

## 编辑对象与保存边界

表单以用户正在编辑的单个对象及其明确字段范围为单位。一个展示柜区块、扫描配置、资料关系或偏好配置各自拥有草稿；“保存”完成该范围的正式提交，成功结果不再等待父列表的第二次保存。对象边界由用途与操作含义决定，界面中的一行、数据库记录或 JSON 字段不直接决定表单粒度。

管理列表展示已保存快照，提供新增、编辑、删除、启停和排序。单项表单保存后刷新相应结果；删除、启停和重排分别完成所声明的操作。列表 Dialog 以关闭结束管理，不包裹总保存表单。取消某一项只放弃该项尚未保存的输入，关闭管理列表保留此前已完成的操作。

对象内部的条件、规则、链接等字段列表直接使用所属对象的草稿，不再建立一份等待总保存的列表草稿。复杂字段编辑器可以暂存当前输入，以“确定”结束本次编辑并交回字段值，取消只放弃本次字段编辑；正式保存仍由所属对象表单完成。独立打开的链接等单项管理入口则直接提交该项修改，存储为整体数组时由拥有者使用完整字段基线完成更新。

从表单打开另一个独立对象的管理或编辑入口时，两者各自保存。新建或修改主题、资料方案等对象已经成功后，关闭或取消原表单不撤回这些结果；原表单中的选择引用仍按自身草稿提交。管理入口与字段编辑器按实际任务区分，不因同在一个 Dialog 内就合并保存边界。

明确的批量创建、批量调整与引导采用可以把多项作为一次业务操作，以“创建”“应用并继续”等动作提交。选择与配置阶段复用字段控件和校验，操作按所属合同保持原子性或交付逐项结果。

<a id="drafts"></a>

## 显式保存与草稿生命周期

Note 以及 Entry、Part 的描述使用正常编辑、明确保存和保存快捷键。用户可以保存尚未写完的内容后继续编辑，无须达到某种发布条件。界面准确显示是否存在未保存修改；保存失败或冲突时，保留当前输入和必要资源。

只有离开会真正丢失草稿时，才提供保存、放弃和继续编辑。仍然保留编辑状态的普通切换不打断用户。未提交正文与图片属于运行期编辑资源，不建立持久恢复稿、恢复附件关系或恢复管理入口。正式保存将正文和真实图片引用一致提交；异常退出留下的暂存按[附件生命周期](../domains/attachments.md)清理。

崩溃、断电或强制结束后，上次成功保存之后的输入可能丢失，界面不承诺自动恢复。已保存数据的事务、附件一致性和文件替换恢复协议仍须完整保证，不能因没有写作恢复而放宽。

<a id="submissions"></a>

## 保存基线与后续输入

```ts
await metadata.profiles.update(profileId, {
  changes: { definition: nextDefinition },
  expected: { definition: originalDefinition },
})
```

每个操作分别规定 changes 的可写范围与 expected 允许比较的事实，不接受任意键或 JSON 路径。普通编辑按本次修改单位核对原值，接口明确允许的相关上下文则按自身合同提供；不能把详情投影中的所有字段都作为基线。definition 按整体核对原值，名称等独立字段分别核对。显示排序变化不能阻挡定义编辑。

点击保存时，固定本次提交内容和基线。成功后以实际提交值建立新基线；等待期间产生的新输入继续保留，旧响应不能覆盖它们。expected 可选只表示直接操作可以不带旧值条件，不会自动给表单提供并发保护。目标和业务不变量仍必须检查，完整规则见[条件提交](../domains/library/write/README.md#concurrency)。

<a id="queries"></a>

## 局部查询与响应式状态

进入视图时查询当前快照，相关提交发生后合并重查。刷新期间可保留可见旧结果，避免闪成空白。离开时释放查询，重新进入时重新读取。大列表保留可见和邻近区间，返回位置保存轻量锚点；查询数据的寿命属于当前视图。

视图使用本窗口的类型化客户端调用本体。查询基础设施只处理取消、串行或尾随重查、迟到结果防护和订阅清理，不持有业务快照。只读结果由视图拥有并传给子组件；独立区块确有需要时才自行查询。变更范围判断必须覆盖因修改而新进入查询条件的记录。

Solid 实现要明确区分响应式读取与初始化快照、只读结果与编辑草稿、view、dialog 和 window owner，以及窗口投影与主进程权威。模块顶层 signal 不能充当所有窗口共用的当前条目，也不能把全部 UI 状态持久化。

状态、异步读取和释放优先组合 Solid 现有的 signal、store、[createResource](https://docs.solidjs.com/reference/basic-reactivity/create-resource)和 [onCleanup](https://docs.solidjs.com/reference/lifecycle/on-cleanup)。按实际查询补充取消与失效重查，不重复维护框架已有的依赖追踪、加载状态或 owner 寿命。简单读取可直接接入，只有共同的实际行为才提取辅助能力。

<a id="loading"></a>

## 加载边界与体验验证

延迟加载按功能入口、完整编辑器、阅读引擎和大型报告划分。入口保持轻量，静态 barrel 不能重新引入重模块。局部历史、较重的关联内容或独立 tab 不阻塞详情首显；路由必需数据则明确显示加载状态。

列表通过有界读取和窗口化控制规模，不能用整库缓存弥补无界接口。无需将小按钮逐个异步加载，也不能用包数量衡量性能。验证应测量真实启动、导航、编辑器打开、滚动、阅读打开与关闭，以及常驻资源。
