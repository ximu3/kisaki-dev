# UnRAR Wasm 的读取、解码与释放验证

2026-10-19，官方 UnRAR 7.23 已通过实际 Wasm 构建，并在 Windows x64 的 Electron 44.5.1／Chromium 152.0.7977.130 中运行 28 个验证场景，全部符合各自的成功或预期失败断言。本目录同时保存后续 XML／CFI 试件复用的 Emscripten 工具链输入。

本实验未覆盖全部 RAR 特性或浏览器组合。特殊成员的拒绝只描述试件的实际行为。

后续的[成员引用验证](../kana-rar-members/member-references.md)已独立验证符号链接、硬链接、复制引用及受限目标解析。下文保留这 28 项基础试件当时的行为；后续构建与记录另存，没有覆盖本轮原始证据。

## 实际读取与输出路径

宿主接到范围请求后执行 HTTP `Range` 读取，检查 206、`Content-Range` 和实际长度，再把这一块字节交给 worker。试件只向虚拟文件系统登记文件名与长度，归档内容不放进 MEMFS。读取函数最多请求 64 KiB，实际场景中最大响应为 32 KiB。

WASI `fd_read` 由 [async-input.js](async-input.js) 整体异步化。暂停范围必须包括读取结果写回和文件位置推进，不能在同步 `FS.read` 的内部回调暂停后让外围副作用继续运行。接续后重新取得当前 Wasm 内存视图，避免内存增长使先前视图失效。

这轮首先发现并修正了两项桥接错误：未带模块名的 Asyncify 导入声明被解释为 `env.fd_read`，而实际导入属于 `wasi_snapshot_preview1`；把暂停放在 `stream_ops.read` 内部还会重复推进文件位置。最终使用 Emscripten 的 `__async: 'auto'` 标记覆盖整个读取调用。机制依据见 [Emscripten 异步接口文档](https://emscripten.org/docs/porting/asyncify.html#marking-js-library-functions-as-async)，最终结果来自实际解码而非文档推断。

UnRAR 的 `RAR_TEST` 输出回调可能一次提供很大的原生缓冲。本轮最大为 4,194,131 字节；[bridge.cpp](bridge.cpp) 每次只复制最多 64 KiB，等待宿主确认后才继续。所有场景中，同时等待确认的消息和宿主传输都最多为一个。不能将 64 KiB 的传输上限解释为原生解码器只占 64 KiB 内存。

成员名称通过扩展宽字符名称读取，再转换成 UTF-8。试件为名称分配明确上限，检测到可能截断时失败，未把 DLL 的短名称缓冲当作成员身份。RAR3 的日文路径、RAR5 的补充平面字符已与上游样本预期核对；更长名称与全部归档名称边界仍需补齐。

## 运行结果

| 范围               | 验证结果                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| RAR3／4／5         | 实际解码普通、solid、多 LZSS 块、ARM filter、BLAKE2 及加密样本；普通成员独立计算 CRC，指定样本另按上游已知内容核对                         |
| solid 选择读取     | 四个 4 KiB 成员全部解码，以及只交付最后一个成员；前置成员通过 `RAR_SKIP` 维持解码依赖，最后一个成员的 SHA-256 与独立生成的内容相同         |
| 内容及文件名加密   | RAR4 和 RAR5 的四种 solid 加密组合均成功；明文长度与独立预期 CRC 相符；缺密码返回 22，错误密码返回 24                                      |
| 四卷归档           | 9 个成员共 117,398 字节，分别符合上游已知 CRC；只提供第一卷时明确失败，未在缺卷处假报成功                                                  |
| 真实输出负载       | 19,842 字节的 RAR 样本解出 20,131,111 字节，按块写入 OPFS，并再次流式读取核对；Wasm 线性内存保持 32 MiB                                    |
| 大尺寸源的按需读取 | 把有效小归档后方补零，形成逻辑尺寸 512 MiB 的源；28 次范围读取共 861 字节，最大单次 377 字节；这只证明按需访问，没有替代真实大归档压力测试 |
| 内存耗尽           | 正常需要约 38.4 MiB 线性内存的 RAR5 加密样本，在 32 MiB 限额构建中返回 `ERAR_NO_MEMORY`（11），随后正常关闭                                |
| 损坏与截断         | 改坏压缩数据后，已输出 90,808 字节仍在最终阶段返回 12；这些临时字节全部丢弃，提交量为零。截断样本在头部读取阶段失败                        |
| 读取取消           | 在延迟的范围响应尚未返回时取消，底层 fetch 被中止；原生调用结束，待处理读取和传输归零                                                      |
| 输出取消           | 已暂存 5,376 字节后，在后续输出等待确认时取消；没有提交成员，OPFS 临时目录已移除                                                           |
| 关闭与重开         | 原生 close 成功，后续读取返回未打开，临时源节点移除；worker 终止后没有新的读取或消息，新 worker 可以再次成功读取同一归档                   |
| 强制终止           | 在解码操作已经开始后终止 worker，宿主待处理工作结束；没有据此宣称已穷尽所有长时间 CPU 解码路径的取消延迟                                   |
| 重定向成员         | RAR3／5 的符号链接、硬链接被识别并明确拒绝；对应内容解析与复制引用仍是未闭合项                                                             |

RAR5 加密 CRC 可能经过密钥处理，分卷首个头部的 CRC 也不能直接视为完整成员 CRC。因此，这两组场景使用上游已知明文或完整成员预期值检查，没有跳过内容验证。BLAKE2 由原生解码器执行，试件另算 CRC 核对已知内容。

内存数字指实际 Wasm 线性内存，不能作为浏览器进程总内存或 OPFS 内部缓存的测量。字典、解码工作区、传输、临时存储与最终图像解码仍须分别计入正式 reader 的资源预算。

## 对接入实现的约束

源读取、输出背压、取消状态与原生句柄由同一解码实例协调。每次只运行一个原生调用；取消通过实际操作状态识别，再按已确认的公开错误合同交付，不能仅凭取消后出现的原生读取错误改变原因。

临时输出在成员校验完成前不可发布。试件使用 OPFS 验证写入、确认、再次读取、失败清理和目录移除；正式实现仍需接到已确认的宿主临时存储合同，并落实缓存预算。试件为便于核对，整次解码成功后才提交结果，不意味着正常成员必须等待整份归档解完才能使用。

分卷只接受本次登记的源。缺卷回调必须拒绝不存在的卷，不能不断允许 UnRAR 重试同一个缺失路径。归档内成员路径也不能形成宿主文件写入路径。

基础试件结束时，链接、硬链接与复制引用的受限目标解析和循环处理尚未验证，后续结果见上述独立记录。目前仍须完成原始名称准入、更大真实归档、极端字典、输出与临时存储预算；长时间计算中的取消；Firefox／WebKit 与公开浏览器支持基线；正式打包后的资源部署和独立消费。MEMFS 元数据适配、密码提供器、公开错误映射及完整阅读生命周期也要在正式接入中验证。本轮不改变已确认的公开合同或独立项目实施状态。

## 复现入口

在仓库根目录使用 Python 与现有 Node 运行：

```powershell
python -B refactor/verification/evidence/kana-rar/prepare-toolchain.py
python -B refactor/verification/evidence/kana-rar/prepare-fixtures.py
python -B refactor/verification/evidence/kana-rar/build-probe.py
python -B refactor/verification/evidence/kana-rar/build-limited.py
python -B refactor/verification/evidence/kana-rar/run-browser.py
```

浏览器运行器沿用已记录的 Electron 44.5.1 路径；第一次准备工具链需要下载约 668 MiB 的固定 SDK。窗口隐藏运行，Node 不暴露给渲染器，验证结束即关闭。记录包含脚本与构建指纹，修改输入后应重新构建并运行相应验证。
