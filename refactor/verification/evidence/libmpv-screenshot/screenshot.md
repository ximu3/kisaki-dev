# Windows 原生截图与 SDR 目标验证

本轮核对 `screenshot-raw subtitles rgba` 能否沿已选 GPU 管线取得带字幕的 SDR 图像，以及结果是否具有独立存储。正常 D3D11 路径通过三个受控场景；软件截图对照保留了源 PQ 编码，不能当作相同的 SDR 结果。

这份记录没有实现正式 Mpv API，也没有修改截图命令、颜色算法或已采用的上游补丁。原型只在独立 Node 子进程运行，不创建窗口、不读取用户媒体、不更改系统显示设置。

## 输入与执行

| 项目               | 实际输入                                                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 系统与运行时       | Windows x64，Node 24.11.1                                                                                                               |
| 引擎               | [Windows 构建候选](../libmpv-package/package.md)，mpv 固定提交 01e2533f3143b8940857ca419b0b367f583e05ca，沿用已接受的修复，FFmpeg 9.0.2 |
| libmpv DLL SHA-256 | 34c9bf9c65fc7010e0a8c90eb1b1fb89f525c80f5bee86c060bd60bbe595bd0a                                                                        |
| 后端               | 直接 D3D11 Render API；软件解码，ANGLE 未装载                                                                                           |
| SDR 输入           | 自有 63×47 sRGB PNG，六个已知色块及中央灰块                                                                                             |
| HDR 输入           | 自有 224×64 十位 BT.2020／PQ 文件，七级灰阶与红色 ASS 矢量字幕                                                                          |
| 截图参数           | subtitles、rgba；三个正常场景使用 screenshot-sw=no，第四个对照使用 yes                                                                  |

[prepare.py](prepare.py)核对既有 GPU 原型五份构建源、当前候选的全部媒体 DLL、头文件与输入文件摘要，再复制原型到独立缓存构建。唯一 C++ 变化是将原型的 `screenshot-raw video` 改成 `screenshot-raw subtitles rgba`，见 [producer.patch](producer.patch)。原始探针及旧证据没有改写。

每个子进程只调用一次原型生产操作。Lua 在新目录生成，只记录首次源属性和目标配置，随后加载受控输入；没有复用会写入旧收据目录的脚本。原型先取得 63×47 GPU 画面和原生截图，随后按既有流程缩放、改变原生输出并关闭核心。JavaScript 在核心关闭后读取截图，释放帧后再次核对截图有效行摘要。

原型的 frame.target 是旧实验的生产模式参数，不是本轮实际颜色目标的权威描述。Display P3 由启动脚本设置，按首次配置记录与独立色块预期核对。本轮不把原型 info 的字符串整数包装当作正式 MpvNode／bigint 转换已经实现。

## 实际结果

| 场景                   | 截图尺寸 | stride／数据字节 | 与 GPU 参考采样的最大通道差 | 结果                                         |
| ---------------------- | -------- | ---------------- | --------------------------- | -------------------------------------------- |
| sRGB                   | 63×47    | 256／12032       | 0                           | 六色与独立 sRGB 输入一致                     |
| Display P3             | 63×47    | 256／12032       | 0                           | 六色与独立原色矩阵及 sRGB 曲线转换预期一致   |
| PQ 到 sRGB，带字幕     | 224×64   | 896／57344       | 0                           | 灰阶保持层次，红色字幕合成正确               |
| 同一 PQ 输入，软件截图 | 224×64   | 896／57344       | 54                          | GPU 画面仍为正确 SDR，截图灰阶保留源 PQ 编码 |

GPU 截图灰阶的红通道为 1、44、137、182、218、246、255，三个通道至多相差 1；字幕内部采样为 RGBA(255, 0, 0, 255)。软件截图灰阶为 16、77、130、148、167、192、230，与从自有源亮度按 ST 2084、十位有限范围量化后独立计算的八位 PQ 码值完全一致；字幕采样为 RGBA(255, 10, 0, 255)。因此这里的差异有源编码依据，不只是两组输出之间的目测比较。

三个正常场景的所有采样 alpha 均为 255。63 像素的一行有 252 个有效字节和 4 个 padding 字节，检查按实际 stride 逐行读取；摘要只涵盖有效像素，不把未定义 padding 当作图像。HDR 截图返回 224×64，GPU 视口为 63×47；本轮比较的是对应色块及字幕内部点，没有把不同尺寸的整幅图像宣称为逐像素相同。

四个场景都在核心已关闭后取得 JavaScript 字节，并在释放两份原型帧后保留相同的有效像素摘要。它证明该复制路径的独立存储，不证明正式 addon 的所有并发、预算与退出行为。

原始观测见 [screenshot-contract.json](screenshot-contract.json)，独立比较见 [verification.json](verification.json)，完整输入及构建摘要见 [source-input.json](source-input.json)。[run.py](run.py)负责执行，[probe.mjs](probe.mjs)检查布局和寿命，[verify.py](verify.py)检查色彩预期；后者可直接复核已有收据，无需重跑原生场景。

## 对设计的含义

Kisaki 继续通过同一 `command` 入口采集，使用就绪的受管 sRGB GPU 输出、`screenshot-sw=no`、subtitles 和 rgba。返回尺寸属于截图自身，不从视口推导；颜色解释来自这套实际使用条件，不能从 rgba 名称推导。Display P3 场景也实际返回 P3 编码字节，不能无条件加 sRGB 标签。

原始 map 只给出 w、h、stride、format、data，没有颜色空间、GPU／软件路径或源帧时间字段。库继续保留这些原生含义，不追加从稍后属性读取猜来的权威元数据；媒体位置和文件归属仍由 media 的明确采集操作关联。[固定命令实现](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/player/screenshot.c#L563)

`screenshot-sw=no` 表示先请求输出后端截图，不是禁止上游软件回退。固定源码在后端未返回图像时仍可转入软件截图；本轮主动启用软件截图证明两条路径的颜色不能等同，但没有注入 GPU 失效来执行自动回退。通用命令保持原生语义，不能因此承诺任意成功结果都具有受管目标颜色，也不通过另一套截图 API、日志文本解析或原生配置锁补造该保证。[路径选择](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/player/screenshot.c#L345)

正常 GPU 截图使用独立目标重新渲染并读回，未缩放模式采用内容显示尺寸；它不是直接读取最后一次 Electron 呈现。故本轮结果不承诺与屏幕逐像素、同一时刻一致。[GPU 截图实现](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/video/out/gpu/video.c#L3677)

## 覆盖边界

本轮关闭正常 Windows GPU 截图的格式、padding、独立持有、两种 SDR 目标及指定 PQ／字幕衔接疑问。负 stride、动态字幕与持续播放的采集、复杂滤镜、HLG、设备失效及完整颜色验收没有执行；也没有验证图片编码、PreparedImage、真实产品会话或 Electron 截图消费。macOS／Linux 及其他设备、架构继续按各自环境验证，平台图形组尚未整体关闭。
