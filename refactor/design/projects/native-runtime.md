# 原生库运行与交付

本页规定 Vantage 与 libmpv-node 共同遵循的 Rust、Node-API、线程、平台包和构建约束。项目内的模块组织与能力合同各自由相应项目定义。

<a id="scope"></a>

## 项目边界与源码结构

Vantage 与 libmpv-node 分别维护自己的 Git 仓库、pnpm 与 Cargo 锁文件、测试、说明、版本和发行。对外入口分别是 @ximu3/vantage 与 @ximu3/libmpv-node，Rust 承担原生实现，Node 是明确承诺的公共消费环境。内部 Cargo crate 不另行发布为需要独立维护版本的 Rust 产品。

两个项目都使用 Node-API 与 napi-rs 接入，分别实现自己的原生能力。Vantage 拥有进程与窗口身份，libmpv-node 拥有 libmpv 实例、视频输出和帧资源；共同需要的工具和普通依赖使用成熟实现。

每个项目的主要工程区如下：

    src/                  公开 Node API 确需的 JavaScript 适配
    crates/
      core/               不依赖 Node-API 的 Rust 原生能力
      binding/            Node-API 导出、值转换、异步回复与环境清理
    tools/                本项目的准备、构建、装配与制品验证流程
    tests/                整包消费、跨环境与真实平台端到端测试
    examples/             使用公开包的最小独立消费示例
    docs/                 公共合同、平台接入与发行维护说明
    release-notes/        本项目各版本的英语说明及按需译文

两个内部 crate 按运行边界划分，依赖方向为 binding → core。core 拥有系统、线程与资源规则，不持有 napi_env、JavaScript 对象或 Node 回调；binding 负责 Node 接入，不重新维护另一份进程、窗口或播放器状态。Rust 测试直接验证核心规则，Node 集成测试验证真实边界和声明。crate 内部按实际职责组合模块；单一功能在某一层即可完成时，不在其他层建立同义包装。

Node 主包由根 package.json 定义，优先使用 napi-rs 生成原生加载入口与声明，放入明确的运行输出。src 保存公共 API 确需的 JavaScript 适配；binding 已能直接提供全部能力时，发布生成入口即可。存在 index.ts 时，只列出实际公开导出。声明以真实导出为依据生成和检查；类型消费独立于二进制加载与图形初始化。

根目录按源码工程、外部运行环境接入、工具和消费验证分区，crate 内部按能力组织。根 src 对应唯一 Node 主包，crates 对应 Cargo 成员，两者各有明确的 manifest 归属。

<a id="binding"></a>

## Node 边界与线程

Node-API binding 只处理真实的语言与环境差异：参数校验、原生值转换、Promise 关联、线程安全回调、观察释放和环境清理。Rust core 报告自身错误，binding 映射为稳定的公开错误类别和必要上下文，不要求消费方解析错误文案。

跨线程传递自有 Rust 值或明确持有的资源，不让短寿命 JavaScript 值离开所属环境。回调不能持有会造成原生等待与 JavaScript 互相锁住的锁；必须交付的操作结果与可以合并／丢弃的状态或画面按各自合同处理，不能用一个无限回调队列承载所有负载。

每个 Node 环境拥有自己的回调和清理关系。单个环境退出不重新使用其回调，也不把其他环境的引用带入；显式停止和关闭仍是正常资源操作，GC 不充当播放结束或被观察程序退出的事实。环境退出通过 Node-API 清理能力收尾，不依赖已经禁止执行的后续 JavaScript 回调。

libmpv-node 的[进程运行库与实例寿命](libmpv-node/lifecycle.md#runtime-lifetime)：同进程共用一套固定媒体运行库，代码映射保留至进程结束；每个 Mpv 和 Node 环境分别拥有状态与清理。核心关闭、Worker 退出和帧释放不触发整套运行库的卸载，实例资源仍须在各自的完成边界回收，版本更新随进程重启生效。

Node-API 的 ABI 保证只覆盖对应接口，外部系统库、图形栈和 libmpv 仍须按各目标检查。两个包的构建工具版本、最低 Node-API 等级与声明的 Node／Electron 实测范围分别记录，不能拿编译 CLI 的最低 Node 版本代替运行兼容范围。

## 平台制品、依赖与工具

每个项目发布一个公共 Node 主包和对应目标的原生平台包，使用自身的固定版本配对。平台包按实际 os、cpu、libc 与 Node-API 条件选择，覆盖规定的 Windows、macOS、glibc Linux 的 x64 与 arm64；不增加范围之外的 musl 或 Universal 制品。

主包保存公开入口、声明和加载规则；平台包保存该目标的 .node 与实际所需运行资源。libmpv-node 的匹配 libmpv 和依赖由本项目一并装配，Kisaki 使用这份发行，不维护第二份下载。平台包不能只带 .node 而依赖开发机 PATH、当前工作目录或未声明的系统媒体库才可运行。

正式安装通过包管理器取得已经完成的制品，不执行联网下载脚本、现场编译或偷偷切换系统库。依赖缺失或目标不匹配按明确加载错误报告；受控源码开发和正式包加载各使用自己的已知路径，不以残留的本地二进制掩盖坏包。

Rust 源码、工具链文件、pnpm-lock.yaml、Cargo.lock、libmpv 构建输入及发行资源清单进入版本控制。构建、暂存的平台包目录和最终 tarball 分别保存，输出只由所属任务写入。原生制品及其资源的来源、配置、许可材料和摘要随发行保存，公共包与平台包使用同一份已经测试的文件。

libmpv-node 的原生准备流程按[固定源码与补丁](libmpv-node/distribution.md)核对提交、补丁及修改前后摘要，维护色调映射的零分母修复、逐次截图来源标记及各自回归用例。源码准备失败不能继续使用旧构建产物；制品记录保留实际应用的补丁集合。

libmpv-node 六个平台包按[共同播放能力基线](libmpv-node/distribution.md#build-capabilities)展开并核对编译功能清单。平台后端差异和当前设备能力单独记录，不能由构建机自动发现的可选包决定公开支持范围。升级验证使用完整原生构建组合，覆盖媒体行为、资源寿命与实际宿主消费。

其[引擎与整包装配](libmpv-node/distribution.md)进一步规定原生来源、运行依赖与数据、版本配对、系统前提和最终 tarball 的核对。平台包的操作系统动态库依赖与可再分发运行库分别处理；安装后的实际加载路径及功能记录不能由暂存目录中的文件存在替代。

tools 内按准备、构建、装配和验证的真实流程组织，命令入口只处理参数和退出状态。CI 选择 runner 与目标并调用同一工具，不在 YAML 中另写一套二进制下载、复制和修补逻辑。测试样本和完整消费示例从公开 tarball 加载，不以跨仓源码 link 验收。

Rust 单元测试贴近被测模块，crate 集成测试放在所属 crate 的 tests/，遵守 Cargo 的发现规则。根 tests/ 只组织整包消费、跨环境和实际桌面／图形端到端验证；样本由使用它的测试拥有。发布平台包和桌面组件安装包属于生成产物，源码、可审查输入与构建输出分别管理。
