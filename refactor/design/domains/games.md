# 游戏、启动与游玩记录

Game 是长期保存的作品，GameLaunchConfig 是一种本地使用选择，GameSession 是本次受管理的运行。当前个人记录、实际有效活动和存档备份分别保存，并通过游戏身份关联。

<a id="model"></a>

## 启动配置与持久记录

| 表                  | 关键引用                                                | 保存的事实                                     |
| ------------------- | ------------------------------------------------------- | ---------------------------------------------- |
| games               | entry_id 为主键并引用 entries.id                        | 游戏条目的专属资料                             |
| game_directories    | id；game_id 引用 games.entry_id                         | 独立登记的游戏内容目录                         |
| game_launch_configs | id；game_id 引用 games.entry_id                         | 启动、监测、目录与存档配置等本地使用选择       |
| game_records        | game_id 为主键并引用 games.entry_id                     | 游戏当前状态与附加时长；完成历史另存           |
| game_play_activity  | id；game_id 必填；launch_config_id 可空引用启动配置     | 实际游玩区间及已知上下文                       |
| game_save_backups   | id；game_id 必填；source_config_id 可空引用来源启动配置 | 应用管理的存档归档、创建信息、备注、锁定与来源 |

GameDirectory 和 GameLaunchConfig 分别直接属于 Game。目录按[内容目录合同](holdings.md#directories)保存，配置不保存 directory_id 或另一份安装位置。配置包含稳定 id、名称与顺序、文件或链接或完整命令、命令启动的可选工作目录、监测条件、存档与备份设置、首选和备注。命令文本包含完整参数；配置不另设参数字段或解释器选项。

游戏可以没有启动配置，资料导入也不创建空配置行。只知道内容目录时，保存 GameDirectory；扫描目录不会仅为保存路径生成配置，也不能默认选择目录中的第一个可执行文件。用户明确创建的未完成配置可以继续补全，未满足启动条件时不能运行或建立会话。

每个配置选择一种监测方式并保存明确的监测目标，默认方式为目录。从内容目录创建配置时，自动将该目录填入监测目标，作为配置字段随正常保存提交。其他情况下不自动填入监测目标，包括已经选择启动文件时；不从启动内容、命令或工作目录持续推导。目标未填写时可以保存为未完成配置，启动前须补齐。配置界面不增加“查看当前匹配结果”入口。

同目录的不同启动方式与多份安装可以分别保存配置，多个配置也可以使用相同路径。平台或模拟器配置可以独立于内容目录存在。从目录创建配置时，将所需位置复制为配置自己的值，之后目录和配置分别维护；批量重定位只处理用户明确选择的配置。启动配置保存使用方式，作品身份、来源绑定和私人评价归 Game，模型不增加 game_installations。

game_records 是以游戏身份保存的可选一对一记录。活动与备份直接属于游戏，可空的配置引用说明其来源，创建时核对配置属于同一游戏。历史保存发生时的名称和来源，后续改名或路径变化保留这些历史值。

备份具有稳定 ID 与 archive_attachment_id。删除配置只解除 source_config_id，游戏仍保留备份记录与历史说明。恢复时须明确当前目标，不能默认覆盖历史路径，也不能仅因属于同一游戏就保证存档兼容。完整规则见 [备份](backups.md)。

<a id="selection"></a>

## 首选、不可用与删除

game_launch_configs.is_preferred 默认 false。每个游戏允许零条或一条 true，切换首选在同一事务完成。启动配置上的这一字段是首选选择的存储依据。

普通打开按[共同目标选择规则](sessions.md#open)处理当前游戏的启动配置。没有活动会话且未显式指定配置时，首选优先于最近实际使用。明确的“继续”入口传入最近配置 ID，“使用首选”入口传入首选配置 ID，均由同一个 open 核对并执行。

主要启动入口采用[启动按钮与右侧下拉](../ui/components.md#local-actions)，主按钮不写配置名称。菜单中显式选择另一配置只启动这一次；设为默认只影响以后未指定配置的打开，不启动或切换当前游戏。配置名称和当前实际采用的配置在菜单、配置管理及游戏面板展示，不增加持久的当前选择。

最近使用来自实际活动，不使用编辑或扫描时间。目标失联时保留配置、记录、活动和备份，并提供修正、重定位或明确替代，不能悄悄换另一套安装。配置修改与重定位保留 ID，不追溯改写历史。

删除配置后保留游戏、当前记录、活动和备份，只解除允许留存的历史引用，不删除安装或存档字节。影响正在使用身份的删除、合并和重归属，必须满足占用规则。删除游戏的确认摘要说明配置、个人记录和应用备份的处理范围，不逐条预览，也不隐式删除用户目录。

## 完整启动与会话就绪

sessions.game.open 先确定配置，再核对游戏、启动内容、适用的工作目录和监测条件。启动方式为文件、链接和命令：文件与链接交给系统打开，命令保存完整文本，按固定的命令解释器语法执行。应用不自行按空格拆分命令，也不将它转换为另一份可编辑的程序与参数配置。

Windows 固定使用系统 cmd.exe，macOS 和 Linux 固定使用 /bin/sh。界面说明当前平台的命令语法，不提供解释器选择，也不跟随用户终端的默认配置。需要 PowerShell、bash、zsh 或其他程序时，由用户在完整命令中显式调用。应用不额外打开用于执行命令的终端窗口，解释器退出不代表游戏退出，实际会话仍依据监测集合判定。

工作目录仅属于命令启动，表示解释器开始执行时的目录，与命令参数及监测范围分别维护。未填写时使用当前用户主目录，界面明确说明这个默认值；不继承 Kisaki 自身的工作目录，不从完整命令或监测条件猜测位置。从游戏内容目录创建命令配置时可以将该目录填入工作目录。明确填写的目录不存在或不可访问时报告问题，不改用另一目录。文件与链接配置不保存或显示不参与其执行的工作目录。

异步准备开始前登记游戏启动占用。发出请求前复查基线并建立观察，将采用的配置固定为本次目标、计时和存档快照。

同一游戏正在建立会话时，已确定为相同配置的重复 open 共享这次建立过程，不重复发出系统启动请求，也不重置等待预算。显式请求另一配置时报告该游戏正在启动，不排队在稍后启动。配置尚未确定时仍遵守共同目标选择与交互权限，不能用合并请求绕过必要选择。多个调用共享执行时，各自取消只结束自己的等待；仍有调用等待时继续执行，全部取消则遵守本次启动的取消规则。

同一游戏只有一个当前使用上下文。已经有受管理会话时返回该会话；调用者显式指定另一配置时，须说明实际已有运行，不能忽略输入后假称完成新启动。

应用不在运行中途接入已有目标。除上述同一游戏的会话复用外，启动前已有符合监测条件的进程时，报告该范围已经在运行，不发送新的启动请求，也不建立会话；该进程是否也被其他游戏观察不改变这条规则。监测范围外的平台客户端可以预先运行，但它的存在不证明本次游戏已经启动。

| 结果                   | 产品含义                                                         |
| ---------------------- | ---------------------------------------------------------------- |
| 系统接受启动请求       | 请求已发出，可能仍在启动器或加载阶段                             |
| 确认本次明确的运行目标 | 建立 GameSession，按实际计时规则记录                             |
| 目录范围内有多个进程   | 共同作为本次监测集合，不要求选择一个主进程，也不重复累计时间     |
| 等待结束而目标未确认   | 会话建立失败；错误明确请求已发出，不发布会话开始，不返回部分会话 |
| 请求失败或目标不可用   | 按完整操作的失败合同反馈                                         |

会话建立的等待必须有界，期间不能重复发出启动请求。已经失败、取消或结束的尝试，不在稍后自动补成成功，也不提供另一个重新监测入口绕过建立流程。

初始等待规则按阶段分别约定，不增加逐游戏的等待设置：

| 阶段           | 等待范围与完成条件                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 启动确认       | 从发出系统启动请求起，最多等待 120 秒取得首个可靠匹配成员；此前的配置选择与必要交互不占用该预算                              |
| 退出确认       | 连续 5 秒可靠观察到集合为空；期间出现成员则继续原会话，观察未知则重新计算可靠空集合时段                                      |
| 关闭或强制终止 | 从该次操作开始，最多等待 10 秒确认外部运行结束，包含上述退出确认；新成员不延长预算，实际退出后的保存与资源收尾不受此预算截断 |

首个匹配的启动器即可建立会话，不额外等待游戏内部加载。空集合和观察未知的区间不累计，也不使用前台暂离宽限补计。关闭请求本身不改变用户暂停状态，等待中仍按实际观察事实计时；超时后继续正常观察，后来确认的退出照常完成会话收尾。

系统已接受启动请求但目标未确认时，以 GameLaunchUnconfirmed 报告确认失败和已经发生的副作用；等待结束与必要观察失败通过安全说明分别表达。没有合法 GameSession 就不提供 partialResult。主动取消或调用归属失效保留其原分类，取消等待不能保证程序没有启动，也不能因此终止未知对象或自动重试。

失败反馈使用本次已取得的事实，区分配置缺项、启动请求被系统拒绝、观察不可用和等待内未确认匹配成员。最后一种表述为“未能确认游戏运行”，保留本次配置的编辑入口；它不能证明程序从未启动。反馈不额外枚举当前进程，也不把修改配置当作重试授权。

启动确认超时的原生反馈遵守[开始游戏反馈](../ui/components.md#game-start-feedback)：主按钮恢复“开始游戏”，Toast 提供本次配置的编辑入口，保存配置不自动重试。没有建立会话时不提供本次游戏的关闭或强制终止操作。

启动确认预算只限制本体等待，取消或超时结束本次等待。解释器与已启动内容按自身寿命继续运行，启动输出仅由相应接入处理。

正常运行从本体发起，持续管理到实际结束或用户在退出流程中明确停止记录。本体的[脱离操作](sessions.md#detach)只服务这一退出选择，不开放 SDK 的附加／脱离或中途接入已有游戏。暂停计时、隐藏面板和恢复本次范围的观察不改变会话归属。

## 进程集合观察与有效计时

processes 接入[Vantage](../projects/vantage/api.md#surface)，通过正式发行的 @ximu3/vantage 采用 processes、windows，以及库级 getForeground 和 observeForeground 入口。原生库负责真实实例与系统操作，由 Kisaki 决定监测与计时。原生订阅中断与 GameSession 中断分别判断，接续与收尾见[完整接入规则](../engineering/integrations.md)。前台状态先保留可核实的进程与窗口事实，再由本体判断是否属于本次监测集合；缺少具体前台窗口不抹去已经确认的前台进程。

| 监测方式 | 匹配对象                         |
| -------- | -------------------------------- |
| 目录     | 指定目录及其子目录中的可执行文件 |
| 文件     | 完整可执行文件路径               |
| 进程     | 完整可执行文件名，不限定所在目录 |

进程方式按完整名称精确匹配，扩展名参与比较，Game.exe 不匹配 GameHelper.exe 或 Game。名称比较在 Windows 不区分大小写，在 macOS 和 Linux 区分大小写。匹配采用 Vantage 提供的完整可执行文件名，不以可能被截断或改写的系统显示名称替代。目录包含关系按路径片段判断，不能把 Game2 算作 Game 的子目录。

三种方式都持续发现可靠匹配的真实进程，并将其纳入本次监测集合。确认成员后，按 ProcessRef 跟踪至实际退出；后续名称、路径变化或暂时无法读取这些字段，本身不将它从集合移除。集合仍继续接纳新的匹配成员，实际计时遵守下方的观察可靠性规则。多个成员属于正常结果，不设置主进程选择步骤，也不额外判断目标是否“像游戏”或游戏内部是否已经加载内容。

本次匹配规则使用固定的配置快照，监测集合按成员纳入和真实退出持续更新。原生实例引用区分复用的 PID，同一 GameSession 可以经历多次成员变化；集合结束条件按完整监测结果判断。会话结束后，后来出现的匹配进程独立于该会话。名称、路径或窗口信息不足时如实表达，进程身份仅用于运行监测。

不同游戏的监测范围可以重叠，不因规则可能相交而拒绝启动或分配排他归属。每个会话独立观察自己的范围，同一进程实际命中多个会话时，可以分别参与各会话计时；每个会话仍只累计一份时间，不按成员数量叠加。这不改变启动前已有运行的处理规则。

目录内常驻的辅助程序同样影响运行判定，不能一边声明监测整个目录，一边暗中排除被猜测为辅助程序的成员。

默认按前台状态计时，配置可以选择运行计时。集合中任一成员处于前台即可满足进程前台条件，运行计时则依据集合中仍有成员存活；两种方式都只累计本次会话的一份时间，不按进程数量叠加。游戏面板交互和默认十分钟暂离宽限，统一遵守 [会话计时](sessions.md)。配置修改不追溯当前会话。暂停只停止累计，观察与占用继续存在；切到后台或没有键鼠输入不表示游戏退出。

休眠、锁屏和无法可靠观察的区间不补计。时长使用单调时间计算，记录保留真实发生时间。确认集合仍有存活成员、仅前台状态未知时，暂停前台计时，运行计时仍可依据已确认的存活状态继续。无法可靠取得必要进程状态时，暂停未知部分的累计并保留上下文；恢复后继续观察本次固定范围，保持原计时方式和用户暂停状态，不补未知区间。

临时查询失败不能解释为集合为空，也不按失败次数或经过时长自动结束会话。只有本次计时必需的观察权限明确失效、系统明确报告必要能力不可用，或宿主无法继续维持上下文时，才以 interrupted 结束。失败分类依据平台接入的结构化原因与实际观察事实，不依据错误文案。截图、聚焦或关闭请求失败，不代表进程观察失效；必要观察仍可用时，保留会话。

interrupted 表示本次监测与记录被迫结束，不证明游戏进程已经退出。保留已提交记录，能够执行收尾时保存尚未提交的已确认部分，不补未知区间、不终止外部程序，也不触发退出备份。中断后不恢复旧会话，不在游戏仍运行时重新接入。等待确认退出的整个时段也不能直接计为游玩。

同一会话可以产生多个有效区间，运行期间定期保存已经确认的部分。异常重启后不恢复计时器，也不补计停机时间。作品是否完成、进程是否运行、计时是否暂停，是三种独立事实。

## 实际窗口与截图

返回游戏与截图使用本次监测集合成员拥有的用户窗口。最小化窗口仍可作为目标，隐藏辅助窗口和 Kisaki 游戏面板不作为目标。先采用当前前台的游戏窗口，再采用本次会话最近实际处于前台且仍有效的游戏窗口；没有上述依据时，采用唯一可用窗口。仍有多个窗口时，在当前调用内选择；没有可用窗口时明确报告。窗口记忆仅属于本次会话，不增加持久的主窗口或主进程配置。

窗口选择只服务于本次操作，不改变监测范围。必要选择遵守 allowInteraction，取消只结束该次窗口操作，不结束游戏会话。操作前再次核对窗口与进程身份，目标已失效时报告问题，不在执行途中改用同名窗口或另一成员。

返回游戏按实际窗口状态恢复最小化并请求焦点。截图也可以先恢复已经确定的最小化目标，并在需要时请求前台；确认恢复后的画面可用后再采集，不能将恢复请求已发出或固定等待一段时间当作完成。恢复、权限或采集失败时明确报告，不改截整个屏幕或另一窗口，也不以旧缩略图冒充当前画面。系统要求授权或选择来源时，在当前调用内完成必要交互，后台调用仍遵守同一交互权限。

游戏截图通过 Vantage 的 windows.capture(windowRef) 取得并固定目标窗口的一帧画面，再对这张静态图片进行可选裁剪，或者直接采用完整图片。裁剪复用[图片处理](attachments.md#images)，不在拖动裁剪框期间重复采集变化中的游戏画面。采集不暂停游戏或计时，也不清除用户暂停；取得原图后，编辑和保存不再依赖游戏继续运行。正式标注采用最终图片，不另存依赖原截图的可编辑区域。

## 关闭、退出与自动备份

正常结束必须确认本次受管理运行实际退出。close 请求正常关闭，terminate 明确请求强制终止；两者都核对实际受管理成员的真实身份并等待结束，不能只因某一个进程退出就完成会话。不能根据旧 PID、同名进程或未经本次观察确认的目录匹配结果终止其他程序。

一次结束操作固定本次监测范围和截止时间，成员集合继续按实际观察更新。在截止时间内新确认的范围内成员也参与该次关闭或强制终止，不把作用对象冻结为调用开始时的名单，也不因新成员出现而延长截止时间。取消、超时或完成后停止继续发出请求；此前已发送的请求仍可能随后生效。操作不扩大监测范围，也不自动终止范围外的子进程。

同一会话进行中的同类结束操作由重复调用共享，不重复发送请求或重置预算。各调用独立等待与取消，取消一个调用不停止其他仍有效的请求；全部取消后停止继续发送请求，进程观察仍按会话寿命继续。

用户明确发起 terminate 时，可以立即接替同一会话尚未完成的 close，不必等普通关闭超时。旧普通关闭停止继续发出请求，尚未完成的调用按被替代的明确失败结束；强制终止从自身开始时取得新的 10 秒外部退出等待预算，并完成实际退出与必要收尾。已经发出的正常退出请求不会被撤回。强制终止进行中收到 close 时，只等待当前结束流程，不再发送正常退出请求；普通关闭本身不能触发强制终止。

不同会话的结束操作命中同一真实进程时，底层合并同时进行的同类退出请求，避免重复触发该进程的关闭交互。各会话仍独立判断自己的集合与完成结果，某个共享成员被明确强制终止不把其他会话的其余成员改成强制路径。当前请求结束后，用户可以明确发起新的尝试。

关闭与强制终止直接按本次范围执行，不因成员也被其他会话观察而增加确认。共享进程实际退出后，各受影响会话分别更新自己的集合，并按剩余成员决定是否结束；不能直接把其他会话一并标为结束。

正常关闭在一次调用中对同一真实进程最多发出一次正常退出请求。尚无可用的正常退出方式时，可在同一截止时间内等待；不能改用强制终止，也不反复关闭该进程随后弹出的保存确认窗口。强制终止同样使用每个成员的真实身份，不能把 PID 复用后的新进程当作旧成员执行请求。

成员已经自行退出，或者因其他成员退出而连带结束，均视为该成员已完成结束。请求前检查仍须处理检查与执行之间的退出：底层请求返回失败后，若可靠确认原实例已退出，则采用已结束事实；仍存活的权限拒绝、实际请求失败和无法确认的状态分别报告，不能仅凭错误码或错误文字吞掉失败。其他成员仍按同一结束流程处理，整体结果依据当前集合实际结束与必要收尾是否完成，不要求每一个成员都必须成功收到退出请求。

关闭没有完成且目标仍在运行时，保持会话与观察。不能用 interrupted 绕过应用退出，也不能自动强制终止。内容已经结束但记录保存失败时，按 [会话关闭合同](sessions.md#close) 报告实际结果。

正常关闭和强制终止使用各自的明确操作；超时后继续观察实际目标。按钮、菜单和 Toast 的行为由[游戏结束操作入口](../ui/components.md#game-end-actions)统一定义。

关闭主窗口可以转入后台。完全退出或更新重启时，用户可以结束游戏后退出，也可以明确停止游戏记录并退出；后者沿[脱离合同](sessions.md#detach)保存已确认活动并解除管理，让外部程序继续运行，不声称游戏已退出。崩溃、系统终止或无法继续观察才使用 interrupted，明确脱离使用 detached；两者都不在重启后接管残留目标。公共流程见[退出协调](../ui/navigation.md#shutdown)。

只有本次已经建立会话且确认 ended reason 为 exited，才考虑自动备份。备份能力在处理结束事实、接纳工作前，按[自动备份的接纳时点](backups.md#automatic)核对同一启动配置当前的开关；游戏启动时的选择不冻结到退出时。启动失败、暂停计时、隐藏面板、interrupted、detached 和技术资源释放都不算游戏退出。

app 通过 events.on 集中订阅 sessions.game.sessionEnded，将事实交给备份能力声明的完整处理入口，并拥有这条固定连接。触发判断和在途工作由备份能力负责；连接代码不解释备份开关或安排业务步骤，备份能力也不为接收事实取得整个 sessions 实例。备份使用本次 saveSource snapshot、skipIfUnchanged: true 和当前仍适用的保留规则，不因首选变化改用其他来源，也不另建触发历史。

备份仍须核对来源和占用。备份失败单独报告，不改变已发生的退出与活动事实。宿主退出时须保留备份执行条件直到收尾完成，不能先销毁所需能力，再发布正常结束。生命周期只使用 [会话事件](../communication.md#session-events) 定义的事件。

## 游戏面板

每次 GameSession 至多按需创建一个游戏面板，是否自动显示由偏好决定。面板绑定该会话，多个游戏分别持有面板、草稿和显示状态。面板显示运行与监测状态、有效时长和记录控制，提供截图标注、返回游戏窗口、作品详情、目录及存档入口。界面使用独立原生窗口，保留游戏自身的图形链路。

移动、置顶或隐藏面板都保留会话，自动显示默认不抢游戏焦点。托盘“游戏面板”列出当前游戏会话，点击后创建或恢复对应面板。会话结束后移除通常入口，不为查看结束信息保留面板或历史列表；正在处理未保存编辑的面板暂留原入口，注明待处理编辑，处理完成并关闭后移除。同一游戏的新会话与尚未处理完的旧草稿并存时，以会话开始时间区分。用户也可通过快捷键或主界面游戏操作菜单唤起活动会话的面板。“打开游戏面板”与“返回游戏”是不同动作，不增加顶层常驻按钮。没有会话时，从详情访问标注与历史，不凭空建立会话。

每个面板使用一个原生窗口，以托盘和快捷键为主要入口，不另设独立任务栏按钮，也不专门提供最小化按钮。平台实际呈现须在对应系统验证，不以任务栏设置推定所有窗口切换器都隐藏该窗口。若窗口被系统最小化，打开面板时恢复它。折叠时隐藏正文，保留同一标题操作栏、名称、计时和常用动作，并缩小实际窗口尺寸；展开时恢复记住的尺寸。位置、置顶、焦点和关闭规则只有一套，不另开悬浮窗或第二份草稿。

折叠、隐藏和关闭分别处理。隐藏保留窗口及草稿；窗口关闭按钮只关闭面板，执行通常的未保存检查，不关闭游戏或结束会话。会话仍活动时可再次创建面板；会话结束后不再重新创建面板。折叠不重建页面，也不触发保存确认。计时等无需正文的动作可以在折叠状态下执行；查看标注时展开列表。新建截图标注先采集画面，再显示、展开编辑；需要确认未保存内容时，先显示相关内容。

折叠后仍使用本窗口快捷键。少量需要在游戏前台触发的核心操作，使用 [偏好](preferences.md) 定义的系统级键鼠入口，并复用同一原生流程。

GameSession 结束时自动关闭对应面板。没有未保存编辑时直接关闭；有草稿时，显示相关内容并沿用[共同关闭流程](../ui/components.md#closing)：保存成功或明确放弃后关闭，继续编辑或保存失败则暂留面板，直到草稿处理完成。隐藏和折叠状态均遵守这一流程。会话结束后，面板只处理剩余草稿，计时、截图等运行操作同步结束。已保存标注与游玩历史从作品详情访问。

隐藏不停止监测，暂停计时也不暂停游戏内部运行。面板内嵌 Annotation，不增加长篇 Note 编辑器；Note 由主界面管理。

## 当前状态与完成记录

game_records 以 game_id 为主键并引用 games.entry_id，保存以下当前值：

| 字段                   | 含义                                                       |
| ---------------------- | ---------------------------------------------------------- |
| status                 | planned、active、onHold 或 null                            |
| additional_duration_ms | 未包含在实际活动中的附加游玩时长，非负安全整数毫秒，默认 0 |

完成历史、当前值缺省和评价归属见[共同记录模型](records.md#schema)，管理入口不要求存在启动配置。用户按自己的通关标准执行[完成操作](records.md#operations)；全成就、全结局和附加内容均不替代该判断。启动、计时和退出只按[会话规则](sessions.md#personal-status)记录实际使用。

## 活动、补记与平台总量

游戏累计时长等于 game_play_activity 中已经确认的有效时长，加上 game_records.additional_duration_ms。编辑、来源总量采用、并发基线与统计遵守四类作品共同的[附加时长合同](records.md#duration)，不另设游戏专属规则。

外部平台总量与本地活动可能重叠，计时口径也可能不同；用户明确采用后才形成附加时长。后续来源变化仍须由用户再次决定是否采用，本地保存采用后的附加时长。

平台拥有列表不证明完成或时长已经采用。Steam 拥有导入不自动承担 playtime_forever 同步。天、周、月图表只使用有真实日期的活动，补记不能放到导入当天，也不能分摊到虚构日期。

最近使用和最近配置来自实际活动或当前会话。补记、完成编辑和导入都不能把今天伪装成最近游玩。删除配置不清除当前记录与活动，来源刷新也不清除私人值。
