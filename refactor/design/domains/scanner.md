# 扫描发现、线索规则与历史

scanner 根据 ScanConfig 发现目录或文件候选，提取线索并调用 ingest 添加尚未入库的作品。用户开启明确选项后，也可为准确对应的已有作品登记本地内容。metadata 与 ingest 负责资料获取和采用，holdings 负责完整登记、文件关联及后续核对。

<a id="discovery"></a>

## 候选边界与新增规则

扫描在发现根的指定层级中，按类型、包含和排除规则查找目录或文件。每个符合条件的路径各自成为一个 Work 候选。目录一旦被认定为候选边界，其内部路径就不再作为本次其他作品的候选。本体恢复索引中明确拥有的工作区整体排除，调用装配提供的只读归属判断，不读取备份私有记录或按名称猜测。同层多个文件不会自动聚合为一部作品的分部。不同路径也不能证明是不同作品，每项仍须由 ingest 确认身份。

公开 scan 检查当前配置的完整范围，接纳时固定扫描配置、registerExistingContent 选择和资料方案快照。扫描创建新作品；选项开启时为已准确对应的作品登记本地内容，不更新已有作品资料或个人记录。

新增使用标准规则：采用合法初始资料和真实分部；已有关联条目复用身份并保留普通资料；必要而缺失的人物、角色和组织可以创建；关联作品只复用已有对象。歧义和无法合法采用的部分，按实际情况进入问题或部分结果。

根作品已经存在时，registerExistingContent 为 false 则跳过该候选，不追加本地内容。为 true 时，scanner 使用 ingest 返回的真实完整身份对应，调用 holdings 的[本地登记](holdings.md#registration)，只登记本次候选明确的目录或文件。相同登记复用，其他位置可以追加；不刷新元数据、覆盖关联或改首选。身份冲突或只有名称相似时不追加，结果分别说明作品已存在与持有是否登记。

目录候选新增成功后，按所属类型登记 GameDirectory、AnimeDirectory、ComicDirectory 或 NovelDirectory。游戏目录独立于启动配置，只有目录输入时不创建配置；用户之后明确选择入口。文件候选成功时，动画、漫画和小说只登记这个明确文件，游戏按明确启动文件初始化配置。文件输入不自动登记父目录，文件路径也不能存入目录表。后续分部文件由 holdings 从已登记内容目录中发现，或由用户明确添加。

新增作品的本地输入继续随 ingest 原子登记；已有作品在明确选项开启后，由 scanner 调用 library.holdings.registerLocalContent 的完整入口。scanner 不直接写表、不解析分部关联，也不调用 holdings 内部步骤。目录、配置、文件与关联以本体事实为准，不建立扫描专属副本。[scanner.recognizers](../extensions/providers.md) 返回线索或 null，不返回猜测列表，也不承担初始来源候选选择。

根离线、空目录、部分枚举、无权限和探测失败须分别报告，不能都表示为空数组，更不能据此删除正式资料。尚未采用的临时候选可以退出本次流程，正式资料则遵守自身删除规则。重复发现已有登记时返回复用结果；关闭已有作品登记时跳过，不重复创建资料或通知。

<a id="configuration"></a>

## 配置字段与管理

ScanConfig 存储在 scan_configs。一份配置对应一个发现根、一个 WorkType 和一份同类型 MetadataProfile。workType 创建后固定，需要其他类型时新建配置。definition 只存扫描规则，不存进度或持有事实。

| 字段                      | 类型与含义                                                           |
| ------------------------- | -------------------------------------------------------------------- |
| id                        | TEXT，稳定主键                                                       |
| name                      | TEXT，非空配置名称                                                   |
| work_type                 | TEXT，限定四类 Work                                                  |
| root_path                 | TEXT，发现根目录的规范绝对路径                                       |
| metadata_profile_id       | TEXT，资料方案外键；适用类型必须与 work_type 匹配                    |
| definition                | TEXT，经过语义校验的 JSON 扫描规则                                   |
| register_existing_content | INTEGER，0/1，非空，默认 false；是否为准确对应的已有作品登记本地内容 |
| watch_enabled             | INTEGER，布尔值，默认 true                                           |
| sort_order                | INTEGER，配置列表的人工排列，沿用统一排序值规则                      |
| created_at                | INTEGER，创建时间，毫秒                                              |
| updated_at                | INTEGER，配置修改时间，毫秒                                          |

definition 的规则如下：

| 键             | 含义                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| entryDepth     | 固定条目层级，正整数，默认 1；1 为发现根的直接子项，2 为下一层，中间层只用于遍历                                                                      |
| inputKinds     | 允许目录、文件或两者；文件同时须符合相应 WorkType 支持的本地输入类型                                                                                  |
| include        | 相对路径条件列表，采用下方路径过滤合同；空列表表示不额外限制，多条取任一                                                                              |
| exclude        | 相对路径条件列表，多条取任一，优先于 include；排除目录同时排除其子树                                                                                  |
| identification | 默认使用目录名或去除扩展名的文件名；可通过正则捕获提取线索，并通过 recognizerId 明确选用多个 scanner.recognizers 实现；算法设置归扩展，不执行任意脚本 |

引用的资料方案必须存在且类型匹配。配置可以通过 recognizerId 明确选择多个识别器，算法设置由扩展管理。每个识别器取得内容相同的只读基础线索，其结果保留实现归属，不接力改写候选，也不调用所有已注册识别器。作品候选的基础名称提取是扫描配置自身的原生能力，不建立另一套扫描识别方案；已有作品内部的[文件识别方案](file-recognition.md#recognition-profiles)由 holdings 管理。

scanner.configs 提供以下管理方法。metadata.profiles 在自己的范围内使用相同的管理语义。

| 方法              | 输入与返回                                                            |
| ----------------- | --------------------------------------------------------------------- |
| list(filter?)     | 按适用类型等明确条件取得人工顺序的配置摘要数组，不包含完整 definition |
| get(id)           | 取得包含完整定义的配置；不存在返回 null                               |
| create(input)     | 返回实际保存的新配置                                                  |
| update(id, input) | input 包含 changes 与可选 expected；返回修改后的完整配置              |
| delete(id)        | 完成符合所属业务引用规则的删除，返回 void                             |
| reorder(input)    | 按排序范围与移动意图完成重排，返回 void                               |

配置摘要按人工顺序返回，历史另行分页。身份和时间由本体生成。reorder 接收实际排序范围与移动意图，不允许任意写 sortOrder，也不拿屏幕上的局部数组覆盖完整顺序。

update 只提交实际 changes。definition 作为整体校验并替换，不执行隐含的深层合并。expected 遵守[字段基线](library-operations.md)合同。

配置保存按结构合法性校验，执行时再核对当前能力是否可用。扩展不可用期间，可以改名、停用或保留引用。ScanConfig 管理扫描意图，已入库对象与绑定由资料库独立管理。删除正在执行的配置后，本次任务继续，界面说明其状态并提供任务入口。

<a id="path-filters"></a>

## 相对路径过滤

scanner 的发现根和 holdings 的内容目录共用以下纯路径条件；各自决定候选层级、读取边界和规则作用范围。include、exclude 都是 PathFilter 数组，默认空数组。不引入可执行脚本、嵌套条件树或按名称猜测的过滤形式。

```ts
type PathFilter =
  { kind: 'path'; path: string } | { kind: 'glob'; pattern: string; ignoreCase: boolean }
```

路径以当前明确根目录为基准，使用 `/` 分隔，不含绝对路径前缀或尾分隔符。根目录本身在过滤合同中使用 `.`；其他值不允许空片段、`.`、`..`、反斜线或盘符前缀。保存时拒绝非法输入，不通过删除片段修复后扩大范围。文件选择器负责将实际路径转换为合法相对值，不能把根外路径保存进过滤条件。

path 表示精确位置，使用与规范绝对路径一致的路径相等规则；`[组]`、`*`、`?` 等字符均按文件名原文处理。“排除此路径”总是生成这一形式。glob 对完整相对路径匹配，ignoreCase 在新建时为 false，用户可以明确修改；它不修改实际路径或输出文字。

| 模式语法      | 含义                                                   |
| ------------- | ------------------------------------------------------ |
| `*`           | 一个路径片段内的零个或多个字符，不跨 `/`               |
| `?`           | 一个路径片段内的一个 Unicode 码点，不跨 `/`            |
| 独立片段 `**` | 零层或多层路径；`**/*.cbz` 包含直接子文件和更深文件    |
| 其他字符      | 按字面量匹配，不支持字符类、花括号展开、否定或正则语法 |

`**` 只能独立占据一个片段，不接受 `a**b` 等其他形式。每个条件分别匹配当前路径；包含列表为空或任一项命中时通过包含筛选，排除列表任一项命中时排除。目录一旦命中排除，整棵子树排除，不再枚举；目录未命中包含不能据此剪去子树，后代仍可能命中。包含某个精确目录只选中该路径；需要包含其子树时使用明确的 `目录/**` 模式。

例如，include 为 `**/*.cbz`、exclude 为精确路径 `备用` 时，可以发现直接和深层 CBZ，但不进入 `备用`。精确排除 `[组]/01.cbz` 只影响该路径；排除一个配置的子树不改变其他配置或其他明确登记目录的范围。

遍历不自动跟随范围内的符号链接或目录联接。需要管理链接目标时，必须把该位置作为明确的发现根、内容目录或单独文件登记；实际读取仍须核对可访问性。根本身来自明确登记，不因此扩大到其他祖先目录。未跟随、排除、达到深度边界和枚举失败分别记录，均不能作为整个物理子树已完整核对的证据。

过滤发生在候选路径层，不进入已经确定的阅读目标内部筛选页面、章节或压缩包成员。格式损坏的配置保留原存储并报告问题，按[损坏配置规则](values.md#read-write)由用户明确重建或删除；scanner 不接纳该配置的新执行，holdings 使用自己的失败边界。

<a id="watch-and-order"></a>

## 监听、并发与采用次序

watch_enabled 默认为 true。有效配置保存并启用后，先接入候选层级的监听，再扫描当前范围；遍历及采用期间的变化合并到有界的待核对范围，在本次执行后继续处理。初始扫描与持续监听之间不能存在遗漏窗口，监听不可用则如实报告其状态。未保存草稿不生效。作品目录内部新增文件由 holdings 处理。

监听变化时，内部按受影响范围核对；无法可靠确定范围时，重新发现整个配置。恢复应用或恢复监听后，先核对当前范围，不补放旧事件。ScanConfig 不提供日历或固定间隔设置。

同一配置不能并行扫描。已有执行尚未终结时，显式 scan 返回忙碌，不能把旧执行当作新请求的结果。监听变化合并为有界的待核对范围，当前执行结束后，再按最新有效配置处理。不同配置可以并行，重复身份及并发提交由 ingest 和 library 保护。

关闭监听或删除配置，会丢弃尚未接纳的去抖请求；已经接纳的任务继续使用固定快照。候选按相对路径稳定排序。第一个成功新增候选确定初始本地登记；后续准确对应同一作品的候选，按 registerExistingContent 分别跳过或登记其他位置。网络响应先后不决定目录采用顺序。

待核对范围保存在[尚未接纳的触发收集](../communication.md#admission)中。扫描拥有者按配置与并发规则接纳执行后，才建立相应 TaskRun；准备、等待和收尾随后归该次执行管理。

前一个候选已经创建作品而首次识别失败时，已提交身份和目录仍保留。后续候选不替换它；选项开启时可以独立登记另一明确位置，关闭时跳过。每次本地登记在提交时重新核对身份对应。监听内部的局部处理不是公开 selected 扫描，结果中的 scope 必须准确说明本次实际覆盖范围。

<a id="preview-and-resolution"></a>

## 预览、排除路径与处理问题

preview 使用规则草稿，展示路径、类型、候选边界、所选文本、命中规则、线索和问题。它不取得远端资料，不创建作品，不移动或重命名文件，也不生成可勾选采用的计划。

公开 scan 不接受所选项重扫、人工 clues 覆盖或通用 expected。重新扫描始终检查当前完整配置，不能称为“仅重试失败项”。

“在此配置中排除此路径”修改该配置 definition.exclude 中的精确相对路径。目录排除覆盖整个子树，不按名称全局排除，也不影响其他配置。配置编辑界面先修改草稿，扫描报告中的独立动作则修改实际配置。普通取消勾选不能暗中变成长久排除。

根据旧报告执行排除前，必须核对配置和当前发现根。配置已删除或根路径已变更时，不能直接套用旧相对路径。排除只改变发现规则，不删除磁盘内容或正式资料。

问题列表读取 ScanRun，支持按配置或汇总查看，并按文字及问题类型筛选。它提供打开路径、打开条目和适用修复入口。身份已经明确时，复用普通 ingest 新增，携带 WorkType、绝对本地路径及种类、确认线索和有效方案选择。此操作不依赖原扫描配置继续存在，也不能静默替换已经失效的明确方案。不另设扫描专属资料获取或采用预览。

不同问题可以引导用户手动添加、更新已有对象资料、核对 holdings、排除路径或修正配置。自动扫描在本次执行中完成识别和报告，需要用户决定的情况留给相应业务入口处理。

单项修复是新操作，旧报告不改写为“已修复”。要验证整体发现结果，应再次预览或扫描。TaskCenter 与 scanner 使用各自报告上下文调用同一业务，不依赖另一套历史存活，并须保留必要本地路径。

问题值保存在本次扫描报告内，可以具有定位键。报告记录扫描当时遇到的问题；清理报告不能证明问题已经解决。

<a id="result"></a>

## 发现结果与候选结果

ScanResult 只由 scanner 定义，包含 discovery 和 candidates。discovery 的结构为 { finished: boolean, candidateCount: number, issues }。finished 只表示范围遍历已经结束，不保证全部路径可读；失败路径仍须报告。candidateCount 是实际已经发现的数量，遍历未完成时不能称为最终总量。

discovery.issues 使用 { path, error: ErrorSummary }，记录无法读取的目录或输入。被过滤的路径不生成候选，排除规则保存在配置快照中。

candidates 按稳定路径顺序保存已处理项。每项包含 path、clues，以及 result: AddResult 或 error: ExecutionFailure<AddResult>；clues 尚未取得时为 null。取得 AddResult 后，localContent 按下表表达本地内容的登记结果，与作品新增或已存在的结果分别呈现。

| localContent.status | 含义与载荷                                                                                      |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| included            | 新作品的明确本地登记已随新增提交；首次识别问题仍在 AddResult.issues 中                          |
| skipped             | 已有作品且本次选项关闭，没有追加本地内容                                                        |
| registered          | 已有作品的登记调用完成；result 为 LocalContentRegistrationResult，可包含已存在登记              |
| failed              | 已有作品的登记失败；error 为 ExecutionFailure<LocalContentRegistrationResult>，保留合法部分结果 |
| notStarted          | 作品对应已经完成，但取消或整体故障发生在本地登记开始前                                          |

新增或对应本身失败时没有 localContent。登记失败不把已有作品改称新增失败，也不撤销此前候选；报告分别统计新增作品、已有作品、实际新增登记、已存在登记与未完成范围。即使没有新增作品，实际新增持有也应作为本次成果呈现。

取消时，已经发现但尚未处理的候选不能伪造为失败。发现数与处理数共同保留本次未完成范围。scanner.finished 交付 scanRunId、scanConfigId、finishedAt 和真实终态。completed 必须带有 ScanResult；failed、cancelled 和 interrupted 保留 error，只有实际形成报告时才带 result。

扫描历史和 TaskRun 从同次执行保存相同的合法事实。任务在失败终态可以有结果，但其他任务不必使用 ScanResult。

<a id="api"></a>

## 执行接口与运行观察

| 能力     | 入口与完成含义                                                              |
| -------- | --------------------------------------------------------------------------- |
| 配置管理 | scanner.configs：列表、详情、创建、修改、删除及排序                         |
| 规则预览 | scanner.preview(input)：按规则草稿展示发现范围、过滤结果和提取线索          |
| 完整执行 | scanner.scan(configId)：等待当次完整扫描，直接交付 ScanResult               |
| 当前运行 | scanner.getState(id)、scanner.observe(id)：读取与观察配置对应的真实运行状态 |
| 扫描历史 | scanner.runs：历史列表、详情与清理                                          |

scan 等待本次完整执行，并直接交付 ScanResult。失败使用[共同完整操作合同](library-operations.md)，不改为返回 TaskRunRef。运行引用来自内部实际任务上下文，不能从历史推测。

ScannerState 包含 watch: { status, error } 和 currentRun: { scanRunId, taskRef } | null。watch.status 为 disabled、starting、active 或 unavailable，error 使用共同安全错误。候选问题或单次扫描失败，不自动表示监听不可用。

暂停、恢复、取消及进度都通过同一 taskRef 交给 tasks，不再保存另一套控制标志。扫描结束后清空 currentRun，不改变用户的监听意愿。

getState 和 observe 按配置 ID 工作。只要配置或已经接纳的执行仍存在，就提供状态；两者都不存在时返回 null。observe 先交付快照，再交付变化，不遗漏订阅之间的状态。一次任务结束后，继续观察后续执行。

配置已删除但执行未结束时，观察仍然有效。全部不存在后，交付 null 并结束。释放订阅只停止接收，不控制执行。configs 与 runs 通过 onInvalidated 分别通知数据变化，运行状态通过 observe 交付。后台重读不能覆盖编辑草稿。

<a id="history"></a>

## 扫描报告与保存

scan_runs 包含 id、scan_config_id、config_snapshot、scope、description、status、result、error、created_at、started_at 和 finished_at。时间使用 UTC 毫秒，未知时为空。error 复用 ErrorSummary。status 为 active、completed、failed、cancelled 或 interrupted，不重复 TaskRun 的暂停过程状态机。

| 业务字段        | 含义                                                                                   |
| --------------- | -------------------------------------------------------------------------------------- |
| scan_config_id  | 当时采用的扫描配置身份                                                                 |
| config_snapshot | 配置名称、作品类型、根目录、扫描规则、registerExistingContent 及实际采用的资料方案快照 |
| scope           | 当次全配置扫描或监听增量核对的实际范围；不从当前配置反推，也不表示提供公开 selected    |
| description     | 必要的运行说明，可空                                                                   |
| result          | 当次已形成的完整 ScanResult 或符合相同合同的有效部分结果                               |

接纳扫描时核对配置并固定快照。起始记录保存成功后，才开始可能产生副作用的工作。每次执行只有一条 ScanRun。配置删除后保留发生时的身份与报告，不级联清理。快照不复制凭据、原始响应或运行对象。

历史中的再次执行明确表示“运行当前配置”。配置已删除时只能查看报告，不能重放旧快照。scanner.runs 提供 list(query, { offset, limit })、get(runId) 和 clear(filter)，不依赖 TaskRun 历史或当前配置存在。

| 项目     | 合同                                                              |
| -------- | ----------------------------------------------------------------- |
| 列表筛选 | 扫描配置身份、状态及创建时间范围                                  |
| 时间边界 | createdFrom 包含起点，createdBefore 不包含终点；时间采用 UTC 毫秒 |
| 排序     | 创建时间倒序，运行 ID 提供稳定次序                                |
| 列表返回 | items 与相同查询范围的 total；不携带完整配置快照或大报告          |
| 详情返回 | 完整 ScanRun；不存在返回 null                                     |
| 清理范围 | 可限定配置和创建时间上界；只处理已结束记录                        |
| 清理返回 | 实际删除数量                                                      |

clear 省略时间上界时，删除选定范围内全部已结束记录，并返回实际数量。扫描历史与任务历史默认均保留，不自动过期。运行中或暂停中的记录不能清理。两套历史的清理互不级联，也不取消任务或删除正式产物。

ScanRun 与 TaskRun.result 各自保存完整 ScanResult，供扫描历史与任务中心独立查看和清理；生成与展示逻辑共用。保存次序和失败处理统一遵守[独立历史合同](tasks.md#history)。scanner 保留当前运行关联，直到整个 tasks.run 收尾结束。

报告构造、两份历史和结果交付共同计入[容量预算](../engineering/performance.md#results)。每项候选的副作用开始前预留其报告与检查点资源；达到预算时停止后续候选，返回 ResourceLimit 和已经形成的合法部分结果。历史列表继续只读摘要，详情按需读取，不以缩短报告维持成功状态。

扫描历史展示最后成功保存的报告；是否仍在执行由当前运行关联判断。已结束而终态无法确认的记录按[历史读取规则](tasks.md#history)展示，保留实际生成的合法结果。

<a id="extraction"></a>

## 原生线索提取

ScanConfig.definition.identification 为 { rules, recognizerIds }：rules 保存有序 ClueExtractionRule，recognizerIds 保存本配置明确选用的去重识别器 ID。两者默认均为空数组。有序线索规则直接保存在 rules 中。每项规则用正则匹配输入，再按明确的输出模板生成定位当前 Work 的线索。它们不写正式元数据，不改变 WorkType 或候选边界，不重命名磁盘内容，也不创建卷或话。没有规则是合法配置，新配置不会默认采用九项预设。

每个候选准备不可变的 baseName 和 relativePath，根始终是 ScanConfig.root_path。目录的 baseName 使用完整目录名，文件则去除最后一个扩展名；无扩展名文件保持原名，开头的单个点不算扩展名。relativePath 相对于扫描根，使用 `/` 分隔，文件保留扩展名，目录无尾分隔符，不含盘符或绝对路径前缀。原始文字及大小写保持不变，目录中的点号不按扩展名处理。

input 选择当前规则的匹配文本，界面分别显示“名称”和“相对路径”。规则自行声明所需文本，不在匹配失败后自动换用另一种。scanner 的文本始终描述待新增作品候选；已有作品内部文件使用 holdings 的[匹配文本](file-recognition.md#recognition-inputs)合同，两者复用正则与模板机制，各自保留明确的发现边界。

执行按列表顺序尝试启用规则。每项选择一份原始文本，并必须匹配完整字符串。第一条完整匹配的规则决定本次解释，随后验证输出。输出无效时记录问题，不能继续尝试后续规则或退回基准名称。

只有所有规则均未匹配时，才把 baseName 作为默认 name。规则已经匹配时，只交付该规则 output 明确生成的值，不补默认名称。输出至少包含一项合法线索，可以只有原文名、日期或完整身份。

规则之间不接力，不反复剥除文本，也不合并后续规则结果。例如，单前缀规则处理“[组] 作品_v1.2”时，结果仍为“作品_v1.2”；若要同时移除两端信息，应使用一条完整格式规则。

多个已选 recognizer 接收内容相同的只读原始输入和基础 clues，不包含其他 recognizer 的结果。基础 clues 可以为空。

<a id="rule-values"></a>

## 规则值与合法输出

```ts
interface ClueExtractionRule {
  id: string
  name: string
  enabled: boolean
  input: 'baseName' | 'relativePath'
  pattern: string
  ignoreCase: boolean
  output: {
    name?: string
    originalName?: string
    releaseDate?: {
      year?: string
      month?: string
      day?: string
    }
    externalIdentities?: readonly {
      source: string
      sourceId: string
    }[]
  }
}
```

id 是配置内部稳定的规则标识，在新建或采用预设时生成。规则保存在配置数组中，数组位置决定执行顺序，name 用于可编辑的展示名称。

pattern 只保存表达式正文，不含分隔符或 flags。执行固定使用 ECMAScript u，ignoreCase 决定是否加入 i，不使用有状态的 g 或 y。编译时增加不改变捕获编号的整串约束，并允许备选分支回溯到完整匹配。不能只检查首次局部结果的长度；$ 在末尾换行之前命中，也不表示覆盖全文。

output 只允许名称、原文名、日期分量和完整外部身份这些固定目标。所有叶字符串使用相同的替换模板：普通文字原样输出，`$<name>` 引用名为 name 的捕获组，`$$` 输出一个字面量 `$`。固定值是不含捕获组引用的模板。模板不支持编号捕获引用、整段匹配引用、条件、函数或脚本；需要字面量 `$` 时使用 `$$`。保存时解析正则的命名组声明并核对全部模板引用，未知组名或非法模板直接报错，不能仅运行一次空串来判断。

至少配置一项输出映射。releaseDate 映射不能为空；externalIdentities 若存在则必须是非空数组，每项明确配置 source 和 sourceId 模板。source 不是 providerId，其合法性不取决于扩展是否运行。UI 为各字段使用相同的模板输入与捕获组插入能力，预览、扫描和 SDK 提交共用配置及解释规则。

| 输出内容           | 处理与失败边界                                                                                                                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| name、originalName | 模板展开后只修整首尾空白，保留内部文字、大小写与标点；不按文字语言猜原文名，不做名称翻译或通用归一化；实际输出只有空白时为错误                                                                            |
| releaseDate        | 模板展开后，年份接受带可选正负号的十进制整数字符串，月日接受无符号十进制整数字符串；完整转换后复用 PartialDate 的安全整数、分量范围与联合日历校验，不使用 parseInt 截取有效前缀                           |
| 可选捕获组         | 模板引用的任一组在本次匹配中缺席时，整个输出字段缺席，不将它替换为空串后保留固定前后缀。捕获了空字符串则仍是实际值，展开后按目标字段校验；日期分量全部缺席时省略 releaseDate                              |
| 一份外部身份       | source 与 sourceId 的输出均缺席时省略该身份；两者均存在且合法时形成身份；只得到一侧、得到空值或不符合身份合同则报告问题。仅执行模板明确规定的组合，不隐式改写来源别名、转小写、执行 NFKC、截断或 URL 解码 |
| 多份外部身份       | 按映射顺序形成结果，以完整 source + sourceId 准确去重；不把同来源的不同标识合并，不据此判断来源中是否实际存在该记录                                                                                       |
| 命中但没有线索     | 作为当前候选的提取问题，不能当成未匹配，也不能靠默认名称掩盖该项没有产出的事实                                                                                                                            |

日期复用 [PartialDate](values.md) 合同。年份支持全部安全整数，0 表示公元前 1 年，负零规范为 0。缺少分量时不补值，可以只有月日、只有日或只有年日，但仍拒绝 02-30 和非闰年的 02-29。四位年份预设只限定命名形式，不缩小普通规则的日期值域。

ExternalIdentity 的两部分由明确模板生成。可以直接引用完整捕获值，也可以指定固定来源和编号前缀。模板展开后的身份仍须完整，不能把缺失组当作空字符串来补造编号。来源别名只有在规则明确写出规范来源时才完成转换，不建立按名称猜测来源的全局映射。

```text
^\[(?<source>vndb)_(?<sourceId>v[1-9][0-9]*)\][\t\p{Zs}]*(?<name>\S[^\r\n]*)$
```

```ts
output: {
  name: '$<name>',
  externalIdentities: [{ source: '$<source>', sourceId: '$<sourceId>' }]
}
```

这个规则可从输入取得 vndb/v17。相对路径“bangumi/subject/123/作品”也可以完整捕获 bangumi 和 subject/123。对于已经约定的“[bgm_123] 作品”命名，可以使用以下规则明确生成规范身份：

```text
^\[bgm_(?<id>[1-9][0-9]*)\][\t\p{Zs}]*(?<name>\S[^\r\n]*)$
```

```ts
output: {
  name: '$<name>',
  externalIdentities: [{ source: 'bangumi', sourceId: 'subject/$<id>' }]
}
```

该规则生成 name 为“作品”、source 为 bangumi、sourceId 为 subject/123 的线索。固定来源和前缀来自用户配置，来源记录是否存在及是否对应当前作品，继续由后续定位和采用规则判断。

需要超出正则与模板的识别能力时，可以由明确选用的识别器处理同一原始路径。识别器返回合法 WorkClues 或 null，返回身份时必须包含完整的 source 和 sourceId。原生 output 不接受任意对象路径、计算表达式或脚本，也不读取本地资料库来补全身份。

<a id="presets"></a>

## 九项命名规则预设

目录顺序也是同批采用时的追加顺序。九项预设的 input 都是 baseName，enabled 都是 true，但只有用户采用后才进入草稿，新配置的规则列表仍为空。

version-suffix 和 lang-suffix 的 ignoreCase 为 true，其余为 false。发行年预设的 output 为 `{ name: '$<name>', releaseDate: { year: '$<year>' } }`，其余预设为 `{ name: '$<name>' }`。

| 目录 ID／规则名称                       | 明确适用的命名约定                                                   | 正例与结果                                              | 反例或保留边界                                                         |
| --------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| bracket-both／两端方括号附注            | 一个或连续多个前置附注、一个结尾附注，中间为正文                     | [组][附注] 作品 [CHS] → 作品                            | [组] 作品 不匹配；[组] 作品 [A] [B] → 作品 [A]                         |
| multi-bracket-prefix／连续方括号前缀    | 至少两个连续前置块都明确属于附注                                     | [组][附注] 作品 → 作品                                  | [组] 作品 不匹配；[组][附注] 没有剩余正文，不回溯借用附注充当名称      |
| release-year-suffix／括号中的四位发行年 | 最后一个圆括号明确记录发行年                                         | 作品 (2024) → name = 作品、releaseDate = { year: 2024 } | 作品 (2024) 后日谈 不匹配；打包年份不应采用这一语义模板                |
| version-suffix／结尾版本标记            | 下划线后为 v 与点分十进制版本，且处于完整结尾                        | 作品_v1.2.3 → 作品                                      | 作品_v1.2_后日谈、作品_v1..2 与作品_v1.2beta 不匹配                    |
| lang-suffix／结尾语言标记               | 连字符或下划线后为 CHS、CHT、JP、EN、KR、SC、TC 之一，且处于完整结尾 | 作品_CHS、作品-en → 作品                                | 作品_EN_后日谈 与作品_ENGLISH 不匹配；不写入原始语言或更改资料语言偏好 |
| bracket-prefix／单个方括号前缀          | 只有第一个块被约定为前置附注                                         | [组][标题] 作品 → [标题] 作品                           | 不继续剥除第二个块；作品 [组] 不匹配                                   |
| paren-prefix／单个圆括号前缀            | 只有第一个圆括号块被约定为前置附注                                   | (组) (标题) 作品 → (标题) 作品                          | 不继续剥除第二个块；作品 (组) 不匹配                                   |
| bracket-suffix／单个方括号后缀          | 只有最后一个方括号块被约定为附注                                     | 作品 [A] [B] → 作品 [A]                                 | 作品 [附注] 后日谈 不匹配，不把正文中间的块当作结尾                    |
| paren-suffix／单个圆括号后缀            | 最后一个圆括号块是普通附注，没有日期语义                             | 作品 (2024) → 作品，仅 name                             | 不产出 releaseDate；作品 (附注) 后日谈 不匹配                          |

九项预设的完整输入均拒绝 CR、LF、U+2028 和 U+2029。预设支持成对的 []、【】、() 和（），不接受错配、同类嵌套或其他任意 Unicode 括号；块之间允许制表符和 Unicode 空格。自定义规则仍按其表达式解释输入，通用编译与匹配机制不另外剔除或统一禁止这些字符。

连续前缀和两端规则假定开头所有方括号块都是附注，因此正文不能以 [ 或 【 开始。这类标题应选择单前缀规则或自定义规则。两端规则只移除一个末尾块。

发行年预设中的 0000 表示 year = 0，不适用于把 0000 当成未知年份的目录。12000、负年或纪元文字可以另配规则，未匹配四位预设不意味着日期非法。通用圆括号后缀没有日期语义。

```text
bracket-both
^(?:(?:\[[^\[\]【】\r\n\u2028\u2029]+\]|【[^\[\]【】\r\n\u2028\u2029]+】)[\t\p{Zs}]*)+(?<name>(?![\[【])\S[^\r\n\u2028\u2029]*?)[\t\p{Zs}]*(?:\[[^\[\]【】\r\n\u2028\u2029]+\]|【[^\[\]【】\r\n\u2028\u2029]+】)$

multi-bracket-prefix
^(?:(?:\[[^\[\]【】\r\n\u2028\u2029]+\]|【[^\[\]【】\r\n\u2028\u2029]+】)[\t\p{Zs}]*){2,}(?<name>(?![\[【])\S[^\r\n\u2028\u2029]*)$

release-year-suffix
^(?<name>\S[^\r\n\u2028\u2029]*?)[\t\p{Zs}]*(?=\([0-9]{4}\)$|（[0-9]{4}）$)[(（](?<year>[0-9]{4})[)）]$

version-suffix
^(?<name>\S[^\r\n\u2028\u2029]*?)_v[0-9]+(?:\.[0-9]+)*$

lang-suffix
^(?<name>\S[^\r\n\u2028\u2029]*?)[-_](?:CHS|CHT|JP|EN|KR|SC|TC)$

bracket-prefix
^(?:\[[^\[\]【】\r\n\u2028\u2029]+\]|【[^\[\]【】\r\n\u2028\u2029]+】)[\t\p{Zs}]*(?<name>\S[^\r\n\u2028\u2029]*)$

paren-prefix
^(?:\([^()（）\r\n\u2028\u2029]+\)|（[^()（）\r\n\u2028\u2029]+）)[\t\p{Zs}]*(?<name>\S[^\r\n\u2028\u2029]*)$

bracket-suffix
^(?<name>\S[^\r\n\u2028\u2029]*?)[\t\p{Zs}]*(?:\[[^\[\]【】\r\n\u2028\u2029]+\]|【[^\[\]【】\r\n\u2028\u2029]+】)$

paren-suffix
^(?<name>\S[^\r\n\u2028\u2029]*?)[\t\p{Zs}]*(?:\([^()（）\r\n\u2028\u2029]+\)|（[^()（）\r\n\u2028\u2029]+）)$
```

采用预设会创建普通规则草稿，生成新 id，并使用当前界面语言提供可编辑名称，不保持持续模板绑定。新规则按目录顺序追加，原规则不动，用户可以自行重排。不能只按 pattern 判断规则相同，也不能在后台把具体规则移到宽泛规则之前。

预览应标明实际命中的规则，后续规则不参与结果。未保存草稿不会启动监听。扫描线索规则、[资料方案](metadata-presets.md)和[展示柜](../ui/showcase.md)分别管理自己的预设目录、配置值和采用操作。引导调用相应模块的创建能力，后台触发由各[功能拥有者](tasks.md#automation)负责。

<a id="validation"></a>

## 保存校验与执行隔离

保存时严格校验整份规则列表，包括停用项的结构、唯一 id、名称、语法、整串编译、命名组、模板引用、输出目标和成对身份映射。停用不豁免非法定义，不完整输入只能留在草稿。格式损坏的存储保留原值并报告问题，停止相关执行；重建或删除沿[共同规则](values.md#read-write)处理。

预览和实际执行共用文本准备、编译、匹配、模板展开及输出校验。预览分别显示捕获内容和最终线索，执行快照保留当时的规则 id、名称与 output，不能用后来的定义解释旧报告。配置无法编译或模板无效时，在接纳执行前拒绝。某个候选输出错误时，只记录该项问题并继续其他候选，不换一条规则重新解释它。

自定义正则必须在可终止的独立执行单元中求值，编译和匹配共同受预算及取消约束。在主进程同步正则外包一层 Promise 超时，不能中止实际求值，因此不满足要求。

holdings 的文件识别方案复用同一执行隔离、预算与取消机制，具体超限影响范围遵守[文件规则合同](file-recognition.md#recognition-output)。共同机制只执行文本规则，不接管作品发现、分部查询或关联写入；业务结果与失败仍由各调用方负责。

scanner 集中维护有限执行预算，预览和实际扫描共用同一限制。预算约束规则编译及单个候选的匹配和线索生成，不将整个目录遍历或资料获取的总时长算作正则超时。超限时终止执行单元，停止本次配置求值，并保留已完成与未完成范围；未处理项不能记为未匹配。阈值由具名的内部实现参数定义，验证覆盖正常规则、恶意回溯、取消及终止后的资源释放，不增加用户必填性能参数，也不自动延长限制后重试。

验收覆盖成对中英文括号、空正文、括号错配、版本和语言后缀、末尾换行、整串回溯、规则顺序及不接力行为，以及保留扩展名的相对路径。九项预设分别验证名称、附注块及输入边界中的 CR、LF、U+2028、U+2029 均不命中；自定义规则明确接受这些字符时，按其表达式正常匹配。输出校验覆盖固定值、捕获引用及其组合、字面量 `$`、未知组名、可选组缺席、四类线索、日期精度、安全整数、零年和闰年、身份双方有无及单缺、空值和完整父范围。相同配置从 UI、SDK、预览和扫描进入时得到相同线索。实际扫描还须验证预算、取消及资源释放。

例如，“[vndb_v17] 中文名｜原文名 (2024-02-29)”可用于验证四类线索共同捕获，但它不是第十项预设。

## 内部职责与执行拥有者

scanner 按保存的配置、持续运行上下文、单次扫描和报告组织实现。manager.ts 拥有各配置的运行上下文及完整扫描调用，具体发现、识别与报告保存由相应能力承担。

| 内部位置       | 负责内容                                                                     |
| -------------- | ---------------------------------------------------------------------------- |
| manager.ts     | 扫描接纳、配置运行上下文、待核对范围、当前运行关联、观察及完整收尾           |
| configs.ts     | 扫描配置的读取、保存、删除、排序及定义校验                                   |
| discovery.ts   | 发现范围、路径过滤、候选边界及稳定路径顺序                                   |
| extract.ts     | 原生命名规则的线索提取，供预览与实际扫描共用                                 |
| recognizers.ts | 原生识别器目录、实现登记及本次明确选用的调用                                 |
| preview.ts     | 按草稿组织只读发现与原生规则预览，不执行入库                                 |
| scan.ts        | 处理一次已接纳扫描的候选，调用识别与 ingest 的完整单项业务，形成实际扫描结果 |
| watch.ts       | 建立指定范围的监听，报告路径变化、失效与实际可用性                           |
| runs.ts        | ScanRun 的报告保存、查询和清理                                               |

manager 统一拥有同一配置的在途扫描与尚未接纳的核对范围。watch 拥有真实监听句柄，manager 根据其状态和当前运行引用组成 ScannerState，不保存另一套任务暂停或取消标志。configs 的正式修改通过明确的提交后绑定影响监听和后续接纳；已接纳扫描仍使用自己的快照。

完整 scan 由 manager 接纳并调用 tasks.run。在真实任务上下文中取得 TaskRunRef，按[扫描报告合同](#history)通过 runs 的内部写入能力建立 ScanRun，并保存本次身份关联。起始报告保存成功后才进入可能产生业务副作用的扫描。公开 scanner.runs 仍只提供历史查询与清理，不开放创建、伪造或修改运行报告的接口。

scan.ts 执行已接纳的业务，通过 ingest 声明的[原生单项业务调用](metadata.md#organization)处理候选，报告真实进度与检查点。manager 使用同次执行形成的报告组织 ScanRun 保存和任务结果交付，tasks 负责 TaskRun 的状态与托管收尾。只有整个 tasks.run 调用结束后，manager 才按本次身份清除运行关联和忙碌占用，再处理仍有效的待核对范围。

报告与任务记录遵守[独立历史保存边界](tasks.md#history)。scanner 在业务回调内保存 ScanRun，tasks 在回调结束后完成 TaskRun；完整 scan 调用仍等待全部托管收尾。两处复用同次生成的结果，不通过联合提交回调或共享事务协调各自历史。

配置删除或关闭监听时，停止相应监听并丢弃尚未接纳的请求，已经接纳的执行继续完成自身收尾。配置删除后只要执行仍存在，运行观察就继续有效；两者都不存在后才结束该观察。报告保存失败按[历史失败规则](#history)停止后续业务并返回实际失败，不由 finally 补写、重新执行或从 TaskRun 推测扫描结果。

manager 负责完整操作和运行集合，具体算法与存储仍由上述能力拥有。其他 feature 使用 scanner 的公开能力，不调用 scan.ts 的内部执行步骤或直接改变运行集合。任务引用、报告与配置分别保持自己的身份和寿命。
