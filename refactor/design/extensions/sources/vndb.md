# VNDB 接入设计

VNDB 提供视觉小说、角色、人员与组织资料，以及本人清单和个人记录。本文定义来源身份、字段、关系、标签、图片、读取路径及账号操作的采用规则。

VNDB 的主要结构化资料通过 [Kana HTTP API](https://api.vndb.org/kana)读取；API 缺少的 Staff 主体类型从官网公开档案读取，不能默认所有 Staff 都是人物。扩展的整体交付范围见[官方目录](../catalog.md)，本页负责来源特有的采用规则；共同 provider 合同、个人记录同步与凭据规则继续由相应文档定义。

关系成员由本页确定的采用规则产生，不随普通属性的选择改变。即使关系请求的 fields 为空，主体类型、原版范围、职责、配音语种和官方关系判定所需的来源数据仍须读取，包括用于判定的来源备注。返回对象与关系的普通属性则遵守本次字段选择，不因内部读取就额外交付 note 或其他属性。

<a id="identities"></a>

## 对象与正式身份

正式身份的 source 为 vndb，sourceId 保留来源原生类别与完整编号。

| 来源记录                       | 本体对应             | 身份与采用规则                                                  |
| ------------------------------ | -------------------- | --------------------------------------------------------------- |
| VN，v 编号                     | 游戏                 | 使用 VN 身份，不以某条 Release 替代                             |
| Character，c 编号              | 角色                 | 使用该角色档案自身身份，作品定位另存关系                        |
| Staff，s 编号                  | 按实际主体类型确定   | staff.id 是主档案身份；人物与公司等类型不能混同，aid 只标识署名 |
| Producer，p 编号，type = in    | 人物                 | 来源明确表示个人，不能按 p 前缀建立组织                         |
| Producer，p 编号，type = co/ng | 组织                 | 分别表示公司或社团，保留实际主体身份                            |
| Release，r 编号                | 资料读取中的发行记录 | 不建立独立作品或本体发行版实体，不把 r 编号作为游戏身份         |

同一 staff.id 下的不同 aid 属于同一主体。aid 可用于来源查询与解释作品署名，不形成独立条目、艺名实体或正式来源绑定。producer 与 staff 是不同来源记录；只有来源明确的身份对应或用户确认才能将其绑定到同一本体条目，不能仅按同名合并。

Staff 类型从同一 s 编号的官网公开档案 Type 行读取。Person 对应人物，Group、Company 和 Repository 对应组织，分别进入 personWorks 与 organizationWorks；其中 Repository 按独立署名的素材品牌或服务采用。API 中的 gender、主体名字或 s 前缀不能代替类型判断。同次读取中，同一 staff.id 的类型只需取得一次，别名命中和多项工作复用该结果。页面读取失败、缺少 Type 或出现未识别类型时按普通来源失败处理，不退回人物类型，也不把受影响的参与集合当作已完整取得。

已验证 s81 为 Person，s167（ZIZZ STUDIO）为 Company，s557（Elements Garden）为 Group，s12140（魔王魂）为 Repository。后者保留自己的组织身份，不据此建立经营者或素材作者的人物档案，也不将其与名称相近的个人合并。实际页面与 API 证据见[主体类型验证](../../../verification/evidence/vndb/staff-types.md)。

<a id="names"></a>

## 名称、别名与本作署名

对于已确认属于人物或组织的 Staff，正式名称与原文名称从主档案取得，按既有名称与语言规则采用。来源别名进入 aliases，作品中的一次署名不覆盖主体名称。人员和组织列表显示当前正式名称；作品实际署名写入对应参与关系的 note，在关系详情中呈现。

来源搜索与详情读取采用不同查询：

| 操作                   | 来源查询                                           | 结果采用                                                       |
| ---------------------- | -------------------------------------------------- | -------------------------------------------------------------- |
| 按名字或艺名搜索       | POST /staff 的 search 筛选，不附加 ismain = 1      | 保留别名命中，按 staff.id 对应主体；同一主体的多条署名结果合并 |
| 读取已确定主体的主档案 | POST /staff 同时筛选 id 与 ismain = 1              | 读取主名与 aliases，作为主体资料依据                           |
| 读取作品参与           | 读取 VN 中 staff 或 va.staff 的 id、aid 及实际署名 | id 对应实际主体，实际署名进入本作关系说明                      |

比如 s81 的主名为浅川 悠，在 v11301 中以小岩井 小百合署名。本体仍对应同一人物，别名可用于搜索，本作配音关系的 note 保留“署名：小岩井 小百合”。这段文字仅供阅读，不作为人物匹配、别名身份或其他业务判断的输入。

同一工作关系中有多个明确署名时，与来源已有说明共同合并保留，遵守[关系业务键与说明规则](../../domains/relations.md#model)。不会因为署名不同新增重复关系。资料读取仍按本次字段选择交付 aliases、note 等属性。

<a id="search-order"></a>

## 搜索相关度与分页

带关键词的来源查询明确使用 sort = searchrank、reverse = false，保留 API 的相关度顺序，不在取得结果后按名称、翻译名称或站点评分重新排列。searchrank 要求顶层是 search，或顶层 and 中只有一个 search 条件；按已知身份读取及没有关键词的完整名单使用各自的稳定顺序，不强行附加 searchrank。

Staff 搜索继续包含别名。同一 staff.id 的多个署名命中归并在首次出现的位置，补主名和判断主体类型都不改变这一位置。人物与组织若需要查询不同原生目录，各查询分别保持源站顺序，不把未返回的相关度分数自行补成跨目录评分，也不将搜索首项当作唯一对应。

cursor 继续表示同一查询、过滤和设置下的下一段来源结果，不能把首页当作完整名单。搜索按需续读，resolve 所需完整候选与资料读取的完整分页由扩展内部完成，沿共同合同区分。

人物搜索同时查询 Staff 与 type = in 的 Producer；组织搜索同时查询 Staff 与 type 为 co、ng 的 Producer。Staff 候选先核对主体类型，只保留本次 Entry 类型。两个目录内部保持原生顺序，合并时从 Staff 开始交替取一项；一个目录结束后继续另一个目录。类型不符和同一 staff.id 的重复署名不占本页结果数量，读取继续到取得本页目标数量或两个目录结束。cursor 保存各目录尚未交付的结果和后续读取位置，不按交替位置制造相关度分数，不按同名合并 s、p 身份。

searchrank 使用源站相关度，但不承诺与网页逐项同序。当前 API 在相关度相同时按来源 id、subid 排列，网页列表则使用名称等后续条件；实测 fate、Rin、Asakawa 的列表次序均有差异。扩展保留各查询的 API 原生顺序，不模仿网页追加无法可靠复现的排序。

<a id="read-paths"></a>

## 读取上下文与关系查询

来源提供 game、character、person 和 organization 四种 Entry 上下文；不声明动画、漫画、小说或 Part 能力。各上下文的根与相关对象使用相同的身份、字段和关系规则，反向读取只改变取得候选的入口，不产生另一份参与事实。

| 读取目标                 | 真实查询与采用                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 游戏根资料与作品关系     | POST /vn 按 v 身份读取所选字段及 relations；按官方关系规则采用                                                                                           |
| 游戏的角色               | POST /character 使用 vn = [id = v 身份]，读取 vns 中对应作品及其发行范围，沿角色关联规则归并                                                             |
| 游戏的人员与组织         | /vn 的 staff、va 与 /release 的 producers 共同形成参与事实；各分支分别使用原版职员、原作语种配音及首个正式原语种完整版规则                               |
| 角色根资料与登场作品     | POST /character 按 c 身份读取根字段与 vns；每个作品分别核对所需发行范围，不把其他作品的定位套用到当前作品                                                |
| 角色对应的配音工作       | 先取得该角色的登场作品，再读取各 VN 的 va；只取 va.character.id 与该 c 身份相等且符合配音范围的记录                                                      |
| s 身份的根资料与参与作品 | POST /staff 以 id 和 ismain = 1 读取主档案；POST /vn 使用 staff = [id = s 身份] 取得候选，再按同一游戏参与规则筛选此主体的工作                           |
| p 身份的根资料与开发发行 | POST /producer 按 p 身份读取根资料；POST /release 使用 producer = [id = p 身份] 取得关联 VN 候选，再对每个 VN 完整核对首个正式原语种完整版中的此主体职责 |

Staff 反向筛选可以命中配音参与；实际关系仍从 VN 的 staff 和 va 字段取得，不能因筛选命中就补出职责。Producer 参与过某条发行也只证明它是候选，不能直接当作本体所采用范围内的开发方或发行方。角色的 seiyuu 筛选不替代带有实际 VN 和 character 的三方配音事实。

反向路径取得的作品按 v 身份去重，再执行本页已定义的范围和角色映射。仅请求当前人物或组织的参与关系时，只交付这个主体的工作；相关端点的普通资料继续遵守 fields。根 identity 缺席而明确提供相关对象 refs 时，按该身份的原生目录读取所选字段，不推造根身份或关系。

按身份查询与关系候选查询使用 sort = id、reverse = false，每次 results 为 1–100，按 page 连续读取到 more = false。Staff 主档案读取带 ismain = 1；搜索使用前节的独立分页。需要完整关系时，所有候选页和依赖的范围查询都完成后才交付数组；局部失败遵守共同 partialResult 合同，不能用首页或某次命中代替完整集合。

primaryImage 候选只对游戏和角色开放，backdropImage 只对游戏开放；候选读取使用下文的实际图片用途与归属规则。人物和组织不声明缺少来源依据的图片字段，iconImage 与 titleLogo 也不因通用接口存在而开放。公开资料不读取本人列表；个人导入与同步使用独立的账号路径。

上述反向请求的实际端点与关联字段见[读取路径验证](../../../verification/evidence/vndb/read-paths.md)。这些样本证明请求可用及实际返回的关联，不替代完整扩展和全量分页验收。

<a id="ordinary-fields"></a>

## 普通资料字段

资料字段使用本体已有的[固定目录](../../domains/metadata-profiles.md#fields)，不把来源的所有列变成本地字段。以下规则只交付本次实际请求的属性，未知、空值与未回答仍按共同合同区分。

| 来源资料                              | 本体字段                    | 采用方式                                                                                                 |
| ------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| VN.titles                             | name                        | 按 preferredLanguages 选择实际存在的标题；无匹配或未指定偏好时取 main 标题的 title，不自动翻译           |
| VN.titles 中 main 标题的 title        | originalName                | 采用来源明确的原始语言标题，不能由选中的译名反填                                                         |
| Character／Producer 的 name、original | name、originalName          | name 按来源已有的名称形式与语言偏好取得；默认优先 original，否则 name。originalName 只采用有原文依据的值 |
| Staff 主署名与 aliases                | name、originalName、aliases | 使用已确定的主档案、别名和署名规则，不把作品署名改成主体主名                                             |
| aliases、实际存在的其他标题与拉丁转写 | aliases                     | 保留来源已有名称形式，按共同名称规范去重，不因此建立新条目                                               |
| VN.olang                              | originalLanguages           | 转为规范语言标识组成的单项列表；languages 是可用语种，不能当作原作语种                                   |
| VN.released                           | releaseDate                 | 按来源给出的年、年月或年月日保存精度；null 与 TBA 表示没有可采用日期，不补出日期或使用当前时间           |
| description                           | description                 | 按下节规则剔除显式剧透，再转为共同 Markdown                                                              |
| extlinks 的 url、label                | externalLinks               | 按实际完整 URL 与来源称谓提供链接；跨站正式身份仍须满足共同身份与粒度规则                                |

VN.released 表达来源的首次正式公开日期。源站当前计算包含官方、非试玩的部分发行，并不限于原作语种；这与本页用于开发、发行署名的“首个正式原语种完整版”是两项不同事实。采用来源的日期声明，不将它冒充所选完整版的日期，也不把完整版筛选结果反写成整部作品最早公开的日期。

游戏和角色的 image 可提供 primaryImage 的原图候选，来源尺寸只作为候选信息，实际字节仍走共同图片验证与准备流程。各用途与范围见[图片候选](#images)，不能把 image.sexual 直接等同于条目 isNsfw，也不凭一张图片补出所有图片能力。

已核验的 Staff 与 Producer API 没有出生、逝世、成立、解散日期或独立肖像字段；这些能力不凭空声明为已经具备，来源原有简介仍可正常采用。站点 average、rating、length_minutes 和 devstatus 不写入用户评分、游玩时长或个人状态，也不挪作其他媒介的声明时长与连载状态。

<a id="descriptions"></a>

## 简介与显式剧透

VNDB 扩展负责解析源站正文格式，在转换为 Markdown 前移除 spoiler 标记所表示的完整片段，包括其中的文字、链接与图片。嵌套、转义以及 raw、code 中的字面标记按源站格式语义处理，不能只删除定界标记而留下剧透文字，也不能误删普通示例。

扩展只交付转换后的 Markdown，剧透片段中的图片引用也不进入返回值。剔除后没有剩余正文时，返回该字段允许的明确空值；读取或转换失败仍按普通执行失败处理。这是 VNDB 扩展内部的正文采用规则，应用沿用既有资料处理流程。

真实样本 c42 的 description 含有显式 spoiler 片段，正文中的其他介绍和来源链接可以保留。剔除正文片段不删除角色，也不改变 workCharacters、personWorks 或 entryTags 的结构化剧透标记。扩展的正文转换验收见[普通字段验证](../../../verification/evidence/vndb/common-metadata.md#明确标记的剧透正文)。

<a id="character-fields"></a>

## 角色字段与定位

角色保存一份当前采用的资料，普通字段按下表投影：

| 来源字段                  | 本体字段     | 采用方式                                                                       |
| ------------------------- | ------------ | ------------------------------------------------------------------------------ |
| birthday                  | birthDate    | 保存已知月、日，不推断年份；来源用于未知分量的 0 不写成合法月份或日期          |
| age                       | age          | 以年为单位的 number 值，不根据生日或当前年份推算                               |
| height、bust、waist、hips | 对应尺寸字段 | 以厘米为单位保存 number 值，不额外取整                                         |
| weight                    | weight       | 以千克为单位保存 number 值，保留实际精度                                       |
| cup                       | cupSize      | 保留来源实际短文本，不截断为固定字母范围                                       |
| blood_type                | bloodType    | a、b、ab、o 对应既有分类；null 保持未知                                        |
| gender 的非剧透值         | gender       | m、f、o 分别对应 male、female、nonBinary；空值与 a 所表示的未确定信息对应 null |

本体性别只有一个当前值，读取来源明确提供的非剧透 gender，不自动改用数组中的剧透值，也不另用 sex 推断 gender。人物 Staff 的 m、f 按相同共同分类采用，但只适用于已经确认的 Person。数值、部分日期和空值使用各自的既有校验，不把缺项补成零。

对于已经确定采用的作品角色关联，VNDB 的 main（主角）与 primary（主要角色）均对应本体 main，细分称谓保留在 note；side 对应 supporting，appears 对应 cameo。使用本体已有分类，不为来源等级另加枚举。vns.spoiler 的 1、2 均对应 isSpoiler = true，0 对应 false；同一业务键归并时沿共同规则保留保护。

<a id="character-scope"></a>

## 角色关联的发行范围与归并

角色名单覆盖同一 VN 正式采用的原作语种版本，包括后续加入的角色，不以首个完整版的日期截断。它表达角色与作品的关联，不宣称角色出现在所有发行版，也不复用职员 eid 或开发、发行署名的首发范围。

从 Character.vns 读取作品身份、role、spoiler 和 release。release 为 null 时，按来源的“All (full) releases”范围采用；存在具体发行记录时，同时核对 official、languages 和该记录的 vns.rtype：仅采用官方、包含作品 olang、且当前 VN 的 rtype 为 complete 或 partial 的记录，排除试玩和非官方发行。多语发行只要实际包含原作语种即可，不凭发行标题中的 English 等字样排除。正式更新补丁也按其真实归属与内容范围判断，不因包装形式另建作品。

同一作品与同一 c 身份的已采用记录归并为一项 workCharacters，按来源 main、primary、side、appears 的顺序取最高定位，再映射为本体分类。任一已采用记录含剧透时，归并结果的 isSpoiler 为 true；被排除的发行不参与定位或剧透计算。note 保留不同版本的实际定位及必要的版本说明，相同说明去重；不保存隐藏的发行范围字段，也不在后续业务中解析 note。role、note、isSpoiler 的输出仍遵守本次字段选择。

因此，v5 的 c1868、c1871 在原版是 side，在 Ecstasy 等后续版本是 primary，归并后均为 main，并保留版本差异。c1875 虽未列入原版，仍作为后续正式版本的主要角色采用。原作语种配音也可以引用这项作品角色关联，不另建一条无版本或原版镜像。

作品入口只采用指向当前 VN 的记录；角色入口只采用该 c 身份实际列出的作品记录。两种入口使用同一范围和归并规则，不把发行包中其他 VN 的身份变成该角色的出场关系。完整读取应完成角色查询分页，并核实所有会影响本次集合的发行范围；必要资料读取失败时按普通来源失败处理，不能通过丢弃未核实项伪装完整名单。

<a id="角色实例与独立身份"></a>

## 角色实例与独立身份

VNDB 的 instance 可能表示年龄或形态差异、平行世界的不同演绎，也可能承载身份剧透，不等同于同一档案下的别名。每个 c 编号仍表示自己的来源档案；不因实例联系或同名而自动合并，不沿 Other instances 扩大作品角色名单，也不把另一个实例的生日、图片或参与关系混入当前角色。

例如 c34 与 c3529 虽同名，来源分别给出 2 月 3 日与 2 月 4 日的生日，并具有不同作品关联，应各自按本身身份与资料回答。API 未提供实例关系，不据此虚构通用角色关系或角色版本实体。用户认定两条本地记录确应合并时，继续使用已有的显式合并与身份冲突规则；每个本地角色仍只保存一套当前采用的设定。

<a id="staff-scope"></a>

## 原版职员范围

自动取得的职员名单采用原版范围。读取 VN.staff 时请求 eid，只保留 eid 为 null 的记录，再按实际主体与职责归并，分别对应人物工作或组织参与。数值 0 也是具体版本编号，不属于原版。官方译版、移植版或其他版本的职员都不混入这一名单，不因版本为官方、与原作同语种或符合界面语言而扩大范围。

原版记录中的实际署名、职责和必要说明照常保留。版本编号只用于解释来源记录，不持久化为本体版本身份。资料字段的语言偏好不改变这项参与范围。

本节确定的是 staff 数组的采用规则。开发方与发行方使用本页的首个正式原语种完整版规则，va 配音使用原作语种采用约定，不能因为它们都位于同一 VN 下就认为范围相同。各分支须遵守资料读取的完整性合同，不能把遗漏的分支当作已完整取得的 personWorks。

<a id="staff-roles"></a>

## 职员职责映射

先按原版范围筛选，再读取实际主体类型。Repository 使用下节的素材提供规则；Person、Group 与 Company 按下表采用来源类别，并以明确的岗位备注补充或细化。表中 other 保留已确认的参与及原始职责，不把人物职责强行赋给组织，也不将局部工作泛化为整个作品的创作或开发。

| 来源职责   | 人物默认职责    | Group／Company 默认职责 | 解释要求                                              |
| ---------- | --------------- | ----------------------- | ----------------------------------------------------- |
| scenario   | scenario        | other                   | 脚本工作不推导为整部游戏的 creator                    |
| director   | director        | other                   | 保留总负责人、助理等实际限定，不套用到翻译团队负责人  |
| chardesign | characterDesign | other                   | 不据此关联作品中的全部角色                            |
| art        | art             | other                   | 类别宽泛，不统一转换为原画或角色设计                  |
| music      | music           | music                   | 保留作曲、编曲等具体工作                              |
| songs      | music           | music                   | 保留演唱职责与曲目说明，不映射 voiceActor             |
| translator | translator      | localization            | 仍只采用已筛出的原版职员，不回收其他版本的名单        |
| editor     | editor          | other                   | 来源表示文字编辑，不推导为影像剪辑                    |
| qa         | other           | other                   | 保留测试、除错、校对等说明，不仅凭类别推导 programmer |
| staff      | other           | other                   | 具体岗位可以由明确备注给出                            |

来源备注中已经明确表达的职责可以映射到本体已有、且适用于当前主体和作品类型的值。适配器识别完整岗位短语及其语境，不以任意子串或人物职业介绍猜测职责。多个明确的独立工作分别采用，助理、协力、总负责、负责曲目等限定保留在 note，不额外生成职责。未识别的说明继续保留，未识别的来源 role 则按普通来源字段失败处理，不能冒充 staff 或 other。

| 明确岗位表达                                       | 人物采用        | 限定                                                            |
| -------------------------------------------------- | --------------- | --------------------------------------------------------------- |
| Programming                                        | programmer      | 不能由 Debug、Development control 或未说明含义的 Scripting 推导 |
| Producer、Executive producer                       | producer        | 保留原始称谓及具体负责范围                                      |
| Original concept                                   | originalCreator | 原案不等于实际编写脚本                                          |
| Storyboards                                        | storyboard      | 游戏分镜，不推导动画系列构成或作画监督                          |
| Character sprites、Event CG drawing                | illustration    | 仅在明确表示实际绘制时采用，不推导 characterDesign              |
| Background art、Event CG coloring、System graphics | art             | 保留背景、上色或界面图像工作，不推导程序开发                    |

职责映射以完整署名与实际工作含义为依据。例如明确的 Programming 采用 programmer，含义未明确的 Scripting 保留 other；producer 短语按其实际作用范围解释。Group 与 Company 可以根据明确备注采用已有职责，如 originalCreator。缺少同义职责时使用 other 并保留原说明，公共枚举沿既定目录使用。

一条来源记录被细化为明确职责后，不再复制一条笼统的父类别。例如 staff＋Programming 只产生 programmer；music＋OP arrangement 仍只有一条 music。若备注确实同时记有制作人与未进一步说明的 OP 影像工作，可以分别保留 producer 和 other，并保留各自说明。相同主体、职责及角色的重复署名按共同业务键合并。职责解释不会扩大原版、所选开发／发行批次或原语种配音的采用范围。

以上解释只发生在来源适配阶段，原始职责、实际署名及必要说明随结果保留。本体关系 note 继续作为阅读内容，不被再次解析来改变职责。

<a id="asset-providers"></a>

## 素材提供署名

Repository 在已采用的原版职员名单中出现时，以组织 other 保留素材提供事实。关系 note 保留原始职责、作品署名与来源说明，并按明确的素材种类写明“音乐素材提供”“图像素材提供”等；种类不明时只写“素材提供”。例如 s12140 在 v3727 中的来源职责为 music、说明为 BGM，对应组织 other，说明为音乐素材提供并保留 BGM。

素材被作品采用不能单独证明该主体为本作直接创作，不由此推导 creator、music 等制作职责，也不代替具体素材作者的身份。素材提供继续使用现有组织与参与关系，不新增素材库实体或专属职责。主体资料、正式来源绑定与别名规则与其他组织一致。

<a id="first-release"></a>

## 首个正式原语种完整版的开发方与发行方

作品档案的开发与发行署名采用首个正式原作语种完整版的批次。VN.developers 汇总了不同发行记录中的开发方，不能直接用作这个名单。来源没有专用的原版 Release 标志，本节的批次范围由以下规则确定，与普通 releaseDate 的首次正式公开含义分开。

读取目标 VN 的 olang，并完整读取符合以下条件的 Release：关联目标 VN，该目标在 vns 中的 rtype 为 complete，official 为 true，patch 为 false，languages 包含原作语种。rtype 须核对当前目标的记录，不能用同一发行包中另一部作品的完整状态代替。查询按来源分页取得全部候选，再确定最早发行日。

所选批次包含同一最早日期的全部候选，包括同日不同平台与包装版本。按 producer.id 分别归并 developer 和 publisher 为 true 的主体，不能只取第一条发行记录。个人开发方映射 creator，组织开发方映射 developer；人物与组织的发行方均映射 publisher。具体名称和主体身份沿前述规则取得。

日期按来源的 YYYY、YYYY-MM、YYYY-MM-DD 和 TBA 解释，该批次以明确日期为依据。TBA 不参与日期比较。若没有完整日期，或其他候选的日期缺失、部分日期可能早于或落在最早完整日期当日，则资料不足以确定所需批次。依赖该范围的关系集合按普通来源失败处理，其他已经取得且符合完整性要求的独立资料可以通过 partialResult 返回；不补出月份或日期，也不把无法确定写成空名单。

开发与发行的采用范围不随界面语言、持有平台或当前启动文件变化。后续移植、译版和再版的开发或发行主体不因此进入该名单，不自动建立发行版对象。

<a id="voice-scope"></a>

## 原作语种配音

配音采用[本体范围](../../domains/relations.md#voice-scope)：只记录作品正式采用的原作语种角色—声优关系，不收录译配。作品归属与语种满足条件即可，不按首发日期截断；v11 的 Realta Nua 配音是说明这一范围的例子，不形成特殊补充流程。

当前 va 只提供人物、角色与自由文本 note，没有独立的配音语种或发行版本字段。本接入采用已确认的来源约定：明确标注配音语种时，与 VN.olang 比较，只保留原作语种；未标注语种时，按作品原作语种采用。空备注及仅说明版本的备注都适用这一缺省。来源明确标为非正式采用的配音不进入名单。

语种判断读取来源的 va.note。Japanese、English 及 English (Uncredited) 等明确语种标注先确定语言，再保留括号中的署名或版本说明；English (original release) 仍是英语，不能被 original release 改判为原作语种。声优的 staff.lang 表示母语，不用于这项筛选，界面语言和资料语言偏好也不改变结果。筛选发生在来源适配时，保留到本体关系 note 中的文字仍只供阅读，不作为后续业务控制字段。

这是本接入对来源资料的采用约定，不是 VNDB API 或编辑规范保证的字段语义。适配器须识别明确语种标注，缺省则依赖源站标明译配，漏标记录仍可能被误收。设计按这一资料质量边界采用，不增加语种选择设置，也不将其解释为支持译配。语种采用后，再按人物、角色与职责的业务键归并，并保留实际署名和来源说明。

<a id="work-relations"></a>

## 官方作品关系

读取 VN.relations 时同时请求 relation、relation_official 与目标 VN 身份，只采用 relation_official 为 true 的直接关系。false 的记录不进入本次资料回答，不能由关系名称、作品名称或同人属性替代这个判断。缺少或无效的官方标记按普通来源字段失败处理，不把读取失败当成 false 或空名单。

官方标记只参与本来源关系的采用判断。本体独立编目、用户手动关系及其他来源各自遵守所属规则。正式关系的增减按资料合并、替换范围与端点确认处理，已有本地关系依据真实操作保持或更新。

从正在读取的作品 A 看向来源返回的目标 B，各类别按以下含义处理：

| 来源值 | B 相对于 A 的含义        | 本体采用                                               |
| ------ | ------------------------ | ------------------------------------------------------ |
| seq    | 续作                     | sequel                                                 |
| preq   | 前作                     | prequel；保存时按共同规则交换端点                      |
| side   | 外传                     | sideStory                                              |
| par    | 外传所依附的主篇         | mainStory；保存时按共同规则交换端点                    |
| alt    | 另一种故事演绎           | alternativeVersion                                     |
| ser    | 同系列                   | related，保留“同系列”说明                              |
| set    | 共享世界、设定等故事背景 | related，保留来源的同设定说明                          |
| char   | 共用角色                 | related，保留“共用角色”说明                            |
| fan    | Fandisc                  | sideStory，保留 Fandisc 说明                           |
| orig   | Fandisc 对应的原作游戏   | mainStory，保留 Fandisc 说明；保存时按共同规则交换端点 |

只处理来源给出的直接边，不沿关系图自动取得更多作品。ser 不自动生成合集，set 和 char 不自动生成另一层世界观或角色对应；三者也不推导为 alternativeVersion。alt 不单凭标题、平台或日期改判为重制、高清版或移植。相反方向的同一事实沿共同规范归并，不能生成两条镜像关系。未知来源类别按普通来源字段失败处理，不转换成 related。

Fandisc 使用本体已有的“外传／补充故事”关系，不新增来源专属类型。fan 和 orig 分别对应 sideStory 与 mainStory，正反向都保留 Fandisc 这一具体称谓，归并后只有一条有方向的关系。不能把 orig 混同于改编的 sourceMaterial，也不因 Fandisc 名称不同就降为 related。是否采用仍取决于独立的 relation_official 标记。

例如，v17 保留三条官方关系，v3794 的非官方续作关系被排除；v11 保留四条官方关系，其中 v50 对应带 Fandisc 说明的 sideStory。从 v50 读取指向 v11 的 orig 时，规范化后仍对应同一条关系。

<a id="personal-roles"></a>

## 个人开发与发行职责

producer.type = in 且明确作为本作开发方署名时，采用人物 creator。人物不另设 developer，也不能由该标志推导 programmer；后者只采用明确的程序工作署名。

个人明确承担出版或发行责任时采用 publisher，与组织 publisher 含义一致。开发和发行标志分别解释，同时存在时可以形成 creator 与 publisher 两项关系。不能从创作、发行或制作人职责互相推导；职责适用性沿用[本体职责合同](../../domains/relations.md#roles)。

<a id="collection-settings"></a>

## 扩展设置与采集范围

采集取向由 VNDB 扩展设置管理，Profile 继续决定采用哪些提供者、字段与关系。扩展设置不变成主应用全局偏好或逐字段 options，也不修改主应用的标签管理职责。

| 设置               | 默认值               | 含义                                                               |
| ------------------ | -------------------- | ------------------------------------------------------------------ |
| 作品标签适用度范围 | 0–3，全部正分标签    | 可设置包含两端的下限和上限，使用有限数值，满足 0 ≤ 下限 ≤ 上限 ≤ 3 |
| 中文标签映射       | 关闭，保留原文       | 开启后按已核对的静态词典采集中文名称，含角色特征的组限定名称       |
| 图片内容范围       | 不限                 | 可以限制为 Safe／Tame 或允许 Suggestive／Violent，见图片规则       |
| 本人连接与同步     | 未连接，自动同步关闭 | 账号、字段、方向和自动执行沿已有个人接入合同设置                   |

适用度使用来源实际数值比较，允许小数，不先显示取整再筛选；例如 1.99 不满足下限 2。来源返回的标签仍须满足正分且非 lie。角色特征没有适用度，作品标签范围不会误用于 traits。设置界面说明范围会改变实际采集的标签，与主应用临时隐藏剧透是不同操作。

一次读取或搜索固定使用启动时的设置与词典版本，缓存按实际条件区分。保存设置只影响后续操作，不重跑已有任务，不更名或删除库内标签，也不改变已经保存的图片。设置只筛选扩展将要交付的内容，正式采用继续遵守本次字段、关系及更新范围。

<a id="tags"></a>

## 公开标签与角色特征

VN.tags 和 Character.traits 分别贡献游戏、角色的 entryTags，复用本体已有的平面标签模型。标签按共同 nameKey 匹配，不保存 g／i 编号为正式标签身份，不建立来源标签树、命名空间或同义词映射。

| 来源资料                   | 本体表达                                                                    |
| -------------------------- | --------------------------------------------------------------------------- |
| VN.tags.name               | 默认保留来源名称；明确开启中文映射时采用已核对译名                          |
| Trait.group_name 与 name   | 以 `group_name: name` 组成可独立理解的名称，例如 Hair: Brown 与 Eyes: Brown |
| description                | 标签说明，沿 VNDB 扩展自己的正文转换规则交付 Markdown                       |
| Tag.category／Trait.sexual | ero 对应 isNsfw = true，cont／tech 对应 false；角色特征直接采用 sexual      |
| 当前标签应用的 spoiler     | 0 对应 isSpoiler = false，1、2 对应 true                                    |

特征名称的组限定属于普通名称的一部分，不成为隐藏的标签分组。名称不随 UI 语言或 Profile 的语言偏好切换；当前 API 没有多语言标签名称，中文由用户明确启用的[名称映射](#chinese-tag-names)提供。不将别名另建为多个标签，只为本次 Entry 范围返回所需标签，不遍历全站词表或补齐父标签。

来源的 applicable 表示是否允许用户继续添加该标签，searchable 表示是否可用于源站检索；二者不直接否定已经返回的应用。例如 v17 已返回 applicable = false 的 No Sexual Content。读取时不能以编辑权限标记代替事实判断。

作品标签默认完整采用来源返回的正分直接标签，用户可以通过适用度范围收窄；lie = true 的应用不采用，避免将来源标明的表面情况当作实际设定。其余标签保留来源剧透标记，按 rating 从高到低排列，同分按规范名称键稳定排序。rating 用于本次来源筛选和排序，不持久保存为标签权重。本次 v17 默认从 203 项中排除 5 项 lie，保留 198 项；范围设为 2–3 时保留 102 项。

角色特征同样采用当前 c 档案的直接应用并排除 lie。特征没有适用度评分，按限定名称的 nameKey 稳定排序；不从作品名册或其他实例补出特征。来源排序只决定新增应用的初始追加次序，不覆盖用户已经整理的顺序。

traits 在当前模型中作为角色标签存在。年龄、生日、性别和尺寸等已经定义的字段使用来源结构化资料；发色、瞳色、种族、性格、服装等描述性特征保留为标签。不能把 Tall、Short 等分类强行换算为数值，也不因为源站具有一个特征组就自行增加本体字段或从标签名称解析另一套结构化属性。

标签自身的 isNsfw 与具体应用的 isSpoiler 分别交付，不传播到 Entry。本接入不凭某张图片或某项角色特征推导游戏、角色的 Entry.isNsfw，也不为此增加新的本体分类。

<a id="chinese-tag-names"></a>

## 可选中文名称映射

中文映射由 VNDB 扩展在形成候选标签名称前完成。开启后保存的名称就是中文名称，并按这个名称计算共同 nameKey；之后按普通标签参与本体采用与展示。

文本材料以 [VNDBTranslatorLib_](https://greasyfork.org/en/scripts/445990-vndbtranslatorlib)的独立映射数据为参考，并可核对 [VNDB 中文翻译计划](https://github.com/mokurin000/vndb_chinese_translation)。映射库 v5.0.0 标为 MIT，网页执行脚本的许可不同；只抽取核对后的标签、特征及组称谓，整理为扩展内的静态词典，保留版本、出处、许可和校订记录，不执行或按需下载用户脚本。

名称按完整原文及实际标签／特征上下文对应，不做正文式子串替换。角色特征保留组限定；同样的 Brown 在 Hair、Eyes 中不能失去区别。Short → 矮小/短 等多义译法、带粗译标记的值及不同含义的同译名须先校订；没有完整可靠映射时保留该项完整原文。词典内的重名须按本体名称规则核对，不能只检查当前一次返回的标签。

映射只处理这些标签名称，不翻译作品名称、原文名称或任意简介。词典随扩展的正常版本交付，运行时不调用机器翻译服务补齐缺项。设置界面须说明：开关与词典更新影响后续采集的名称，不自动整理既有标签。

例如库中已有 Romance，开启后新采集的恋爱会按另一个 nameKey 处理。旧标签及其已有关系保持，按 merge 更新时可能同时保留两者；用户可以使用主应用已有的标签合并，选择保留的标签并迁移关系。VNDB 扩展不自动更名全库标签，也不新增自己的标签管理界面。按明确的关系 replace 范围重新采用，则继续沿主应用既有规则处理该次关联。

<a id="images"></a>

## 图片用途、归属与候选

图片以 ImageCandidate 和 FileInput 交付，保留来源提供的原图 URL、可用缩略图及尺寸，并按来源图像身份去重。每张实际图片独立形成候选，原图字节按本次预览或采用需要读取。

| 来源图像                        | 可提供的用途            | 归属要求                                                             |
| ------------------------------- | ----------------------- | -------------------------------------------------------------------- |
| VN.image                        | 游戏 primaryImage       | 直接属于当前 VN 的源站主图                                           |
| Character.image                 | 角色 primaryImage       | 直接属于当前 c 档案，不混入其他实例                                  |
| Release.images 中 pkgfront、dig | 游戏 primaryImage 候选  | images.vn 明确指向当前 VN；未指定时，发行记录必须只包含当前这一部 VN |
| VN.screenshots                  | 游戏 backdropImage 候选 | 使用当前 VN 的实际截图，保留原图，不自动擦除文字或提取背景           |

pkgback、pkgcontent、pkgside、pkgmed 不充当作品封面；多作品包装且 images.vn 为空的整盒图片不分配给其中每部游戏。dig 是数字宣传图，可能包含独立标志，来源类型本身不足以识别 titleLogo 或 iconImage。这两项能力不由 VNDB 声明；当前核对渠道也不提供 Staff、Producer 的独立肖像或组织标志。

发行图片的语言限定使用 images.languages；为空时沿用该发行的 languages。语言偏好可以影响候选次序，不改条目身份、原作语言或开发发行范围。图片是否为实拍、所属发行与原始用途仍按实际来源解释，不将清晰度或宽高比当作身份依据。

默认保留符合用途与归属要求的全部图片候选，不因 sexual、violence 或缺少评定票数而过滤。用户可以在 VNDB 扩展设置中限制图片范围；设置只影响后续读取和候选浏览，不自动移除已保存图片。

限制选项沿源站现有等级解释：仅 Safe／Tame 时要求至少一票且 sexual、violence 均不超过 0.4；允许 Suggestive／Violent 时，要求至少一票且两项均不超过 1.3；不限范围为默认，并包含更高等级及未评定图片。这些值只表达图片自身的来源评定，不推导 Entry.isNsfw。

筛选由扩展完成，再返回普通候选。限制后没有可选图片时返回空候选集合；读取失败不能伪装成经过过滤的空集合。既有游戏预设继续使用 VNDB 背景候选，无须增加应用处理步骤或更改资料方案结构。本次 v11、v17 的截图默认各保留十张；用户限制为 Safe／Tame 时分别为八张、十张。

<a id="account-fields"></a>

## 本人记录的字段与连接

本人记录操作由 VNDB 扩展自己的界面、任务及私有状态拥有，调用 ingest 与 library 完整操作；不注册同步 provider，也不把私人字段放入 metadata。明确导入可以创建尚未收录的游戏并采用本人记录，持续同步以本地为准，字段限于状态投影、本人评分和最早已知完成日期。

| 来源字段              | 对应与限制                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| vote                  | 10–100 整数与本体评分同值对应，null 表示未评分；本体 0–9 不可回写，不夹到边界                          |
| finished              | 出站对应最早已知完成日期；入站可为没有历史的作品提供一次完成事实，不覆盖已有历史；写入与清空限制见下文 |
| started               | 本体没有同义开始日期，保留在来源端，不写入活动、加入日期或额外来源列                                   |
| added、voted、lastmod | 来源技术时间，不改本地技术时间、加入日期或完成日期                                                     |
| notes、自定义 labels  | 不参与持续同步，修改其他字段时保留原值                                                                 |
| releases.list_status  | 远端的发行收藏情况，不证明本地持有文件，不生成 holdings                                                |

日期按来源返回的日历值处理，不转成时间戳或按时区移日。本体完成日期使用完整 CalendarDate 或 null，出站取全部已知日期的最小值。例如存在 2021-05-12、2024-08-03 和一条日期未知的记录时，写入 2021-05-12；日期未知不参与计算。

finished 只提供一个完成日期，不是逐次历史。明确导入时，本地没有完成记录才初始化一条：Playing 与合法 finished 可以同时形成 active 和过去的完成记录；只有 Finished、没有日期时初始化未知日期记录。本地已有历史时保留全部日期和备注，不按源日期新增、配对或覆盖某条记录。来源空日期不删除本地历史，技术时间也不用于补全。

完成日期写入须为 1970–2099 年间的合法完整年月日，既要符合本体日历校验，也要落在来源的写入范围内。当前 Kana 服务拒绝 finished = null，已有日期保持不变；需要清空已有远端日期时，扩展在组织写入前将该字段判为无法映射，其他独立字段仍可继续。两侧原本都为空时沿普通未变化规则处理。不能发送空日期后报告成功，也不通过删除并重建列表项完成清空。这是当前来源写入能力的限制，不改变本体可空日期及入站 null 的含义，实测见[账号读写验证](../../../verification/evidence/vndb/account-roundtrip.md)。

公开资料读取使用匿名请求，与个人连接分开。个人令牌保存在 secrets，通过 GET /authinfo 核对返回的账号 id 与 permissions；用户名只用于显示，不额外要求用户填写另一个账号 ID。完整本人读取需要 listread，回写还需要 listwrite；仅有写权限不能绕过当前值、写入结果与隐私核对。普通格式保存与联网验证沿[凭据合同](../private-data.md#connection)分开。

VNDB 不在本接入中提供自动刷新或程序化撤销令牌；用户从源站令牌页取得、更换和撤销令牌，本地断开只清除本地连接。写接口也可能因缺少 listwrite 返回 401，不能仅凭一次 401 就删除凭据；结合 authinfo 与已核对权限区分权限不足和令牌失效，不解析原始错误文字作判断。

<a id="account-reading"></a>

## 清单导入与同步读取

本人清单通过 POST /ulist 读取，user 明确使用当前已核验账号的 id。GET /ulist_labels 取得该账号的标签定义与隐私属性，列表只请求本次所需的记录字段及 labels.id；不为同步状态、评分或日期额外取得私人备注。自定义标签可以用于选择源清单范围，不因参与筛选就变成本地标签或持续同步字段。

本人清单支持手动导入，以及默认关闭的[自动导入](../synchronization.md#automatic-import)。自动导入按所选账号清单及标签范围读取当前成员，补齐本地缺少的 VN；既有游戏只复用，不自动采用其评分、状态或完成日期变化。没有导入历史名单，本地删除后仍符合来源范围的 VN 可以再次被导入；Release 收藏仍不另建作品或本地持有记录。

一次导入按所选范围读取完整清单：以 id 升序、每批 1–100 项读取，后续使用 id 大于上一批末项的条件，直到 more = false。已有 VN 身份对应的游戏复用本地条目，未对应游戏正常创建，身份冲突报告该项失败。本地游戏文件不是导入前提。

本人列表仅需计数时使用 results = 1；当前部署对 results = 0 返回 400。成员完整性以分页结束为准，各标签可能有交集，单个标签计数或计数之和都不能替代成员清单。

每轮自动导入重新核对当前清单，added 和 lastmod 只提供来源时间信息。日常出站同步按每批最多 100 个明确身份，读取已对应且在配置范围内的 VN；它与自动导入的清单轮询分别执行。

来源明确说明，已经从 VNDB 数据库删除的作品不会出现在 /ulist 响应中，即使网页个人列表仍保留它们。权限不足、请求未完成或缺少某条返回记录，都不能据此删除本地作品或清除个人值。完整读取只证明本次 API 返回范围已读完，不证明获得账号的历史记录或包含所有网页占位项；缺项沿既有无法对应与删除边界报告，不伪装成空字段回答。

<a id="account-status"></a>

## 本人列表与当前状态

个人记录与公开资料读取分开。状态对应使用当前已确认账号的完整标签集合，不从他人的公开清单取得私人值，也不能把无权限读取的标签当作不存在。固定标签按 id 解释，自建同名标签不参与状态映射。

| 来源标签                            | 明确导入时的本地采用                                            |
| ----------------------------------- | --------------------------------------------------------------- |
| 1 Playing                           | 当前状态 active                                                 |
| 2 Finished                          | 当前状态 null；本地没有历史时初始化一条完成记录                 |
| 3 Stalled                           | 当前状态 onHold                                                 |
| 4 Dropped                           | 不采用状态，保留已有状态并报告无法映射；新建游戏仍为未设置      |
| 5 Wishlist，且没有 1–4 中的进度标签 | 当前状态 planned                                                |
| 记录存在且完整标签中没有以上标签    | 当前状态 null，保留完成历史；明确 finished 日期仍可提供完成事实 |

VNDB 网页选择 1–4 中的一个进度时会移除其他三个，API 虽允许并存，本接入仍按单一进度解释。并存的 Wishlist 不覆盖进度：Finished＋Wishlist 采用完成事实并清除当前状态，Playing＋Wishlist 采用 active，独立愿望继续留在远端。Dropped 与 Wishlist 并存时仍报告状态无法映射，不改用 planned。Dropped 不触发本地删除，所选评分与明确的 finished 日期仍可独立采用。导入时若 1–4 中出现多项，该状态字段无法映射，保留本地状态并报告，不按数组顺序选择，也不弹出冲突选择页。出站仍可按明确本地目标应用下文的局部标签规则。6 Blacklist、7 Voted 和自定义标签都不映射本地状态或收藏。

状态出站先按本地事实生成一个平台目标：非空当前状态优先；当前状态为空且有完成记录时为 Finished；两者都没有时为清空。active、onHold 分别写入 1、3，完成投影写入 2，同时移除其他 1–4 标签并保留 Wishlist；planned 写入 5 并移除 1–4。本地 active 与两条过去的完成记录只写 Playing，不同时写 Finished。

写入使用 labels_set 与 labels_unset 做局部修改，不直接提交其他标签和未选字段的覆盖值。来源因评分自动维护 Voted 的行为正常接受，不发送覆盖整个标签集合的 labels，也不将完成次数或备注写成自定义标签。

本地当前状态为空且没有完成记录时，平台目标才是清空。远端只有 Wishlist 时移除 5；没有 Wishlist 时清除 1–4。若远端同时具有进度与 Wishlist，清掉进度后仍会表示 planned，无法同时保留独立愿望并对应空投影，因此该字段报告无法映射，不删除愿望标签，也不引导用户改成其他状态来完成本次同步。其他独立字段继续处理。

Finished 只能支持一次完成事实的初始采用，不提供全路线、全成就、逐次次数或游玩活动。本地已删除全部完成记录后再次明确导入 Finished，可以重新初始化一条；自动同步不反向恢复。平台已确认没有个人记录时，不为了清空状态发送会新建列表项的 PATCH。账号连接、写入确认、可见性、创建范围和重试遵守[共同同步合同](../synchronization.md)。

<a id="account-visibility"></a>

## 回写与列表可见性

源站没有逐条记录的独立隐私参数：记录上的标签全部为私有时，记录才保持私有；没有标签时也为私有。评分存在时会自动加入 Voted，清空评分时会自动移除它。因此评分、状态和标签定义必须一起核对，不能只对状态变更检查隐私。

扩展读取本人标签定义与当前记录，核对并说明评分、状态和 Voted 对实际可见性的影响。正常写入沿用来源规则，即使记录因此在公开与私有之间变化也不阻止操作；不提供源站无法独立表达的逐条可见性选择或保持承诺，不修改全局标签隐私、添加无关标签或覆盖整份标签集合来干预结果。

相互影响的评分与状态修改合并为同一次 PATCH 核对，避免分步写入产生意外的中间状态。未选的文字、日期和自定义标签不发送覆盖值；已确认无变化时不发送 PATCH，没有记录且只请求清空时不创建记录。回写结果不确定时先回读核对，再保存已确认值，不直接重复提交；本地指纹未变不能代替对平台现值的核对。

这些检查遵守既有同步合同，但该 API 没有提供这组操作的条件写入或跨端原子保证。扩展须在提交前重读必要事实、提交后核对结果，按实际变化报告冲突或失败，不宣称能够阻止来源端同时发生的修改，也不为此增加应用层同步事务或恢复框架。

来源核对与样本范围见[验证记录](../../../verification/evidence/extensions.md#vndb)。
