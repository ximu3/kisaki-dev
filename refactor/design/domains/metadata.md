# 资料获取与本地采用

一次资料操作由三个领域共同完成。metadata 定位来源记录，读取资料，并按方案整合候选。ingest 根据明确的新增或更新目的，决定候选如何用于本地对象。library 校验正式模型，保证业务数据完整提交。

[资料方案](metadata-profiles.md) 定义获取规则，[预设](metadata-presets.md) 提供可复制的初值，[Provider](../extensions/providers.md) 定义来源能力。本文说明这些能力如何组成一次完整操作。

<a id="ownership"></a>

## 职责与操作入口

metadata 负责来源侧的判断，包括搜索条目、取得图片候选、组织 provider.resolve 定位目标，以及执行 MetadataProfile 中的读取、对应和合成规则。调用者通过本次输入和请求范围，指定需要处理的对象与字段。

ingest 负责本地采用。它查询 library，取得已有身份、当前值和允许修改的范围，再决定复用或创建对象，以及补空、覆盖或替换哪些内容。metadata 不自行读库，也不作这些本地决定。正式约束、完整写入、合并和删除由 library 负责。

| 操作                               | 行为                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------- |
| metadata.search                    | 调用一个指定 provider 的条目搜索，返回 SourceEntry 候选。                   |
| metadata.fetch                     | 按方案完成来源定位、读取、对应和整合，返回候选资料与本次结果信息。          |
| ingest.add                         | 从 profile 或 prepared 输入执行标准新增；根条目已有对应对象时，返回已存在。 |
| ingest.update                      | 固定本地目标，从 profile 或 prepared 输入取得资料，再执行完整更新。         |
| ingest.addMany / ingest.updateMany | 对各输入执行相应的完整操作，逐项提交，并汇总实际结果。                      |

来源搜索和独立获取可直接调用 metadata。普通新增只调用一次 ingest，由它组织获取、对应与提交。界面在 features/ingest 中组织新增和更新，并组合方案选择与搜索能力，不另设 Adder 模块。

scanner 发现待新增候选后调用 ingest。library/holdings 负责识别本地文件，只把文件绑定到已有作品和分部，不创建分部，也不反向调用 ingest 或 scanner。新增采用来源明确提供的真实分部清单，不要求本地文件齐全；资料缺失时不补造分部，也不把部分清单称为完整清单。

新增包含本地内容时，ingest 先原子提交作品、分部和明确的本地登记。目录按作品类型登记到各自目录表；单有游戏目录时不创建启动配置，明确的启动输入才初始化配置。动画、漫画和小说提交后，再显式请求 holdings 首次识别。识别失败不会撤销已提交资料，结果必须说明失败，并允许独立重试核对。scanner 不在之后补写登记。后续核对仍只使用当前已有分部，可以留下未关联文件。

已有资料更新自身不组织目录发现、文件登记或关联修改。分部清单或匹配依据实际提交变化后，holdings 在自动刷新开启时按[资料变化后的文件核对](file-maintenance.md#refresh)处理受影响作品的已登记空关联文件；手动新增、更正本地分部也遵循相同机制，不专为某个资料更新入口追加扫描阶段。资料更新按自身提交结果完成，后续匹配单独执行和反馈，失败不回滚资料，也不能把资料更新成功解释为文件关联已经全部完成。

新增目录使用 holdings 的[默认发现范围](holdings.md#directory-discovery)，方案引用默认 NULL。手动输入明确选择了已保存同类文件识别方案时，将引用随目录一并校验和提交，首次识别读取实际提交值。MetadataProfile 与扫描线索规则均不提供文件方案的隐含默认；零散文件也不据此登记父目录或获得文件级长期方案配置。

直接手填资料和写入已明确的个人值调用 library。个人记录导入若需先对应来源，可由完整导入流程协调，但这些记录不进入 MetadataCandidate。普通元数据操作不修改评分、状态、笔记、活动记录或启动配置。远端同步和完整备份恢复分别使用自己的操作语义。

## 方案输入与已取得的候选

MetadataInput 通过 profile 和 prepared 分配资料获取责任。profile 提供方案与定位线索，由本体读取并合成；prepared.data 提供已经取得的候选，relationScopes 一次声明其完整关系范围。两种输入共用本地对应、对象复用或创建及采用规则。候选可以包含条目、分部和关系，实际创建所需资料由对应操作核对。

ingest.add 和 addMany 的单项输入可以另带 initial，接收主条目适用的 evaluation、record 和 completionRecords，复用 library.entries.create 的初始个人值合同。initial 与 MetadataInput 分开，由调用方明确提供，不来自 provider、processor、资料方案或 MetadataCandidate。创建时，主条目和这些初值在同一个图事务提交，再发布实际变更；不能先暴露空个人记录，再靠来源订阅补写。alreadyExists 不采用 initial，调用方明确更新已有个人值时，分别使用 entries 的当前值操作与 completions 的适用历史操作。

官方迁移与资料文件导入遵循[共同导入流程](../extensions/importers.md#flow)：以输入中已知且可准确映射的资料形成 prepared 候选，满足最低条件的新作品可直接新增，适用个人初值通过 initial 共同提交。已有作品按实际身份复用，所选资料按明确补空或覆盖范围更新。NFO、ComicInfo 与 calibre OPF 使用同一规则，不要求先联网获取；联网补充由用户另外发起普通 profile 更新。批次接续由导入器按[进度合同](../extensions/importers.md#repeat)负责，不改变 ingest 的单项完成条件。

prepared 不能承载字段 patch、LibraryWriteGraph 或已经确定的本地写指令。调用者若已完成本地决定，应直接调用 library。扩展可以自行取得和整理候选，再通过 ingest 采用，无需把全部整理逻辑放进 provider 或 processor，也无需重写本地采用规则。

MetadataCandidate 按 objects 和 relations 组织，使用正式字段、关系值和外部身份。临时对象 key 只用于连接本次候选。原始 identification 与可采用字段分开，匹配不使用加工后的显示值；partMatching 保存本次明确启用的分部回退规则，复用资料方案中同一规则类型。profile 获取固定该方案的分部规则，prepared 提供者则显式携带其采用的规则；省略或空规则只允许按完整身份或明确目标对应，不隐含加载默认方案。候选不含本地 create/update 指令，因此也不同于某个来源的原始 MetadataReadResult。字段缺席和明确空值保持区别，具体形状见[候选资料合同](metadata-contracts.md)。

根目标与关联对象分别完成本地对应，候选资料通过校验后，仍按用户选择确定采用权限和正式绑定。ingest 根据本次更新选择推导读取范围，调用者只维护这份采用意图。

## 条目搜索、选择与分页

条目搜索查找来源 Entry，read 读取明确对象的资料，图片候选能力提供可选资源。这三个入口各有用途。系统不提供通用字段搜索、任意图选择，或混合 entry/field 的请求。简介等内容通过字段读取取得；Part 从所属 Entry 的范围内读取，不作为与 Entry 平级的搜索目标。已知完整身份时可以直接定位。

metadata.search 每次调用一个 provider，输入 providerId、entryType、query，以及可选的 cursor 和 preferredLanguages。provider.search 接收同样的业务输入，但不再包含 providerId；运行资源通过 context 提供。返回值为 { records: SourceEntry[], nextCursor?: string }。

cursor 只适用于同一 provider、条目类型、查询和语言条件。首次请求省略 cursor，续读时原样传回 nextCursor；条件改变后重新开始。是否存在 nextCursor 决定能否继续，空页本身不表示搜索结束。

共享 EntrySearcher 分别调用用户选中的 provider，按来源分组并保留各来源原始顺序。每组独立加载、显示失败和重试；先返回的结果先显示，来源排列保持用户选择的顺序。各来源的相关性分数只在本组内使用。搜索选择由搜索界面管理，MetadataProfile 用于后续资料获取与合成。

条目和图片候选接近列表末尾时自动有界续读，同一批次不会重复请求。失败后保留已有结果，由用户重试，不循环自动重试。大量结果按需虚拟化；图片列表只加载可见预览，不预先下载所有原图。

远端 cursor 可以映射来源的页号或偏移，但系统不承诺持久搜索会话或任意跳页，也不伪造完整 total。本地列表仍使用区间与 total。各来源的分页能力可参见 [VNDB](https://api.vndb.org/kana#database-querying)、[SteamGridDB](https://www.steamgriddb.com/static/openapi.yml) 和 [AniList](https://docs.anilist.co/guide/graphql/pagination)。resolve 和 read 所需的完整来源分页由 provider 内部完成。

搜索结果保留真实身份、类别、识别资料和 provider。同一完整身份不会重复加入选择，但同名结果不会自动归组。多选默认表示多个目标。只有用户明确选择“作为同一条目”，或为单一目标选择“补充来源”，结果才组成同一目标组。组内记录可展开和移除，代表记录不具有额外权威。

批量操作按目标组执行，每组整理一份 clues。分组不持久化，也不产生获取后采用稿。组内类型和范围必须相容；若不同身份已分别绑定到不同本地 Entry，系统应报告冲突，不能用分组替代本地合并。

已选目标在翻页、更改关键词或调整 provider 后继续保留，用户可以移除或清空。迟到查询不能覆盖新查询的候选，各组分页也不改变已有选择。界面只有部分远端结果时，应写“选择本页”或“选择已返回结果”，不能声称选择了全部远端匹配。scanner 不先执行搜索，也不维护另一套搜索组合；人工修正可以通过搜索补充身份，再发起新的 ingest 操作。

图片候选能力单独声明用途、查找输入和 ImageCandidate。read 中的图片字段仍返回候选资源集合，支持读取图片不代表支持独立图片搜索。图片也可以来自文件或链接。选择动作只交付所选结果，不隐式保存。用户用 B 的图片替换 A 的图片时，只修改 A 的指定字段，不创建 B、不绑定 B 的身份，也不读取其他字段。

## 定位线索与来源对应

公开定位输入是一份描述同一目标的 clues，可以包含适用的完整身份、名称、原名和日期。来源页面 URL、搜索 provider、排名、分页、简介和图片不属于定位线索。resolve 负责来源内查询、标识解释及原生范围判断，metadata 再按 matching 规则对应结果。字段来源的优先级不能决定根对象的身份。

用户确认多条记录属于同一目标后，共享纯逻辑负责合并 clues。记录自身的身份及来源明示属于同一目标的交叉身份，按 source + sourceId 去重。单值保留已有有效值，只有缺失时才从补充记录取得。日期作为完整值保留或补充，不拼接不同来源的年月日。更换线索必须由调用者明确指定；移除记录后，根据剩余选择重新整理。系统不提供可配置的线索合并策略，也不增加 ingest records 参数。

人工确认的身份进入本次 clues，不改写原 SourceEntry.externalIdentities；该字段只表达来源自身声明的交叉身份。原始记录仍留在搜索器中，供展示和移除。clues 只用于准备定位，不保证保存全部来源资料，也不修改方案的 providers、字段来源、优先序或匹配规则。正式身份在创建或明确更新时才采用；add 返回已存在时不顺带追加身份。

Entry 和 Part 优先按完整 ExternalIdentity 对应。Part 还必须属于当前作品范围，局部数字相同不能证明身份相同。多个明确身份若指向不同本地 Entry，应报告冲突，名称回退不能覆盖该冲突。没有直接对应时，只执行 matching 中明确启用且有序的回退。主 Entry、相关 Entry 和 Part 分别遵守类型及作品范围规则，不增加独立 Part resolve。

来源引用确定读取目标，来源识别资料用于 matching。分层记录的名称由 provider 按[来源命名规则](../extensions/providers.md#identity)组合，直接用于对应，无需先请求 fields.entry.name；查询词、界面装饰和处理器输出各留在原用途。

已确定的身份或本地目标约束其他来源。仅有名称等弱线索且形成多个无法确认相同的候选组时，返回歧义，不按响应时间、数量或字段优先级选择。

关联对象具有完整身份时，可以定向读取，即使该来源没有同源根记录也不自动否决。但执行仍须尊重实际范围，不伪造根对象或关系。不同工作按作品、人物、职责和可选角色的完整维度对应；NULL 角色不是通配符。名称推断可用于本次合成，但必须保留依据，不自动形成长期强绑定。缺少身份的对象不能共用空键，多候选也不能直接取首项。

<a id="enrichment"></a>

## 定位补足与执行依赖

definition.providers 是本次方案参与提供者的唯一显式集合，同时限定定位补足和普通读取。已对应的来源可以贡献真实名称、日期和交叉身份，帮助其他来源继续定位。系统不会扫描全部已安装 provider，也不会根据 source 自动加入实现。哪个 provider 先具备执行条件、先返回结果，都不决定它是主来源。

providers 是方案唯一的参与来源清单。未被 fields 或 relations 引用的 provider 只帮助定位，其普通资料不参与采用。每份方案至少提供一项可请求资料能力。Wikidata 等来源可以在不同方案中承担不同用途；各来源仍需确认自己的真实身份。

定位补足使用原始识别事实，不使用翻译或加工后的显示值，并保留事实出处和推断依据。尚未确认的候选不能混入目标事实，重复出现同一推断也不会使其变成直接映射。新取得的直接证据继续按身份规则判断。

只有新的有效信息改变了定位条件，才重试相应定位。规范化后的输入相同就不重复调用。所需对应已完成、没有新信息、问题仍无法消解、预算耗尽或执行取消时，流程按实际结果结束。

本次执行或来源会话内，可以按实际参数复用定位、读取及其依赖。执行结束后释放这些资源，不把快照共享给独立执行，也不建立持久补全表或通用调度系统。调用者不控制 provider 的内部阶段。

局部失败按真实依赖隔离。例如，B 的范围不成立时不能使用 B，但已确认的 A 可以保留；人物字段读取失败不必否定已确认的工作关系。只有新人物缺少创建所需资料时，才影响该人物及依赖它的关系。集合是否完整与字段是否完整分别判断。

具体角色工作若依赖作品与角色关联，采用计划应明确补齐该关联。若同次请求又要求移除它，应报告矛盾，不能靠写入顺序或修改来源规则掩盖。

<a id="requests"></a>

## 按需字段与对象范围

同一 profile 可以用于完整资料、主图、简介、关系或指定分部字段。本次 request 只选择读取范围，不改变来源、合成或 matching 规则，也不生成隐含方案。执行前必须校验请求是否受配置支持，不能只取请求与配置的交集，却声称全部完成。

```json
{
  "objects": {
    "entry": { "fields": ["name"] },
    "relatedEntries": {
      "person": { "fields": ["name"] }
    }
  },
  "relations": {
    "personWorks": { "fields": ["note"] }
  }
}
```

read 按 objects 和 relations 接收请求，每个节点的 fields 选择普通字段。relations 中出现某项，即请求该关系集合及必要端点；fields: [] 表示只读取成员维度。relatedEntries 和 parts 可以通过 refs: ExternalIdentity[] 指定对象。未提供 refs 时，范围来自本次关系端点或已经成立的 Entry 上下文，不进行全站搜索。refs 只限制对象字段范围，不缩小另外请求的关系集合。完整输入见 [Provider](../extensions/providers.md)。

ingest 将所选本地对象转换为来源身份或 Entry 范围，provider 不接收本地主键。人物、角色、组织和关联作品必须来自真实关系或明确候选，不能在缺少关系时补造。分部有完整身份时，可直接读取，无需先取同源根或全部兄弟分部；缺少身份时，按作品目录对应，不能把编号当作身份。

只读取分部字段的方案是合法方案，不必同时配置归属或收录规则。A 决定清单、B 补充字段时，B 只能补充已选成员，不能扩大清单。

响应中已有的资料，只有符合相应字段来源规则时才能复用；实际输出仍限于请求范围。名称线索和搜索显示文字不会自动成为正式字段。请求名称也不保证来源有值。创建所需资料不足时，可以在本次允许的范围内补充读取；仍不足则按结果合同报告。用户可在普通新增或编辑入口补充输入后发起新操作，执行中不临时插入补填或采用确认，也不虚构默认值。

根对象再次作为关系端点出现时，仍使用 fields.entry 及根字段请求。已经对应为同一人物的对象只产生一份字段候选，但其不同工作关系分别保留。相关对象不会自动执行另一份方案，也不会触发递归抓取整张资料图。

<a id="adoption"></a>

## 新增、更新与本地对应

add 建立一个明确条目，初始化真实资料、分部和所选关系，并为必要的新对象提供合法初值。根条目已存在时返回 alreadyExists，不刷新资料，也不追加本地内容。手动新增、扫描、deeplink，以及 profile/prepared 输入都遵守同一规则。新增不使用 adoption 配置，不提供获取后的整份采用预览，也不继承更新偏好。

update 固定已有 Entry 或 Part 以及明确选择的字段和关系范围。来源结果不能使操作转向其他目标。执行从所选范围推导写入，不先纳入全部候选，再用 keep 逐项关闭。更新分部清单可以补充真实缺失分部；更新关系可以创建所需人物。但既有共享对象的普通资料，只有该对象也是明确更新目标时才能修改。

例如，从动画页更新某个人物头像时，实际目标是该人物，动画只提供上下文。对象位于 profile 的 entry、relatedEntries 或 parts 中，并不因此获得本地写入权限。

| 情况                               | 标准行为                                                       |
| ---------------------------------- | -------------------------------------------------------------- |
| 所需关联对象已存在                 | 复用身份；普通资料只有在它也是明确更新目标时才修改             |
| 缺少所选关系必需的人物、角色或组织 | 按合法初始资料创建；资料不足时报告受影响的对象及关系           |
| 明确采用的真实分部清单中有缺失分部 | 建立并初始化；清单缺项不自动删除已有分部                       |
| 来源列出尚未入库的关联作品         | 不自动建立这些独立作品                                         |
| 用户明确选择添加关联作品           | 执行新增操作；界面可组织这项动作，不将其藏入更新策略的创建开关 |

人物、角色和组织始终是独立共享对象，读取其履历不会递归创建作品。用户希望添加新的关联作品时，应另作明确新增，界面可以组织这项动作，但不把它藏在任意创建或复用矩阵中。

本地七类 Entry 按完整身份自动复用。原始 name、originalName 和 aliases 按[名称比较](#name-comparison)在同类型中查找等值建议；来源 matching 不授予本地复用权限。无身份的关联人物、角色和组织按以下规则处理：

| 本地对应依据                       | 采用结果                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------- |
| 完整身份唯一命中                   | 复用目标，按本次授权更新关系                                                          |
| 没有身份命中，也没有名称或别名建议 | 本次允许创建且必要资料齐备时新增                                                      |
| 只有一个名称或别名建议             | 保留本地对象，报告 associationSkipped / ambiguousEndpoint，不按名称自动复用或再建一份 |
| 有多个建议或身份冲突               | 排除受影响的对象及依赖关系，保留其余合法分支                                          |

已有关系中的同名对象也遵守这张表。结果可引导用户打开条目或关系编辑，明确整理对象；这不插入执行中的采用预览。仍缺少可靠身份时，后续资料更新继续保留人工关系。名称不足以对应的分支也不能提供删除旧关系的依据。

Part 按下述同作品唯一匹配规则处理，复用已有匹配值与比较语义。

Part 先按完整身份或本次已明确的本地目标对应；其余情况按本次 partMatching 在同作品、同类分部及相同编号范围内匹配。编号本身不是身份，只有本次明确启用相应规则且结果唯一、没有身份或范围冲突时，才允许复用。新建同时要求本次已选择的真实清单范围，不能把未回答、不可判断或身份冲突当作缺少成员。

<a id="local-parts"></a>

### 分部的本地对应决策

| 已确认事实                                           | 本地结果                                                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 全部有效来源身份只命中一个范围相容的 Part            | 复用该 Part；按正式身份合同采用本次明确的等价身份                                                |
| 身份指向多个目标、其他作品或不相容种类               | 冲突；不继续用名称或编号回退                                                                     |
| 本次操作已明确某个本地 Part 目标                     | 核对目标、归属及已有身份，成立后只更新该目标；不以候选字段重新选择对象                           |
| 没有直接对应，第一条可用回退规则唯一命中             | 复用；后续规则不再选择另一个目标                                                                 |
| 某条可用规则命中多项                                 | 歧义；停止该对象的回退，不用更弱规则挑一项                                                       |
| 可用规则全部无命中，且本次明确采用完整清单中的该成员 | 可以新建合法 Part；存在已知版本、归属或身份冲突时仍拒绝                                          |
| 没有可用规则，也没有直接对应                         | 已有同范围 Part 时报告依据不足；目标范围尚为空或所属 Work 正在新建时，可按明确清单初始化真实成员 |
| 只更新既有分部字段，没有选择清单新增                 | 保持固定目标集合；无命中不创建 Part                                                              |

可用规则的每个字段都必须有可比较的原始识别值，缺项不作为通配符；按配置顺序尝试，零命中才继续下一条。字段适用性、名称、日期和编号比较共用[matching 合同](metadata-profiles.md#fields)。仅有类别或为空的编号不构成可用识别键。漫画话使用作品话号时限定作品，使用卷内话号时先唯一对应该卷，再比较 volumeChapters 的编号；两种编号不互相回退。

本次候选中的重复对象先按来源合成规则归并。同一批次的本地对应还须核对彼此结果：两个尚未证明同一内容的候选不能各自创建后再按处理顺序碰巧复用；无法唯一对应的对象及其依赖关系按 IngestIssue 排除，独立合法分支继续。资源准备完成后，ingest 重读本次匹配所依赖的同作品范围，核对目标、身份和唯一性，再立即进入 library 的已准备图同步提交接入；这段复核与提交之间没有 await。准备期间的改名、改号或新增同号项使原决定失效时报告 TargetChanged，不重新选择其他目标。该内部接入复用正式图校验与短事务，只接收已准备的图和资源，不公开匹配策略或事务回调。

回退复用只决定本次采用目标，不自动追加来源身份；新 Part 的真实来源身份正常保存。普通刷新保留既有 Part ID、个人标记、文件关联和人工顺序。MangaDex 无 ID 卷因此可以在唯一规则命中时反复更新同一卷；出现两个可匹配卷时报告歧义，不取首项或生成第三项。

同一动画内已经更正 Episode 与 Extra 种类的对象，仍按保留的完整来源身份对应现有 Part。刷新以其本地种类判断是否属于本次所选范围；范围之外保留，不能按来源默认种类当成缺项重新创建。处于更新范围内时采用相容的共同字段，种类专属字段仅在来源与本地种类一致时采用；资料更新不调用 changeKind，也不撤销用户的种类更正。

<a id="name-comparison"></a>

名称比较固定执行 NFC 规范化、去除首尾空白、折叠连续空白，并忽略英文字母大小写。不删除标点、不转换译名或简繁体，也不丢弃卷号和版本信息。各回退都使用真实依据。复合键的每个值必须有回答且按字段相等，缺失值不是通配符；只有唯一且无冲突时才能对应。外部 ID 使用来源自己的规范，不套用名称规则。

推断对应可以服务候选合成，但不能自动追加长期身份。只有直接依据或明确确认的对应才形成正式绑定；明确新建对象时，所选原始来源身份可以正常保存。搜索、预览和换图不回写身份。身份冲突应通过明确更正、跳过或完整本地合并处理，不能靠字段 overwrite 搬移绑定。

同一来源对象回答中的 identity 与 externalIdentities 共同参与对应，包含该来源明确声明等价的其他原生记录。全部身份只命中同一合法本地目标时复用该目标；允许采用身份的完整操作可以一并登记其余明确等价的身份。命中多个目标时报告冲突，不以代表身份决定胜负，也不把普通弱匹配结果扩写为来源身份组。代表身份变化而其他已绑定身份仍一致时，不重新创建对象。

新增界面组织类型、独立搜索、目标、方案、适用初值和本地输入。搜索来源与资料方案不会互相暗改。用户提交后执行一次完整操作，结果通过 Toast、系统通知和 TaskCenter 呈现，不另设添加结果区或问题列表。普通手填仍然可用。修正后发起新操作，不让旧任务一直等待人工裁决。

<a id="update-entrypoints"></a>

## 统一的资料更新入口

作品及其分部的来源资料更新统一从作品更新器发起。作品字段、资料关系、分部清单和已有分部字段均在其中选择，各类更新共用这一入口。

| 更新范围     | 明确目标与采用边界                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| 作品自身字段 | 当前作品的所选字段，按具体字段的补空或覆盖方式采用                                                                 |
| 资料关系     | 本次选择的关系及成员范围；既有共享对象的普通资料只有被明确纳入更新目标时才能修改                                   |
| 分部清单     | 当前作品及明确分部种类的清单；复用已有身份并保留旧字段，补充能够确认归属的缺失分部，来源漏项不删除本地分部         |
| 已有分部字段 | 按分部种类和字段选择作品范围的更新，例如本作品全部分集的简介；执行前固定该类已有对象，不提供逐个挑选具体分部的界面 |

分部使用所属作品类型的资料方案。已知分部身份可以直接读取；必要时由所属作品提供来源上下文，但上下文不扩大写入范围。只更新已有分部字段时，无须同时选择作品字段或刷新清单。

作品更新器只选择作品范围、分部种类和字段，不嵌入具体分部选择器。执行层由所选整体范围取得本地对象并固定更新输入，仍以明确的 Entry 或 Part 为目标，沿已有完整更新与批量合同执行；不把来源多返回的成员自动扩大为已有字段的覆盖目标，也不把 Part 提升为 Entry。

新分部以本次合法取得的资料初始化，与已有分部的字段采用分别处理。本次目标与采用方式在执行前确定，更换方案、字段回填或来源多返回对象都不能扩大修改范围。界面具体入口遵守[共同资料更新交互](../ui/components.md#metadata-update)。

<a id="update"></a>

## 字段与关系的更新方式

字段省略表示不更新，fill 表示补空，overwrite 表示覆盖。界面的“全部补空”或“全部覆盖”直接填写各具体字段，提交范围由这些字段完整表达。metadata、fields 和 relations 位于同一层：

```ts
ingest.update(animeRef, {
  metadata: {
    type: 'profile',
    profileId
  },
  fields: {
    name: 'overwrite',
    description: 'fill'
  },
  relations: {
    personWorks: {
      mode: 'append',
      fields: {
        note: 'overwrite'
      }
    }
  }
})
```

此例修改动画字段及其人员关系，不修改既有人物的普通资料。所需新人物按标准规则初始化，不设置 creation.person。读取可以为对象对应或新对象初始化取得更多数据，但不会扩大已有对象的修改范围。prepared 输入遵守同样限制。

作品更新器分别选择分部字段与分部所属清单。字段更新处理已确定成员，清单更新补齐真实缺项。漫画的卷话收录单独选择补齐或替换，默认补齐；替换只移除完整范围内不再保留的收录关系，卷、话与私人记录保留。普通资料更新保持已有人工排列。

关联人物资料以实际人物为更新目标，可以复用作品上下文中已取得的候选。批量更新先固定目标，再选择各项方式并报告结果。界面记住的更新偏好用于后续更新，新建仍按新增合同执行。

独立关系集合支持仅更新已有成员、append 和替换明确范围。关系属性的 fill/overwrite 与成员处理方式分别指定。只有业务键相同的关系才能更新属性；append 保留来源未出现的本地项。

关系更新可提供用户 scope，字段与解释见[固定范围](metadata-contracts.md#relation-scopes)。本次输入的 relationScopes 提供完整回答依据，用户 scope 提供修改授权；替换只移除二者共同覆盖且本次未保留的关系。空数组沿同一规则处理。缺少完整范围时，合法事实继续补充或更新，受影响的替换报告 incompleteRange。既有关系 ID 和人工顺序按正常规则保留。

Part 创建时明确所属作品，普通更新保持归属；分部删除与作品合并使用各自的完整操作。

作品联系共用一份正式记录。更新某作品的 workRelations 时，先按端点和规范方向对应，再处理与该作品直接相连的所选范围；不根据 from/to 的存储位置划分维护方。修改或移除同一关系会反映在两端，不影响另一作品与其余作品的关系，详见[关系采用范围](relations.md#maintenance)。

update 和 updateMany 在目标及方式确定后，直接完成获取、对应、准备和提交。无法采用的分支，以及仅供该分支使用的新对象，在提交前排除；结果报告合法部分的实际完成情况。需要调整输入时，用户处理问题后发起新的完整操作。

图片选择、普通表单和扫描发现预览分别服务各自的输入准备；[本地合并](library-operations.md#merge-action)按明确目标与固定规则执行。资料更新采用本节流程：根对象歧义或必要值不足使该项失败，批次继续；关联对象的局部问题只排除相应依赖，保留合法独立部分。疑似已有对象按对应不足报告，不能当作缺项再创建一份。

<a id="results"></a>

## 单项与批量结果

```ts
type AddResult =
  | {
      outcome: 'added'
      entry: EntryRef
      issues: IngestIssue[]
    }
  | {
      outcome: 'alreadyExists'
      entry: EntryRef
      matchedIdentities: readonly ExternalIdentity[]
      issues: IngestIssue[]
    }

interface UpdateResult {
  outcome: 'updated' | 'unchanged'
  target: EntryRef | PartRef
  issues: IngestIssue[]
}
```

added 表示根条目已经实际创建。alreadyExists 表示完整身份已准确对应已有根条目，matchedIdentities 是本次用于对应的非空完整身份集合；同名不产生此结果。该结果自身不写资料或持有，scanner 仅在已启用登记选项时另行调用 holdings，提交时再核对这组身份。updated 表示本次产生了真实变化，变化可以只发生在分部或关系上；unchanged 表示处理后没有变化，并不保证来源资料齐全。

根条目已创建，但部分关系或首次本地识别失败时，结果仍为 added，并通过 issues 说明局部问题。某个来源失败，但其他资料足以合法采用时，正常结果也可附带来源失败问题。若根目标不明、必要值缺失、身份冲突或业务图提交失败，导致整项操作不能成立，应返回 ExecutionFailure，不能伪装成已存在或未变化。

可选字段正常缺失、fill 遇到已有值、取得相同值，都不自动构成 issue。issue 表达提交前已排除的分支，或提交后附带工作的失败，不能用来允许写图时忽略约束。公共定义见[采用问题](#issues)。

```ts
{
  total: 3,
  items: [
    { index: 0, result: addedResult },
    { index: 1, error: failure },
    { index: 2, result: existingResult }
  ]
}
```

批量结果中的 total 是原始输入数，index 对应输入位置。每项包含结果或失败，不另设 TaskItem 身份。合法批次在单项失败后继续；处理完全部输入后，可以正常返回含有失败项的报告。

整批被取消或无法继续时，ExecutionFailure.partialResult 保留已经得到的合法报告，未开始项不伪造失败。某项失败前已经发生的事实，通过该项的 partialResult 保留。根条目提交后再取消，不能抹去新增事实；只有获取、尚未提交时，则不能声称已经更新。调用者和 TaskCenter 使用相同的真实结果，不必再根据任务引用回查。

<a id="commit"></a>

## 提交与执行边界

公开调用完成一次完整资料操作：按需读取与来源对应、本地采用决定、资产准备、当前事实复核、短事务内的业务图写入，以及提交后通知和适用的首次 holdings 识别。内部按实现需要复用这些步骤。

library.writeGraph 接收目标与内容均已明确的本地写入请求。最终事务再次核对身份、目标、基线和约束，不能只靠事务外的“不存在”检查防止重复。必要资料或业务图写入失败时，整项回滚。非必需图片失败时，可以报告资料已保存、资产未完成。

明确空值按字段合同处理，未回答保留本地值。关系替换在输入的完整回答范围与用户授权范围内执行。长批次通常按完整作品分别提交；必须共同成立的数据共享原子边界。

取消会停止后续工作及可取消请求，同时保留已完成事实。重试只用于已有安全语义的步骤，不能任意重放超时写入。单项操作对应一个任务，批次对应一个任务，均等待最终业务结果；prepared 较快也不改变任务合同。

人工、扩展、导入和后台调用共用以上语义，各类别的实现由其业务模块组织。来源接入验证端到端行为、身份对应质量、资料粒度、关系回答范围、部分依赖、并发提交和性能。

<a id="issues"></a>

## 采用问题的公共合同

desktop-contracts/ingest 定义 IngestIssue，用于报告影响本次请求的局部采用问题。每项包含安全 message、下表规定的上下文及正式引用或 ErrorSummary。问题随本次结果交付；provider.read 的失败继续使用其自身合同。

| code               | 必需上下文及允许的补充                                                                                                                     | 所表达的事实                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| providerFailed     | providerId、operation: resolve/read、error: ErrorSummary                                                                                   | 某来源未完成；仅在其余资料仍允许合法采用时出现在正常结果                                     |
| sourceAmbiguous    | providerId、entryType；已有确切输入时带 identity                                                                                           | 已请求的来源对应仍有未解决歧义，影响实际采用；正常未命中不是 issue，根目标不能确定时整次失败 |
| processorFailed    | processorId、固定资料目录内的 field、error                                                                                                 | 该字段的处理器链失败，本次不采用该字段；其余合法字段继续，见[加工规则](metadata-profiles.md#processors)                                                 |
| valueRejected      | 固定资料目录内的 field、reason: invalidValue/unsupportedValue；已知时带 providerId、target 或 identity                                     | 取得的值不满足该领域合同，不把缺席或合法空值当错误                                           |
| associationSkipped | 固定 relations 目录内的 relation、reason: missingEndpoint/ambiguousEndpoint/invalidDimension/incompleteRange；已知端点的本地引用或外部身份 | 关系成员或所选替换范围无法采用；在提交前确定受影响分支并保留其余合法部分                     |
| imageFailed        | 固定图片字段、error；已知时带 target、providerId                                                                                           | 所选非必需图片未能采用，其他合法资料已完成                                                   |
| holdingsFailed     | work: WorkRef、error                                                                                                                       | 资料及明确本地登记已经成立，首次识别或后续明确的本地处理没有完成                             |

field 和 relation 从[资料方案固定目录](metadata-profiles.md)中选择，并带有对象类别，不能使用任意 JSON 路径。target 表示本地引用，identity 表示来源身份。无法确定完整上下文时，只保留实际已知范围，不生成隐藏定位码。新的问题类型由所属领域明确扩展合同，不使用 unknown 加任意数据兜底。来源名称只用于必要展示，不决定业务分支。

扫描发现、候选 AddResult 和未完成范围由 [ScanResult](scanner.md#result) 表达，并归 scanner 管理。任务历史按各业务自身的结果合同保存相应快照。

## 获取与采用的内部组织

metadata 按来源能力、保存的方案与单次获取分别组织。提供者和处理器的登记具有自己的寿命，不因此建立一个统管全部搜索、配置和获取的管理实例。

| 内部位置            | 负责内容                                                     |
| ------------------- | ------------------------------------------------------------ |
| providers.ts        | 原生提供者目录、实现登记及选用绑定                           |
| field-processors.ts | 字段处理器目录、实现登记及受限调用                           |
| profiles            | 资料方案的保存、定义校验、默认选择及预设                     |
| search.ts           | 单个提供者的搜索、分页和本次结果                             |
| fetch               | 按方案完成一次资料获取，组织定位、读取、对应、合成与字段加工 |

fetch 的完整入口拥有本次采用的实现绑定、输入快照、原始线索、已尝试的定位条件、读取会话和调用内缓存。定位补足与按需读取可以往复协作；只有新信息改变条件时才继续相应定位，不将其固定为逐阶段只执行一次的流水线。执行完成、失败或取消时，由取得资源的本次获取完成会话关闭和清理。

来源对应、字段与集合合成、字段加工各自保留明确规则，按实际协作需要在 fetch 内拆分。内部实现接收所需输入并返回实际事实或结果，不通过相互调用完整 fetch 接口推进流程，也不共用包含数据库、UI 和任意服务的全局上下文。加工结果不修改原始身份依据，来源缺席、明确空回答与失败分别保留。

ingest 按完整新增、完整更新及其本地决定组织：

| 内部位置    | 负责内容                                                   |
| ----------- | ---------------------------------------------------------- |
| add.ts      | 完整新增、单项与批量新增的业务实现，以及适用的首次持有识别 |
| update.ts   | 固定目标与范围的完整更新，以及对应批量业务实现             |
| matching.ts | 本地身份对应、复用与冲突判断                               |
| adoption.ts | 所选字段与关系的本地采用决定，包括补空、覆盖和替换         |
| graph.ts    | 将已经明确的采用结果组织成现有 LibraryWriteGraph 输入      |

metadata 实现来源对应，ingest 按本地身份规则完成复用。graph.ts 在本次调用中构造候选图，正式模型校验与数据库事务提交由 library.writeGraph 完成。

单项、批量与扫描共用实际新增或更新的业务实现，任务包装由明确入口组织一次，不在每个内部步骤或批次成员中嵌套任务。其他 feature 通过 metadata 与 ingest 的完整能力调用，不直接进入 fetch 的内部阶段或自行拼接本地图写入步骤。

ingest 为 scanner 和批量执行提供明确的原生单项业务调用，复用完整新增或更新的输入、结果与规则，并使用调用方已经接纳的执行上下文。独立调用的入口负责自己的任务托管；已有任务中的单项业务不再次创建 TaskRun。这个协作入口保持单项业务完整性，不开放本地对应、采用或事务写入的中间步骤，也不因内部协作而增加窗口或 SDK 方法。
