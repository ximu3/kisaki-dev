# Node 回调与 Electron 跨文件交接

本组验证同一个 libmpv 核心在受控文件切换中的真实 Node 回调、迟到工作隔离与共享纹理回收。普通 Node 和 Electron 各运行两种线程轮询节奏，四组通过。它补充[原生播放切换检查](../libmpv-playback/verification.md)未覆盖的 JavaScript 与消费进程交接，没有实现正式公共包，也不将结果扩大到任意脚本或所有平台。

## 输入、线程与资源

使用既有固定探针 DLL 和直接 D3D11 入口，复用未修改的 [producer.cpp](../libmpv-gpu/producer.cpp)。输入为既有生成的红、蓝两段 FFV1 视频；来源、二进制、输入及本组源码摘要保存在 [handoff-contract.json](handoff-contract.json)。没有读取用户媒体或配置，没有显示窗口、切换 HDR 或修改显示设置。

[handoff.cpp](handoff.cpp)在一个核心中依次执行红、蓝、红、缺失文件、蓝的加载，并在蓝色视频中定位到 0.5 秒。控制与渲染在不同原生线程推进；渲染线程不执行普通控制调用。两组节奏分别为渲染每 3 ms／控制每 1 ms，以及渲染每 1 ms／控制每 3 ms。这些数值改变探针轮询节奏，不声称赋予操作系统线程优先级或穷尽所有调度。

on_before_start_file 使用独立弱客户端，playlist-entry-id 观察使用另一独立弱客户端；控制／观察、帧和 hook 通过三个独立 Node-API ThreadsafeFunction 通道交付。hook 由 JavaScript 完成协调后明确继续，没有从原生事件读取顺序推断其他 JavaScript 回调已经执行。

在途原生帧最多四张，达到上限时继续 skip-rendering。帧通过独立 GPU 复制持有，原型使用读回完成作为复制同步依据；这组没有验证生产实现中的无读回同步或纹理池复用。读回也用于测试像素，正式交付不应因此增加常态 CPU 像素复制。

## 受控交接协议

1. 宿主为每次交付登记使用独立 token。它表示订阅所属的应用交接范围，不是原生帧自带的文件身份，也没有增加到正式 NativeFrame 合同。
2. 收到新文件开始前的 hook 后，关闭旧交付，向渲染线程提交停止订阅。渲染线程排空当时待处理的旧原生更新，再从同一帧回调通道确认屏障。
3. 登记新的交付范围后继续 hook。结合同一次 start-file 的原生条目身份、file-loaded、playback-restart 和非 REDRAW／REPEAT 的候选画面判断就绪。
4. 消费端先接纳新的交接范围并确认，再接受相应纹理。尚未交付的候选只保留最新一张，被替换持有立即归还。
5. 旧范围的异步工作即使迟到也只处理自己的持有，不能以当前会话重新解释它。

像素没有参与这些接纳判断。生成素材的颜色只作为独立验证依据，检查每次被接纳的画面是否实际属于目标素材。

## 主动制造迟到工作

[scenario.cjs](scenario.cjs)保留一张旧红帧，直到蓝色文件已经就绪才继续其 Node 处理。此时直接使用“当前会话”重新标记它，会把真实红帧关联到蓝色视频；每组都记录了这个反例。实际接纳规则根据原交接范围拒绝它并归还持有。

另一张旧红帧已经进入消费方，但暂停消费，直到新的交接范围生效才继续。普通 Node 与沙箱 Electron renderer 都拒绝它。Electron 记录消费状态前后未被这张旧帧改写；这是消费状态与像素检查，不是物理屏幕呈现回执。

延后工作的放行使用明确条件，不依赖固定延时碰巧跨过文件切换。每组还保留首张红帧直到播放核心关闭，再读取其内容。Electron 中额外保留 VideoFrame clone，只有其关闭后，allReferencesReleased 才归还对应原生持有。

## 本次结果

| 运行环境 | 渲染轮询 | 创建／最终归还 | 最大在途 | 接纳画面 | 迟到 Node 丢弃 | 迟到消费丢弃 |
| -------- | -------- | -------------- | -------- | -------- | -------------- | ------------ |
| Node     | 3 ms     | 16／16         | 4        | 8        | 4              | 1            |
| Node     | 1 ms     | 14／14         | 4        | 7        | 3              | 1            |
| Electron | 3 ms     | 15／15         | 4        | 7        | 4              | 1            |
| Electron | 1 ms     | 15／15         | 4        | 7        | 4              | 1            |

共创建并最终归还 60 张原生帧，最后存活数量均为零；每组在关闭核心时仍有一张被外部持有，随后读取仍为红色。Electron 共完成 16 次导入，每次 allReferencesReleased 恰好调用一次。

五次加载使用不同的原生 playlist entry；缺失文件的命令回复为成功，随后才报告加载错误，没有发布就绪画面，下一次蓝色加载恢复成功。四组实际定位结果均为 0.5 秒。所有被接纳的画面通过颜色核对，四组均记录一个按当前会话重新标记旧帧会出错的反例。

[verify.py](verify.py)独立核对源码与输入摘要、条目身份、加载完成条件、像素、迟到工作和引用计数，并生成 [analysis.json](analysis.json)。帧数量随线程调度可能变化，验收依据是颜色与归属正确、迟到工作被拒绝、在途上限及最终全部回收，不要求每次重复运行产生相同数量。

## 结论与范围

这组证据支持在明确控制内容操作、使用原生 hook 协调、隔离迟到工作时复用播放核心。它不要求在帧中补造文件 ID，也不要求为了普通换文件默认重建核心。

本次仅覆盖 Windows x64、当前固定 DLL、单一 GPU、64×48 BGRA8 与生成素材，关闭硬件解码且音频输出为 null。没有验证音频到物理显示的同步、字幕、HDR、快速并发加载取消、任意脚本自行切换、队列溢出、renderer 崩溃或 Node 环境强制退出。正式订阅接口、GPU 复用池及其他平台仍需各自实现和验证。此前低峰值线性 NaN 未被修复，相关未通过状态保持有效。

## 复现

先准备既有固定 GPU 输入与红、蓝素材，再从仓库根运行：

```sh
python refactor/verification/evidence/libmpv-handoff/run.py
python refactor/verification/evidence/libmpv-handoff/verify.py
```

构建使用锁定依赖并离线执行。临时 addon、Electron 用户目录和中间收据均位于仓库忽略缓存；正式源码、摘要收据和分析结果保存在本目录。
