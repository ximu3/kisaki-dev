# CI 编排方案正式采用

用户在完成[方案与实测](../README.md)后确认开始实施。本轮将已验证的原型纳入正式工程合同和任务入口，研究分支保留原始比较与失败记录。验证对应 W00 的工程与测试入口范围；后续项目在所属工作包接入业务、宿主与发行检查，并按实际职责调整工作流组织。

## 实现范围

- 选择任务完成后，仓库检查、六目标运行／制品和六目标开发回归在独立 runner 并行；Required checks 核对选择、执行和有依据的跳过。
- 运行检查与打包复用一次有限构建；根打包入口通过 Turbo 的本包构建依赖保持独立可运行，打包消费者校验既有构建身份、完整文件集合和摘要。
- 开发回归只提前准备原生输入与所需公共依赖。Windows 原生窗口观察直接使用既有 .NET API，并传递取消、等待观察进程关闭；严格环境和原有断言预算保留。
- GitHub 官方缓存按系统、架构、Node 和任务职责分组；选择原因中的上游构建标记不提升为全量验证。
- 正式 workflow 使用同一份六目标声明、macOS 部署目标步骤和 runner 环境记录。macOS 的 13.0 只定义一次，并在对应任务安装依赖前设置。
- 移除实验专用 workflow 与三个残留的测量用源码注释，保留原始记录。工程工作区合同、构建合同和 CONTRIBUTING 同步明确准备责任，以及 4／10／15 分钟的反馈目标和统计边界。

## 验证与交付

源码提交 `1d186a55c6f2f5349dd5ae89835f3bb4c6d9d5ba` 的[正式 CI 40522832587](https://github.com/ximu3/kisaki-dev/actions/runs/40522832587)十五项任务全部通过，另一个 PR 标题工作流也通过。实际完整等待为 11 分 55 秒，累计 runner 时间为 82 分 17 秒。各阶段原始时长、选择范围及验证汇总见 [summary.json](ci-40522832587/summary.json)。

六目标每个均执行工程工具五项、四窗口、七项开发场景、二十次启动及正常退出、一个最终载体用例。原生与 SQLite 共七项：Windows x64 全部通过，其余五目标因临时测试根位于同一文件系统而明确跳过跨文件系统移动，其余六项通过，与既有条件一致。仓库消费者两项覆盖八个公共包，浏览器交互一项通过。

六目标的构建身份均为 `a045d504b629d0d0645895e044a99e010cbc353cc1c775730a628863618ac98b`，与本机一致。每个目标仅执行一次应用构建；运行检查前后的构建清单摘要、修改时间与打包回执核对通过。十四份附件的报告和元数据已归档，二十六份候选及更新文件均在上传目录中。小附件完整下载并核对 SHA-256；大型附件核对报告 CRC、远端摘要和文件目录，未声称在本机重新计算全部大型二进制摘要。

本机完整 `pnpm check` 的 48 项常规测试、actionlint 1.7.12 对三份正式 workflow 的检查均通过。YAML 展开的任务、步骤、条件及两个六目标矩阵与已测原型一致，仅更新环境记录的显示名称，见 [workflow 核对](local/workflow-equivalence.json)。独立根打包命令成功，日志中只有一次应用构建；生成的原样 ZIP 真实启动和正常退出通过。根开发回归七项通过，测试报告为 115.27 秒。四类失效构建拒绝复用原型同一校验实现的证据，不因类型导入整理重复运行。日志、摘要和回执见 [local](local/files.json)，四份本机候选按回执摘要核对后保存在忽略目录 `artifacts/ci-adoption/2026-10-27/local-windows-x64`。

随后仅补充证据的提交 `85d2078` 在[完整 CI 40525500828](https://github.com/ximu3/kisaki-dev/actions/runs/40525500828)出现一次 macOS x64 开发回归失败：第一个用例在 120 秒内没有观察到首次 ready；其余六个开发用例、其他五目标开发回归和全部运行／制品任务通过，Required checks 正确拒绝通过。该次源码与首轮通过版本相同，但原辅助函数没有保存控制器状态和输出，无法从失败断言区分构建未完成与启动失败。该运行保留在 [ci-40525500828](ci-40525500828/run.json)，不计入成功测量。

为补齐诊断，开发测试现在通过 Vitest 的测试结束钩子保存控制器的最后 32 个状态、错误、最后 16,384 个字符的输出与实际退出状态，沿既有开发报告上传；运行实现、断言和等待预算未改变。本机七项开发回归通过，耗时 108.19 秒，见 [local/diagnostics](local/diagnostics/files.json)。两组 macOS x64 探针运行九次独立首次启动，均通过，首次 ready 为 58.9–102.6 秒，见 [40529204600](startup-40529204600/observations.json) 与 [40531784303](startup-40531784303/observations.json)。没有复现原失败，不能据此确认原因或声称已经修复。

第二组原拟比较公共包构建缓存命中与未命中。复核日志后发现，两个 `cached` 任务虽然恢复了归档，实际构建仍全部未命中：限定测试范围的透传参数参与 Turbo 任务哈希，而缓存准备命令没有这些参数。九次采样均应按实际未命中记录，不能作为缓存条件对照。相同输入下的[本机计划比较](local/cache-plan-comparison.json)确认了这一差异；没有透传参数的正式测试入口与缓存准备哈希一致，正式 CI `40525500828` 的六目标开发任务也均实际复用两个上游构建。修正后的探针使用完整开发入口，并在执行前核对真实构建任务的 HIT／MISS；一次尚未开始测量的[探针运行](startup-40534731178/run.json)因排除无命令任务的诊断脚本修正而取消，保留原记录。

带诊断的提交 `511110c` 在[完整 CI 40533584014](https://github.com/ximu3/kisaki-dev/actions/runs/40533584014)通过全部六目标开发回归，macOS x64 首次 ready 为 94.134 秒。Linux x64 的最终载体用例在第二次、通过开发通道启动后，立即查询系统窗口列表得到 false；同一用例首次普通启动的有界窗口观察及运行检查已通过。应用在 renderer 挂载和 `window.show()` 调用完成后报告 ready，外部窗口列表的更新不与该消息同步。该分支改为沿用已有 30 秒窗口观察预算和取消信号，持续要求真实系统窗口出现，再验证正常退出。本机原样 ZIP 通过，耗时 4.66 秒，见 [local/window-observation](local/window-observation/files.json)；修正的 Linux 实际载体验证尚待下一轮 CI。该失败与原 macOS 启动超时分别保留，不计入成功测量。
