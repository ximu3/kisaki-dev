# 受管输出责任方案比较

这是受管使用约定的取舍记录。当前规则以[视频输出](../../../design/projects/libmpv-node/video.md#constraints)为准。

<a id="finding"></a>

## 两种要求并不相同

帧的内存与资源寿命由库负责：引擎退出、输出切换或尺寸改变都不能让已经交付的帧失效，也不能留下无人处理的原生等待。这项责任不应依赖调用方遵守某张配置清单。

原生 vo 改变会改变输出驱动，target-trc 改变会改变像素传递函数。这些操作与资源损坏不同；采用的使用约定要求调用方尊重输出拥有者的配置范围，库继续负责资源寿命。

[图形原型](../libmpv-gpu/verification.md)现已分别验证这两件事：保留的共享纹理在缩放、原生 vo 切换及核心销毁后仍可读取；使用明确 sRGB 与 auto 峰值后，改变 target-trc 为 linear 使测试灰色从 128 变为 55。后者只证明颜色设置确实影响像素，不把该数值比较当作完整色度学验收。因此资源安全不能成为冻结全部设置的笼统理由，而固定颜色描述也不能在原生目标变化后继续无条件沿用。

<a id="comparison"></a>

## 已采用路线与另一方案的取舍

| 比较项             | 保留原生配置语义，明确使用约定                     | 自带 libmpv 增加原生配置保护                   |
| ------------------ | -------------------------------------------------- | ---------------------------------------------- |
| 受管设置归属       | 调用方遵守受管模式约定；直接输入做可行的检查       | 受保护设置由输出拥有者控制，原生写入前强制检查 |
| 脚本与 profile     | 可以使用，但调用方保证不改写约定由输出拥有的设置   | 可以使用，冲突写入由引擎拒绝；其他设置照常生效 |
| 正常使用时的帧合同 | 保证已选目标与描述一致                             | 保证已选目标与描述一致                         |
| 违反受管配置约定   | 报告可检测的冲突；不能保证所有内部改写都被提前阻止 | 对已覆盖的受保护设置，在生效前拒绝冲突         |
| 资源寿命           | 继续由库完整负责                                   | 继续由库完整负责                               |
| 升级成本           | 主要跟随公开 API 与既有行为回归                    | 另需维护补丁、私有接入与各写入路径回归         |
| 必须接受的代价     | 收窄“所有入口均前置拒绝”的承诺                     | 承担原生配置控制机制的长期维护                 |

两条路线都不能通过“写回原值”伪装成前置保护。设置可能已经触发输出重建或影响一帧颜色；事后观察也无法证明此前没有变化。

所采用的使用约定路线必须明确列出约定范围，不能用“未定义行为”推卸帧寿命和清理责任。已知直接冲突可以提前报告 renderConflict；脚本内部改写的检测与停止是补充机制，不应被描述成完整隔离。违反约定的任意脚本组合不再具有固定颜色解释的保证。库不通过持续写回原值隐藏冲突，也不因一个输出配置冲突自动退出整个核心。

这个边界已经明确接受：脚本违反约定时，检测之前可能已经交付受影响的画面，不能保证零错误标记帧。这里的原生配置保护指选项写入的强制前置检查，与正常的线程同步无关。若以后要求任意脚本都无法破坏受管输出，需要收紧可用入口或增加上游层面的写入保护，属于合同变更。

<a id="native-protection"></a>

## 原生保护实际意味着什么

[能力与设置探针](../libmpv-catalog/verification.md)确认，直接调用、Lua 与 apply-profile 均能修改原生输出设置。公共 Client API 没有任意选项写入的前置拦截接口。配置变更通知发生在写入之后，所以纯 Node 校验覆盖不了所有路径。[配置写入实现](https://github.com/mpv-player/mpv/blob/41f6a645068483470267271e1d09966ca3b9f413/options/m_config_frontend.c)

<a id="assessment"></a>

## 已确认的职责边界

按绑定库的职责保留上游行为，将受管设置作为明确的使用合同，继续严格承担资源与帧寿命。现有证据没有证明必须通过配置锁才能维持资源安全；本库不额外承担强制限制所有脚本设置的宿主控制承诺。

<a id="validation"></a>

## 验证范围

现有 GPU 与设置探针没有实现原生配置保护。具体受管设置和帧描述边界已在输出合同列明；后续验证覆盖直接检查、可检测冲突和配置切换的实际处理，纯观察不被当作消除所有竞争的机制。

Windows 已确认采用上游合入的直接 D3D11 Render API，并按[固定源码与补丁清单](../../../design/projects/libmpv-node/distribution.md)自行构建。直接后端已有原生和 Electron 原型；最终依赖组合、受管设置与完整平台验收见[视频输出终态设计](../../../design/projects/libmpv-node/video.md)。这项选择不改变本页已经确认的使用约定路线，也不将现有探针 DLL 直接转作发行包。[上游提交](https://github.com/mpv-player/mpv/commit/4255130de410e0cbdab694b951085409d466b704)
