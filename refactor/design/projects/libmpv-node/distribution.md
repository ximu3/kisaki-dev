# libmpv-node 构建与发行

本页定义固定构建输入、播放能力、补丁、动态依赖、许可和最终平台包。

<a id="dependencies"></a>

## 构建输入与运行依赖

每次发行由一份原生构建清单固定 mpv、FFmpeg、libass、libplacebo、相应字体与网络依赖，以及实际使用的图形接入库。清单包含精确来源、摘要、工具链、目标、配置、必要修改和产物依赖；锁定范围覆盖传递依赖。必需功能显式启用并在缺失时构建失败，不能随构建机可用包静默变化。

组件用途与功能目录见[构建输入](#inputs)，包配对、非代码资源和加载见[发行清单](#artifact)与[加载规则](#loading)。六目标使用正式构建和消费验证后的制品。

所选固定提交的 Meson 文件将 FFmpeg、libass 和 libplacebo 列为构建依赖。文件中的最低版本只表示兼容要求，不是本项目已经选定的版本组合；正式发行的完整版本与功能矩阵须通过实际六个平台目标构建后冻结。[构建依据](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/meson.build)

延续[既定交付](../native-runtime.md#delivery)和[许可方向](../../engineering/licensing.md#third-party)：优先满足完整播放要求的实际 LGPL 构建及动态交付。libmpv-node 自己装配匹配的媒体运行库，Kisaki 消费同一份平台包；不借用 Electron 附带的 ANGLE，也不依靠开发机 PATH 或系统安装的另一份媒体库。操作系统图形驱动与平台框架是明确的运行前提，尤其 Linux 的 EGL、GBM、DRM 与驱动组合需要单独列出。

Windows 生产端采用直接 D3D11，完整 libmpv 构建显式携带自身依赖。验收核对实际导入依赖、加载路径和同进程使用；运行时不改写全局 PATH，也不借用 Electron 的私有图形库。

运行库按[进程寿命](lifecycle.md#runtime-lifetime)装载，播放器实例与 Node 环境分别收尾，代码映射驻留不放宽实例资源的回收要求。正式依赖的多实例、环境退出与版本配对检查覆盖这项使用方式；重复装载实验的失败保留其原始范围，不因改变装载策略而标记为已修复。

平台包仍覆盖 Windows、macOS、glibc Linux 的 x64 与 arm64，系统下限保持[现有合同](../../engineering/build.md#platforms)。工具链、最低 Node-API、Node 与 Electron 测试范围分别记录。当前工作区的 Electron 41.2.0 不替代已规划的 44.5.1 消费验证。

### 标准发行采用共同的完整播放能力基线

已确认以一份完整播放能力清单驱动六个平台的构建，平台差异主要来自系统后端与实际硬件能力。下表是交付要求，具体编解码器、协议、滤镜和后端必须进一步展开为构建清单与对应检查，不以表中类别代替实际通过记录。

| 范围       | 已确认的标准发行基线                                              |
| ---------- | ----------------------------------------------------------------- |
| 内容输入   | 本地文件、HTTP(S)、明确列出的原生流协议，以及 Node 自定义只读协议 |
| 音视频     | 完整的软件解码基础、各平台适用的硬件解码与音频输出                |
| 字幕       | ASS／SSA、常用文本与位图字幕、内嵌和外部字体、复杂样式与动态效果  |
| 媒体处理   | 原生音视频滤镜、缩放、色彩转换与色调映射                          |
| 配置与脚本 | 原生配置、profile、Lua 与 JavaScript，沿用已确认的使用约定        |
| 渲染交付   | 两种 SDR GPU 颜色目标、独立软件 Render API 和既定平台共享资源路径 |

接口合同、构建清单与运行查询分别说明支持范围、已编入能力及当前设备条件。实际功能通过原生查询与随包清单核对，执行失败按既定结构化语义交付。Client、Render 和 Stream API 各自维持完整接入合同。

mpv、补丁、FFmpeg、libass、libplacebo 和平台接入组件作为一套共同验证的构建组合维护。每项外部组件明确对应的功能用途、固定来源和构建配置；必要功能缺失时构建失败，不随构建机可用包静默改变。当前实验中的 MSYS2 依赖集合保持研究环境的定位，正式组合另行核对。

升级以实际构建组合为单位验收，检查媒体播放、字幕、颜色、控制调用、资源寿命和宿主消费。补丁移除遵守[补丁维护规则](#当前采用的补丁)。具体版本、编译开关、动态库装配与回归细节按这份能力范围落实；需要改变能力范围或长期维护边界时再讨论。

## 平台接入与上游来源

Windows 已确认采用官方合入的直接 D3D11 Render API。正式依赖使用包含该入口的完整固定上游提交，加明确列入清单的必要修复补丁，自行构建并固定所有输入；不跟随移动的 nightly，不将功能补丁回移到旧稳定版，也不把第三方探针 DLL 直接作为发行物。当前源码输入固定为 01e2533f3143b8940857ca419b0b367f583e05ca 加黑色字幕零分母保护与截图来源标记，应用、回归和移除规则见[源码与补丁](#当前采用的补丁)。FFmpeg、libass、libplacebo 等完整依赖组合在验证后冻结。

本项入口通过提交 4255130de410e0cbdab694b951085409d466b704 合入上游，新增适配复用已有 ra_d3d11 与 gpu 渲染管线。它接纳调用方设备、包装目标纹理、提交和释放引用，媒体算法仍由上游处理。图形入口的选择不改变公开输出合同，也不自动提供 gpu-next 的嵌入能力。[上游提交](https://github.com/mpv-player/mpv/commit/4255130de410e0cbdab694b951085409d466b704)、[原生资源与线程合同](https://github.com/mpv-player/mpv/blob/4255130de410e0cbdab694b951085409d466b704/include/mpv/render_d3d11.h)

| 平台    | 已选接入                        | 交付资源                 |
| ------- | ------------------------------- | ------------------------ |
| Windows | 直接 D3D11 Render API           | D3D11 纹理及 NT 共享句柄 |
| macOS   | CGL／OpenGL 接入 IOSurface 目标 | IOSurface                |
| Linux   | EGL／OpenGL 接入可导出图像      | dma-buf                  |

Windows 生产端采用上述原生输出路线。Electron 自身的图形实现由 Electron 管理，独立库使用自己的明确依赖。三种平台接入共用输出、同步和持有合同；平台与驱动的真实差异分别验证。生产端不隐式切换到 OpenGL／ANGLE。

采用较新上游提交时，验证覆盖该提交相对既有基线的全部相关变化，以及最终依赖装配和六目标制品。当前 D3D11 机制使用固定提交 01e2533f3143b8940857ca419b0b367f583e05ca，其初始化、脚本、尺寸、持帧关闭和 Electron 引用回收结果见[GPU 原型](../../../verification/evidence/libmpv-gpu/verification.md)。

Windows 使用本节确定的上游版本与原生输出接口，媒体颜色处理使用上游能力。

透明参考图的反例继续如实保留，不单独构成更换渲染器的门槛。正常不透明播放、字幕、HDR 片源到 SDR 的映射和资源边界仍须按实际要求验收。macOS／Linux 按[平台依据规则](../../../verification/acceptance.md#platform-evidence)以接口与源码完成设计；正式运行结果不能借用 Windows 原型，GPU 与软件输出继续显式选择。

## 能力与构建输入的对应

构建先声明需要的能力，再选择并固定提供它的组件。所选组件、配置和传递依赖作为一个组合验证；依赖的最低版本要求不充当发行锁定版本，构建机自动发现的组件也不决定支持范围。

| 能力                 | 构建责任                                                                                     | 检查依据                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 文件、网络与只读协议 | FFmpeg 的 demuxer、protocol、网络和 TLS 实现；libmpv Stream CB；适用的原生输入模块           | 实际编译目录、选定协议的读取与定位；HTTPS 包括证书校验所需的实际来源             |
| 音视频解码与处理     | FFmpeg 的软件解码器、解析器、音视频滤镜、缩放与重采样；实际采用的外部解码及处理库            | 编译配置与目录分别核对，覆盖约定的格式、位深与处理行为                           |
| 字幕与字体           | libass、FreeType、HarfBuzz、FriBidi 及所选字体发现后端                                       | ASS／SSA、文本与位图字幕、附带字体、系统字体与复杂排版；字体发现配置也是运行资源 |
| 脚本与配置           | mpv 的配置、profile、Lua 后端与 MuJS                                                         | 原生配置与两类脚本实际执行；已选源码支持的 Lua 版本以其 Meson 输入为准           |
| GPU 与软件输出       | 既定 Render API、libplacebo、实际使用的着色器工具及平台互操作                                | [共享资源、完成同步与颜色合同](platforms.md)；软件 Render API 独立验收           |
| 平台播放后端         | Windows 的 WASAPI／D3D11VA；macOS 的 CoreAudio／VideoToolbox；Linux 选定的音频与硬件解码后端 | 编译包含、运行可用、实际播放分别记录；存在选项不代表当前设备支持                 |

交付范围包括完整 Client／Render／Stream API 绑定与既定播放基线。可选编码器、设备输入和滤镜按实际构建清单列出启用项、未启用项及理由。改变已确认能力或长期维护范围时先讨论，并据此修订构建清单与验收。

libcurl 未编入 mpv 不能单独证明没有 HTTP(S)：FFmpeg 自身的协议与 TLS 后端也可承担输入。类似地，启用了 D3D11 渲染不能证明已启用 D3D11VA 解码，已有 Lua 也不能证明 JavaScript 可用。清单按这些真实责任分别检查。

字体发现同样按平台明确：Windows 的 DirectWrite、macOS 的 CoreText，以及 Linux 的 Fontconfig 与配置各自记录。额外编入的字体后端也要说明所需数据，不能因 DLL 完整就忽略配置文件。当前 libass 来源的自动选择优先使用适用的原生提供器。[libass 的提供器顺序](https://github.com/libass/libass/blob/0.17.5/libass/ass_fontselect.c)

## 实际组合与许可

继续优先采用满足能力要求的实际 LGPL 构建及动态交付。mpv 的 `-Dgpl=false` 只选择 mpv 自己的代码范围；FFmpeg、字体、着色器工具和其他依赖仍须分别核对配置、来源与适用条款。FFmpeg 启用 GPL 组件会改变其整体许可，不能以封装包的许可或单个 mpv 开关覆盖它。[mpv Copyright](https://github.com/mpv-player/mpv/blob/01e2533f3143b8940857ca419b0b367f583e05ca/Copyright)、[FFmpeg 许可说明](https://ffmpeg.org/legal.html)

上游 LGPL 模式排除的部分原生窗口输出与本库受管共享图像接入不是同一层能力。例如 Linux 的原生 X11 VO 和 EGL／dma-buf 交给 X11 桌面上的消费应用须分开判断，后者按既定路线核对接口与源码，并在正式平台验收记录运行结果。发现必需能力无法在候选组合内成立时，讨论具体差异，不静默切换许可或删除平台。

发行同时保存第三方声明、适用的许可全文、修改、精确对应源码和构建材料。Windows 的 Visual C++ Redistributable 与系统 UCRT 不是同一个交付责任；前者若被产物依赖，须选择适用的再分发来源和部署方式，不能把开发机 System32 中恰好存在的文件当作系统保证。[Microsoft C++ 部署](https://learn.microsoft.com/en-us/cpp/windows/deployment-in-visual-cpp?view=msvc-170)

## 主包、平台包与发行清单

主包拥有公开入口、声明与平台选择；六个平台包各自包含该目标的 addon、匹配引擎、非系统动态依赖和必要数据。主包与平台包使用精确版本关系，平台清单还要匹配构建身份。不能只比较 JavaScript 版本或能否装载 Node-API 就放行另一套引擎。

构建清单随发行材料交付，至少记录以下事实：

| 部分           | 内容                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| 身份与兼容条件 | 项目版本、构建身份、os／cpu／libc、系统及 ABI 下限、实际 Node-API 等级和宿主验证范围 |
| 原生来源       | mpv 提交与补丁、各直接及传递组件的版本／来源摘要、工具链、配置与必要修改             |
| 制品与资源     | 包内相对路径、用途、大小、摘要、动态导入关系、动态插件及数据文件的位置               |
| 系统前提       | 真正由系统或驱动提供的接口、平台框架、图形栈与设备条件                               |
| 功能与声明     | 实际选项／命令／属性目录、编译能力、语义声明来源及相应消费记录                       |
| 许可与来源材料 | 每项交付内容的声明、许可、对应源码、构建和重新链接材料的入口                         |

构建目录、暂存包和 tarball 分开。以暂存内容生成清单，再从最终 tarball 安装并核对字节；签名和平台路径修正须在最终摘要及验收之前完成。消费方不跨仓引用源码、开发目录或临时二进制。

## 制品加载与系统接口

正式安装由包管理器取得完成的制品，不执行安装时联网下载或源码编译。缺少平台包、版本不配、ABI 不符或资源缺失时明确失败，不回退到 PATH、当前目录或另一套系统媒体库。源码开发使用单独指定的开发输入，不能掩盖坏包。

Windows 从已解析的平台包位置装载，并限制依赖目录。PE 普通导入和延迟导入都需要检查；按名称动态装载的模块、字体配置、证书资源等不在静态导入表内，须由其组件的实际用途继续核对。不能把所有不在包里的 DLL 都归为系统文件，也不能只复制某次场景观察到的模块。

绝对 DLL 路径与受限搜索目录不等于隔离所有同名模块：Windows 还会考虑已装载模块。正式运行库在创建核心之前核对配对与实际媒体模块身份，对不匹配情况明确失败；不能静默接受宿主先装入的另一版本。不同版本共存及宿主已有媒体依赖仍是候选装配需要验证的条件。[Windows DLL 搜索规则](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order)

macOS 使用包内可重定位的依赖引用并区分系统 Framework，最终签名覆盖实际装配。Linux 核对 ELF 的依赖、相对加载位置和符号版本下限，系统 EGL／GBM／DRM 与驱动按既定平台前提处理。仅写入 rpath、使用局部装载标志或目录分开，都不能代替实际依赖及宿主互操作验证。

同进程共用的运行库遵守[常驻代码与独立实例寿命](lifecycle.md#runtime-lifetime)。关闭核心、释放帧和 Worker 退出仍回收各自资源；版本更新随进程重启生效。旧研究探针中的整库卸载／重装失败不因换了打包目录而视为已修复。

<a id="consumer"></a>

## 宿主消费与平台资源验证

普通 Node 与 Electron 都从同一组 tarball 安装。最小消费应完成公开入口加载、实际原生工作与明确收尾，并核对媒体模块来自安装内容。清理子进程 PATH、使用独立空工作目录可以排除部分开发路径依赖；它们不能代替没有开发工具和额外运行库的干净机器。

Electron 接入方负责将平台包的原生文件和数据放到可由操作系统直接访问的位置。`.node` 和它需要的动态库不能只留在不可直接装载的归档内部；asar unpack 或 extra resources 的选择由本体构建执行，加载器根据安装后的真实位置找到完整依赖，不假定源码目录结构。Kisaki 不另行下载或维护第二份 libmpv。

图像仍按[本体画面接入](../../engineering/integrations.md#adapter)导入、显示并在消费引用全部结束后释放。包加载通过、核心关闭、图像消费完毕与用户播放会话完成是不同事实。打包试验不能替代完整 Mpv 实现、真实共享图像交接或平台下限验收。

## 截图来源标记补丁

[screenshot-source.patch](../../../implementation/patches/libmpv/screenshot-source.patch)只修改 player/screenshot.c，为 screenshot-raw 的 map 结果增加 source 字段。vo 表示图像来自实际 VO 截图分支；software 表示显式软件截图或正常 VO 未返回图像后采用的软件回退。原有 w、h、stride、format 和 data 的含义、截图选择、颜色计算与回退行为保持原生规则。

字段在实际取图过程中确定，并与该次图像一起返回，不查询稍后的引擎状态。没有图像时沿原命令失败，不制造 source-only 成功。source 不表示所有 VO 都是 GPU，也不构成独立颜色证明；Kisaki 将它与自己已经固定的受管 GPU／sRGB 条件共同核对。

补丁 SHA-256 为 a71f6fed21e0a5754f76cf5c0df9e34126488e0330332fc5259ffeb79d316f57，修改前后源码摘要与顺序保存在[实施清单](../../../implementation/patches/libmpv/manifest.json)。Windows x64 的完整候选构建、正常 GPU、显式软件和强制取图回退结果见[截图来源实测](../../../verification/evidence/contract-closure/2026-10-22/README.md#screenshot)。故障注入只存在于测试构建，不进入实施补丁。

## 构建与升级

libmpv-node 独立项目的原生准备流程接管这份清单、补丁和对应回归用例。每次构建核对完整上游提交、补丁摘要与受影响源码的修改前后摘要，按清单顺序应用；任何不匹配都结束构建，不静默跳过、模糊套用或在构建时临时改写补丁。制品记录包含上游提交与实际补丁集合，配套源码和修改说明随发行材料保存。

FFmpeg、libass、libplacebo、工具链与传递依赖另行固定，补丁的采用不表示同源实验中的 MSYS2 预制依赖已成为发行选择。尚未归因的重复装载失败和并行寿命异常仍按[验证记录](../../../verification/evidence/libmpv-upstream-fix/verification.md)处理。

升级上游时检查补丁所修复的路径，并重跑普通视频、三组原色、低峰值字幕、近黑、半透明合成和原有有限像素对照，再完成相应平台与宿主的验证。上游已包含等效修复且不加补丁也通过这些检查后，从清单移除补丁并更新固定输入。不能仅因补丁无法继续应用就认定上游已经修复。

维护范围按已经确认的问题与行为界定。此项已验证修复的正常构建、回归和上游升级由实施者落实；扩大公开能力、增加引擎配置保护或长期承担新的算法差异时，继续按项目的讨论规则处理。
