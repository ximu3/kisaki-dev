# 产品范围与共同原则

Kisaki 是面向 ACGN 收藏、使用与记忆的本地资料库。它帮助用户长期整理作品及相关角色、人物和组织的资料，管理自己持有的内容，顺畅地使用作品、记录经历，并回顾与展示收藏。编目、持有、使用和记录可以独立成立，也能在需要时连贯协作。

<a id="principles"></a>

## 产品原则

<a id="judgment"></a>

先确认要解决的实际问题，再比较实现方式。简洁与原生优先是产品和工程的重要判断依据，按[全项目准则](engineering/conventions.md#simplicity-native)共同约束体验、实现、测试和文档。已确认的交付目标、受支持的使用场景和有依据的技术约束可以支撑设计；假想需求、形式上的完整或单纯“更保险”不能成为增加机制的理由。

设计按以下顺序判断：

1. 满足已确认的用户目标，准确表达资料、操作结果和用户意图。常见流程能够完成，失败与部分完成如实呈现。
2. 让概念、责任与操作直接易懂。名称与所指相符，常见任务使用少而连贯的步骤，用户能够预知结果；有实际用途的差异明确保留。
3. 优先采用平台与工具的原有能力及惯用方式，保留用户熟悉的输入、窗口与系统交互。统一产品体验时尊重有意义的平台差异。
4. 在满足目标的方案之间，比较用户操作、内部机制、失败后处理和长期维护的总复杂性；增加层次、配置或自定义行为需要具体收益。

简洁与原生从整体使用与维护成本判断，不能只看画面是否空、代码是否短或是否使用系统控件。已有能力能够完成目标时直接采用；确有缺口时做职责明确的补充。预览、重试、防重、恢复、自研和抽象根据实际收益选择，必要的数据和资源边界仍须完整。

结构化资料用于辨认作品、理解内容和创作参与；合集与标签用于表达用户自己的整理方式。共同的资料库保留不同媒介的用途：游戏需要启动和存档管理，小说需要分卷，漫画需要卷与话，动画需要分集和附加内容，角色与配音也需要准确对应。

用户拥有的数据应当能够长期保留，并且始终可以理解。本地功能不依赖官方云服务持续可用。文件操作、后台工作和远端修改都必须说明如何发起、影响什么，以及产生了什么结果。没有本地文件的作品可以正常编目；来源没有提供某项资料，也不能被当作该字段确定为空。

现有应用的界面设计与交互体验整体保留，不做整体改版。本规格规定的局部调整和新增能力在既有设计体系内完成，具体规则见[现有 UI 保留原则](ui/components.md#existing-ui)。

主界面、使用窗口和官方扩展共用信息层次、紧凑布局和操作规则，复用基础组件、语义样式及键盘行为。流程以明确输入、执行和结果反馈为主，预览用于确有作用的场景；执行、确认与编辑反馈见[共同界面](ui/components.md#previews)。

功能和资料来源的选择，需要同时考虑资料准确性、对 ACGN 模型的适用程度、持续可用性，以及用户能否完成整个操作流程。来源语言、来源的整理方式和用户本人账号中的记录各有含义，接入时应分别处理。

<a id="scope"></a>

## 桌面交付范围

本体管理七类独立条目：游戏、动画、漫画、小说、角色、人物和组织。围绕这些对象提供资料浏览与编辑、合集与标签、笔记与标注、资料获取与更新、扫描与持有维护、使用记录与统计、本地展示、任务、扩展、偏好、系统集成和应用更新。

游戏功能以日 Gal 为重点，主要服务 ADV、Galgame 和视觉小说。其他游戏可以获得适用的支持，但不据此改变核心模型、资料预设和主要体验。资料预设统一以“游戏资料”表示用途。

完整交付包含以下内容：

- Electron 桌面应用，包括主进程、preload、主界面、阅读器、播放器、游戏面板和独立扩展宿主。
- 八个公开包，分别负责桌面合同、视觉基础、Solid UI、扩展 API、SDK、分发格式、CLI 和共享 RPC。扩展脚手架由 CLI 提供。
- 33 项 [官方扩展](extensions/catalog.md)，其中资料或平台扩展 17 项、迁移导入扩展 13 项、语言扩展 3 项。
- 新库初始化、工程与测试工具、构建发行、使用文档和协作规范。
- Vantage、Kana、libmpv-node 和 oauth-relay 四个 [独立技术项目](projects/README.md) 的交付，以及桌面应用和官方扩展对其正式发行物或服务的接入。

桌面应用支持 Windows、macOS、Linux，每个系统均覆盖 x64 和 arm64。六个目标分别验证适用功能、原生依赖、系统集成、安装与更新；具体支持条件见 [桌面交付](engineering/build.md)。

第三方平台的账号连接、用户库导入和个人记录同步由扩展提供。本体自有账号、云服务端、云同步、公开 Web 展示、移动端、常驻 daemon，以及面向用户的独立应用 CLI 不属于本次桌面交付。真人影视和 phash-match 不在正式产品范围内。TMDB 只接入适用的动画、人物和组织资料。

kisaki 仓库按 clients、site 和候选 server 划分工程归属。当前交付范围是 clients/desktop 中的桌面客户端、八个公共包和官方扩展；Webview 属于桌面扩展界面。clients/web、site 与 server 保留后续工程归属，服务端同仓须满足源码公开范围相容和许可明确。四个独立技术项目各自维护仓库。软件许可与服务访问见[许可约定](engineering/licensing.md)。

<a id="model"></a>

## 模型边界

模型以七类条目为编目主体，真实分部、用户文件、启动配置、个人记录、合集、标签和应用附件分别管理各自事实。作品的[当前状态与逐次完成记录](domains/records.md)、分部完成标记及实际活动独立保存。身份模型限定于这些直接对象，作品母体、内容表达、发行物、出版版本、系列、企划、副本与体验轮次不设独立身份层级。

作品和真实卷保存当前采用的资料及其来源对应，多份文件分别保存。外部身份用于定位来源对象，不构成完整的出版版本档案。译本、装帧和发行批次等未结构化管理的背景，可以写入简介、说明、私人笔记或来源链接。来源对象不同或文件不同，都不自动意味着需要建立另一个作品。

结构化资料关系分为作品联系、作品角色、人物工作和组织参与。人物工作可以指定本作角色，组织参与限定于真实作品范围。人物、角色和组织本身可以独立编目与收藏；关联只用于实际存在的作品关系。

角色范围包括具有角色身份的人类、动物、机器人、AI 和拟人形象。普通载具、装备、设定机体、舰船、虚构组织、地点和道具属于范围外对象；Organization 管理现实参与主体。来源采用见[角色资料范围](domains/catalog.md#characters)。

配音资料只记录作品正式采用的原作语种角色—声优关系，不收录译配；具体采用要求见[配音资料范围](domains/relations.md#voice-scope)。

人物任职、机构成员、组织控制与沿革、独立人物关系、没有作品范围的角色创作或运营，以及权利关系，均属于结构化模型之外的背景。用户可以用普通标签、合集和笔记自行整理，应用按这些内容各自的普通语义保存和使用。本体与来源接入的结构化关系统一遵守本节范围。作品参与需要主体署名和明确的作品范围，不能从共同背景或其他参与关系推导。

合集用于表达系列、分支、世界观、发行顺序、推荐和记忆等整理视角。一个条目可以属于多个合集，每个合集独立保存内容和顺序。全库不强制唯一归组、正典归属或系列层级。合集成员之间的作品关系仍需明确记录，不能从同属一个合集自动推导。

漫画与小说的作品类别和文档版式分别表达不同含义。两类作品共用阅读能力，固定页面或文本重排由实际文件决定；作品类别负责资料、卷话组织和个人记录，不限制内核的呈现能力。具体行为见[阅读合同](domains/reader.md)。

<a id="vocabulary"></a>

## 领域词汇

| 名称             | 含义与使用范围                                                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Entry            | 游戏、动画、漫画、小说、角色、人物和组织的共同称呼。七类内容共享基础身份，各自再有一层具体类型结构。                              |
| ExternalIdentity | 由 source 与完整、规范的 sourceId 组成的外部身份。七类 Entry 和五类真实 Part 均可使用，但不会因此获得新的对象层级或独立操作能力。 |
| Work             | 游戏、动画、漫画和小说四类作品的共同称呼。只有这些类型拥有作品状态与对应的消费规则。                                              |
| Collection       | 用户编排的条目集合，具有自己的名称、说明和组织行为。                                                                              |
| Tag              | 赋予条目的分类或描述标签，可以独立管理。                                                                                          |
| Organizer        | 合集与标签的统称；两类能力各自维护模型、数据表与完整操作。                                                                        |
| Catalog          | 资料库所知道的对象及其关系。即使没有本地文件，这些资料也可以完整存在。                                                            |
| Holdings         | 用户本地文件与内容之间的绑定。文件路径可以变化，这些文件不属于应用资产。                                                          |
| Attachment       | 应用负责保存的资产字节，例如封面、背景和内文图片。它不表示用户的媒体文件。                                                        |
| Part             | 作品下真实存在的卷、话、分集或附加内容。各类分部有自己的类型和表，不共享基础身份或父表。                                          |
| Record           | 用户评价、当前状态、完成事实、分部标记及活动等个人记录的统称；各类记录由对应业务分别管理。                                        |
| Operation        | 一次具有完整产品含义的查询或修改。它可以在短事务中完成，也可以是具有独立状态的长流程。                                            |
| TaskRun          | 一次受管理的执行，统一提供控制、进度和业务结果。它不代替正式活动记录。                                                            |
| Session          | 实际使用内容时的运行会话，对应打开、播放、阅读或监测的生命周期。                                                                  |
| Module           | 用于组织代码职责和静态依赖的边界。它可以是一个文件，也可以是一组协作文件；是否需要运行实例取决于实际状态与资源。                  |

Entry、EntryType 和 EntryRef 专指七类条目，Work 与 WorkType 则专指其中四类作品。共同基础表为 entries；具体类型和通用引用使用 entry_id，适用的类型字段使用 entry_type。work_* 表及 work_id、work_type、order_in_work 表达作品含义，不另设 Work 父表。

Organization 的类型值是 organization，表名是 organizations，引用字段是 organization_id。work_organization_links 保存组织参与作品的关系。具有独立身份的公司、工作室、社团和品牌可以编目为组织；主体身份、普通资料和在具体作品中的署名分别保存。

Part 包括 NovelVolume、ComicVolume、ComicChapter、AnimeEpisode 和 AnimeExtra，每种分部独立建表。PartRef 联合这五种具体引用，资料模块用 parts 统称分部。Profile 已有根类型上下文，因此使用 volume、chapter、episode 和 extra。

ExternalIdentity 只表达来源对应，不决定对象层级。Entry 和 Part 都可以保存完整的 source 与 sourceId；SourceEntry 则只表示七类条目的来源定位结果。Part 的资料通过所属 Entry 的读取范围取得，不提供独立 Profile、search、resolve 或顶层 read。一次回答内的临时键只用于连接该次对象与关系，不能作为跨次身份。

界面按实际对象使用“作品”“条目”“人物”等称呼，不机械展示抽象类型名。窗口、任务、文件和其他带 ID 的技术对象不会因此成为 Entry。媒体文件、媒体工具和 MIME 类型也保留各自的技术含义。
