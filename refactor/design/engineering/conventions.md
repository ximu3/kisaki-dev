# 设计、实现与验证准则

桌面本体、公共包、官方扩展、独立技术项目和工程工具遵守同一套实现质量要求。功能行为、代码、界面文案和使用说明共同构成完整交付。

<a id="proportionality"></a>
<a id="simplicity-native"></a>

## 简洁、原生与适度复杂度

简洁与原生优先，是全项目设计、实现和审查的重要准则。采用满足已确认目标的最简单完整方案，同时计算用户负担、实现、验证与长期维护成本，避免过度防御、过度测试和过度设计。代码、界面、配置、文档和测试都受这项要求约束；既有合同、实现与测试同样需要说明其保留价值。

**简洁。** 减少完成目标所需的概念、步骤、状态、配置和间接层，让正常流程可以直接读懂和使用。少写行数、合并文件或隐藏必要信息本身不构成简化；把内部复杂性转嫁给用户、把共同规则复制到多处，也不算成本降低。必要的用户数据、权限、公开合同和资源边界保持完整。

**原生能力。** 优先使用操作系统、语言、运行时、框架和工具已有的公开能力、配置与惯用流程，遵守其类型、响应式、异步和生命周期语义。新的产品概念和必要封装按实际目标建立，机制沿用平台原有语义。先比较与需求相关的平台和工具能力，再核对可采用版本的实际支持，决定是否需要自研协议、组件、调度、缓存或适配。封装只承担真实的产品语义、权限边界、资源寿命或必要兼容，不再维护同一工具已有的一套发现、配置、状态或执行机制。不同平台的真实能力可以保留差异，不为表面统一改造成更弱的共同接口。

**原生体验。** 保留用户熟悉的窗口、菜单、文件选择、键盘、文本编辑、输入法、焦点和辅助技术行为。基础网页控件优先采用语义 HTML，复杂交互使用所选框架的成熟原语；自定义样式和产品流程不能无意夺走已有能力。具体规则见[系统能力与控件语义](../ui/components.md#native-interaction)。原生优先不以 Rust 代码数量或系统控件数量衡量，也不自动改变已确认的 Electron／Solid 架构与界面保留范围。

需求依据包括已确认的交付目标、受支持的真实使用方式、相关故障、外部输入与平台约束。尚未实施的已确认功能仍属于交付范围；未经确认的未来消费者、并行用法和兼容场景不自动成为需求。必要性不明时，先查证或讨论，不把推测写成必须实现的保证，也不以简化为由缩减用户已经确认的能力。

涉及效果、能力、用户习惯或维护责任的方案取舍，先向用户说明依据、选项、代价与建议，讨论确定后再修改正式规则。共同准则用于比较方案，不代替用户作出取舍；明确的事实纠错和已确认合同内的实现工作按授权完成。

**设计与抽象。** 从直接可读的正常流程出发。新增层次、通用协议、插件点、策略接口、状态与配置，应服务于明确职责或实际变化。少量重复可以比错误的统一更简单；为相同代码复用而建立的机制也要比较维护成本。保持代码容易修改，不为可能出现的需求提前建立框架。

**防御与恢复。** 校验、锁、去重、重试、补偿、回退、超时和资源预算，需要对应实际入口、资源竞争、失败后果或上游约束。在所属边界完成必要校验，可信内部调用使用已经成立的合同。对明确不支持的用法说明约束即可，例如同一工作副本内独立构建顺序执行时，不另建跨命令并发防护。用户数据持久性、外部信任边界与真实资源寿命继续按其实际风险处理。

**测试。** 用例证明用户或消费者关心的行为、明确合同和有依据的回归条件。不能照抄实现、冻结无关目录或配置细节，也不能为了证明自己增加的机制而制造场景。只因实现能够处理某个极端条件，不意味着必须长期维护其测试。公共入口、正常失败及相关边界按价值覆盖；测试及辅助代码承担与生产代码相同的复杂度成本。

**验证投入。** 按变更影响选择能够回答当前问题的检查与运行环境，已有证据仍适用时复用。普通文档、命名、等价配置移动或输出身份变化，不自动要求整套桌面、性能、制品与六目标回归。新增平台能力、原生边界和实际运行行为变化，执行对应验证。全项目审查表示逐项核对，不表示每个文件都要新增测试；交付时的完整覆盖也不表示每次修改都重跑全部组合。

**社区与事实。** 重要的架构、并发、取消、包组织和测试策略，从要实现的功能与实际需求出发，主动查阅相关社区讨论、维护者意见和成熟项目实践，比较不同做法、替代方案及其代价。研究范围不局限于现有技术栈或已经选定的版本，也不能只寻找支持既有设计的依据。形成候选方案后，再以官方资料和必要验证核对当前或候选工具版本的能力、限制与适用前提。分清真实限制、通行建议和某个项目的特定选择，不能凭记忆、讨论热度或一个例子宣称最佳实践。关键取舍在所属文档或审查记录中留下简短依据与来源；普通实现选择不因此增加独立审批、模板或证明材料。

这些判断参考 [Google 的复杂度与测试审查](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、[YAGNI 对推测性能力的讨论](https://martinfowler.com/bliki/Yagni.html)及[行为测试与变更探测测试的区别](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html)。具体方案仍须核对 Kisaki 的目标和技术条件；已有规范若与本准则的依据冲突，应回到用户目标修订，重要行为与公开合同的变更继续按[实施讨论规则](../../implementation/work-packages.md#unexpected-issues)处理。

## 编码规范归属

各项目的完整编码规范位于自身仓库根目录的 `CONVENTIONS.md`，随源码版本管理。Kisaki monorepo 的应用、公共包和官方扩展采用其根规范；Vantage、Kana、libmpv-node 和 oauth-relay 分别维护自己的根规范，按自身语言、运行环境和职责落实已确认要求。

实施时遵守本篇及各项目专有合同。

编码规范涵盖实现质量、源码语言、命名与类型、注释、错误、日志和边界处理。项目范围、工作包与进度由相应产品和实施文档维护，各类入口引用所属规则，不重复维护同一条定义。

其他文档与协作入口按[文档归属](documentation.md#owners)引用编码规范。

<a id="quality"></a>

## 实现质量

设计与实现按[产品判断原则](../product.md#judgment)评估整体质量。实现应符合所用技术栈和运行环境的现代化最佳实践，保持代码干净、清晰、统一、易维护。主流程直接表达业务意图，名称准确对应职责；公共合同、状态、资源和失败处理都有明确的负责模块。

架构与代码组织遵守[完整重设计与重写范围](../../README.md#rewrite)，从产品目标、公开合同、数据和资源归属及运行约束推导。旧实现及其规范、AGENTS.md、skill 和历史设计不作为默认模板。需要延续的用户行为以已确认要求为准，实现独立设计；保留结构需要目标依据。

优先使用语言、框架和运行时提供的成熟公开能力，并遵守其类型、异步、响应式和生命周期约定。选择自研能力时，说明现有能力不能满足的实际约束或自研的具体收益，并计入实现、验证和持续维护成本。版本与运行环境按 [工作区规范](workspace.md) 检查，不能用类型逃逸、私有 API 或关闭检查掩盖接口和环境不匹配。

<a id="deprecated-apis"></a>

自维护代码与配置发现弃用提示时，依据当前锁定版本的类型声明和官方迁移说明核对替代方式；存在适用于既定运行环境的成熟替代时，迁移并验证行为及检查范围。涉及兼容性或公开合同的取舍先讨论，确认保留的用法记录具体原因与移除条件。不能用屏蔽提示、类型逃逸、修改第三方源码或强制覆盖传递依赖来制造检查通过的结果。

抽象用于复用已有机制或隔离明确的变化点，以职责清晰、真实复用收益和持续维护成本评价。共享代码保留各领域与媒介的含义，局部小策略留在所属模块。

正式运行路径按当前合同交付可执行的行为，调用方同步采用同一实现。测试替身限于测试环境，未完成能力记入状态页。变更完成时清理失去用途的代码、类型、依赖、资源和说明，保持正式结构与当前用途一致。

<a id="readability"></a>

## 代码可读性

本体、公共包、扩展、原生实现、工具、配置和测试采用相同的可读性要求。阅读者应能从名称、类型与主流程判断代码负责什么、数据如何变化、何时完成，以及失败和退出由谁处理。

| 方面           | 具体要求                                                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 名称与值的含义 | 同一概念使用统一词汇；名称表达对象、动作或业务判断。跨边界的数量标明单位和口径，例如 timeoutMs、sizeBytes；缩写限于明确的领域惯例。局部短名称须能由紧邻上下文确定含义，不用编号或模糊名称掩盖不同职责。     |
| 函数与组件     | 每项实现围绕一个连贯职责，调用层表达相近的语义层次。业务步骤、技术机制和界面呈现出现独立职责时拆分；小型内聚逻辑保持就近，不以固定行数或参数数量机械拆函数。                                                |
| 控制流程       | 主路径按实际执行顺序展开，前置失败与无效输入及时返回。多分支、嵌套条件和带副作用的操作使用清楚的 if、switch、循环或具名步骤，不使用嵌套三元表达式或长表达式链压缩流程。简单的二选一取值可以使用三元表达式。 |
| 数据与副作用   | 输入、局部变化、持久状态和返回值的关系可追踪。变量不在中途改换业务含义；写入、登记、资源获取和释放在具名调用或显式语句中出现，不藏进条件表达式、映射回调或属性读取。                                        |
| 类型与状态     | 使用能表达合法组合的类型，分别表达缺省、未知、空值和失败。正式合同直接复用拥有者的定义；不通过 any、连续断言或多个含义不明的布尔值掩盖边界或状态关系。外来数据的校验见[边界规则](#validation)。             |
| 异步与资源     | 代码明确等待什么、哪些工作可以并行，以及取消和关闭如何结束在途操作。锁、订阅、句柄和临时文件的获取与清理能够对应，失败分支同样保持真实的完成语义。                                                          |
| 表达与排版     | 按逻辑步骤分段，相关声明和使用保持接近。复杂条件提取为准确的业务判断，中间值用于解释有实际含义的计算阶段；不以减少行数为目标合并无关操作。格式由统一工具处理。                                              |

提取函数或模块应当让职责、复用或变化点更清楚。只有改名转发、没有新增含义的包装应当消除；可读性问题先通过命名、类型和流程调整解决，注释补充代码本身无法表达的理由与约束。

空行表达语义步骤的转换。输入读取与校验、资源准备、执行、结果交接和清理按实际关系分段；同一步中的紧密操作保持相邻。一个函数跨越不同职责或资源寿命时，提取有明确输入、结果和负责范围的步骤。长条件和分支展开后仍须能看清主路径，避免把后续操作贴在多行条件、循环或异常处理之后。分段不按固定行数进行，也不在每条语句之间机械插入空行。

Prettier 等格式工具负责缩进、换行和语法排版，不负责判断逻辑分段、命名和职责。格式检查通过后仍需实际通读主流程及其失败和关闭路径。

<a id="logical-sections"></a>

### 逻辑分段

一个逻辑段完成一个可以说清楚的步骤。分段依据数据、状态或资源责任的转换，不按行数划分；同一段内的语句共同形成这个步骤的结果。

| 情形 | 排版与组织 |
| --- | --- |
| 读取或构造输入及其直接校验 | 声明、使用和对应守卫保持相邻；通过校验后，进入下一步骤前留空行。 |
| 准备资源、执行工作、采用结果 | 各步骤之间留空行；获取与清理仍通过同一 try／finally 或所属生命周期对应。 |
| 分支、循环与异常处理结束 | 后面开始另一件事时留空行；else、catch、finally 保持完整控制结构。多行控制流使用代码块。 |
| 局部辅助函数 | 与前后的执行语句分开；名称和参数说明其步骤，函数头不重复逐行过程。只做改名转发的函数不构成独立步骤。 |
| 构造返回值或交付结果 | 前面的计算、I/O 或状态变更已经结束时另起一段；单次纯计算直接返回即可。 |
| 类型、对象、数组、CSS 与配置 | 按同一职责的成员成组；平行成员保持统一顺序，同组不逐项插入空行。 |
| 测试 | 按准备条件、执行动作、核对结果分段。连续场景分别分段，清理与其创建的资源对应；动作和断言可以在一个 expect 中表达。 |

一个文件承载完整工作流时，先让读者找到入口和主流程，再按实际操作定位辅助实现。某段需要独立解释输入、结果、状态或资源寿命时，考虑提取为具名步骤；同层主流程保持相近的语义粒度。注释不用于替代缺失的逻辑分段。

<a id="directory-readability"></a>

### 文件与目录的可读性

目录按职责与所有权组织。目录名称表达所负责的能力、工作对象或工程边界，文件名说明具体工作，避免层层重复同一个含义。通用规则如下：

1. **同级职责粒度相近。** 每一级目录采用清楚的划分依据，例如工程任务、业务能力或运行边界；完整能力与其专用辅助实现保持拥有关系。
2. **专用实现随拥有者放置。** 为某个能力服务的辅助模块归该能力内部；测试对实现的复用本身不构成上移理由。
3. **共享放在最小合理范围。** 根据相同语义、实际消费者和维护责任确定共同归属，继续遵守程序、包和运行环境边界。
4. **入口与支撑角色清楚。** 完整任务、默认入口、配置与内部支撑应容易区分。共享目录有明确的内容及依赖约束，不要求每个顶层项都能独立执行。
5. **文件与目录按实际需要选择。** 单文件可以表达完整职责，多模块协作或明确的工程边界可以形成目录；不按文件数量机械拆分、合并，也不增加纯转发层。

具体目录名称与内容约束由所在工程确定。桌面应用 src/shared 仍只保存纯合同及适用的纯规则，tools/lib 可以提供 Node 工程支撑；二者分别遵守所属边界。工具组织的具体示例见[桌面应用工具](layout.md#desktop-tools)。

W00 可以建立已确认的独立程序、workspace 项目、打包输入和分发资料边界；骨架说明应标明当前阶段，不能用占位函数、空结果或假数据表示尚未实现的能力。未进入当前交付范围的工程仍不预建。

不同程序保留各自入口和寿命，可以共用已经相同的视图、协议和机制。目录移动同时更新导入、配置、测试发现及所属文档；生成文件和历史验证材料按各自归属保留。

审查时以一条正常路径和相关失败、取消或关闭路径核对上述要求。关键判断的依据应能在所属合同、就近注释或对应测试中找到；不以行数、注释数量或统一套用某种设计模式代替判断。

覆盖范围包括所有当前自维护的程序、公共包、扩展工程配置、工具、测试、模板与配置文件，也包括这些内容的目录归属。全覆盖表示逐项核对，不要求每个文件都发生修改；同构文件可以成组审查，但逐项核对身份与配置差异。依赖锁和绑定生成物通过生成流程与消费验证核对，历史探针与第三方内容不作为当前实现改写。

<a id="configuration-layout"></a>

### 工程配置的归属

本体、公共包、官方扩展、作者模板、仓库工具和独立项目采用同一配置归属规则。配置属于实际使用它的工程；跨项目共享的基线由共同拥有者提供，不把各包内部配置集中到仓库根目录。文件数量和项目规模不改变配置职责。

| 配置职责 | 位置与要求 |
| --- | --- |
| 工具默认发现的实际入口与项目声明 | 保留工具约定的位置，如项目根目录的 tsconfig.json、tsdown.config.ts、kisx.config.ts、package.json 和 Cargo.toml。入口承担实际配置或项目组织职责。 |
| 明确供多个项目继承的共享基线 | 由共同拥有者提供稳定入口，如 @kisaki3/typescript-config 与 @kisaki3/eslint-config。消费者声明依赖并通过 exports 采用，基线不混入单个项目的环境配置。 |
| 环境配置、测试变体与其他内部工具配置 | 放在所属工程的 `config/<工具名>/`，如 config/typescript、config/vite、config/vitest 和 config/playwright，保留工具及用途明确的文件名。 |
| 工具规定的专用目录 | 沿用 .github/workflows、.cargo 等原生约定，不为统一外观改写工具发现行为。 |

只有默认入口的工程保持该入口，有实际内部配置时再建立相应目录。不为维持根文件名增加只有转发含义的文件，也不预建空的 config 层级。config 保存工程配置，tools 实现工程流程，tests 拥有用例与辅助；程序中的配置读取 API、运行期设置和用户数据仍由各自业务拥有。

迁移同时维护默认入口与项目引用、相对路径、类型检查和编辑器识别、开发监听、缓存及构建身份输入。配置重组保持实际源码覆盖与环境边界，globals 按文件的真实宿主确定，不为机械保留旧配置快照增加类型项目。产品纯合同不因此获得 Node／DOM 全局，公共声明消费者及自有声明拥有层的完整检查保持，消费者仍取得同义的公开制品。具体落点由[仓库布局](layout.md#workspace)和[工作区配置](workspace.md#workspace)记录。

<a id="design-completion"></a>

## 设计充分性与实现自由

设计明确对象身份、字段含义与默认值、完整操作、公开输入输出与错误、并发与原子边界、取消与资源寿命、主要交互及支持范围。对影响这些含义的主要分支，提供可以得到确定结果的规则和例子；已知缺口继续完成设计，不交由实施者临时补定。

容易产生歧义的规则使用精确类型、行为表或例子；确有技术风险时，用小型探针验证。全量声明、导出目录、常规 CRUD 签名和组件参数随实现形成。设计定稿同时核对规则依据、一致性、实施充分度，以及[内容组织与表述](documentation.md#writing)。

局部函数和文件拆分、索引、数据结构、同语义算法优化，以及已确定预算内的批量与并发调优，由实施者判断。规格给出约束和验收依据，不预写所有实现细节。实现选择如果改变了公开含义、主要行为或支持范围，仍按[实施讨论规则](../../implementation/work-packages.md#unexpected-issues)处理。

验证在能够直接证明承诺的边界取得证据，各接入层验证自己新增的风险，并复用仍适用的既有结果。设计充分性、正式实现和运行验收分别判断。

<a id="source-language"></a>

## 源码语言

JavaScript 运行环境中的自维护源码统一使用 TypeScript。普通模块、工具、配置、测试和示例使用 .ts，需要 JSX 的界面使用 .tsx；不维护 .js、.jsx、.mjs 或 .cjs 源文件。本体私有原生模块的 Node 接入和工程生成模板遵守同一规则，ESM 或 CommonJS 格式由构建配置决定。

Rust 原生实现、SQL、CSS 和声明式配置使用各自适用的语言。源码语言要求不改变编译产物和第三方发行内容的格式；运行所需 JavaScript 由 TypeScript 或绑定工具生成，生成结果不手工修改。类型、lint 和源码结构检查覆盖工具、配置、测试与模板，不能只检查产品 src。

<a id="naming"></a>

## 代码组织与命名

目录和普通 .ts、.tsx 文件使用 kebab-case。组件、类型和类使用 PascalCase，函数和变量使用 camelCase。程序入口使用 entry.ts、entry.tsx 或能说明职责的名称；index.ts 只列出实际公共导出。

类别目录直接组织同类文件；需要多个文件协作的模块拆成目录。模块内部直接导入所需文件，公共导出入口用于外部消费，以保持依赖方向清楚。

<a id="module-imports"></a>

模块导入按依赖关系选择统一机制：跨包通过已声明的包名和正式 exports 消费，公共包提供构建结果，私有工程包按固定宿主提供 JSON 或 TypeScript 入口；包内有稳定命名需求的模块入口通过所属 package.json 的 imports 声明，以 `#` 开头；模块内部协作使用相对导入。命名入口需要明确的模块边界，不为每个文件或目录建立别名。

| 依赖关系 | 导入形式 | 唯一定义 |
| --- | --- | --- |
| 应用、公共包、扩展及独立工程之间的包代码 | 包名及公开子入口 | 所属 package.json 的 exports，以及使用者声明的依赖 |
| 同一包内的稳定模块入口 | `#native` 等 `#` 名称 | 所属 package.json 的 imports |
| 同一模块内部 | `./`、`../` 相对路径 | 模块自身的文件组织 |
| 仓库共用工程配置和函数 | `@kisaki3/typescript-config`、`@kisaki3/eslint-config`、`@kisaki3/tooling` 的明确子入口 | 私有 workspace 包的 exports 与消费者 devDependencies |

包内入口由所属包唯一维护，代码与测试使用同一入口，类型检查、构建与依赖检查通过标准包解析读取它，不分别维护等价的 TypeScript paths 或构建器 alias。`#` 是 Node 包内映射的前缀，不表示原生二进制或特定权限。当前 `#native` 命名本体原生能力的 Node 入口，主进程与原生测试消费同一合同；二进制定位与加载由该入口负责。

imports 按发起导入文件所属的包生效，与 tsconfig.extends 的继承链无关，也不由命令的工作目录决定。根任务处理应用源码时读取应用的包映射；根工程自己的文件不能借此使用应用的私有 `#native`。imports 的相对文件目标位于所属包内，也可以指向已声明的外部包；不通过 `../` 指向包外的共享源码。

仓库共用工程配置和函数属于固定工具链内的源码复用，分别由根 packages 下三个私有工程包拥有。消费者通过 workspace devDependencies 和明确 exports 使用；TypeScript 读取 JSON 配置，ESLint 使用锁定的 jiti 加载 TypeScript 配置，tsx 与测试运行器处理 tooling 的 TypeScript 源码。源码入口不需要空 build 或独立监听，不另建 paths、resolve.alias 或 Vitest 解析开关。产品运行代码、公共包导出声明与仓库外作者模板不依赖这些私有工程包；公开包继续使用构建后的入口。

模块位置解析与访问权限分别管理，检查依据解析后的实际目标；类型导入同样受约束。别名不能开放另一工程的私有 src 或 tools。工具可消费本工程明确供工程流程使用的纯合同、纯数据及合适的纯函数，不直接启动依赖应用运行环境的模块；共用支撑不反向依赖具体工作流、命令入口或测试夹具。只为实际稳定入口命名，不以相对路径的层数机械决定是否增加别名。

打包程序在构建时解析并编入所需的内部模块。最终产物中保留的内部导入及 imports 映射必须指向实际交付的内容，不依赖开发目录中的源码；公开库同时通过仓库外制品消费验证。

同级目录保持相近的职责粒度，分类按维护需要组织能力，公开 API 按调用需要展开。每项公开能力有唯一实现拥有者，装配连接实际入口；内部分类可以独立于公开合同调整。

按模块负责的对象、操作、状态和资源寿命命名，再按协作与维护需要拆分。manager 管理一组对象及其生命周期，coordinator 协调参与者执行，registry 负责登记、查找与集合变化。相同职责采用相近表达，有实际差异时保留各自组织方式。

具体能力的实例或闭包持有持续状态、接纳关口、并发控制和释放责任。外部调用完整业务能力，装配层使用声明的创建与生命周期入口；内部执行步骤与状态容器保持私有。状态组织与管理职责共同决定是否需要 manager。

模块协作、应用装配及窗口和 SDK 的开放范围遵守[入口与依赖边界](../architecture.md#module-interfaces)。依赖按实际使用的能力声明，正式值直接复用所属合同，私有运行类型留在本体；不为可见范围机械增加门面、目录或同义类型。

小型纯辅助函数可以放在 utils 中，业务策略、持久化、IPC 和运行副作用则应放在语义明确的模块中。不同 Entry 可以采用适合自身职责的组织方式，不要求相同的文件或 Spec 结构。

<a id="source-layout"></a>

## 工程目录与职责落点

各工程的目录树与职责说明对应，交代公开入口、私有实现、依赖方向，以及测试、样本、资源、工具和生成产物的归属，并用典型功能核对落点。manifest、公开接口和资源所有权表达实际工程边界；分类目录只承担组织作用。小型职责使用单文件，辅助文件随真实协作需要拆分。

官方扩展逐项确定页面、账号或凭据、导入对象与触发、同步方向和字段，并说明请求、解析、映射及界面的源码职责。共用客户端、连接和私有状态各有唯一拥有者；相同结构引用共同方案，来源差异单独说明，资源扩展按自身规模组织。Node、Webview 与 Solid 模板负责初始运行结构，未确定的业务设计记入[设计进度](../../implementation/status.md#design)。

<a id="validation"></a>

## 边界校验与不过度防御

文件、网络、IPC、扩展输入和持久化数据在进入系统的对应边界按合同解析。纯校验规则由定义该值的模块维护，传输适配负责调用和结果交付。可信内部调用使用已经成立的结构合同，不在每一层重复检查同一结构。

结构合法与业务操作可执行分别判断。负责操作的模块保障数据完整性、当前并发条件、取消状态和资源生命周期；数据库约束与事务也继续承担各自职责。缺省值、可恢复情况和失败结果必须有明确的合同依据。

边界检查、缺省和恢复措施都需要对应实际输入、资源归属与失败后果。负责边界的模块完成一次必要校验并交付明确结果，可信内部代码沿已经成立的合同执行。重试与备用路径按具体业务需要设置，界面和使用说明沿[文案规则](../ui/components.md#copy)解释实际影响。

普通失败按所属合同报告并完成清理，同时说明重复操作、取消或部分完成后保留了什么结果，以及用户如何通过已有操作补做。重试、防重、补存、补偿和恢复各自需要明确业务依据、范围、寿命与失败结果。自动重放须有所属操作的明确许可，回复丢失或断连按该合同处理。

持久化边界遵守[宽容读取、严格写入](../domains/values.md)。安全缺省按当前存储合同恢复，格式迁移使用正式迁移流程。自定义编码的列通过 customType 复用纯规则，普通列采用内置类型；值校验、编码、数据库约束与业务事务各负责本层条件。

解析外来数据时使用 parse、validate、require、assertValid 等名称；判断可信业务状态时使用 is、has、can、should。

<a id="comments"></a>

## 注释的覆盖范围与写法

代码注释统一使用简洁英文，按代码对象明确覆盖要求，适用于本体、公共包、扩展、原生实现、工具、配置和测试。文档注释说明该对象的职责与调用合同，内部注释解释实现理由和约束；名称、类型和直观代码已经表达的信息不逐字复述。

文件与模块的职责、依赖关系和整体生命周期由[项目文档](documentation.md#owners)维护，不作为文件头或模块概述注释重复编写。代码注释归到具体函数、组件、类、类型及局部实现，说明这些对象自身的合同与约束。

调整注释规范的覆盖范围与原则时，先与用户讨论并确认。

<a id="comment-objects"></a>

### 各类代码对象

组件与类按调用契约确定说明范围。公开消费入口需要可独立理解的说明；内部对象在职责、输入含义、状态、焦点、失败或资源条件未由名称、类型和直观实现表达时补充说明。简单内部展示片段和未增加合同的实现不因具名而另写同义用途。其余代码对象继续遵守下表各自的必需范围。

公开消费入口指包的公开导出、SDK，以及模块向其他模块承诺的稳定能力；单个文件中的 export 关键字本身不决定公开性。Props、接口或基类已经定义的字段和行为由其拥有者维护，实现只说明新增约束。

| 代码对象             | 必需范围                                                                                                                     | 位置与内容                                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 函数与方法           | 对外消费的函数和方法、完整业务操作，以及承担 I/O、状态修改、并发协调或资源管理的具名函数。简单私有纯函数按实际说明需要处理。 | 声明前使用 JSDoc，说明用途与适用的输入约束、返回含义、完成条件、失败和副作用。内部复杂步骤另加就近注释，不用函数头复述实现步骤。               |
| 组件 | 公开组件，以及具有额外输入、受控状态、回调时序、焦点、无障碍或清理合同的内部组件。 | 在声明前说明调用者需要知道的行为。简单内部展示片段由名称、Props 和直观实现表达职责；Props 的字段合同只在其定义处维护。 |
| 响应式工具与状态工厂 | 供复用的 hook、composable、响应式控制器，以及创建持续状态或资源的工厂。                                                      | 在创建入口说明调用环境、输入是否响应式、返回值是快照还是活跃状态，以及订阅、异步工作和清理归属。                                               |
| 类 | 公开类，以及拥有领域不变量、状态、资源寿命或非直观构造条件的内部类。 | 说明适用职责、状态与生命周期；构造和方法只补充各自新增的条件。内部实现已经完全遵循接口时引用原合同，不重复同义说明。 |
| 接口                 | 对外接口、依赖注入接口、扩展参与接口和有稳定职责的内部协议。                                                                 | 接口声明前说明它代表的能力或对象、实现方与调用方责任；成员的行为约束写在对应成员处。实现类直接遵循接口文档，只补充实现特有的限制。             |
| 类型与类型别名       | 公开类型、领域值、状态模型、跨进程或持久化结构，以及含义不能由名称与结构直接确定的内部类型。                                 | 定义前说明业务含义、身份、粒度或有效状态；不把类型展开结果当作说明。同义类型直接复用，不为添加注释复制定义。                                   |
| 属性、字段与参数     | 单位、默认值、精度、坐标系、空值含义、取值范围、所有权或相互约束不能由类型直接表达的成员。                                   | 在字段定义处或函数的 @param 中说明，信息只维护在拥有该合同的位置。私有状态字段说明不变量，普通局部变量不要求逐个注释。                         |

| 工具与配置           | 工具入口和工作流函数，以及影响环境、安全、构建或发行的非直观配置项。                                                         | 工具函数遵守对应的函数规则；配置说明用途、非默认值依据及作用范围。不支持注释的格式，在所属 schema、工具帮助或最近的维护文档中说明。            |

Rust 的 fn、struct、enum、trait 和关联方法按对应职责使用 Rustdoc。生成的绑定与类型声明从原始定义取得文档，不手工维护第二份说明。接口已规定的合同由实现引用，只有实现新增的行为或约束才需要补充。

### 注释应说明的合同

上表要求文档化的对象，按其实际语义交代以下内容：

- 输入与数据含义：单位、坐标系、时区、精度、默认值、空值、身份和字段之间的约束；schema、序列化、迁移及映射说明必须保留的含义。
- 行为与完成：前置条件、返回值、错误、幂等性和副作用；异步调用明确何时算完成，取消是否仍可能留下已发生的结果。
- 状态与资源：状态转移、互斥范围、重入与迟到结果；资源的取得、借用、转交、释放责任和顺序，以及关闭与失败清理条件。
- 实现依据：非直观业务取舍、平台与协议约束、安全前提、算法和性能取舍；引用稳定的合同或来源，不以“特殊处理”“兼容处理”代替理由。

### 形式与维护

文档注释紧邻声明，首句概括用途或关键合同；@param、@returns、@throws 等标签只在能补充有用信息时使用，不重复参数类型、填充空标签或堆叠装饰性分隔线。内部注释紧邻所解释的代码。代码职责不清或流程过于复杂时，先改善命名、类型和结构，再补充必要解释。

注释以对象实际提供的行为和调用者需要知道的合同为主。需要说明限制时，写清触发条件、实际结果或责任归属；例如“编译失败时保留上一次输出”“调用者在关闭后释放目录”。泛泛宣称安全、严格、不会误用或不会破坏既有结果，不能替代这些信息。代码对象需要文档化，也不意味着必须给它补一条通用的保证句；名称已经表达的动作，只补充尚未表达的完成、失败、默认值或资源条件。

注释与实现、类型、测试和公共文档在同一次变更中更新。正常代码不保留重构经过、进度记录、注释掉的旧实现或未来实现占位。确有尚不能消除的临时限制时，使用 `TEMP:`、`TODO:` 或 `FIXME:` 标记，写明原因、影响和具体移除条件；必要时引用对应问题，不能只写“以后优化”。

设计问题在[状态页](../../implementation/status.md#design)记录，规则修订回到所属主题；实施待办在工作包中管理。长期说明遵守[项目文档规范](documentation.md#owners)，界面文字遵守[文案规范](../ui/components.md#copy)。审查按代码对象核对覆盖，再按实际合同核对内容；缺少必需说明和已经失效的注释都属于需修正的问题。

<a id="errors"></a>

## 错误与异常边界

应用自行抛出的错误使用安全英文消息，通过 cause 保留原始异常。错误分类依靠类型或原因字段，不能按 error.message 文本分支。只有需要补充业务上下文、执行恢复、改变边界消息，或在负责失败的层记录日志时才捕获错误。

<a id="logging"></a>

## 日志与用户反馈

运行代码使用项目日志包装。日志前缀采用稳定、单层的责任领域，动态 ID、路径和扩展身份作为参数传入，不能成为不断增长的 logger 名称。

日志记录生命周期、失败、恢复、后台结果和连接变化，不记录每一帧、每次渲染或每次监听回调。完整数据库行、HTTP body、用户正文、无界数组，以及 token、OAuth 值和签名材料不得进入日志。

负责失败的模块记录一次必要且符合上述范围的上下文，并返回安全错误。界面入口或后台工作负责人按[通知规则](../ui/components.md#notifications)统一反馈同一次失败。

<a id="delivery"></a>

## 完整改动与实施判断

工作包的交付内容与验收范围由[实施计划](../../implementation/work-packages.md)定义。基础库除自身测试外，还需要通过真实消费者验证。

工作包的全部交付内容符合规范、适用验证通过，且无用途内容完成清理后，才能将工作标记为完成。代码协作遵守 [工作区规则](workspace.md#collaboration)，发行遵守 [版本流程](releases.md)。设计、实现、验证和发布分别依据真实结果记录。

实现判断遵守[设计充分性与实现自由](#design-completion)，涉及规则变更时按[实施讨论规则](../../implementation/work-packages.md#unexpected-issues)处理。
